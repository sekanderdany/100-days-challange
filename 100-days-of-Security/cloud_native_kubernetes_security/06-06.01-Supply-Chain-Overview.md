# 06.01 - Supply Chain Overview

## 1️⃣ What This Topic Is

Supply Chain Security examines security measures for securing Kubernetes supply chains, understanding images, builds, deployments, and secure supply chain configurations.

**What this means:**
- Kubernetes Supply Chain = software delivery pipeline (Source Code, Build, Image Registry, Deployment, Runtime)
- Supply Chain Security = security measures (Image Signing, SBOM, Admission, Vulnerability Scanning, Pipeline Security)
- Supply Chain Threats = supply chain attacks (Dependency Confusion, Source Tampering, Build Compromise, Registry Poisoning)
- Secure supply chain configurations (policies, auditing, monitoring)

**The Key Concepts:**

1. **Kubernetes Supply Chain Security Areas**
   - Source code security (VCS, PR Reviews, Code Analysis)
   - Build security (CI/CD, Build Scripts, Artifact Signing)
   - Image registry security (Image Registry, Image Signing, Notary)
   - Deployment security (Admission Controllers, Validation, Monitoring)
   - Runtime security (Runtime Monitoring, Threat Detection, Response)

2. **Security Principles**
   - Defense in depth (Source, Build, Registry, Deployment, Runtime)
   - Least privilege (supply chain access)
   - Zero-trust (never trust, always verify)
   - Immutable infrastructure (immutable tags, immutable infrastructure)
   - Audit everything (audit logging)

**Why this matters:**
- Supply chain security is critical for cluster security
- Supply chain controls all software delivery
- Supply chain compromise = cluster-wide compromise
- Supply chain handles all software delivery

## 4️⃣ How It Works (Conceptual)

### Kubernetes Supply Chain Security Areas

**1. Source Code Security**
- **Purpose**: Secure source code
- **Security Measures**: 
  - Source code security (VCS, PR reviews, code analysis)
  - Source code policies (branch protection, required checks)
  - Source code monitoring (PR events, code analysis events)
- **Common Misconfigurations**: 
  - No source code security (no VCS, no PR reviews)
  - No source code policies (no branch protection, no required checks)
- **Example**: Source code security with VCS

**Source Code Security Types:**
- **VCS (Version Control System)**: 
  - VCS (Git, GitHub, GitLab, Bitbucket)
  - VCS security (2FA, branch protection, required checks)
  - Least privilege

- **PR Reviews**: 
  - PR reviews (required approvals, code owners)
  - PR review enforcement (branch protection)
  - Least privilege

- **Code Analysis**: 
  - Code analysis (static analysis, dynamic analysis, security tools)
  - Code analysis tools (Snyk, SonarQube, CodeQL)
  - Least privilege

**Best Practices:**
- Use source code security (VCS, PR reviews, code analysis)
- Implement source code policies (branch protection, required checks)
- Implement source code monitoring (PR events, code analysis events)
- Regular source code security audits

**Example**:
```yaml
# Source code security with VCS (secure, advanced)
name: Source code security
on:
  push:
    branches: [ main ]
jobs:
  security-scan:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    - uses: snyk/actions/snyk@master
```

**2. Build Security**
- **Purpose**: Secure builds
- **Security Measures**: 
  - Build security (CI/CD, build scripts, artifact signing)
  - Build policies (required checks, signing)
  - Build monitoring (build events, artifact events)
- **Common Misconfigurations**: 
  - No build security (no CI/CD, no signing)
  - No build policies (no required checks, no signing)
- **Example**: Build security with CI/CD

**Build Security Types:**
- **CI/CD (Continuous Integration/Continuous Deployment)**: 
  - CI/CD (Jenkins, GitHub Actions, GitLab CI)
  - CI/CD security (secrets, access control, audit logging)
  - Least privilege

- **Build Scripts**: 
  - Build scripts (Dockerfile, Makefile, build.sh)
  - Build script security (static analysis, dynamic analysis, security tools)
  - Least privilege

- **Artifact Signing**: 
  - Artifact signing (signing, verification, key management)
  - Artifact signing tools (cosign, gpg, sigstore)
  - Least privilege

**Best Practices:**
- Use build security (CI/CD, signing)
- Implement build policies (required checks, signing)
- Implement build monitoring (build events, artifact events)
- Regular build security audits

**Example**:
```yaml
# Build security with CI/CD (secure, advanced)
name: Build security
on:
  push:
    branches: [ main ]
jobs:
  build-and-sign:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    - uses: docker/build-push-action@v4
      with:
        push: true
        tags: ${{ secrets.DOCKER_REGISTRY }}/${{ github.repository }}:latest
        secrets: |
          DOCKER_REGISTRY
          DOCKER_PASSWORD
    - uses: sigstore/cosign-installer@main
```

**3. Image Registry Security**
- **Purpose**: Secure image registries
- **Security Measures**: 
  - Image registry security (Image Registry, Image Signing, Notary)
  - Image registry policies (access control, immutability)
  - Image registry monitoring (image events, image vulnerabilities)
- **Common Misconfigurations**: 
  - No image registry security (no registry, no signing, no notary)
  - No image registry policies (no access control, no immutability)
- **Example**: Image registry security with Notary

**Image Registry Security Types:**
- **Image Registry**: 
  - Image Registry (Docker Hub, ECR, GCR, ACR)
  - Image Registry security (access control, vulnerability scanning, encryption)
  - Least privilege

- **Image Signing**: 
  - Image signing (signing, verification, key management)
  - Image signing tools (cosign, docker trust, notation)
  - Least privilege

- **Notary**: 
  - Notary (signing, verification, trust distribution)
  - Notary tools (notary, TUF, Rekor)
  - Least privilege

**Best Practices:**
- Use image registry security (registry, signing, notary)
- Implement image registry policies (access control, immutability)
- Implement image registry monitoring (image events, image vulnerabilities)
- Regular image registry security audits

**Example**:
```bash
# Image registry security with Notary (secure, advanced)
notary verify <image-name>
```

**4. Deployment Security**
- **Purpose**: Secure deployments
- **Security Measures**: 
  - Deployment security (Admission Controllers, Validation, Monitoring)
  - Deployment policies (required checks, immutability)
  - Deployment monitoring (deployment events, deployment anomalies)
- **Common Misconfigurations**: 
  - No deployment security (no admission controllers, no validation)
  - No deployment policies (no required checks, no immutability)
- **Example**: Deployment security with Admission Controllers

**Deployment Security Types:**
- **Admission Controllers**: 
  - Admission Controllers (ValidatingAdmissionWebhook, MutatingAdmissionWebhook)
  - Admission Controller security (access control, audit logging)
  - Least privilege

- **Validation**: 
  - Validation (image validation, policy validation, schema validation)
  - Validation tools (OPA Gatekeeper, Kyverno, Ratify)
  - Least privilege

- **Monitoring**: 
  - Monitoring (deployment events, deployment anomalies)
  - Monitoring tools (Prometheus, Grafana, AlertManager)
  - Least privilege

**Best Practices:**
- Use deployment security (admission controllers, validation, monitoring)
- Implement deployment policies (required checks, immutability)
- Implement deployment monitoring (deployment events, deployment anomalies)
- Regular deployment security audits

**Example**:
```yaml
# Deployment security with Admission Controllers (secure, advanced)
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionWebhook
metadata:
  name: image-validator
spec:
  rules:
  - apiGroups: [""]
    apiVersions: ["v1"]
    operations: ["CREATE", "UPDATE"]
    resources: ["pods"]
  clientConfig:
    url: https://image-validator.default.svc
```
