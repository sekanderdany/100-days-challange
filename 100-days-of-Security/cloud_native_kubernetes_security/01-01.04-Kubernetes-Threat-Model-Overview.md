# 01.04 - Kubernetes Threat Model Overview

## 1️⃣ What This Topic Is

Kubernetes Threat Model Overview examines the landscape of threats facing Kubernetes environments, understanding how attackers think, what attack vectors exist, and how to defend against them.

**What this means:**
- Threat model is systematic approach to understanding threats
- Identifies assets, threats, and vulnerabilities
- Guides security control implementation
- Prioritizes defense efforts

**The Threat Model Components:**

1. **Assets (What are we protecting?)**
   - Kubernetes cluster (control plane, worker nodes)
   - Workloads (applications, data)
   - Credentials (secrets, tokens, certificates)
   - Infrastructure (cloud providers, networks)

2. **Threat Agents (Who are the attackers?)**
   - External attackers (hackers, script kiddies)
   - Insiders (malicious insiders, compromised accounts)
   - Supply chain attackers (compromised dependencies)
   - Cloud-specific threats (provider misconfigurations)

3. **Attack Vectors (How do they attack?)**
   - Compromised credentials
   - Vulnerable components (CVEs)
   - Misconfigurations
   - Zero-day exploits
   - Lateral movement
   - Data exfiltration

4. **Impact (What happens if successful?)**
   - Cluster compromise
   - Data theft
   - Service disruption (DoS)
   - Cryptojacking
   - Reputation damage

**Why this matters:**
- Understanding threats enables proactive defense
- Threat model guides security investments
- Prioritizes critical vulnerabilities
- Helps design secure architectures

## 2️⃣ What Problem It Solves

### Problem 1: Unpredictable Threat Landscape

**Without threat model:**
- Don't know what threats exist
- Can't prioritize security efforts
- Reactive instead of proactive
- Always one step behind attackers

**With threat model:**
- Understand threat landscape
- Prioritize vulnerabilities by risk
- Proactive security posture
- Stay ahead of attackers

### Problem 2: Ineffective Security Spending

**Without threat model:**
- Spend on wrong security controls
- Overlook high-risk areas
- Wasted resources
- Security gaps remain

**With threat model:**
- Focus on high-impact threats
- Efficient resource allocation
- Risk-based prioritization
- Maximum security ROI

### Problem 3: Incident Response Challenges

**Without threat model:**
- Can't predict next attack
- Slow incident detection
- Incomplete remediation
- Repeat incidents

**With threat model:**
- Understand likely attack paths
- Early detection of suspicious activity
- Rapid incident response
- Prevent future attacks

### Real-World Impact

**Example: Capital One Breach (2020)**
- **Vulnerability**: Compromised MFA credentials
- **Root cause**: No threat model for external access
- **Threat model issue**: External access threat not prioritized
- **Impact**: Attacker accessed 40 million customer records
- **Lesson**: Model external threats, implement strong MFA

**Example: SolarWinds Supply Chain Attack (2020)**
- **Vulnerability**: Compromised Orion software updates
- **Root cause**: No supply chain threat model
- **Threat model issue**: Third-party dependencies not verified
- **Impact**: Attacker accessed 18,000+ customers
- **Lesson**: Model supply chain threats, verify all dependencies

**Example: Kubernetes Cryptojacking Attacks (2018)**
- **Vulnerability**: Exposed API server to internet
- **Root cause**: No threat model for API server access
- **Threat model issue**: API server exposure not identified as threat
- **Impact**: Attacker deployed miners across clusters
- **Lesson**: Model management plane threats, restrict API access

## 3️⃣ When You Should Use This

### **ALWAYS** - Threat modeling is essential for ALL Kubernetes security

**When Designing Security Architecture:**
- Model threats for each component
- Identify attack paths to critical assets
- Design controls to block attack vectors
- Layer defenses based on threat model

**When Conducting Risk Assessments:**
- Use threat model to identify risks
- Quantify risk (impact × likelihood)
- Prioritize remediation by risk level
- Document findings and mitigation plans

**When Responding to Incidents:**
- Use threat model to understand attack path
- Identify compromised components
- Trace lateral movement
- Plan containment and eradication

### Scenarios where this is critical:

**Multi-Tenant SaaS Platforms:**
- Model threats between tenants
- Understand cross-tenant attack vectors
- Design isolation based on tenant threat model
- Monitor for cross-tenant access attempts

**Financial Services (PCI-DSS):**
- Model financial data threats
- Identify compliance gaps
- Design controls for financial data protection
- Document threat model for auditors

**Healthcare (HIPAA):**
- Model patient data threats
- Identify insider threats
- Design strong access controls
- Audit trail for access tracking

**Critical Infrastructure:**
- Model nation-state threats
- Design resilience against APTs
- Implement strong monitoring
- Have incident response plan

## 4️⃣ How It Works (Conceptual)

### Threat Modeling Frameworks

**1. STRIDE Threat Model**
- **Spoofing**: Impersonating system or user
- **Tampering**: Modifying system or data
- **Repudiation**: Denying actions taken
- **Information Disclosure**: Exposing sensitive information
- **Denial of Service**: Disrupting service availability
- **Elevation of Privilege**: Gaining unauthorized higher privileges

**Application to Kubernetes:**
- **Spoofing**: Compromised API server credentials
- **Tampering**: Modifying etcd data or pod specs
- **Repudiation**: Attacker denies creating pods
- **Information Disclosure**: Accessing secrets in etcd
- **Denial of Service**: DoS attacks on API server or Kubelet
- **Elevation of Privilege**: Container escape to host, cluster-admin access

**Example**: Attacker spoofs API server by stealing admin credentials, then elevates privilege to cluster-admin by creating privileged pods.

**2. MITRE ATT&CK Matrix**
- **Initial Access**: Entry point into cluster
- **Execution**: Running malicious code
- **Persistence**: Maintaining presence
- **Privilege Escalation**: Gaining higher privileges
- **Defense Evasion**: Avoiding detection
- **Credential Access**: Obtaining credentials
- **Discovery**: Understanding environment
- **Lateral Movement**: Moving through cluster
- **Collection**: Gathering data
- **Exfiltration**: Stealing data
- **Command and Control**: Remote control
- **Impact**: Achieving objectives

**Application to Kubernetes:**
- **Initial Access**: Compromised credentials, vulnerable component
- **Execution**: Running malicious pod or container
- **Persistence**: CronJob, DaemonSet, deployment update
- **Privilege Escalation**: Container escape, over-privileged RBAC
- **Defense Evasion**: Rootless containers, deleting logs
- **Credential Access**: Reading secrets from etcd, pods
- **Discovery**: Enumerating pods, services, nodes
- **Lateral Movement**: Moving to other nodes, namespaces
- **Collection**: Scraping application data, logs
- **Exfiltration**: Copying data to attacker server
- **Command and Control**: K8s backdoor, webhook
- **Impact**: Cluster compromise, data theft, cryptojacking

**Example**: Initial access via exposed Kubelet API → Execution of malicious pod → Privilege escalation via container escape → Discovery of cluster → Lateral movement to other nodes → Collection of application data → Exfiltration via network → Cryptojacking.

**3. PASTA Threat Model**
- **P**: Potential for abuse
- **A**: Currently being abused
- **S**: Sustainable and stable
- **T**: Transient or dynamic
- **E**: Evolving
- **R**: Resurgent
- **I**: Incident response

**Application to Kubernetes:**
- **P**: Exposed API server, vulnerable Kubelet, weak RBAC
- **A**: Active cryptojacking, active attacks
- **S**: Malicious DaemonSets (persistent)
- **T**: Exploit kits (constantly evolving)
- **E**: New Kubernetes vulnerabilities regularly
- **R**: Zero-day in Kubernetes
- **I**: Responding to ongoing compromise

**Example**: Exposed Kubelet API (Potential) → Attacker discovers vulnerability (Active) → Attacker deploys DaemonSet with miner (Sustainable) → New vulnerability discovered (Evolving) → Zero-day exploit (Transient) → Security team responds (Incident response).

**4. DREAD Model**
- **D**: Decouple (attack components)
- **R**: Relate (components interact)
- **E**: Explain (how attacks work)
- **A**: Affect (impact of attacks)
- **D**: Decouple (separate concerns)

**Application to Kubernetes:**
- **Decouple**: Separate concerns (credentials, access, components, logs)
- **Relate**: Show how concerns relate (credentials → access → components)
- **Explain**: Document how attacks exploit relationships
- **Affect**: Prioritize risks based on impact
- **Decouple**: Address concerns independently

**Example**: Decouple concerns (API server credentials, Kubelet access, etcd secrets, audit logs) → Relate (API server credentials give Kubelet access, Kubelet access gives etcd secrets, audit logs show all access) → Explain (Attacker steals credentials, uses Kubelet, accesses etcd, logs show attack) → Affect (Prioritize: etcd secrets > API server credentials > Kubelet access > audit logs) → Decouple (Secure each independently: MFA, network isolation, encryption, SIEM).

### Kubernetes-Specific Threats

**1. Control Plane Threats**
- **API Server**: Authentication bypass, authorization bypass, DoS
- **etcd**: Unauthorized access, data theft, backup exposure
- **Scheduler**: Pod placement manipulation, resource exhaustion
- **Controller Manager**: Unauthorized object creation, state manipulation

**Attack Vectors**:
- Compromised admin credentials
- Vulnerable components (CVEs in control plane)
- Misconfigured RBAC
- Exposed etcd to network
- API server without authentication

**Impact**:
- **Critical**: Compromise of control plane = cluster compromise
- Attacker can deploy any workload
- Attacker can access all secrets
- Attacker can delete all workloads

**Defenses**:
- Strong authentication (MFA, certificates)
- Least privilege RBAC
- etcd encryption at rest
- Network isolation for etcd
- Audit logging and monitoring
- Regular updates and patches

**2. Worker Node Threats**
- **Kubelet**: API exposure, authentication bypass, pod manipulation
- **Container Runtime**: Container escape, vulnerable images, socket exposure
- **Kube-proxy**: Network rule manipulation, service spoofing
- **Node OS**: Kernel vulnerabilities, misconfiguration

**Attack Vectors**:
- Exposed Kubelet API
- Container runtime vulnerabilities
- Compromised container images (supply chain)
- Node OS vulnerabilities
- Container escape to host

**Impact**:
- **Critical**: Compromise of worker node = workload compromise
- Attacker can access all pods on node
- Attacker can escape to host
- Node can be used for lateral movement

**Defenses**:
- Secure Kubelet (TLS, authentication)
- Secure container runtime (socket permissions)
- Scan images for vulnerabilities
- Regular OS updates
- Security contexts (non-root, read-only filesystem)

**3. Workload Threats**
- **Vulnerable Applications**: SQL injection, XSS, vulnerabilities
- **Compromised Secrets**: Exposed in configuration files, environment variables
- **Privileged Containers**: Container escape, host access
- **Insecure Configurations**: Default configurations, weak security contexts

**Attack Vectors**:
- Application vulnerabilities
- Secrets in configuration files
- Environment variables with secrets
- Running as root
- Mounting host filesystems
- Using privileged containers

**Impact**:
- **High**: Application compromise = data breach
- Compromised secrets = cluster access
- Container escape = host compromise
- Sensitive data theft

**Defenses**:
- Scan applications for vulnerabilities
- Use secret management (don't put secrets in code)
- Security contexts (runAsNonRoot, drop capabilities)
- Network policies
- Seccomp profiles

**4. Network Threats**
- **Pod-to-Pod Communication**: Unrestricted network access
- **Service Exposure**: Services exposed to internet
- **Ingress Controller**: Web vulnerabilities, misconfiguration
- **Data Exfiltration**: Copying data to attacker servers

**Attack Vectors**:
- Network attacks between pods
- Service scanning and exploitation
- Ingress controller vulnerabilities
- Data exfiltration over network
- Man-in-the-middle attacks

**Impact**:
- **Medium-High**: Network compromise = lateral movement
- Data exfiltration = data breach
- Service compromise = application breach
- Unauthorized access to services

**Defenses**:
- Network policies (default-deny with explicit allow)
- Secure ingress controllers (TLS, WAF)
- Encrypted pod-to-pod communication (service mesh)
- Monitor network traffic
- DLP solutions for data exfiltration

**5. Supply Chain Threats**
- **Compromised Images**: Malicious code in container images
- **Vulnerable Base Images**: Outdated base images with CVEs
- **Compromised Dependencies**: Malicious or vulnerable libraries
- **Build Pipeline Attacks**: Injecting malicious code during build

**Attack Vectors**:
- Compromised image registry
- Typosquatting (malicious packages with legitimate names)
- Vulnerable base images
- Supply chain attacks in build pipeline
- Malicious dependencies

**Impact**:
- **Critical**: Supply chain compromise = cluster compromise
- Malicious code runs in all pods
- Data theft, cryptojacking
- Cluster backdoors

**Defenses**:
- Use private image registry
- Sign and verify images
- Scan images for vulnerabilities
- Use minimal, updated base images
- SBOM (Software Bill of Materials) for dependencies
- Secure build pipeline

### Attack Lifecycle

**Typical Kubernetes Attack Lifecycle:**

```
1. Reconnaissance
   Attacker scans for exposed services
   Port scanning, service enumeration
   Vulnerability scanning

2. Initial Access
   Attacker gains entry point
   Compromised credentials
   Exploited vulnerability
   Misconfigured service

3. Execution
   Attacker runs malicious code
   Creates malicious pod or deployment
   Executes backdoor or cryptojacking

4. Persistence
   Attacker maintains access
   DaemonSet for cluster-wide presence
   CronJob for periodic execution
   Modified deployment to include malicious sidecar

5. Privilege Escalation
   Attacker gains higher privileges
   Container escape to host
   Exploit RBAC misconfiguration
   Access etcd or secrets

6. Defense Evasion
   Attacker avoids detection
   Deletes logs
   Uses rootless containers
    Disables monitoring

7. Credential Access
   Attacker obtains credentials
   Reads secrets from pods
   Accesses etcd
   Steals service account tokens

8. Discovery
   Attacker understands environment
   Enumerates pods, services, nodes
   Maps cluster architecture
   Identifies sensitive workloads

9. Lateral Movement
   Attacker moves through cluster
   Accesses other nodes
   Accesses other namespaces
   Compromises other workloads

10. Collection
    Attacker gathers data
    Scrapes application data
    Exports secrets
    Copies configuration

11. Exfiltration
    Attacker steals data
    Transfers to attacker server
    Data breach
    Cryptojacking

12. Impact
    Attacker achieves objectives
    Cluster compromise
    Data theft
    Service disruption
    Reputation damage
```

**Mitigation at Each Stage:**
- **Reconnaissance**: Network policies, minimize exposure
- **Initial Access**: Strong authentication, vulnerability management
- **Execution**: Admission controllers, pod security policies
- **Persistence**: Regular pod scanning, monitor DaemonSets/CronJobs
- **Privilege Escalation**: Security contexts, RBAC, runtime security
- **Defense Evasion**: Logging, monitoring, Falco
- **Credential Access**: Secret management, least privilege, encryption
- **Discovery**: Network policies, RBAC, monitoring
- **Lateral Movement**: Network segmentation, namespace isolation
- **Collection**: Monitor data access, DLP
- **Exfiltration**: Network monitoring, egress controls, DLP

### **Common Mistakes in Threat Modeling**

❌ **Mistake 1**: Not updating threat model
- Reality: Threat landscape evolves rapidly
- Fix: Regularly update threat model based on new threats

❌ **Mistake 2**: Not considering all assets
- Reality: Workloads, credentials, infrastructure are all assets
- Fix: Model threats for all assets, not just cluster

❌ **Mistake 3**: Not quantifying risk
- Reality: Not all threats are equal
- Fix: Use risk matrix (impact × likelihood)

❌ **Mistake 4**: Not considering supply chain
- Reality: Supply chain is major attack vector
- Fix: Model third-party dependencies, image security

### **Common Interview Questions**

**Q1: What is a threat model and why is it important?**
**Good Answer**: A threat model is a systematic approach to understanding threats facing an environment. It's important because:

1. **Structured approach**: Frameworks like STRIDE, MITRE ATT&CK provide structure
2. **Asset identification**: Know what you're protecting
3. **Threat identification**: Understand who attacks and how
4. **Risk assessment**: Quantify and prioritize risks
5. **Defense guidance**: Guides security control implementation
6. **Proactive security**: Stay ahead of attackers
7. **Efficient spending**: Focus resources on highest risks

Without threat modeling, security is reactive and unfocused. With threat modeling, security is proactive, prioritized, and efficient.

**Q2: What are the key threat models for Kubernetes?**
**Good Answer**: Key threat models for Kubernetes include:

1. **STRIDE**: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege
2. **MITRE ATT&CK**: Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Exfiltration, Command and Control, Impact
3. **PASTA**: Potential, Active, Sustainable, Transient, Evolving, Resurgent, Incident
4. **DREAD**: Decouple, Relate, Explain, Affect, Decouple

Each model provides different perspective. STRIDE is good for initial threat modeling. MITRE ATT&CK is good for analyzing attacks and tactics. PASTA is good for tracking emerging threats. DREAD is good for understanding relationships.

**Q3: What are the most critical threats to Kubernetes?**
**Good Answer**: The most critical threats to Kubernetes are:

1. **Control Plane Compromise**:
   - API server exposure or compromise
   - etcd access without encryption
   - Over-privileged RBAC
   - Impact: Complete cluster compromise

2. **Container Escape**:
   - Privileged containers
   - Vulnerable container runtime
   - Compromised container images
   - Impact: Host compromise, lateral movement

3. **Credential Compromise**:
   - Compromised service accounts
   - Exposed secrets in code or configuration
   - Kubeconfig theft
   - Impact: Unauthorized access to cluster

4. **Supply Chain Attacks**:
   - Compromised container images
   - Vulnerable base images
   - Malicious dependencies
   - Impact: Cluster compromise, malware deployment

5. **Lateral Movement**:
   - No network policies
   - Over-privileged service accounts
   - Namespace isolation failures
   - Impact: Rapid cluster-wide compromise

These threats are critical because they lead to complete cluster compromise, data theft, or cryptojacking. Defending against them is priority for any Kubernetes security program.

**Q4: How do you prioritize security investments using threat model?**
**Good Answer**: Security investments should be prioritized using risk assessment:

1. **Identify vulnerabilities**: Through scanning, assessments, threat modeling
2. **Assess risk**: Risk = Impact × Likelihood
3. **Prioritize**: Address highest risks first
4. **Create remediation plan**: P0 (immediate), P1 (high), P2 (medium), P3 (low)
5. **Track progress**: Monitor remediation efforts
6. **Measure effectiveness**: Track vulnerability reduction over time

**Example Risk Matrix**:
| Vulnerability | Impact | Likelihood | Risk | Priority |
|---------------|--------|-------------|------|----------|
| etcd unencrypted | Critical | High | Critical | P0 |
| API exposed | Critical | High | Critical | P0 |
| Weak RBAC | High | Medium | High | P1 |
| No network policies | High | Medium | High | P1 |
| Privileged containers | High | Medium | High | P2 |
| Outdated K8s | Medium | Low | Medium | P2 |

P0 vulnerabilities require immediate action (within 24 hours). P1 vulnerabilities require short-term action (within 1 week). P2 vulnerabilities require medium-term action (within 1 month).

**Q5: How does threat modeling relate to CIS benchmarks?**
**Good Answer**: Threat modeling and CIS benchmarks are complementary:

1. **CIS Benchmarks**: Provide specific security configuration guidance
   - Concrete controls and configurations
   - Auditable checklist
   - Based on industry best practices
   - Good for compliance and security posture

2. **Threat Modeling**: Provides threat context and prioritization
   - Understanding of attack vectors
   - Risk-based prioritization
   - Adaptable to changing threat landscape
   - Good for proactive defense

3. **Integration**: Use both together:
   - Threat model identifies critical threats
   - CIS benchmarks provide controls to mitigate threats
   - Risk assessment prioritizes which CIS controls to implement first
   - Document findings and track progress

**Example**: Threat model identifies "etcd unencrypted" as critical risk. CIS benchmark provides guidance for enabling etcd encryption. Risk assessment prioritizes this control. Combined approach ensures critical vulnerabilities are addressed first.
