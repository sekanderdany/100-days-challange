# 04.01 - Kubernetes Identity Overview

## 1️⃣ What This Topic Is

Kubernetes Identity Overview examines the fundamentals of Kubernetes identity, authentication, and authorization (IAM), understanding how Kubernetes manages identities, security contexts, and access control.

**What this means:**
- Kubernetes IAM = managing who can access what
- Identity = users, service accounts, groups
- Authentication = verifying who you are
- Authorization = verifying what you can do
- Access control = enforcing access policies

**The Key Concepts:**

1. **Kubernetes Identity Components**
   - Service accounts (cluster, namespaces)
   - Users (external, managed)
   - Groups (RBAC groups, OIDC groups)
   - Security contexts (pod-level, container-level)
   - Admission controllers (authentication, authorization)

2. **Security Principles**
   - Defense in depth (authentication, authorization, auditing)
   - Least privilege (access control)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Kubernetes IAM is foundation of cluster security
- Kubernetes IAM controls all access to cluster resources
- Kubernetes IAM compromise = cluster-wide compromise
- Kubernetes IAM handles all authentication and authorization

## 2️⃣ What Problem It Solves

### Problem 1: Unmanaged Kubernetes Identities

**Without Kubernetes IAM:**
- Unmanaged Kubernetes identities
- Attacker can impersonate identities
- Cluster compromise
- Data theft and service disruption

**With Kubernetes IAM:**
- Managed Kubernetes identities
- Attacker cannot impersonate identities
- Cluster protected
- Data and services protected

### Problem 2: Over-Privileged Kubernetes Identities

**Without Kubernetes IAM:**
- Over-privileged Kubernetes identities
- Attacker can escalate privileges
- Cluster-wide compromise
- Data theft and service disruption

**With Kubernetes IAM:**
- Least privilege Kubernetes identities
- Privilege escalation prevented
- Cluster protected
- Data and services protected

### Problem 3: No Kubernetes IAM Monitoring

**Without Kubernetes IAM:**
- No Kubernetes IAM monitoring
- Security incidents undetected
- Incident response delayed
- Cluster compromise

**With Kubernetes IAM:**
- Kubernetes IAM monitoring enabled
- Security events detected
- Real-time detection
- Rapid incident response

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Over-privileged service accounts
- **Root cause**: No Kubernetes IAM least privilege
- **IAM issue**: Attacker escalated to cluster-admin
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Implement Kubernetes IAM least privilege

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Unmanaged Kubernetes identities
- **Root cause**: No Kubernetes IAM management
- **IAM issue**: Attacker impersonated cluster-admin
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement Kubernetes IAM management

**Example: Capital One Breach (2019)**
- **Vulnerability**: No Kubernetes IAM monitoring
- **Root cause**: No Kubernetes IAM audit logging
- **IAM issue**: Security incidents undetected
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement Kubernetes IAM monitoring

## 4️⃣ How It Works (Conceptual)

### Kubernetes Identity Components

**1. Service Accounts**
- **Purpose**: Provide identity for pods to access Kubernetes API
- **Security Measures**: 
  - Service accounts per namespace
  - Service accounts per workload
  - Service account tokens (short-lived)
  - Service account RBAC
- **Common Misconfigurations**: 
  - No service accounts (all pods use default)
  - Over-privileged service accounts
  - No service account RBAC
  - Long-lived service account tokens
- **Example**: Service accounts for namespaces

**Service Account Types:**
- **Cluster-Level Service Accounts**: 
  - Service accounts for cluster-wide resources
  - Used by system components
  - Used by add-ons

- **Namespace-Level Service Accounts**: 
  - Service accounts for namespace resources
  - Used by workloads in namespace
  - Least privilege

- **Service Account Tokens**: 
  - Service account tokens (JWT)
  - Short-lived tokens
  - Token rotation
  - Token projection

- **Service Account RBAC**: 
  - Service account RBAC (roles, role bindings)
  - Least privilege
  - Namespace-level RBAC

**Best Practices:**
- Create service accounts per namespace
- Create service accounts per workload
- Use least privilege RBAC
- Use short-lived tokens
- Implement token rotation

**Example**:
```yaml
# Service accounts for namespaces (secure, advanced)
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secure-service-account
  namespace: secure-namespace
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: secure-role
  namespace: secure-namespace
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: secure-role-binding
  namespace: secure-namespace
subjects:
- kind: ServiceAccount
  name: secure-service-account
  namespace: secure-namespace
roleRef:
  kind: Role
  name: secure-role
  apiGroup: rbac.authorization.k8s.io
```

**2. Users**
- **Purpose**: Provide identity for humans to access Kubernetes API
- **Security Measures**: 
  - External users (LDAP, OIDC)
  - Managed users (cloud provider IAM)
  - User RBAC (roles, role bindings)
  - User audit logging
- **Common Misconfigurations**: 
  - No user RBAC (all users have cluster-admin)
  - No user audit logging (no audit trail)
  - No user management (unmanaged users)
  - Long-lived user tokens
- **Example**: Users for cluster access

**User Types:**
- **External Users**: 
  - External users (LDAP)
  - External users (OIDC)
  - SSO integration
  - User management

- **Managed Users**: 
  - Cloud provider IAM users
  - Managed users (Azure AD, Google Workspace)
  - SSO integration
  - User management

- **User RBAC**: 
  - User RBAC (roles, role bindings)
  - Cluster-level RBAC
  - Namespace-level RBAC
  - Least privilege

- **User Audit Logging**: 
  - User authentication logging
  - User authorization logging
  - User audit trail
  - Compliance reporting

**Best Practices:**
- Use external users (LDAP, OIDC)
- Use managed users (cloud provider IAM)
- Implement user RBAC (least privilege)
- Implement user audit logging
- Implement SSO integration

**Example**:
```yaml
# Users for cluster access (secure, advanced)
# This would be done via OIDC, LDAP, or cloud provider IAM
# For example, using Azure AD (AAD Pod Identity):
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
  labels:
    aad-pod-identity-binding: "true"
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secure-service-account
  namespace: secure-namespace
  annotations:
    azure.workload.identity/use: "true"
    azure.workload.identity/client-id: "${AAD_CLIENT_ID}"
    azure.workload.identity/tenant-id: "${AAD_TENANT_ID}"
```

**3. Groups**
- **Purpose**: Provide group-based RBAC for Kubernetes IAM
- **Security Measures**: 
  - RBAC groups (roles, role bindings)
  - OIDC groups (group-based access)
  - LDAP groups (group-based access)
  - Group RBAC (least privilege)
- **Common Misconfigurations**: 
  - No RBAC groups (individual user RBAC)
  - Over-privileged groups
  - No group RBAC (cluster-admin groups)
  - No group management
- **Example**: Groups for cluster access

**Group Types:**
- **RBAC Groups**: 
  - Roles (cluster-wide, namespace)
  - Role bindings (associate roles with subjects)
  - Cluster role bindings
  - Least privilege

- **OIDC Groups**: 
  - OIDC groups (email, federated)
  - Group-based RBAC
  - Group-based access control

- **LDAP Groups**: 
  - LDAP groups (user groups)
  - Group-based RBAC
  - Group-based access control

**Best Practices:**
- Use RBAC groups (roles, role bindings)
- Use OIDC groups for group-based RBAC
- Use LDAP groups for group-based RBAC
- Implement least privilege groups
- Regular group audits

**Example**:
```yaml
# Groups for cluster access (secure, advanced)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: developer-role
rules:
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list", "watch", "create", "update", "delete"]
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: developer-role-binding
subjects:
- kind: Group
  name: "developers@example.com"
roleRef:
  kind: ClusterRole
  name: developer-role
  apiGroup: rbac.authorization.k8s.io
```

**4. Security Contexts**
- **Purpose**: Provide security isolation for pods and containers
- **Security Measures**: 
  - Pod-level security contexts
  - Container-level security contexts
  - Non-root containers
  - Drop all capabilities
  - Read-only root filesystem
  - Seccomp profiles
  - AppArmor profiles
- **Common Misconfigurations**: 
  - No security contexts (root, privileged containers)
  - No seccomp profiles (all system calls allowed)
  - No AppArmor profiles (no Linux security policies)
  - Writable root filesystem
  - Privilege escalation allowed
- **Example**: Security contexts for pods

**Security Context Types:**
- **Pod-Level Security Contexts**: 
  - Run as non-root user
  - Run as non-root group
  - No privilege escalation
  - Drop all capabilities
  - Read-only root filesystem
  - Seccomp profiles
  - AppArmor profiles

- **Container-Level Security Contexts**: 
  - Run as non-root user
  - Run as non-root group
  - No privilege escalation
  - Drop all capabilities
  - Read-only root filesystem
  - Seccomp profiles
  - AppArmor profiles

**Best Practices:**
- Enforce pod-level security contexts
- Enforce container-level security contexts
- Use non-root containers
- Drop all capabilities
- Use read-only root filesystem
- Use seccomp profiles
- Use AppArmor profiles

**Example**:
```yaml
# Security contexts for pods (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: security-context-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    allowPrivilegeEscalation: false
    capabilities:
      drop: [ALL]
    readOnlyRootFilesystem: true
    seccompProfile:
      type: RuntimeDefault
    appArmorProfile:
      type: unconfined
    fsGroup: 2000
    supplementalGroups:
    - 3000
    sysctls:
    - net.ipv4.ip_unprivileged_port_start: 80
  containers:
  - name: security-context-container
    image: security-context:v1
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
      seccompProfile:
        type: RuntimeDefault
      appArmorProfile:
        type: unconfined
```

**5. Admission Controllers**
- **Purpose**: Provide additional authentication and authorization
- **Security Measures**: 
  - Authentication webhook (OIDC, LDAP)
  - Authorization webhook (RBAC, ABAC)
  - Validating admission controllers
  - Mutating admission controllers
  - Audit logging
- **Common Misconfigurations**: 
  - No admission controllers (all requests allowed)
  - Over-privileged admission controllers
  - No admission controller RBAC
  - No admission controller audit logging
- **Example**: Admission controllers for cluster access

**Admission Controller Types:**
- **Authentication Webhook**: 
  - OIDC authentication
  - LDAP authentication
  - SSO integration
  - External authentication

- **Authorization Webhook**: 
  - RBAC webhook
  - ABAC webhook
  - Group-based RBAC
  - External authorization

- **Validating Admission Controllers**: 
  - Resource validation
  - Security validation
  - Compliance validation
  - Best practices enforcement

- **Mutating Admission Controllers**: 
  - Resource mutation
  - Default resource injection
  - Security default injection
  - Compliance defaults

**Best Practices:**
- Implement authentication webhook (OIDC, LDAP)
- Implement authorization webhook (RBAC, ABAC)
- Implement validating admission controllers
- Implement mutating admission controllers
- Implement admission controller audit logging

**Example**:
```yaml
# Admission controllers for cluster access (secure, advanced)
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: authentication-webhook
webhooks:
- name: oidc-authentication-webhook
  rules:
  - operations: ["CREATE", "UPDATE", "CONNECT", "DELETE", "GET", "LIST", "WATCH"]
    apiGroups: ["*"]
    apiVersions: ["*"]
    resources: ["*"]
    scope: "*"
    excludeResourceTypes: ["events"]
  failurePolicy: Fail
  matchPolicy: Equivalent
  timeoutSeconds: 30
  admissionReviewVersions: ["v1"]
  sideEffects: NoneOnDryRun
  clientConfig:
    service:
      name: oidc-authentication-service
      namespace: auth-system
      path: /authenticate
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: authorization-webhook
webhooks:
- name: rbac-authorization-webhook
  rules:
  - operations: ["CREATE", "UPDATE", "DELETE", "GET", "LIST", "WATCH"]
    apiGroups: ["*"]
    apiVersions: ["*"]
    resources: ["pods", "services", "configmaps", "secrets"]
    scope: "*"
  failurePolicy: Fail
  matchPolicy: Equivalent
  timeoutSeconds: 30
  admissionReviewVersions: ["v1"]
  sideEffects: NoneOnDryRun
  clientConfig:
    service:
      name: rbac-authorization-service
      namespace: auth-system
      path: /authorize
```
