# 04.02 - Authentication (Tokens, Certificates)

## 1️⃣ What This Topic Is

Authentication (Tokens, Certificates) examines security measures for securing Kubernetes authentication mechanisms, understanding token-based authentication, certificate-based authentication, and secure authentication configurations.

**What this means:**
- Kubernetes authentication = verifying who you are
- Token-based authentication = service account tokens, OIDC tokens
- Certificate-based authentication = X.509 certificates, mTLS
- Secure authentication configurations (rotation, expiration)

**The Key Concepts:**

1. **Kubernetes Authentication Mechanisms**
   - Service account tokens (JWT)
   - OIDC tokens (OpenID Connect)
   - X.509 certificates (client certificates)
   - mTLS (mutual TLS)
   - Certificate rotation
   - Token rotation

2. **Security Principles**
   - Defense in depth (tokens, certificates, rotation)
   - Least privilege (token permissions)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Authentication is foundation of cluster security
- Authentication controls all access to cluster resources
- Authentication compromise = cluster-wide compromise
- Authentication handles all authentication events

## 2️⃣ What Problem It Solves

### Problem 1: Weak Authentication Mechanisms

**Without secure authentication:**
- Weak authentication mechanisms (plaintext tokens)
- Attacker can steal authentication credentials
- Cluster compromise
- Data theft and service disruption

**With secure authentication:**
- Strong authentication mechanisms (encrypted tokens, certificates)
- Attacker cannot steal authentication credentials
- Cluster protected
- Data and services protected

### Problem 2: Long-Lived Authentication Tokens

**Without secure authentication:**
- Long-lived authentication tokens
- Attacker can use stolen tokens indefinitely
- Cluster compromise
- Data theft and service disruption

**With secure authentication:**
- Short-lived authentication tokens
- Token rotation implemented
- Token expiration enforced
- Cluster protected
- Data and services protected

### Problem 3: No Certificate Rotation

**Without secure authentication:**
- No certificate rotation
- Attacker can use stolen certificates indefinitely
- Cluster compromise
- Data theft and service disruption

**With secure authentication:**
- Certificate rotation implemented
- Certificate expiration enforced
- Certificate lifecycle managed
- Cluster protected
- Data and services protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Long-lived service account tokens
- **Root cause**: No token rotation
- **Authentication issue**: Attacker used stolen tokens indefinitely
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Implement token rotation

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Weak authentication mechanisms (plaintext tokens)
- **Root cause**: No token encryption
- **Authentication issue**: Attacker stole plaintext tokens
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement token encryption

**Example: Capital One Breach (2019)**
- **Vulnerability**: No certificate rotation
- **Root cause**: No certificate lifecycle management
- **Authentication issue**: Attacker used stolen certificates indefinitely
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement certificate rotation

## 4️⃣ How It Works (Conceptual)

### Kubernetes Authentication Mechanisms

**1. Service Account Tokens**
- **Purpose**: Provide identity for pods to access Kubernetes API
- **Security Measures**: 
  - JWT tokens (short-lived)
  - Token rotation
  - Token expiration
  - Token encryption
  - Token binding
- **Common Misconfigurations**: 
  - Long-lived tokens (no expiration)
  - No token rotation (static tokens)
  - No token encryption (plaintext tokens)
  - No token binding (tokens not bound to pods)
- **Example**: Service account tokens with JWT

**Service Account Token Types:**
- **JWT Tokens**: 
  - JSON Web Tokens
  - Short-lived tokens
  - Token rotation
  - Token expiration
  - Token encryption

- **Token Rotation**: 
  - Automatic token rotation
  - Manual token rotation
  - Token lifecycle management
  - Token revocation

- **Token Expiration**: 
  - Token expiration policies
  - Short-lived tokens
  - Automatic token expiration
  - Token expiration enforcement

**Best Practices:**
- Use short-lived tokens
- Implement token rotation
- Implement token expiration
- Implement token encryption
- Implement token binding

**Example**:
```yaml
# Service account tokens with JWT (secure, advanced)
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secure-service-account
  namespace: secure-namespace
  annotations:
    service-account.kubernetes.io/autogen-managed-secret: "true"
    service-account.kubernetes.io/token-expiration: "3600"
---
apiVersion: v1
kind: Pod
metadata:
  name: secure-token-pod
  namespace: secure-namespace
spec:
  serviceAccountName: secure-service-account
  containers:
  - name: secure-token-container
    image: secure-token:v1
    env:
    - name: KUBERNETES_SERVICE_ACCOUNT_TOKEN
      valueFrom:
        fieldRef:
          fieldPath: /var/run/secrets/kubernetes.io/serviceaccount/token
```

**3. X.509 Certificates**
- **Purpose**: Provide identity for clients to access Kubernetes API
- **Security Measures**: 
  - X.509 certificates (client certificates)
  - Certificate rotation
  - Certificate expiration
  - Certificate revocation
  - Certificate binding
- **Common Misconfigurations**: 
  - Long-lived certificates (no expiration)
  - No certificate rotation (static certificates)
  - No certificate revocation (no CRL)
  - Weak certificate configuration (weak algorithms)
  - No certificate encryption (plaintext certificates)
- **Example**: X.509 certificates with client certificates

**X.509 Certificate Types:**
- **Client Certificates**: 
  - X.509 client certificates
  - Certificate rotation
  - Certificate expiration
  - Certificate revocation
  - Certificate binding

- **Certificate Rotation**: 
  - Automatic certificate rotation
  - Manual certificate rotation
  - Certificate lifecycle management
  - Certificate revocation

- **Certificate Expiration**: 
  - Certificate expiration policies
  - Short-lived certificates
  - Automatic certificate expiration
  - Certificate expiration enforcement

- **Certificate Revocation**: 
  - Certificate revocation (CRL)
  - OCSP (Online Certificate Status Protocol)
  - Certificate revocation enforcement

- **Certificate Binding**: 
  - Certificate subject binding
  - Certificate SAN (Subject Alternative Name)
  - Certificate SPI (Subject Public Key Info)
  - Certificate binding enforcement

**Best Practices:**
- Use short-lived certificates
- Implement certificate rotation
- Implement certificate expiration
- Implement certificate revocation
- Implement certificate binding

**Example**:
```yaml
# X.509 certificates with client certificates (secure, advanced)
apiVersion: certificates.k8s.io/v1
kind: Certificate
metadata:
  name: secure-client-certificate
  namespace: secure-namespace
spec:
  secretName: secure-client-certificate-secret
  duration: 2160h # 90 days
  renewBefore: 720h # 30 days before expiration
  privateKey:
    algorithm: RSA
    size: 2048
  dnsNames:
  - api.example.com
  - "*.example.com"
  subject:
    organizations:
    - Example Company
    - Security Team
  commonName: Secure Client Certificate
  emailAddresses:
  - security@example.com
  usages:
  - client auth
  - digital signature
```

**4. mTLS (Mutual TLS)**
- **Purpose**: Provide encrypted authentication for API server and clients
- **Security Measures**: 
  - mTLS configuration
  - Strong TLS (TLS 1.3, strong ciphers)
  - Certificate validation
  - Certificate rotation
  - Certificate expiration
- **Common Misconfigurations**: 
  - No mTLS (plaintext communication)
  - Weak TLS (outdated protocols, weak ciphers)
  - No certificate validation (any certificate accepted)
  - Long-lived certificates (no expiration)
  - No certificate rotation (static certificates)
- **Example**: mTLS configuration with TLS 1.3

**mTLS Types:**
- **API Server mTLS**: 
  - API server mTLS configuration
  - API server certificate validation
  - API server certificate rotation
  - API server certificate expiration

- **Kubelet mTLS**: 
  - Kubelet mTLS configuration
  - Kubelet certificate validation
  - Kubelet certificate rotation
  - Kubelet certificate expiration

- **Controller mTLS**: 
  - Controller mTLS configuration
  - Controller certificate validation
  - Controller certificate rotation
  - Controller certificate expiration

- **Strong TLS**: 
  - TLS 1.3 (latest protocol)
  - Strong ciphers (AES-GCM, ChaCha20)
  - Strong key exchange (ECDHE, X25519)
  - Strong signature (Ed25519, RSA-2048)

**Best Practices:**
- Implement mTLS for all components
- Use TLS 1.3 (latest protocol)
- Use strong ciphers (AES-GCM, ChaCha20)
- Use strong key exchange (ECDHE, X25519)
- Implement certificate rotation
- Implement certificate expiration

**Example**:
```yaml
# mTLS configuration with TLS 1.3 (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: mtls-api-server
  namespace: kube-system
spec:
  containers:
  - name: kube-apiserver
    image: k8s.gcr.io/kube-apiserver:v1.27.0
    args:
    - --tls-cert-file=/etc/kubernetes/pki/apiserver.crt
    - --tls-private-key-file=/etc/kubernetes/pki/apiserver.key
    - --client-ca-file=/etc/kubernetes/pki/client-ca.crt
    - --tls-min-version=VersionTLS13
    - --tls-cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
    - --request-header-client-CA=X-Client-Certificate
    - --authorization-mode=Webhook
    - --enable-bootstrap-token-auth=true
    - --enable-token-request=true
```
