# 01.10 - Privilege Escalation

## 1️⃣ What This Topic Is

Privilege Escalation examines how attackers gain elevated permissions in Kubernetes environments, understanding privilege escalation vectors, detection techniques, and mitigation strategies.

**What this means:**
- Privilege escalation = gaining higher permissions
- Attacker wants to elevate privileges from pod → node → cluster
- Multiple escalation vectors exist in Kubernetes
- Understanding escalation helps prevent cluster compromise

**The Key Concepts:**

1. **Escalation Types**
   - Container-to-host (container escape)
   - Pod-to-node (Kubelet API, node access)
   - Pod-to-cluster (API server, etcd access)
   - Namespace-to-cluster (cluster-admin access)

2. **Escalation Vectors**
   - Vulnerable container images (kernel exploits)
   - Privileged containers (host access)
   - Over-privileged RBAC (excessive permissions)
   - Misconfigured security contexts (capabilities)
   - Vulnerable container runtime (exploits)

**Why this matters:**
- Privilege escalation leads to cluster compromise
- Container escape enables host access
- Over-privileged RBAC enables cluster control
- Cluster control = data theft, service disruption

---

## 2️⃣ What Problem It Solves

### Problem 1: Container-to-Host Escape

**Without understanding privilege escalation:**
- Can't detect when container escapes to host
- Attacker can access all pods on node
- Attacker can compromise control plane
- Cluster-wide compromise

**With understanding privilege escalation:**
- Know container escape vectors
- Can detect escape attempts
- Can implement security contexts
- Can prevent host access

### Problem 2: Pod-to-Node Access

**Without understanding privilege escalation:**
- Can't detect when pod accesses node
- Attacker can use Kubelet API
- Attacker can access other pods on node
- Node compromise

**With understanding privilege escalation:**
- Know Kubelet API access vectors
- Can detect unusual API calls
- Can implement network policies
- Can restrict node access

### Problem 3: Namespace-to-Cluster Access

**Without understanding privilege escalation:**
- Can't detect when namespace gains cluster access
- Over-privileged RBAC gives cluster control
- Attacker can access all resources in cluster
- Cluster-wide compromise

**With understanding privilege escalation:**
- Know RBAC over-privilege vectors
- Can detect unusual API calls
- Can implement RBAC limits
- Can audit RBAC permissions regularly

### Real-World Impact

**Example: CVE-2019-11234 (Container Escape)**
- **Vulnerability**: Vulnerable container runtime
- **Root cause**: No container runtime updates
- **Privilege escalation issue**: Container escape to host
- **Impact**: Attacker accessed all pods on node
- **Lesson**: Update container runtime, use security contexts

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Exposed Kubelet API
- **Root cause**: No Kubelet authentication
- **Privilege escalation issue**: Pod-to-node access
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Secure Kubelet API, implement network policies

**Example: Capital One Breach (2019)**
- **Vulnerability**: Over-privileged service account
- **Root cause**: No RBAC limits
- **Privilege escalation issue**: Namespace-to-cluster access
- **Impact**: Attacker accessed all resources in cluster
- **Lesson**: Implement least privilege RBAC, audit permissions

## 4️⃣ How It Works (Conceptual)

### Privilege Escalation Vectors

**1. Container Escape (Container-to-Host)**
- **Purpose**: Escape container to gain host access
- **Attacker Use**: Exploit kernel vulnerabilities, misconfigured containers
- **Detection Challenge**: Container escape is hard to detect
- **Example**: Container escape via privileged container

**Escalation Flow:**
```
Attacker gains pod access → Exploits container escape → Attacker has host access → Attacker accesses all pods on node → Lateral movement
```

**Detection:**
- Monitor for container escape attempts
- Monitor for host process execution
- Monitor for unusual file system access
- Use Falco for runtime security

**Mitigation:**
- Use security contexts (non-root, drop capabilities)
- Use pod security policies (restrict privileged containers)
- Use seccomp/AppArmor profiles
- Update container runtime regularly

**Example**:
```yaml
# Privileged container (dangerous)
apiVersion: v1
kind: Pod
metadata:
  name: privileged-container
spec:
  containers:
  - name: app
    image: nginx:1.25-alpine
    securityContext:
      privileged: true  # DANGEROUS
      hostNetwork: true  # DANGEROUS
```

**2. Pod-to-Node Access (Kubelet API)**
- **Purpose**: Access Kubelet API to control node
- **Attacker Use**: Exploit exposed Kubelet API, compromised credentials
- **Detection Challenge**: Kubelet API calls look legitimate
- **Example**: Attacker uses Kubelet API to create malicious pods

**Escalation Flow:**
```
Attacker gains pod access → Attacker discovers node IP → Attacker accesses Kubelet API → Attacker creates malicious pods on node → Node compromise
```

**Detection:**
- Monitor for unusual Kubelet API calls
- Monitor for unauthorized pod creation
- Monitor for unusual node access
- Audit Kubelet API logs

**Mitigation:**
- Secure Kubelet API (TLS, authentication)
- Implement network policies (restrict Kubelet access)
- Use authorization webhook (Kubelet API)
- Monitor Kubelet API access

**Example**:
```bash
# Attacker uses Kubelet API to create malicious pod
curl -k https://node-ip:10250/api/v1/namespaces/default/pods -X POST -H "Content-Type: application/json" \
  -d @malicious-pod.json
```

**3. Pod-to-Cluster Access (API Server)**
- **Purpose**: Access API server to gain cluster control
- **Attacker Use**: Exploit over-privileged RBAC, compromised credentials
- **Detection Challenge**: API server calls look legitimate
- **Example**: Attacker uses cluster-admin to access all resources

**Escalation Flow:**
```
Attacker gains API server access → Attacker uses cluster-admin → Attacker accesses all resources → Cluster compromise → Data theft, service disruption
```

**Detection:**
- Monitor for unusual API calls
- Monitor for cluster-admin usage
- Monitor for unusual resource access
- Audit API server logs

**Mitigation:**
- Implement least privilege RBAC
- Audit RBAC permissions regularly
- Use service account token limits
- Monitor cluster-admin usage

**Example**:
```bash
# Attacker uses cluster-admin to access all resources
kubectl auth can-i get secrets --all-namespaces --as cluster-admin
# Returns: yes
```

**4. Over-privileged RBAC (Namespace-to-Cluster)**
- **Purpose**: Gain cluster control from namespace
- **Attacker Use**: Exploit over-privileged RBAC, compromised credentials
- **Detection Challenge**: RBAC over-privilege looks like legitimate
- **Example**: Namespace admin gains cluster-admin access

**Escalation Flow:**
```
Attacker gains namespace admin access → Attacker discovers cluster-admin role → Attacker creates cluster-admin binding → Attacker has cluster control
```

**Detection:**
- Monitor for unusual role bindings
- Monitor for unusual role creations
- Monitor for unusual cluster-admin bindings
- Audit RBAC logs regularly

**Mitigation:**
- Implement least privilege RBAC
- Use RoleBindings instead of ClusterRoleBindings
- Audit RBAC permissions regularly
- Use RBAC validation tools

**Example**:
```bash
# Attacker creates cluster-admin binding
kubectl create clusterrolebinding admin-binding \
  --clusterrole=cluster-admin \
  --serviceaccount=default:namespace-admin
```

**5. Security Context Escalation (Capabilities)**
- **Purpose**: Exploit excessive capabilities
- **Attacker Use**: Exploit Linux capabilities to escape container
- **Detection Challenge**: Capability exploitation is hard to detect
- **Example**: Attacker uses CAP_SYS_ADMIN to escape container

**Escalation Flow:**
```
Attacker gains pod access → Attacker uses excessive capabilities → Attacker exploits CAP_SYS_ADMIN → Container escape → Host access
```

**Detection:**
- Monitor for suspicious capability usage
- Monitor for unusual system calls
- Monitor for container escape attempts
- Use Falco for runtime security

**Mitigation:**
- Drop all unnecessary capabilities
- Use security contexts (drop capabilities)
- Use seccomp/AppArmor profiles
- Read-only filesystem

**Example**:
```yaml
# Pod with excessive capabilities (dangerous)
apiVersion: v1
kind: Pod
metadata:
  name: capabilities-escape
spec:
  containers:
  - name: app
    image: alpine:3.18
    securityContext:
      capabilities:
        add: ["SYS_ADMIN"]  # DANGEROUS
```

### Privilege Escalation Detection Techniques

**1. Container Escape Detection**

- Detect unusual file system access
- Detect suspicious system calls

**2. Kubelet API Detection**

**3. API Server Detection**

- Audit API server logs

**4. RBAC Detection**

### **2. Applying Privilege Escalation Mitigation**

**Example: Implementing Security Contexts**

```bash
echo "=== Security Contexts Implementation ==="

# 1. Create pod with security contexts (non-root, drop capabilities)
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:1.25-alpine
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
EOF

# 2. Verify security contexts
kubectl get pod secure-pod
kubectl describe pod secure-pod | grep -A 10 "Security Context:"

# DOCUMENT: What security contexts did you implement?
```

**Example: Implementing Pod Security Policies**

```bash
echo "=== Pod Security Policies Implementation ==="

# 1. Create PSP to restrict privileged containers
cat <<EOF | kubectl apply -f -
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: restricted
spec:
  privileged: false
  allowPrivilegeEscalation: false
  requiredDropCapabilities:
  - ALL
  volumes:
  - configMap
  - downwardAPI
  - emptyDir
  - persistentVolumeClaim
  - secret
  hostNetwork: false
  hostIPC: false
  hostPID: false
  runAsUser:
    rule: MustRunAsNonRoot
EOF

# 2. Verify PSP
kubectl get psp restricted
kubectl describe psp restricted | grep -A 20 "Privileged:"

# DOCUMENT: What PSP did you implement?
```

**Example: Implementing Least Privilege RBAC**

```bash
echo "=== Least Privilege RBAC Implementation ==="

# 1. Create namespace-admin role (not cluster-admin)
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: namespace-admin
  namespace: production
rules:
- apiGroups: [""]
  resources: ["pods", "services", "configmaps"]
  verbs: ["get", "list", "watch", "create", "update", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: namespace-admin-binding
  namespace: production
subjects:
- kind: User
  name: namespace-admin-user
roleRef:
  kind: Role
  name: namespace-admin
  apiGroup: rbac.authorization.k8s.io
EOF

# 2. Verify RBAC
kubectl auth can-i get secrets --all-namespaces --as namespace-admin-user
# Should return: yes for production namespace only

# DOCUMENT: What least privilege RBAC did you implement?
```

### **Common Mistakes in Privilege Escalation Detection/Mitigation**

❌ **Mistake 1**: Not using security contexts
- Reality: Containers run as root by default
- Fix: Always use runAsNonRoot: true

❌ **Mistake 2**: Not dropping capabilities
- Reality: Containers have all Linux capabilities
- Fix: Always drop ALL capabilities

❌ **Mistake 3**: Not using PSPs
- Reality: Privileged containers are common
- Fix: Use PSPs to restrict privileged containers

❌ **Mistake 4**: Not auditing RBAC
- Reality: Over-privileged RBAC is common
- Fix: Audit RBAC permissions regularly

### **Common Interview Questions**

**Q1: What are common privilege escalation vectors in Kubernetes?**
**Good Answer**: Common privilege escalation vectors in Kubernetes include:

1. **Container Escape (Container-to-Host)**: 
   - Vulnerable container runtime (kernel exploits)
   - Privileged containers
   - Excessive capabilities (CAP_SYS_ADMIN)
   - Attacker escapes container to host
   - Attacker accesses all pods on node

2. **Pod-to-Node (Kubelet API)**: 
   - Exposed Kubelet API
   - Compromised credentials
   - Attacker accesses Kubelet API
   - Attacker creates malicious pods on node
   - Node compromise

3. **Pod-to-Cluster (API Server)**: 
   - Over-privileged RBAC
   - Compromised credentials
   - Attacker uses cluster-admin
   - Attacker accesses all resources
   - Cluster compromise

4. **Namespace-to-Cluster (RBAC)**: 
   - Over-privileged namespace roles
   - Cluster-admin bindings
   - Attacker creates cluster-admin binding
   - Cluster control
   - Cluster compromise

Each vector allows attacker to gain elevated privileges.

**Q2: How do you detect privilege escalation in Kubernetes?**
**Good Answer**: Privilege escalation detection in Kubernetes includes:

1. **Container Escape Detection**: 
   - Monitor for container escape attempts
   - Detect host process execution
   - Detect unusual file system access
   - Use Falco for runtime security

2. **Kubelet API Detection**: 
   - Monitor for unusual Kubelet API calls
   - Detect unauthorized pod creation
   - Detect unusual node access
   - Audit Kubelet API logs

3. **API Server Detection**: 
   - Monitor for unusual API calls
   - Detect cluster-admin usage
   - Detect unusual resource access
   - Audit API server logs

4. **RBAC Detection**: 
   - Monitor for unusual role bindings
   - Detect unusual role creations
   - Detect unusual cluster-admin bindings
   - Audit RBAC logs regularly

5. **Runtime Security Detection**: 
   - Monitor for suspicious processes
   - Detect unusual system calls
   - Detect container escape attempts
   - Use Falco for runtime security

Detection tools: Falco, Kubernetes audit logs, rbac-lookup.

**Q3: How do you mitigate privilege escalation in Kubernetes?**
**Good Answer**: Privilege escalation mitigation in Kubernetes includes:

1. **Security Contexts**: 
   - Run as non-root user
   - Drop all capabilities
   - Use read-only filesystem
   - Implement seccomp/AppArmor profiles
   - Prevent privilege escalation

2. **Pod Security Policies**: 
   - Enforce security configurations
   - Restrict privileged containers
   - Require non-root users
   - Drop capabilities
   - Enforce least privilege

3. **Least Privilege RBAC**: 
   - Limit RBAC to least privilege
   - Use RoleBindings instead of ClusterRoleBindings
   - Audit RBAC permissions regularly
   - Use service account token limits

4. **Runtime Monitoring**: 
   - Monitor for suspicious processes (Falco)
   - Monitor for container escape attempts
   - Set up alerts for suspicious activity
   - Enable automated response

5. **Container Runtime Updates**: 
   - Keep container runtime updated
   - Patch CVEs in runtime
   - Use secure runtime configurations

6. **Regular RBAC Audits**: 
   - Audit RBAC permissions regularly
   - Detect over-privileged RBAC
   - Detect unusual role bindings
   - Implement automated remediation

Combined approach provides defense in depth against privilege escalation.

**Q4: What's most dangerous privilege escalation vector in Kubernetes?**
**Good Answer**: The most dangerous privilege escalation vectors are:

1. **Container Escape (Container-to-Host)**: Because it's most dangerous
   - Attacker can execute code on host
   - Cluster compromised if host is control plane
   - Enables lateral movement and persistence
   - Complete cluster compromise

2. **Namespace-to-Cluster (RBAC)**: Because it's hard to detect
   - Over-privileged RBAC gives cluster control
   - Attacker can access all resources
   - Cluster-wide compromise
   - Hard to detect with RBAC alone

3. **Pod-to-Node (Kubelet API)**: Because it's powerful
   - Attacker can create malicious pods on node
   - Node compromise
   - Lateral movement to other nodes

Container escape is most dangerous because it gives host access. Namespace-to-cluster is most dangerous because it's hard to detect. Kubelet API is most dangerous because it's powerful.

**Q5: How do Pod Security Policies help prevent privilege escalation?**
**Good Answer**: PSPs help prevent privilege escalation by:

1. **Enforcing Security Configurations**: 
   - Require non-root users
   - Prevent privileged containers
   - Require dropping capabilities
   - Restrict volume types
   - Enforce least privilege

2. **Preventing Privilege Escalation**: 
   - Set allowPrivilegeEscalation to false
   - Prevent privilege escalation within container
   - Prevent container escape attempts

3. **Restricting Access**: 
   - Restrict host access
   - Restrict network access
   - Restrict file system access
   - Prevent lateral movement

4. **Validating Images**: 
   - Validate images before deployment
   - Implement image scanning policies
   - Reject vulnerable images
   - Prevent malicious code execution

5. **Monitoring and Alerting**: 
   - Alert on PSP violations
   - Detect insecure configurations
   - Enable automated response
   - Prevent deployment of insecure pods

PSPs enforce security standards and prevent insecure configurations that enable privilege escalation.
