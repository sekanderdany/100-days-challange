# 01.02 - Trust Boundaries & Data Flow

## 1️⃣ What This Topic Is

Trust Boundaries & Data Flow examines how data moves through Kubernetes and where security controls (trust boundaries) exist between components.

**What this means:**
- Trust boundaries are points where authentication/authorization occurs
- Data flow is the path data takes through the system
- Each boundary is an opportunity to enforce security
- Understanding flow helps identify where to apply controls

**The Key Concepts:**

1. **Trust Boundary**
   - Point where two components interact
   - Authentication: "Who are you?"
   - Authorization: "What can you do?"
   - Enforcement point for security policies

2. **Data Flow**
   - Path data takes through the system
   - From user to workload
   - Through multiple components
   - Each hop is a potential attack point

**Why this matters:**
- Attackers exploit weak trust boundaries
- Data flow reveals attack paths
- Security must be enforced at boundaries
- Understanding flow helps design defenses

---

## 2️⃣ What Problem It Solves

### Problem 1: Invisible Attack Paths

**Without understanding data flow:**
- Don't know how attackers can move through system
- Can't predict lateral movement
- Miss security gaps in critical paths
- Ineffective incident response

**With data flow understanding:**
- Map all data paths
- Identify potential attack routes
- Place security controls at critical points
- Effectively trace attacks during incidents

### Problem 2: Weak Trust Boundaries

**Without understanding trust boundaries:**
- Don't know where to enforce security
- Apply controls at wrong points
- Miss authentication/authorization opportunities
- Attacker bypasses security easily

**With trust boundary understanding:**
- Know where to place security controls
- Enforce authentication at all boundaries
- Apply authorization appropriately
- Attacker faces multiple security layers

### Problem 3: Inconsistent Security

**Without understanding boundaries and flow:**
- Security controls inconsistent
- Some paths have controls, others don't
- Creates weak links attackers can exploit
- Difficult to audit and maintain

**With boundary and flow understanding:**
- Consistent security at all boundaries
- Uniform controls across data paths
- No weak links in security chain
- Easier to audit and maintain

### Real-World Impact

**Example: Tesla API Server Bypass (2018)**
- **Vulnerability**: Weak authentication at API server trust boundary
- **Root cause**: API server didn't enforce authentication
- **Trust boundary issue**: User → API Server boundary was weak
- **Impact**: Attacker accessed cluster directly, deployed miners

**Example: Cryptojacking via Kubelet (2018)**
- **Vulnerability**: Kubelet API exposed without authentication
- **Root cause**: Kubelet trust boundary was open
- **Trust boundary issue**: API Server ↔ Kubelet boundary bypassed
- **Impact**: Attacker controlled worker nodes, deployed miners

**Example: etcd Data Exfiltration (2019)**
- **Vulnerability**: etcd exposed to network without authentication
- **Root cause**: etcd trust boundary was weak
- **Trust boundary issue**: API Server ↔ etcd boundary bypassed
- **Impact**: Attacker accessed all cluster secrets and configs

## 3️⃣ When You Should Use This

### **ALWAYS** - Understanding trust boundaries and data flow is essential for ALL Kubernetes security

**When Designing Security:**
- Map all trust boundaries
- Design authentication at each boundary
- Design authorization based on data flow
- Place security controls at critical points

**When Investigating Incidents:**
- Trace attack through data flow
- Identify which boundaries were bypassed
- Understand lateral movement
- Plan remediation based on attack path

**When Configuring Security:**
- Place controls at appropriate boundaries
- Configure authentication based on trust requirements
- Configure authorization based on data access needs
- Monitor boundary violations

### Scenarios where this is critical:

**When implementing multi-cluster:**
- Understand trust boundaries between clusters
- Design authentication for cross-cluster access
- Plan data flow between clusters
- Configure federation security

**When implementing service mesh:**
- Add new trust boundaries (service-to-service)
- Implement mutual TLS at each boundary
- Understand data flow through mesh
- Configure policies for mesh boundaries

**When using managed Kubernetes (EKS/GKE/AKS):**
- Understand provider-managed boundaries
- Understand your-managed boundaries
- Design security for your responsibilities
- Monitor boundary violations

**When responding to breaches:**
- Trace attacker through data flow
- Identify compromised boundaries
- Understand what was accessed
- Plan remediation based on attack path

## 4️⃣ How It Works (Conceptual)

### Primary Trust Boundaries

**1. User ↔ API Server**

**Boundary**: External user requests Kubernetes API

**Authentication**: "Who are you?"
- Methods:
  - **Client certificates**: x.509 certificates
  - **Bearer tokens**: Service account tokens, OIDC tokens
  - **Basic auth**: Username/password (not recommended for production)

**Authorization**: "What can you do?"
- **RBAC (Role-Based Access Control)**:
  - Roles: Namespace-scoped permissions
  - ClusterRoles: Cluster-wide permissions
  - RoleBindings: Bind roles to users/service accounts
  - ClusterRoleBindings: Bind cluster roles

**Trust Model**: API Server trusts valid authentication tokens

**Data Flow**:
```
User Request → Authentication → Authorization → Admission Control → etcd Store
```

**Security Implications:**
- **Critical boundary**: All cluster management flows through here
- **Single point**: If compromised, attacker has cluster access
- **Strong controls required**: Multi-factor authentication, least privilege RBAC
- **Monitoring required**: Track who accesses what resources

**Example**:
```yaml
# User with limited permissions
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: default
subjects:
- kind: User
  name: developer
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**2. API Server ↔ etcd**

**Boundary**: API Server stores and retrieves cluster state

**Authentication**: Client certificate authentication
- API Server presents client certificate to etcd
- etcd validates certificate
- Only API Server can access etcd

**Authorization**: Certificate-based access control
- **Client certificates**: Identify API Server
- **TLS encryption**: Encrypts data in transit
- **Certificate authority**: Manages certificate issuance

**Trust Model**: etcd trusts API Server's client certificate

**Data Flow**:
```
API Server → TLS + Client Cert → etcd → Cluster State
```

**Security Implications:**
- **Highly sensitive**: Contains all cluster secrets and configurations
- **Critical component**: If compromised, entire cluster compromised
- **Strong encryption required**: TLS for all communication
- **Isolation required**: etcd should be network-isolated
- **Backups required**: Regular encrypted backups

**Example Configuration**:
```yaml
# API Server to etcd TLS configuration
apiVersion: v1
kind: Pod
metadata:
  name: kube-apiserver
  namespace: kube-system
spec:
  containers:
  - name: kube-apiserver
    command:
    - kube-apiserver
    - --etcd-servers=https://etcd:2379
    - --etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
    - --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
    - --etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key
```

**3. API Server ↔ Scheduler**

**Boundary**: API Server schedules pods via scheduler

**Authentication**: Service account tokens
- Scheduler uses service account tokens
- Tokens are mounted in scheduler pod
- API Server validates tokens

**Authorization**: RBAC
- Scheduler has cluster-admin-like permissions
- Creates pod bindings (assigns pods to nodes)
- Modifies cluster state

**Trust Model**: API Server trusts scheduler's service account

**Data Flow**:
```
API Server → Pod (unscheduled) → Scheduler (schedules) → API Server → Pod Binding
```

**Security Implications:**
- **Important boundary**: Controls pod placement
- **High privilege**: Scheduler can place pods on any node
- **Least privilege**: Scheduler should have minimal necessary permissions
- **Taints/tolerations**: Additional control mechanism
- **Monitoring required**: Track scheduling decisions

**Example**:
```yaml
# Scheduler service account permissions
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: system:node-controller
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch", "create", "update", "delete"]
- apiGroups: [""]
  resources: ["pods/binding"]
  verbs: ["create"]
```

**4. API Server ↔ Controller Manager**

**Boundary**: API Server controllers maintain cluster state

**Authentication**: Service account tokens
- Controllers use service account tokens
- Tokens mounted in controller pods
- API Server validates tokens

**Authorization**: RBAC
- Controllers have cluster-admin-like permissions
- Create/update/delete Kubernetes objects
- Maintain desired state

**Trust Model**: API Server trusts controllers' service accounts

**Data Flow**:
```
API Server → Desired State → Controller Manager → Actual State → API Server → Update
```

**Security Implications:**
- **High privilege**: Has broad cluster access
- **State management**: Creates and modifies critical objects
- **Namespace management**: Controls isolation boundaries
- **Monitoring required**: Track controller actions

**Example**:
```yaml
# Controller manager service account
apiVersion: v1
kind: ServiceAccount
metadata:
  name: replication-controller
  namespace: kube-system
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: system:controller
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update", "delete", "patch"]
```

**5. API Server ↔ Kubelet**

**Boundary**: API Server creates pods on worker nodes

**Authentication**: TLS + certificates
- API Server presents certificate to Kubelet
- Kubelet validates certificate
- Mutual TLS for secure communication

**Authorization**: Node authorization (optional webhook)
- **Node authorization**: Validate if node can run specific pods
- **Webhook**: External authorization decision
- **Admission control**: Validate pod before creation

**Trust Model**: API Server trusts Kubelet's certificate, Kubelet trusts API Server

**Data Flow**:
```
API Server → Pod Spec → Kubelet → Container Runtime → Container
```

**Security Implications:**
- **Critical boundary**: Controls what runs on nodes
- **Node-level security**: If Kubelet compromised, node compromised
- **Pod security**: Pod security contexts enforced here
- **Admission control**: Validate pods before they run
- **Monitoring required**: Track what pods run on which nodes

**Example**:
```yaml
# Kubelet pod security context
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:alpine
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
```

**6. Kubelet ↔ Container Runtime**

**Boundary**: Kubelet manages container lifecycle

**Authentication**: Unix socket (on same host)
- Kubelet communicates with containerd via Unix socket
- No network authentication (same host)
- Socket permissions provide access control

**Authorization**: Security contexts, profiles
- **Security contexts**: runAsUser, capabilities, etc.
- **Seccomp profiles**: System call filtering
- **AppArmor/SELinux**: Mandatory access control

**Trust Model**: Kubelet trusts container runtime (same host)

**Data Flow**:
```
Kubelet → Container Runtime (socket) → Container
```

**Security Implications:**
- **Critical boundary**: Controls container execution
- **Same-host trust**: Socket-based communication (not network)
- **Container escape**: If compromised, attacker accesses host
- **Security enforcement**: Pod security contexts, profiles enforced here
- **Socket security**: Critical to secure container runtime socket

**Example**:
```yaml
# Secure containerd configuration
version = 2

[plugins]
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
    SystemdCgroup = true
```

**7. Pod ↔ Pod (Network)**

**Boundary**: Pods communicate over network

**Authentication**: Network policies (if configured)
- **Network policies**: Control pod-to-pod communication
- **Default**: All pods can communicate (if no policies)
- **Whitelist model**: Explicitly allow communication

**Authorization**: Pod labels/selectors
- **Pod selectors**: Match pods based on labels
- **Namespace isolation**: Policies can be namespace-scoped
- **Service discovery**: DNS-based pod discovery

**Trust Model**: Pods trust network (if policy allows), or are isolated

**Data Flow**:
```
Pod A → Network Policy → Pod B
```

**Security Implications:**
- **Important boundary**: Controls lateral movement
- **Default permissive**: Without policies, all communication allowed
- **Network segmentation**: Policies create isolation zones
- **East-west traffic**: Pod-to-pod communication controlled
- **Monitoring required**: Track network traffic between pods

**Example**:
```yaml
# Network policy: default-deny
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# Network policy: allow web-to-db
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-database
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: webserver
    ports:
    - protocol: TCP
      port: 5432
```

**8. Service ↔ Pod (Service Discovery)**

**Boundary**: Services route traffic to pods

**Authentication**: Kube-proxy (iptables/IPVS rules)
- **Kube-proxy**: Implements services on each node
- **IPTables/IPVS**: Network rules for service routing
- **No authentication**: Trust based on pod labels

**Authorization**: Service selection
- **Pod labels**: Pods selected by labels
- **Namespace scope**: Services are namespace-scoped
- **Endpoint updates**: Kube-proxy updates as pods change

**Trust Model**: Kube-proxy trusts API Server (service definitions)

**Data Flow**:
```
Client → Service (ClusterIP) → Kube-proxy (IPTables) → Pod
```

**Security Implications:**
- **Important boundary**: Controls service-to-pod routing
- **Network manipulation**: If Kube-proxy compromised, routing manipulated
- **Service spoofing**: Malicious pods could mimic legitimate services
- **Network policies**: Apply to service traffic too
- **Monitoring required**: Track service endpoint changes

**Example**:
```yaml
# Service definition
apiVersion: v1
kind: Service
metadata:
  name: web-service
  namespace: production
spec:
  selector:
    app: webserver
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
```

### Complete Data Flow Example

**User Creating Pod:**
```
1. User Request → API Server
   Authentication: "Who are you?" (token/cert)
   Authorization: "Can you create pods?" (RBAC)
   Admission Control: "Is pod secure?" (policies)

2. API Server → etcd
   Authentication: Client certificate
   Encryption: TLS
   Action: Store pod definition

3. API Server → Scheduler
   Authentication: Service account token
   Authorization: Cluster-wide permissions
   Action: Schedule pod to node

4. Scheduler → API Server
   Action: Create pod binding

5. API Server → Kubelet
   Authentication: TLS + certificate
   Authorization: Node authorization (webhook)
   Action: Create pod on node

6. Kubelet → Container Runtime
   Authentication: Unix socket
   Action: Start container
   Security: Apply security contexts, profiles

7. Kubelet → API Server
   Action: Report pod status

8. Other Pods → New Pod (if network policy allows)
   Network Policy: Check if communication allowed
   Action: Allow or deny traffic
```

**Security Controls at Each Boundary:**
1. **User ↔ API Server**: Authentication, RBAC, admission control
2. **API Server ↔ etcd**: TLS, client certificates, encryption at rest
3. **API Server ↔ Scheduler**: Service account tokens, RBAC
4. **API Server ↔ Controller**: Service account tokens, RBAC
5. **API Server ↔ Kubelet**: TLS, certificates, node authorization
6. **Kubelet ↔ Container Runtime**: Socket permissions, security contexts, profiles
7. **Pod ↔ Pod**: Network policies
8. **Service ↔ Pod**: Kube-proxy, iptables, network policies

Understanding trust boundaries and data flow should guide **all security decisions** in Kubernetes.

**Example: Securing User ↔ API Server Boundary**

```bash

kubectl api-versions | grep rbac.authorization.k8s.io
```

### **Common Mistakes in Trust Boundary Security**

❌ **Mistake 1**: Not authenticating at all boundaries
- Reality: Every component interaction requires authentication
- Fix: Configure authentication at all trust boundaries

❌ **Mistake 2**: Not authorizing appropriately
- Reality: Each component needs appropriate permissions
- Fix: Apply RBAC with least privilege at all boundaries

❌ **Mistake 3**: Assuming network boundaries exist
- Reality: Default Kubernetes has no network boundaries
- Fix: Implement network policies (default-deny model)

❌ **Mistake 4**: Not monitoring boundaries
- Reality: Boundary violations indicate attacks
- Fix: Monitor authentication failures, authorization denials, network policy violations

**User ↔ API Server Boundary:**
- **Critical**: Gateway to cluster, all operations flow through it
- **Vulnerabilities**: No RBAC, no admission control, no audit logging
- **Impact**: Unauthorized cluster access, bypassed policies

- **Critical**: Contains all cluster data (secrets, configs)
- **Vulnerabilities**: Not encrypted at rest, network exposed
- **Impact**: Data theft, cluster compromise
- **Remediation**: Enable encryption, network isolation, TLS

**API Server ↔ Scheduler Boundary:**
- **Important**: Controls pod placement
- **Vulnerabilities**: Can bypass taints, evade resource limits
- **Impact**: Compromised node placement, resource exhaustion
- **Remediation**: Taints/tolerations, pod security, resource quotas

**API Server ↔ Controller Manager Boundary:**
- **Important**: Maintains cluster state
- **Vulnerabilities**: Over-privileged service account, weak RBAC
- **Impact**: Manipulated cluster state, unauthorized object creation
- **Remediation**: Least-privileged service accounts, RBAC, audit logging

**API Server ↔ Kubelet Boundary:**
- **Critical**: Controls what runs on nodes
- **Vulnerabilities**: API exposed, weak authentication
- **Impact**: Attacker controls node, creates arbitrary pods
- **Remediation**: Kubelet authentication, authorization webhook, network policies

**Kubelet ↔ Container Runtime Boundary:**
- **Critical**: Controls container execution
- **Vulnerabilities**: Socket exposed, insecure config
- **Impact**: Container escape, host compromise
- **Remediation**: Security contexts, seccomp/AppArmor, secure config

**Pod ↔ Pod Boundary:**
- **Important**: Controls lateral movement
- **Vulnerabilities**: No network policies, bypass possible
- **Impact**: Network attacks, lateral movement
- **Remediation**: Network policies, service mesh, segmentation

**Service ↔ Pod Boundary:**
- **Important**: Controls service-to-pod routing
- **Vulnerabilities**: Can manipulate network rules, bypass policies
- **Impact**: Network attacks, service spoofing
- **Remediation**: Network policies, service mesh, RBAC

**Key Learning Points:**

1. **Each boundary is attack surface**: Must secure all boundaries
2. **Control plane is critical**: If compromised, cluster compromised
3. **Worker nodes are targets**: If compromised, attacker controls workloads
4. **Add-ons extend attack surface**: Must secure DNS, ingress, CNI
5. **Architecture guides security**: Understanding architecture helps design defenses
6. **Trust boundaries exist**: Components authenticate to each other
7. **Defense in depth**: Multiple security layers across architecture

## 8️⃣ Security Best Practices

### **Do's ✅**

**1. Secure All Trust Boundaries**
- User ↔ API Server, API Server ↔ etcd, etc.
- Every boundary needs authentication and authorization
- Apply security controls at all boundaries
- Don't skip any boundary

**2. Understand Trust Boundaries**
- Components authenticate to each other
- Configure authentication at all boundaries
- Monitor trust boundary violations
- Document trust relationships

**3. Apply Least Privilege**
- RBAC with least privilege
- Service accounts with minimal permissions
- Cluster-wide permissions rarely needed
- Node authorization where appropriate

**4. Monitor Boundary Violations**
- Track authentication failures
- Track authorization denials
- Track network policy violations
- Set up alerting for suspicious activity

**5. Regularly Update Components**
- Keep Kubernetes updated
- Update certificates before expiration
- Rotate service account tokens
- Patch boundary components

**6. Document Boundaries**
- Document authentication methods
- Document authorization model
- Document trust relationships
- Document incident response procedures

### **Don'ts ❌**

**1. Don't Skip Trust Boundaries**
- Every component interaction is a boundary
- Secure all boundaries with authentication and authorization
- Don't assume provider secures everything

- Each boundary needs specific security
- Understand boundary-specific security requirements
- Don't apply generic controls to all boundaries

### **Common Interview Questions**

**Q1: What are trust boundaries in Kubernetes?**
**Good Answer**: Trust boundaries are points where Kubernetes components interact and enforce authentication and authorization. Key boundaries include:

1. **User ↔ API Server**: Authentication (certificates, OIDC, tokens) and Authorization (RBAC)
2. **API Server ↔ etcd**: TLS + client certificates
3. **API Server ↔ Scheduler/Controller**: Service account tokens and RBAC
4. **API Server ↔ Kubelet**: TLS + certificates and node authorization
5. **Kubelet ↔ Container Runtime**: Unix socket (same host), security contexts and profiles
6. **Pod ↔ Pod**: Network policies (if configured), otherwise all traffic allowed
7. **Service ↔ Pod**: Kube-proxy (iptables/IPVS)

Each boundary must have authentication and authorization. If any boundary is bypassed or misconfigured, attacker can move laterally through system.

**Q2: What are the key trust boundaries in Kubernetes and why are they critical?**
**Good Answer**: The most critical trust boundaries are:

1. **User ↔ API Server**: Gateway to cluster, all operations flow through it
2. **API Server ↔ etcd**: Contains all cluster data (secrets, configs), if compromised, entire cluster compromised
3. **API Server ↔ Kubelet**: Controls what runs on nodes, if compromised, attacker controls node
4. **Kubelet ↔ Container Runtime**: Runs all containers, if compromised, attacker can escape to host

Each boundary requires strong security controls because compromising them gives attackers significant access to the cluster or host.

**Q3: How do trust boundaries relate to defense in depth?**
**Good Answer**: Trust boundaries create defense in depth by enforcing security at multiple points in the data flow. For example:
- User → API Server (authentication + authorization)
- API Server → etcd (TLS + encryption)
- API Server → Kubelet (TLS + certificates)
- Kubelet → Container Runtime (security contexts + profiles)

If one boundary is bypassed, other boundaries still provide protection. Defense in depth requires multiple security controls at each boundary, not just one.

**Q4: What's the difference between authentication and authorization at trust boundaries?**
**Good Answer**: At trust boundaries:

**Authentication** (Who are you?):
- User ↔ API Server: Certificates, OIDC, tokens
- API Server ↔ etcd: Client certificates
- API Server ↔ Kubelet: Certificates
- API Server ↔ Scheduler/Controller: Service account tokens

**Authorization** (What can you do?):
- User ↔ API Server: RBAC (roles, clusterRoles)
- API Server ↔ Scheduler: RBAC (pod placement permissions)
- API Server ↔ Controller: RBAC (object creation/deletion)

Authentication identifies the principal (user, service account, component). Authorization determines what actions the principal can perform on what resources.

**Q5: How do you identify a trust boundary bypass?**
**Good Answer**: Trust boundary bypasses can be identified by:

1. **Monitoring**: Watch for successful actions that bypass expected authorization
2. **Audit logs**: Review logs for unauthorized access
3. **Network traffic**: Detect lateral movement that bypasses network policies
4. **Component behavior**: Abnormal component behavior (e.g., Kubelet creating unexpected pods)
5. **Boundary violations**: Failed authentication or authorization attempts

Tools like Falco (runtime security), kube-bench (CIS compliance), and audit logging help identify trust boundary bypasses during incidents.
