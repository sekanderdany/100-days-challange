# 03.03 - Scheduler Security

## 1️⃣ What This Topic Is

Scheduler Security examines security measures for securing Kubernetes scheduler, understanding scheduler security, scheduling policies, and advanced configurations.

**What this means:**
- Scheduler security = securing Kubernetes pod scheduling
- Defense in depth for scheduler
- Least privilege for scheduler
- Secure scheduler configurations

**The Key Concepts:**

1. **Scheduler Security Areas**
   - Scheduler authentication (mTLS, client certificates)
   - Scheduler authorization (RBAC, webhook)
   - Scheduler encryption (at rest and in transit)
   - Scheduling policies (affinity, anti-affinity, taints, tolerations)
   - Scheduler isolation
   - Scheduler monitoring

2. **Security Principles**
   - Defense in depth (authentication, authorization, encryption)
   - Least privilege (scheduler permissions)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Scheduler is critical for cluster operations
- Scheduler is primary attack target
- Scheduler compromise = cluster compromise
- Scheduler handles all pod scheduling

## 2️⃣ What Problem It Solves

### Problem 1: Unauthenticated Scheduler Access

**Without scheduler security:**
- Unauthenticated scheduler access
- Attacker can access scheduler API
- Cluster compromise
- Data theft and service disruption

**With scheduler security:**
- Scheduler authentication required (mTLS, client certificates)
- Unauthorized access prevented
- Cluster protected

### Problem 2: Over-Privileged Scheduler Access

**Without scheduler security:**
- Over-privileged scheduler access
- Attacker can escalate privileges
- Cluster-wide compromise
- Data theft and service disruption

**With scheduler security:**
- Least privilege scheduler access (RBAC, webhook)
- Privilege escalation prevented
- Cluster protected

### Problem 3: Scheduler Denial of Service

**Without scheduler security:**
- No scheduler rate limiting
- Attacker can DoS scheduler
- Cluster disruption
- Service unavailability

**With scheduler security:**
- Scheduler rate limiting implemented
- DoS attacks prevented
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unauthenticated scheduler
- **Root cause**: No scheduler authentication
- **Scheduler issue**: Attacker accessed scheduler API without authentication
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Configure scheduler authentication

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Over-privileged scheduler access
- **Root cause**: No scheduler least privilege
- **Scheduler issue**: Attacker escalated to scheduler-admin
- **Impact**: 57 million customer records accessed
- **Lesson**: Configure scheduler least privilege

**Example: Capital One Breach (2019)**
- **Vulnerability**: Scheduler DoS
- **Root cause**: No scheduler rate limiting
- **Scheduler issue**: Attacker DoSed scheduler
- **Impact**: Service disruption, data access
- **Lesson**: Configure scheduler rate limiting

## 4️⃣ How It Works (Conceptual)

### Scheduler Security Areas

**1. Scheduler Authentication**
- **Purpose**: Verify who can access scheduler
- **Security Measures**: 
  - mTLS (mutual TLS)
  - Client certificate authentication
  - Token-based authentication (service accounts)
  - Anonymous access (disabled)
- **Common Misconfigurations**: 
  - No scheduler authentication (all access allowed)
  - Weak authentication (weak certificates)
  - Anonymous access enabled
  - Long-lived tokens
  - Weak TLS (outdated protocols, weak ciphers)
- **Example**: Scheduler with mTLS and client certificates

**Scheduler Authentication Types:**
- **mTLS (Mutual TLS)**: 
  - Scheduler verifies client certificates
  - Client verifies scheduler certificates
  - Prevents man-in-the-middle attacks
  - Prevents unauthorized access

- **Client Certificates**: 
  - X.509 certificates
  - Certificate-based authentication
  - Certificate rotation
  - Revocation

- **Token-Based Authentication**: 
  - Service account tokens
  - Bearer tokens
  - Short-lived tokens
  - Token rotation

**Best Practices:**
- Use mTLS for scheduler
- Use client certificate authentication
- Use short-lived tokens
- Implement certificate rotation
- Use strong TLS (TLS 1.3, strong ciphers)
- Disable anonymous access

**Example**:
```yaml
# Scheduler with mTLS and client certificates (secure)
apiVersion: v1
kind: Pod
metadata:
  name: kube-scheduler
  namespace: kube-system
spec:
  containers:
  - name: kube-scheduler
    image: k8s.gcr.io/kube-scheduler:v1.27.0
    args:
    - --client-ca-file=/etc/kubernetes/pki/client-ca.crt
    - --tls-cert-file=/etc/kubernetes/pki/scheduler.crt
    - --tls-private-key-file=/etc/kubernetes/pki/scheduler.key
    - --tls-min-version=VersionTLS13
    - --tls-cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
    - --anonymous-auth=false
```

**2. Scheduler Authorization**
- **Purpose**: Control what can be done with scheduler
- **Security Measures**: 
  - RBAC (Role-Based Access Control)
  - Authorization webhook
  - Namespace-based authorization
  - Resource-based authorization
  - Default-deny with explicit allow
- **Common Misconfigurations**: 
  - No scheduler authorization (all access allowed)
  - Over-privileged RBAC
  - No resource-based authorization
  - No namespace-based authorization
- **Example**: Scheduler with RBAC and webhook

**Scheduler Authorization Types:**
- **RBAC (Role-Based Access Control)**: 
  - Cluster roles (cluster-wide permissions)
  - Roles (namespace permissions)
  - Role bindings (associate roles with subjects)
  - Cluster role bindings
  - Least privilege

- **Authorization Webhook**: 
  - External webhook validates requests
  - Rejects or allows requests
  - Flexible authorization

- **Namespace-Based Authorization**: 
  - Namespace-level permissions
  - Tenant-level isolation
  - Least privilege

- **Resource-Based Authorization**: 
  - Resource-level permissions
  - Fine-grained permissions
  - Least privilege

**Best Practices:**
- Use least privilege RBAC
- Use authorization webhook for flexibility
- Use namespace-based authorization for multi-tenancy
- Use resource-based authorization for fine-grained control
- Regular RBAC audits

**Example**:
```yaml
# Scheduler RBAC (least privilege)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: scheduler-reader
rules:
- nonResourceURLs:
  - /metrics
  - /health
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: scheduler-reader-binding
subjects:
- kind: ServiceAccount
  name: scheduler-reader
roleRef:
  kind: ClusterRole
  name: scheduler-reader
  apiGroup: rbac.authorization.k8s.io
```

**3. Scheduling Policies**
- **Purpose**: Control how pods are scheduled
- **Security Measures**: 
  - Node affinity
  - Node anti-affinity
  - Pod affinity
  - Pod anti-affinity
  - Taints and tolerations
  - Node selectors
- **Common Misconfigurations**: 
  - No scheduling policies (pods scheduled anywhere)
  - Insecure scheduling policies
  - No node isolation
  - Overly permissive policies
- **Example**: Scheduling policies for security

**Scheduling Policy Types:**
- **Node Affinity**: 
  - Pod must run on specific node
  - Node-based isolation
  - Security requirements

- **Node Anti-Affinity**: 
  - Pod must not run on specific node
  - Spread pods across nodes
  - High availability
  - DoS mitigation

- **Pod Affinity**: 
  - Pod must run with specific pod
  - Co-location for security
  - Performance optimization

- **Pod Anti-Affinity**: 
  - Pod must not run with specific pod
  - Spread pods across nodes
  - DoS mitigation
  - High availability

- **Taints and Tolerations**: 
  - Node isolation
  - Security requirements
  - Dedicated nodes for security
  - Critical workloads

- **Node Selectors**: 
  - Pod must run on nodes with specific labels
  - Node-based isolation
  - Security requirements

**Best Practices:**
- Use node affinity for security requirements
- Use node anti-affinity for DoS mitigation
- Use taints and tolerations for node isolation
- Use node selectors for security requirements
- Regular scheduling policy reviews

**Example**:
```yaml
# Scheduling policy (taints and tolerations for security)
apiVersion: v1
kind: Pod
metadata:
  name: security-pod
spec:
  containers:
  - name: security-container
    image: security:v1
  tolerations:
  - key: dedicated-node
    operator: Equal
    value: "true"
    effect: NoSchedule
  nodeSelector:
    matchLabels:
      security: dedicated
```

**4. Scheduler Encryption**
- **Purpose**: Encrypt scheduler data and communication
- **Security Measures**: 
  - Scheduler to API server encryption (mTLS)
  - Scheduler to kubelet encryption (mTLS)
  - Scheduler encryption at rest
  - Scheduler encryption in transit
- **Common Misconfigurations**: 
  - No scheduler encryption (plaintext communication)
  - Weak TLS (outdated protocols, weak ciphers)
  - No mTLS for scheduler communication
  - No encryption at rest
- **Example**: Scheduler with encryption

**Scheduler Encryption Types:**
- **Scheduler to API Server Encryption**: 
  - mTLS for scheduler to API server
  - Certificate-based authentication
  - Encryption key rotation

- **Scheduler to Kubelet Encryption**: 
  - mTLS for scheduler to kubelet
  - Certificate-based authentication
  - Encryption key rotation

- **Scheduler Encryption at Rest**: 
  - Scheduler secrets encryption
  - KMS encryption
  - Encryption key rotation

**Best Practices:**
- Use TLS 1.3 or higher
- Use strong ciphers
- Use strong key exchange (ECDHE, etc.)
- Use certificate-based authentication
- Implement certificate rotation
- Use KMS for encryption at rest

**Example**:
```yaml
# Scheduler encryption (secure)
apiVersion: v1
kind: Pod
metadata:
  name: kube-scheduler
  namespace: kube-system
spec:
  containers:
  - name: kube-scheduler
    image: k8s.gcr.io/kube-scheduler:v1.27.0
    args:
    - --kubeconfig=/etc/kubernetes/scheduler.conf
    - --tls-cert-file=/etc/kubernetes/pki/scheduler.crt
    - --tls-private-key-file=/etc/kubernetes/pki/scheduler.key
    - --tls-min-version=VersionTLS13
    - --tls-cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
```

**5. Scheduler Isolation**
- **Purpose**: Isolate scheduler from other components
- **Security Measures**: 
  - Scheduler network isolation
  - Scheduler to API server encryption (mTLS)
  - Scheduler to kubelet encryption (mTLS)
  - Scheduler authentication and authorization
- **Common Misconfigurations**: 
  - No scheduler isolation (all components in same network)
  - No scheduler to API server encryption
  - No scheduler to kubelet encryption
  - Over-privileged scheduler access
- **Example**: Scheduler isolation

**Scheduler Isolation Types:**
- **Scheduler Network Isolation**: 
  - Scheduler network isolation
  - Scheduler to API server encryption (mTLS)
  - Scheduler to kubelet encryption (mTLS)
  - Scheduler network policies

- **Scheduler Process Isolation**: 
  - Scheduler process isolation
  - Scheduler least privilege
  - Scheduler authentication

- **Scheduler Identity Isolation**: 
  - Scheduler identity separation
  - Scheduler authentication
  - Scheduler authorization

**Best Practices:**
- Implement scheduler network isolation
- Implement scheduler to API server encryption (mTLS)
- Implement scheduler to kubelet encryption (mTLS)
- Implement scheduler authentication
- Implement scheduler least privilege
- Implement scheduler monitoring

**Example**:
```yaml
# Scheduler isolation (secure)
apiVersion: v1
kind: Pod
metadata:
  name: kube-scheduler
  namespace: kube-system
spec:
  containers:
  - name: kube-scheduler
    image: k8s.gcr.io/kube-scheduler:v1.27.0

      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
      runAsNonRoot: true
```
