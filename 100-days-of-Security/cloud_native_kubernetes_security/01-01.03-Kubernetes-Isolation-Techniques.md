# 01.03 - Kubernetes Isolation Techniques

## 1️⃣ What This Topic Is

Kubernetes Isolation Techniques examines the multiple layers of isolation in Kubernetes and how they work together to provide defense in depth for applications and the cluster.

**What this means:**
- Isolation prevents attackers from moving laterally
- Multiple layers provide defense in depth
- Different isolation mechanisms serve different purposes
- Understanding isolation helps design secure architectures

**The Four Cs of Isolation:**

1. **Cluster-Level Isolation**
   - Separation between clusters
   - Multi-tenant considerations
   - Cluster federation boundaries

2. **Node-Level Isolation**
   - Isolation between worker nodes
   - Node taints and tolerations
   - Node selectors and affinity
   - Network segmentation

3. **Namespace-Level Isolation**
   - Logical separation of resources
   - Resource quotas
   - Network policies
   - Role-based access control

4. **Pod-Level Isolation**
   - Container isolation
   - Security contexts (user, capabilities)
   - Seccomp profiles (system calls)
   - AppArmor/SELinux (mandatory access control)
   - Resource limits

**Why this matters:**
- Isolation prevents lateral movement
- Defense in depth uses multiple layers
- Breaches in one layer don't compromise entire system
- Isolation is foundational to cloud security

---

## 2️⃣ What Problem It Solves

### Problem 1: Lateral Movement

**Without isolation:**
- Attacker compromises one pod
- Attacker moves to other pods on same node
- Attacker compromises entire node
- Rapid cluster compromise

**With isolation:**
- Attacker compromises one pod
- Isolation limits what attacker can access
- Attacker cannot move laterally
- Containment prevents cluster-wide compromise

### Problem 2: Resource Exhaustion

**Without isolation:**
- No resource limits on pods
- One pod can consume all node resources
- Other pods starved (DoS)
- Node becomes unresponsive

**With isolation:**
- Resource quotas at namespace level
- Resource limits on pods
- Limits requests per namespace
- Prevents resource exhaustion

### Problem 3: Tenant Coexistence

**Without isolation:**
- Multi-tenant clusters share resources
- No tenant separation
- Tenant A can access Tenant B's resources
- Compliance violations (data mixing)

**With isolation:**
- Namespace-level separation per tenant
- RBAC per tenant
- Network policies between tenants
- Quotas per tenant
- Tenant isolation enforced

### Real-World Impact

**Example: Cryptojacking Attack (2018) - No Pod Isolation**
- **Vulnerability**: Compromised container accessed host
- **Root cause**: No container isolation (run as root)
- **Isolation issue**: Container could access host resources
- **Impact**: Attacker compromised worker node, deployed miners
- **Lesson**: Use security contexts, non-root containers

**Example: Uber Data Breach (2016) - No Namespace Isolation**
- **Vulnerability**: Compromised credentials accessed all namespaces
- **Root cause**: No namespace-level RBAC
- **Isolation issue**: Credentials had cluster-wide access
- **Impact**: Attacker accessed entire cluster
- **Lesson**: Use least privilege RBAC per namespace

**Example: Tesla Kubernetes Breach (2018) - No Node Isolation**
- **Vulnerability**: Compromised console accessed all nodes
- **Root cause**: No node-level access controls
- **Isolation issue**: Nodes not isolated from management plane
- **Impact**: Attacker accessed all worker nodes
- **Lesson**: Use taints, network segmentation, RBAC

## 3️⃣ When You Should Use This

### **ALWAYS** - Isolation should be applied at ALL levels in Kubernetes

**When Designing Multi-Tenant Clusters:**
- Use namespace-level isolation per tenant
- Implement RBAC per tenant
- Use network policies between tenants
- Set resource quotas per tenant
- Monitor cross-tenant access

**When Securing Production Workloads:**
- Use pod-level isolation (security contexts)
- Implement seccomp/AppArmor profiles
- Use resource limits
- Network policies between pods
- Run as non-root users

**When Running Sensitive Workloads:**
- Use multiple isolation layers
- Namespace-level isolation
- Network policies for communication
- Strong pod security contexts
- Monitoring and alerting

**When Implementing Service Mesh:**
- Use service mesh for pod-to-pod isolation
- Implement mutual TLS
- Use network policies with service mesh
- Monitor service-to-service communication

### Scenarios where this is critical:

**Multi-Tenant SaaS Platforms:**
- Namespace isolation per tenant is critical
- RBAC per tenant required
- Network policies between tenants
- Resource quotas per tenant
- Audit logs for compliance

**Financial Services:**
- Strong isolation is critical (PCI-DSS, SOX)
- Network segmentation required
- RBAC with least privilege
- Encrypted communication
- Comprehensive monitoring

**Healthcare (HIPAA):**
- Patient data isolation required
- Namespace-level separation per patient group
- Strict RBAC required
- Audit logging for access tracking
- Network policies for data segregation

**Government/Defense:**
- Need for Compartmentalization
- Strong isolation across all layers
- Zero-trust architecture
- Air-gapped environments for classified data

## 4️⃣ How It Works (Conceptual)

### Cluster-Level Isolation

**1. Multi-Cluster Isolation**
- Separate clusters for different environments
- Development, staging, production clusters
- Different teams have different clusters
- Federation with strong authentication

**Security Benefits:**
- Compromise in one cluster doesn't affect others
- Reduced attack surface per cluster
- Easier compliance (per-cluster requirements)
- Clear separation of concerns

**Example:**
```bash
# Production cluster
kubectl config use-context production-cluster

# Development cluster
kubectl config use-context development-cluster

# No cross-cluster access (by design)
```

**2. Cluster Federation**
- Multiple clusters communicate securely
- Federation API with authentication
- Selective resource sharing
- Strong trust boundaries between clusters

**Security Benefits:**
- Controlled cross-cluster communication
- Centralized management with isolation
- Reduced administrative overhead
- Strong trust boundaries

**Example:**
```yaml
# Federation configuration
apiVersion: core.k8s.io/v1alpha1
kind: ClusterRole
metadata:
  name: federation-reader
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list"]
---
apiVersion: core.k8s.io/v1alpha1
kind: ClusterRoleBinding
metadata:
  name: federation-reader-binding
subjects:
  - kind: User
    name: federation-admin
roleRef:
  kind: ClusterRole
  name: federation-reader
```

### Node-Level Isolation

**3. Node Taints and Tolerations**
- Taints prevent scheduling of pods on specific nodes
- Tolerations allow specific pods to be scheduled
- Used for dedicated nodes or specialized workloads
- Prevents unwanted pod placement

**Security Benefits:**
- Isolates sensitive workloads to specific nodes
- Prevents scheduling of untrusted pods
- Physical or logical separation
- Reduces attack surface

**Example:**
```yaml
# Node taints
apiVersion: v1
kind: Node
metadata:
  name: production-node
spec:
  taints:
  - key: workload
    value: production
    effect: NoSchedule
---
# Pod toleration (allows scheduling)
apiVersion: v1
kind: Pod
metadata:
  name: production-app
spec:
  tolerations:
  - key: workload
    value: production
    effect: NoSchedule
  containers:
  - name: app
    image: myapp:1.0
```

**4. Node Selectors and Affinity**
- Node selectors: Schedule pods on specific nodes
- Node affinity: Rules for pod placement
- Pod anti-affinity: Prevent pods from being co-located
- Used for isolation and performance

**Security Benefits:**
- Ensures sensitive pods run on specific nodes
- Prevents co-location of untrusted pods
- Logical separation of workloads
- Compliance requirements

**Example:**
```yaml
# Node affinity
apiVersion: v1
kind: Pod
metadata:
  name: sensitive-app
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: security-level
            operator: In
            values:
            - high
  containers:
  - name: app
    image: myapp:1.0
---
# Pod anti-affinity (separation)
apiVersion: v1
kind: Pod
metadata:
  name: production-app
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: other-app
        topologyKey: kubernetes.io/hostname
  containers:
  - name: app
    image: myapp:1.0
```

**5. Network Segmentation**
- Separate networks for different environments
- VPC peering with strict controls
- Subnet isolation
- Network policies for pod-to-pod communication

**Security Benefits:**
- Network-level isolation
- Reduced attack surface
- Controlled communication between segments
- Compliance with network security standards

**Example:**
```yaml
# Network policy for segmentation
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: isolate-sensitive-namespace
  namespace: sensitive-workloads
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: untrusted-namespace
    - podSelector:
        matchLabels:
          app: trusted-app
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: trusted-namespace
    - podSelector:
        matchLabels:
          app: trusted-app
```

### Namespace-Level Isolation

**6. Namespace-Level RBAC**
- Roles and RoleBindings per namespace
- ClusterRoles and ClusterRoleBindings for cluster-wide access
- Service accounts with least privilege
- Deny all by default, allow explicitly

**Security Benefits:**
- Namespace-level authorization
- Least privilege access
- Clear separation of permissions
- Audit logging per namespace

**Example:**
```yaml
# Namespace with RBAC
apiVersion: v1
kind: Namespace
metadata:
  name: production
---
# Role for production
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: production-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list", "watch"]
---
# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: production-reader-binding
  namespace: production
subjects:
- kind: User
  name: production-developer
roleRef:
  kind: Role
  name: production-reader
  apiGroup: rbac.authorization.k8s.io
```

**7. Resource Quotas**
- Limit resources per namespace
- Prevents resource exhaustion
- CPU, memory, storage limits
- Object count limits

**Security Benefits:**
- Prevents Noisy Neighbor problem
- Fair resource allocation
- Compliance with capacity planning
- DoS prevention

**Example:**
```yaml
# Resource quota
apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    persistentvolumeclaims: 2
    pods: 10
  scopes:
  - NotTerminating
  - BestEffort
---
# Limit range for default namespace
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: default
spec:
  limits:
  - max:
      cpu: "800m"
      memory: 2Gi
      ephemeral-storage: 10Gi
  default:
    cpu: "500m"
    memory: 1Gi
    ephemeral-storage: 5Gi
  type: Container
```

**8. Network Policies**
- Control pod-to-pod communication
- Default-deny or allow-all models
- Namespace-scoped or cluster-scoped
- Ingress and Egress rules

**Security Benefits:**
- Lateral movement prevention
- Segmentation of workloads
- Zero-trust network model
- Compliance with network security

**Example:**
```yaml
# Default-deny all
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# Allow specific communication
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-db
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: webserver
    ports:
    - protocol: TCP
      port: 5432
```

### Pod-Level Isolation

**9. Security Contexts**
- Run as non-root user
- Drop all capabilities
- Read-only root filesystem
- Prevent privilege escalation

**Security Benefits:**
- Reduced attack surface
- Containment if compromised
- Least privilege
- Defense in depth

**Example:**
```yaml
# Pod security context
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
    supplementalGroups: [5000]
  containers:
  - name: app
    image: nginx:alpine
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
```

**10. Linux Capabilities**
- Fine-grained control over privileged operations
- Drop all capabilities, add only what's needed
- Prevents privilege escalation
- Reduces attack surface

**Security Benefits:**
- Least privilege for containers
- Prevents certain system calls
- Defense in depth
- Audit trail of capability usage

**Example:**
```yaml
# Drop all capabilities
capabilities:
  drop: [ALL]
# Add only specific capability
capabilities:
  add: [NET_BIND_SERVICE]
```

**11. Seccomp Profiles**
- System call filtering
- Default profiles (RuntimeDefault, Docker, etc.)
- Custom profiles for specific workloads
- Prevents kernel exploitation

**Security Benefits:**
- Reduces kernel attack surface
- Prevents certain system calls
- Container isolation
- Defense in depth

**Example:**
```yaml
# Use default profile
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-pod
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:alpine
```

**12. AppArmor/SELinux**
- Mandatory access control for Linux
- Profile-based security
- Enforces security policies at kernel level
- Prevents unauthorized access

**Security Benefits:**
- Strongest isolation mechanism
- Kernel-level enforcement
- Prevents file system access
- Audit logging

**Example:**
```yaml
# AppArmor profile
apiVersion: v1
kind: Pod
metadata:
  name: apparmor-pod
  annotations:
    container.apparmor.security.beta.kubernetes.io/apparmor: my-profile
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:alpine
```

**AppArmor Profile:**
```
#include <tunables/global.h>

profile my-profile {
  # Deny all file writes
  deny /** rw,

  # Allow read access to /var/log
  /var/log/** rw,

  # Deny network access (except DNS)
  deny network raw tcp stream,
  network raw udp stream,

  # Allow DNS
  network /etc/resolv.conf r,

  # Allow read access to /usr/share/nginx
  /usr/share/nginx/** r,
}
```

**13. Resource Limits**
- CPU and memory limits per container
- Limits requests (QoS)
- Prevents resource exhaustion
- Ensures fair resource allocation

**Security Benefits:**
- Noisy Neighbor prevention
- Resource isolation
- QoS guarantees
- DoS prevention

**Example:**
```yaml
# Pod with resource limits
apiVersion: v1
kind: Pod
metadata:
  name: resource-limited-pod
spec:
  containers:
  - name: app
    image: nginx:alpine
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
```

### Service Mesh Isolation (Advanced)

**14. Mutual TLS (mTLS)**
- All service-to-service communication encrypted
- Service identity per service
- Certificate-based authentication
- Prevents man-in-the-middle

**Security Benefits:**
- Strong encryption of all traffic
- Service identity and authentication
- Prevents spoofing
- Compliance with encryption standards

**Example:**
```yaml
# Istio peer authentication
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: mtls-policy
spec:
  mtls:
    mode: STRICT
```

**15. Service-to-Service Authorization**
- Authorization policies between services
- Source/destination checks
- JWT-based tokens
- Fine-grained access control

**Security Benefits:**
- Zero-trust service-to-service
- Least privilege between services
- Audit logging
- Prevents lateral movement

**Example:**
```yaml
# Istio authorization policy
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: web-to-database-policy
spec:
  selector:
    matchLabels:
      app: webserver
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/database"]
    - to:
      operation:
        methods: ["GET"]
        namespaces: ["database"]
```

### **Common Mistakes in Isolation**

❌ **Mistake 1**: Not using multiple isolation layers
- Reality: Each layer provides different protection
- Fix: Use cluster → node → namespace → pod isolation

❌ **Mistake 2**: Running pods as root
- Reality: Root access in containers is dangerous
- Fix: Always use runAsNonRoot: true

❌ **Mistake 3**: No network policies
- Reality: All pods can communicate
- Fix: Implement default-deny with explicit allow

❌ **Mistake 4**: No resource quotas
- Reality: One namespace can consume all resources
- Fix: Implement resource quotas per namespace

## 8️⃣ Security Best Practices

### **Do's ✅**

**1. Use Multiple Isolation Layers**
- Cluster-level isolation (multi-cluster)
- Node-level isolation (taints, network segmentation)
- Namespace-level isolation (RBAC, network policies, quotas)
- Pod-level isolation (security contexts, profiles)

**2. Defense in Depth**
- Each layer provides different protection
- Breach in one layer doesn't compromise entire system
- Multiple layers create stronger security posture

**3. Least Privilege**
- Run pods as non-root
- Drop all capabilities
- Use least privilege RBAC
- Minimal required access only

**4. Zero-Trust Network Model**
- Default-deny network policies
- Explicit allow only necessary communication
- Mutual TLS for service mesh
- Strong authentication at boundaries

**5. Resource Quotas**
- Limit resources per namespace
- Prevent resource exhaustion
- Ensure fair allocation

**6. AppArmor/SELinux**
- Enable for all pods
- Use strong profiles
- Regularly update profiles
- Monitor violations

**7. Regular Reviews**
- Review isolation configuration quarterly
- Audit effectiveness
- Update based on lessons learned
- Remove outdated isolation controls

### **Don'ts ❌**

**1. Don't Run Pods as Root**
- Root access in containers is dangerous
- Always use runAsNonRoot: true
- Use non-root users

**2. Don't Skip Network Policies**
- Default Kubernetes allows all communication
- Implement default-deny with explicit allow
- Network policies are critical for lateral movement prevention

**3. Don't Ignore Resource Quotas**
- One namespace can consume all resources
- Implement resource quotas per namespace
- Prevents Noisy Neighbor problem

**4. Don't Drop All Capabilities**
- Drop all, add only what's needed
- Use minimal required capabilities
- Regularly review what's needed

**5. Don't Use Default Security Contexts**
- Default contexts may run as root
- Always configure security contexts
- Use runtime default seccomp profiles

### **Common Interview Questions**

**Q1: What are the different levels of isolation in Kubernetes?**
**Good Answer**: Kubernetes provides multiple layers of isolation:

1. **Cluster-Level**: Multi-cluster, federation, network segmentation between clusters
2. **Node-Level**: Taints, tolerations, node selectors, network segmentation
3. **Namespace-Level**: RBAC, resource quotas, network policies, LimitRange
4. **Pod-Level**: Security contexts (user, capabilities), seccomp profiles, AppArmor/SELinux, resource limits

Each layer provides different protection and creates defense in depth. Isolation prevents lateral movement and contains breaches to specific levels.

**Q2: Why is defense in depth important for isolation?**
**Good Answer**: Defense in depth is critical because:

1. **Layered protection**: If one layer is bypassed, other layers still provide protection
2. **Breach containment**: Breach in pod doesn't immediately compromise entire cluster
3. **Compartmentalization**: Sensitive workloads isolated from others
4. **Reduced attack surface**: Each layer reduces what attacker can access
5. **Multiple security controls**: Different techniques (RBAC, network policies, security contexts) at each layer
6. **Compliance**: Layered isolation meets regulatory requirements

Without defense in depth, breaching one component gives attackers access to entire cluster.

**Q3: How do you implement pod-level isolation in Kubernetes?**
**Good Answer**: Pod-level isolation includes:

1. **Security Contexts**:
   - `runAsNonRoot: true`: Don't run as root
   - `runAsUser: 1000`: Run as non-root user
   - `allowPrivilegeEscalation: false`: Prevent privilege escalation
   - `readOnlyRootFilesystem: true`: Read-only filesystem
   - `capabilities: drop: [ALL]`: Drop all, add only what's needed

2. **Seccomp Profiles**:
   - `type: RuntimeDefault`: Default secure profile
   - Custom profiles: For specific workloads

3. **AppArmor/SELinux Profiles**:
   - Profiles loaded on nodes
   - Applied via annotations
   - Kernel-level enforcement

4. **Resource Limits**:
   - CPU and memory limits
   - Prevents resource exhaustion
   - Provides Quality of Service

Example configuration:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  annotations:
    container.apparmor.security.beta.kubernetes.io/apparmor: secure-profile
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
    capabilities:
      drop: [ALL]
  containers:
  - name: app
    image: nginx:alpine
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      resources:
        limits:
          memory: "128Mi"
          cpu: "100m"
```

**Q4: How do network policies provide isolation?**
**Good Answer**: Network policies provide pod-to-pod communication control:

1. **Default-Deny Model**: All traffic blocked by default
2. **Explicit Allow**: Only specific communication allowed
3. **Namespace-Level**: Policies can be namespace-scoped
4. **Pod Selector**: Policies apply to specific pods based on labels
5. **Ingress and Egress**: Control inbound and outbound traffic
6. **Layered Isolation**: Works with other isolation layers

Example:
```yaml
# Default-deny
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# Specific allow
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-db
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: webserver
    ports:
    - protocol: TCP
      port: 5432
```

**Q5: What's the strongest isolation mechanism in Kubernetes?**
**Good Answer**: The strongest isolation mechanism is **AppArmor/SELinux** because:

1. **Kernel-level enforcement**: Works at Linux kernel level
2. **Mandatory access control**: Policies enforced by kernel, cannot be bypassed by userspace
3. **File system access control**: Can control file reads/writes at kernel level
4. **System call filtering**: Seccomp restricts which syscalls containers can make
5. **Strongest containment**: Even if container compromised, isolation prevents host access

AppArmor is stronger than security contexts and seccomp profiles because it provides mandatory access control that containers cannot bypass. However, defense in depth requires using all isolation mechanisms together.
