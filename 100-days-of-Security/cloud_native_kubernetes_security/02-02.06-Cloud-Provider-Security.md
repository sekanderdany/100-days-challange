# 02.06 - Cloud Provider Security

## 1️⃣ What This Topic Is

Cloud Provider Security examines security measures for securing Kubernetes on cloud providers (AWS EKS, GCP GKE, Azure AKS), understanding cloud-specific security configurations and best practices.

**What this means:**
- Cloud provider security = security controls for managed Kubernetes
- Understanding shared responsibility model
- Cloud-specific security configurations
- Cloud-native security services (IAM, KMS, etc.)

**The Key Concepts:**

1. **Cloud Provider Security Areas**
   - AWS EKS security (IAM, KMS, VPC)
   - GCP GKE security (IAM, KMS, VPC)
   - Azure AKS security (IAM, KMS, VPC)
   - Shared responsibility model
   - Cloud-native security services

2. **Security Principles**
   - Understand shared responsibility
   - Use cloud-native security services
   - Encrypt everything (at rest and in transit)
   - Implement least privilege (IAM)
   - Monitor and audit cloud resources

**Why this matters:**
- Cloud provider has shared responsibility
- Cloud provider manages control plane
- Cloud provider provides security services
- Cloud provider compliance (SOC 2, PCI-DSS, etc.)

## 2️⃣ What Problem It Solves

### Problem 1: Misunderstanding Shared Responsibility

**Without cloud provider security:**
- Unclear who is responsible for what
- Security gaps exist
- Cluster compromise
- Data theft

**With cloud provider security:**
- Shared responsibility understood
- Cloud provider manages control plane security
- Customer manages workloads and network security
- Security gaps addressed

### Problem 2: Not Using Cloud-Native Security Services

**Without cloud provider security:**
- Not using cloud IAM
- Not using cloud KMS
- Not using cloud VPC
- Missing cloud-specific security benefits

**With cloud provider security:**
- Cloud IAM for authentication
- Cloud KMS for encryption
- Cloud VPC for network isolation
- Cloud-native security benefits

### Problem 3: Non-Compliant Cloud Configurations

**Without cloud provider security:**
- Non-compliant with cloud provider security requirements
- Compliance violations (SOC 2, PCI-DSS, HIPAA, GDPR)
- Audit failures
- Regulatory fines

**With cloud provider security:**
- Compliant with cloud provider security requirements
- Compliance maintained
- Audits passed
- Regulatory compliance

### Real-World Impact

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Misconfigured AWS credentials
- **Root cause**: No AWS IAM least privilege
- **Cloud provider issue**: Attacker accessed all AWS resources
- **Impact**: 57 million customer records accessed
- **Lesson**: Use AWS IAM with least privilege

**Example: Capital One Breach (2019)**
- **Vulnerability**: Misconfigured AWS IAM
- **Root cause**: Over-privileged AWS IAM roles
- **Cloud provider issue**: Attacker accessed AWS S3 buckets
- **Impact**: 106 million customer records accessed
- **Lesson**: Use AWS IAM with least privilege

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Misconfigured AWS security groups
- **Root cause**: Open AWS security groups
- **Cloud provider issue**: Attacker accessed AWS resources
- **Impact**: Data exposure, resource theft
- **Lesson**: Use AWS security groups with least privilege

## 4️⃣ How It Works (Conceptual)

### Cloud Provider Security Areas

**1. AWS EKS Security**
- **Purpose**: Secure Kubernetes on AWS
- **Security Measures**: 
  - AWS IAM (authentication and authorization)
  - AWS KMS (encryption)
  - AWS VPC (network isolation)
  - AWS Security Groups (firewall rules)
- **Common Misconfigurations**: 
  - No AWS IAM (all access allowed)
  - No AWS KMS (unencrypted secrets)
  - No AWS VPC (all resources in same network)
  - Over-privileged IAM roles
- **Example**: AWS EKS with IAM and KMS

**AWS Security Best Practices:**
- Use AWS IAM with least privilege
- Use AWS KMS for encryption
- Use AWS VPC for network isolation
- Use AWS Security Groups for firewall rules
- Use AWS CloudTrail for audit logging
- Use AWS GuardDuty for threat detection

**Example**:
```yaml
# AWS EKS cluster with IAM and KMS (secure)
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: my-eks-cluster
managedNodeGroups:
  - name: managed-node-group
    iam:
      withAddonPolicies:
        enabled: true
      serviceAccountARN: arn:aws:iam::123456789012:role/eks-node-role
    instanceType: t3.medium
    desiredCapacity: 2
    volumeSize: 20
    ssh:
      allow: false
      publicKeyPath: /dev/null
cloudProvider:
  aws:
    region: us-west-2
    auth:
      kubeconfigPath: /tmp/kubeconfig-aws
secretsEncryption:
  provider: aws-kms
  keyARN: arn:aws:kms:us-west-2:123456789012:key/12345678-1234-1234-123456789012
```

**2. GCP GKE Security**
- **Purpose**: Secure Kubernetes on GCP
- **Security Measures**: 
  - GCP IAM (authentication and authorization)
  - GCP KMS (encryption)
  - GCP VPC (network isolation)
  - GCP Firewall (firewall rules)
- **Common Misconfigurations**: 
  - No GCP IAM (all access allowed)
  - No GCP KMS (unencrypted secrets)
  - No GCP VPC (all resources in same network)
  - Over-privileged IAM roles
- **Example**: GCP GKE with IAM and KMS

**GCP Security Best Practices:**
- Use GCP IAM with least privilege
- Use GCP KMS for encryption
- Use GCP VPC for network isolation
- Use GCP Firewall for firewall rules
- Use GCP Cloud Audit Logs for audit logging
- Use GCP Security Command Center for threat detection

**Example**:

**4. Shared Responsibility Model**
- **Purpose**: Understand who is responsible for what
- **Security Measures**: 
  - Cloud provider manages control plane security
  - Customer manages workloads and network security
  - Shared responsibility model varies by provider
- **Common Misconfigurations**: 
  - Misunderstanding shared responsibility
  - Not managing customer responsibilities
  - Not using cloud provider security services
- **Example**: Shared responsibility model

**Shared Responsibility Best Practices:**
- Understand shared responsibility model
- Use cloud provider security services
- Manage customer responsibilities
- Document shared responsibility
- Conduct regular security reviews

**Example**:
```
AWS Shared Responsibility Model:
- AWS manages: Control plane, IAM, KMS, VPC, Security Groups, CloudTrail, GuardDuty
- Customer manages: Workloads, network policies, RBAC, secrets, security contexts

GCP Shared Responsibility Model:
- GCP manages: Control plane, IAM, KMS, VPC, Firewall, Cloud Audit Logs, Security Command Center
- Customer manages: Workloads, network policies, RBAC, secrets, security contexts

Azure Shared Responsibility Model:
- Azure manages: Control plane, IAM, Key Vault, VNet, Network Security Groups, Monitor, Security Center
- Customer manages: Workloads, network policies, RBAC, secrets, security contexts
```

### Cloud Provider Security Detection Techniques

**1. Cloud IAM Monitoring**
- Monitor for unusual IAM access
- Detect over-privileged IAM roles
- Detect IAM policy violations
- Detect credential theft

**2. Cloud KMS Monitoring**
- Monitor for unusual key access
- Detect key usage anomalies
- Detect encryption key misconfigurations
- Detect key rotation issues

**3. Cloud VPC Monitoring**
- Monitor for unusual network traffic
- Detect VPC misconfigurations
- Detect network security group violations
- Detect network anomalies

**4. Cloud Security Services Monitoring**
- Monitor cloud security services (CloudTrail, Cloud Audit Logs, Monitor, Security Center, GuardDuty)
- Detect security events
- Detect misconfigurations
- Detect threats

**5. Cloud Compliance Monitoring**
- Monitor for compliance violations
- Detect non-compliant configurations
- Detect compliance audit failures
- Detect regulatory violations

## 6️⃣ Where It Should Be Applied (With Example)

Cloud provider security should guide **ALL managed Kubernetes deployments**.

### **1. Applying AWS EKS Security**

**Example: Configure AWS EKS with IAM and KMS**

```bash
echo "=== AWS EKS Security Configuration ==="

# 1. Create IAM role for EKS (least privilege)
cat <<EOF > /tmp/eks-iam-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/eks-node-role"
      },
      "Action": [
        "ec2:Describe*",
        "ec2:DescribeInstances",
        "autoscaling:Describe*",
        "autoscaling:DescribeAutoScalingGroups",
        "autoscaling:DescribeScalingActivities",
        "autoscaling:DescribeLaunchConfigurations",
        "autoscaling:DescribeTags",
        "ecr:GetAuthorizationToken",
        "ecr:BatchCheckLayerAvailability",
        "ecr:GetDownloadUrlForLayer",
        "ecr:GetRepositoryPolicy",
        "eks:Describe*"
      ],
      "Resource": "*"
    }
  ]
}
EOF

# 2. Create KMS key for EKS encryption
aws kms create-key \
  --alias eks-encryption-key \
  --description "EKS cluster encryption key" \
  --region us-west-2

# 3. Create EKS cluster with IAM and KMS
eksctl create cluster \
  --name my-eks-cluster \
  --region us-west-2 \
  --nodes 2 \
  --node-type t3.medium \
  --managed \
  --ssh-access \
  --ssh-public-key ~/.ssh/id_rsa.pub \
  --instance-type t3.medium \
  --version 1.27 \
  --vpc-private-subnet-ids subnet-1,subnet-2 \
  --encryption-provider aws-kms \
  --encryption-key-id arn:aws:kms:us-west-2:123456789012:key/12345678-1234-1234-123456789012

# 4. Verify EKS security
aws eks describe-cluster --name my-eks-cluster --region us-west-2

```
