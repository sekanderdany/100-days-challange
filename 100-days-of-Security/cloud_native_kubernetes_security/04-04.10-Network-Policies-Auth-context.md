# 04.10 - Network Policies (Auth context)

## 1️⃣ What This Topic Is

Network Policies (Auth context) examines security measures for securing Kubernetes network policies, understanding network isolation, traffic segmentation, and secure network policy configurations.

**What this means:**
- Kubernetes Network Policies = traffic control for pods
- Network isolation = segmenting pod-to-pod traffic
- Traffic segmentation = controlling ingress/egress traffic
- Secure network policy configurations (labels, namespaces, pods)

**The Key Concepts:**

1. **Kubernetes Network Policy Security Areas**
   - Namespace isolation (NetworkPolicies)
   - Pod-to-pod communication (NetworkPolicies)
   - Ingress/Egress rules (NetworkPolicies)
   - Network policy enforcement (CNI plugins)
   - Network policy monitoring (traffic logs, policy violations)

2. **Security Principles**
   - Defense in depth (namespace isolation, pod-to-pod communication, ingress/egress rules, enforcement, monitoring)
   - Least privilege (network policy access)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Network policies are critical for cluster security
- Network policies control all pod-to-pod traffic
- Network policies control all ingress/egress traffic
- Network policies compromise = cluster-wide compromise
- Network policies handle all network traffic

---

## 2️⃣ What Problem It Solves

### Problem 1: Unmanaged Network Traffic

**Without network policies:**
- Unmanaged network traffic (all pods can communicate)
- Attacker can move laterally across cluster
- Cluster compromise
- Data theft and service disruption

**With network policies:**
- Managed network traffic (isolated pods)
- Attacker cannot move laterally
- Cluster protected
- Data and services protected

### Problem 2: Unrestricted Ingress/Egress

**Without network policies:**
- Unrestricted ingress/egress (all traffic allowed)
- Attacker can exfiltrate data
- Cluster compromise
- Data theft and service disruption

**With network policies:**
- Restricted ingress/egress (segmented traffic)
- Attacker cannot exfiltrate data
- Cluster protected
- Data and services protected

### Problem 3: No Network Policy Monitoring

**Without network policies:**
- No network policy monitoring
- Traffic events undetected
- Policy violation events undetected
- Incident response delayed
- Cluster compromise

**With network policies:**
- Network policy monitoring enabled
- Traffic events detected
- Policy violation events detected
- Real-time detection
- Rapid incident response
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unmanaged network traffic
- **Root cause**: No namespace isolation
- **Network policy issue**: Attacker moved laterally across cluster
- **Impact**: Attacker accessed production secrets
- **Lesson**: Implement namespace isolation

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Unrestricted ingress/egress
- **Root cause**: No ingress/egress rules
- **Network policy issue**: Attacker exfiltrated data
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement ingress/egress rules

**Example: Capital One Breach (2019)**
- **Vulnerability**: No network policy monitoring
- **Root cause**: No network policy audit logging
- **Network policy issue**: Policy violation events undetected
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement network policy monitoring

  - Least privilege

  - Least privilege

- **Namespace Policies**:

**Example**:
```yaml
# Namespace isolation with NetworkPolicies (secure, advanced)
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
  labels:
    app: secure-app
    environment: production
    network-policy: deny-all
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: secure-namespace

  podSelector: {}

  - Ingress
  - Egress
```
