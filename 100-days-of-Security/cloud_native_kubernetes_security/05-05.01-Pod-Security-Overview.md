# 05.01 - Pod Security Overview

## 1️⃣ What This Topic Is

Pod Security Overview examines security measures for securing Kubernetes pods, understanding pod security threats, vulnerabilities, and secure pod configurations.

**What this means:**
- Kubernetes Pod Security = securing pods (containers)
- Pod Security Threats = pod security vulnerabilities
- Pod Security Vulnerabilities = pod security issues
- Secure pod configurations (images, security contexts, resources)

**The Key Concepts:**

1. **Kubernetes Pod Security Areas**
   - Pod images (base images, tags, security scanning)
   - Security contexts (user, groups, capabilities, seccomp)
   - Pod resources (limits, requests, quotas)
   - Pod policies (security policies, network policies)

2. **Security Principles**
   - Defense in depth (images, security contexts, resources, policies)
   - Least privilege (pod security access)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Pod security is critical for cluster security
- Pod security protects all workloads
- Pod security compromise = cluster-wide compromise
- Pod security handles all pod security

---

## 2️⃣ What Problem It Solves

### Problem 1: Unmanaged Pod Images

**Without pod security:**
- Unmanaged pod images (vulnerable images)
- Attacker can exploit image vulnerabilities
- Cluster compromise
- Data theft and service disruption

**With pod security:**
- Managed pod images (secure images)
- Attacker cannot exploit image vulnerabilities
- Cluster protected
- Data and services protected

### Problem 2: Weak Security Contexts

**Without pod security:**
- Weak security contexts (privileged containers)
- Attacker can escalate privileges
- Cluster compromise
- Data theft and service disruption

**With pod security:**
- Strong security contexts (restricted containers)
- Attacker cannot escalate privileges
- Cluster protected
- Data and services protected

### Problem 3: No Resource Limits

**Without pod security:**
- No resource limits (no CPU/memory limits)
- Attacker can exhaust resources
- Cluster compromise
- Data theft and service disruption

**With pod security:**
- Resource limits configured (CPU/memory limits)
- Attacker cannot exhaust resources
- Cluster protected
- Data and services protected

### Problem 4: No Pod Policies

**Without pod security:**
- No pod policies (no security policies)
- Attacker can move laterally
- Cluster compromise
- Data theft and service disruption

**With pod security:**
- Pod policies configured (security policies, network policies)
- Attacker cannot move laterally
- Cluster protected
- Data and services protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unmanaged pod images
- **Root cause**: No image scanning
- **Pod security issue**: Attacker deployed malicious containers
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Implement image scanning

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Weak security contexts
- **Root cause**: No security contexts
- **Pod security issue**: Attacker escalated privileges
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement security contexts

**Example: Capital One Breach (2019)**
- **Vulnerability**: No pod policies
- **Root cause**: No pod policies
- **Pod security issue**: Attacker moved laterally
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement pod policies

## 4️⃣ How It Works (Conceptual)

### Kubernetes Pod Security Areas

**1. Pod Images**
- **Purpose**: Secure pod images (base images, tags, security scanning)
- **Security Measures**: 
  - Base images (official images, signed images)
  - Image tags (specific versions, immutable tags)
  - Security scanning (vulnerability scanning, compliance scanning)
  - Image policies (allow-list, deny-list)
- **Common Misconfigurations**: 
  - No base images (latest tag)
  - No image tags (floating tags)
  - No security scanning (vulnerable images)
  - No image policies (all images allowed)
- **Example**: Pod images with base images

**Pod Images Types:**
- **Base Images**: 
  - Base images (official images, signed images)
  - Base image tags (specific versions, immutable tags)
  - Base image security (vulnerability scanning, compliance scanning)
  - Base image policies (allow-list, deny-list)
  - Least privilege

- **Image Tags**: 
  - Image tags (specific versions, immutable tags)
  - Image tag policies (allow-list, deny-list)
  - Image tag security (vulnerability scanning, compliance scanning)
  - Least privilege

- **Security Scanning**: 
  - Security scanning (vulnerability scanning, compliance scanning)
  - Security scanning tools (Trivy, Clair)
  - Security scanning policies (allow-list, deny-list)
  - Least privilege

**Best Practices:**
- Use base images (official images, signed images)
- Use image tags (specific versions, immutable tags)
- Implement security scanning (vulnerability scanning, compliance scanning)
- Implement image policies (allow-list, deny-list)
- Regular image audits

**Example**:
```yaml
# Pod images with base images (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: secure-namespace
spec:
  containers:
  - name: secure-container
    image: nginx:1.14.2
    securityContext:
      runAsUser: 1000
      runAsGroup: 1000
```

**2. Security Contexts**
- **Purpose**: Secure pods (user, groups, capabilities, seccomp)
- **Security Measures**: 
  - User contexts (runAsUser, runAsGroup, fsGroup)
  - Group contexts (supplementalGroups)
  - Capabilities (drop, add, Linux capabilities)
  - Seccomp profiles (RuntimeDefault, Unconfined, Localhost)
  - SELinux options (level, user, role, type)
- **Common Misconfigurations**: 
  - No user contexts (root user)
  - No group contexts (root group)
  - No capabilities drop (all capabilities)
  - No seccomp profiles (Unconfined)
  - No SELinux options (no SELinux)
- **Example**: Security contexts with user contexts

**Security Contexts Types:**
- **User Contexts**: 
  - User contexts (runAsUser, runAsGroup, fsGroup)
  - User context security (least privilege)
  - Least privilege

- **Group Contexts**: 
  - Group contexts (supplementalGroups)
  - Group context security (least privilege)
  - Least privilege

- **Capabilities**: 
  - Capabilities (drop, add, Linux capabilities)
  - Capabilities security (least privilege)
  - Least privilege

- **Seccomp Profiles**: 
  - Seccomp profiles (RuntimeDefault, Unconfined, Localhost)
  - Seccomp profile security (least privilege)
  - Least privilege

- **SELinux Options**: 
  - SELinux options (level, user, role, type)
  - SELinux options security (least privilege)
  - Least privilege

**Best Practices:**
- Use user contexts (runAsUser, runAsGroup, fsGroup)
- Use group contexts (supplementalGroups)
- Use capabilities (drop, add, Linux capabilities)
- Use seccomp profiles (RuntimeDefault, Unconfined, Localhost)
- Use SELinux options (level, user, role, type)
- Regular security context audits

**Example**:
```yaml
# Security contexts with user contexts (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: secure-namespace
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000
    seLinuxOptions:
      level: s0:c123,c456
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: secure-container
    image: nginx:1.14.2
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
          - ALL
```

**3. Pod Resources**
- **Purpose**: Secure pods (limits, requests, quotas)
- **Security Measures**: 
  - Resource limits (CPU limits, memory limits)
  - Resource requests (CPU requests, memory requests)
  - Resource quotas (CPU quotas, memory quotas)
  - Resource policies (limit ranges, priority classes)
- **Common Misconfigurations**: 
  - No resource limits (no CPU/memory limits)
  - No resource requests (no CPU/memory requests)
  - No resource quotas (no CPU/memory quotas)
  - No resource policies (all pods can use all resources)
- **Example**: Pod resources with resource limits

**Pod Resources Types:**
- **Resource Limits**: 
  - Resource limits (CPU limits, memory limits)
  - Resource limits security (least privilege)
  - Least privilege

- **Resource Requests**: 
  - Resource requests (CPU requests, memory requests)
  - Resource requests security (least privilege)
  - Least privilege

- **Resource Quotas**: 
  - Resource quotas (CPU quotas, memory quotas)
  - Resource quotas security (least privilege)
  - Least privilege

- **Resource Policies**: 
  - Resource policies (limit ranges, priority classes)
  - Resource policies security (least privilege)
  - Least privilege

**Best Practices:**
- Use resource limits (CPU limits, memory limits)
- Use resource requests (CPU requests, memory requests)
- Use resource quotas (CPU quotas, memory quotas)
- Use resource policies (limit ranges, priority classes)
- Regular resource audits

**Example**:

**4. Pod Policies**
- **Purpose**: Secure pods (security policies, network policies)
- **Security Measures**: 
  - Security policies (Pod Security Standards, Pod Security Policies)
  - Network policies (NetworkPolicies)
  - Admission policies (validating, mutating)
  - Pod security compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
- **Common Misconfigurations**: 
  - No security policies (all pods can run)
  - No network policies (all pods can communicate)
  - No admission policies (all pods can run)
  - No pod security compliance (no SOC 2, PCI-DSS, HIPAA, GDPR)
- **Example**: Pod policies with security policies

**Pod Policies Types:**
- **Security Policies**: 
  - Security policies (Pod Security Standards, Pod Security Policies)
  - Security policies enforcement (Pod Security Policies)
  - Security policies compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
  - Least privilege

- **Network Policies**: 
  - Network policies (NetworkPolicies)
  - Network policies enforcement (NetworkPolicies)
  - Network policies compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
  - Least privilege

- **Admission Policies**: 
  - Admission policies (validating, mutating)
  - Admission policies enforcement (Admission Controllers)
  - Admission policies compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
  - Least privilege

- **Pod Security Compliance**: 
  - Pod security compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
  - Pod security auditing (audit logging)
  - Pod security reporting (compliance reporting)
  - Least privilege

**Best Practices:**
- Use security policies (Pod Security Standards, Pod Security Policies)
- Use network policies (NetworkPolicies)
- Use admission policies (validating, mutating)
- Use pod security compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
- Regular pod security audits

**Example**:

```yaml
  - Ingress
```
