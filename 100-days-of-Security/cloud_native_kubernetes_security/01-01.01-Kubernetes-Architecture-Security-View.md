# 01.01 - Kubernetes Architecture (Security View)

## 1️⃣ What This Topic Is

Kubernetes Architecture (Security View) examines Kubernetes components through a security lens, understanding how each component works, its security implications, and potential vulnerabilities.

**What this means:**
- Kubernetes is a complex distributed system
- Each component has specific security responsibilities
- Understanding architecture helps identify vulnerabilities
- Security must be built into each layer

**The Kubernetes Architecture:**

```
┌─────────────────────────────────────────────────────────────────┐
│                     Kubernetes Cluster                      │
├─────────────────────────────────────────────────────────────────┤
│                  Control Plane                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐     │
│  │ API Server │  │Scheduler  │  │Controller │     │
│  └──────────┘  └──────────┘  └──────────┘     │
│       │              │              │              │
│       └──────────────┴──────────────┘              │
│                      │                              │
│                ┌─────▼─────┐                        │
│                │    etcd    │                        │
│                └────────────┘                        │
├─────────────────────────────────────────────────────────────────┤
│                    Worker Nodes                         │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐     │
│  │ Kubelet   │  │Kube-proxy │  │Container  │     │
│  │           │  │           │  │ Runtime   │     │
│  └──────────┘  └──────────┘  └──────────┘     │
│       │              │                              │
│       └──────────────┴──────────────────────┐        │
│                                          │        │
│                                   ┌──────▼─────┐   │
│                                   │    Pods     │   │
│                                   │ (Containers)│   │
│                                   └─────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

**Key Components (from Security Perspective):**

1. **Control Plane Components**
   - API Server: Gateway to cluster
   - etcd: Cluster state database
   - Scheduler: Pod placement
   - Controller Manager: Maintains desired state

2. **Worker Node Components**
   - Kubelet: Pod lifecycle manager
   - Kube-proxy: Network proxy
   - Container Runtime: Runs containers

3. **Add-ons (Optional but Common)**
   - DNS (CoreDNS): Service discovery
   - Ingress Controller: External access
   - Network Plugin: Pod networking
   - Dashboard: UI for cluster

**Why this matters:**
- Each component is a potential attack surface
- Compromising any component can compromise cluster
- Understanding architecture helps design security controls
- Security must be layered across all components

## 2️⃣ What Problem It Solves

### Problem 1: Complex Attack Surface

**Without understanding architecture:**
- Don't know where to focus security efforts
- Protect wrong components while others are vulnerable
- Miss security gaps in critical paths
- Inefficient security resource allocation

**With architecture understanding:**
- Know which components are most critical
- Focus security on highest-risk areas
- Understand attack paths and dependencies
- Efficient security resource allocation

### Problem 2: Misconfigured Security Controls

**Without understanding architecture:**
- Apply security controls incorrectly
- Control plane security conflicts with workload security
- Overlook component-specific vulnerabilities
- Security controls don't work as expected

**With architecture understanding:**
- Apply controls at appropriate layers
- Control plane security complements workload security
- Address component-specific vulnerabilities
- Security controls work as designed

### Problem 3: Ineffective Incident Response

**Without understanding architecture:**
- Can't trace attack paths during incidents
- Don't know which components are affected
- Overlook lateral movement between components
- Incomplete incident remediation

**With architecture understanding:**
- Trace attack paths accurately
- Identify all affected components
- Detect lateral movement
- Complete incident remediation

### Real-World Impact

**Example: Tesla Kubernetes Cryptojacking (2018)**
- **Vulnerability**: Unsecured Kubernetes console (API server)
- **Root cause**: API server exposed without authentication
- **Architecture issue**: Control plane component exposed
- **Impact**: Attacker gained cluster control, deployed miners

**Example: Cryptojacking Attack via Kubelet (2018)**
- **Vulnerability**: Exposed Kubelet API on worker nodes
- **Root cause**: Kubelet listening on all interfaces without authentication
- **Architecture issue**: Worker node component compromised
- **Impact**: Attacker deployed cryptocurrency miners across cluster

**Example: etcd Exposure (2019)**
- **Vulnerability**: etcd exposed to network
- **Root cause**: etcd not properly isolated or secured
- **Architecture issue**: Cluster database compromised
- **Impact**: Attacker accessed cluster secrets and configuration

## 4️⃣ How It Works (Conceptual)

### Control Plane Security Architecture

**1. API Server (kube-apiserver)**
- **Function**: Central management endpoint, REST API, authentication, authorization
- **Security responsibilities**:
  - Authenticate all requests
  - Authorize actions (RBAC)
  - Validate and configure objects
  - Admission control (policies)
  - Serve as trust boundary

**Security implications:**
- **Critical component**: All cluster management flows through API server
- **Authentication required**: Unauthorized access = cluster compromise
- **Authorization enforced**: RBAC controls what users can do
- **Admission control**: Policy enforcement before objects created

**Vulnerabilities:**
- Exposed API server (no authentication)
- Over-privileged RBAC
- Bypassed admission control
- API server vulnerabilities (CVEs)

**Security controls:**
- Authentication (certificates, OIDC, tokens)
- Authorization (RBAC)
- Network policies (restrict API access)
- Admission controllers (policies)
- TLS for all communication

**2. etcd (Cluster State Database)**
- **Function**: Consistent, highly-available key-value store for cluster state
- **Security responsibilities**:
  - Store all cluster data (secrets, configs)
  - Provide consistent state
  - Support high availability
  - Encrypt sensitive data

**Security implications:**
- **Highly sensitive**: Contains all cluster secrets and configuration
- **Critical component**: If compromised, entire cluster compromised
- **Attack target**: Primary target for data theft

**Vulnerabilities:**
- Exposed to network
- Unencrypted data at rest
- Weak authentication
- Outdated etcd version

**Security controls:**
- Encrypt at rest (encryption provider)
- Network isolation (VPC, firewall)
- TLS for client-server communication
- Client certificate authentication
- Regular backups (encrypted)

**3. Scheduler (kube-scheduler)**
- **Function**: Assigns pods to nodes based on resource requirements and constraints
- **Security responsibilities**:
  - Follow placement policies
  - Respect taints and tolerations
  - Enforce resource limits
  - Maintain security constraints

**Security implications:**
- **Pod placement**: Controls which pods run on which nodes
- **Attack surface**: If compromised, can influence pod placement
- **DoS potential**: Can be flooded with scheduling requests

**Vulnerabilities:**
- Bypassed taints/tolerations
- Evaded resource limits
- Manipulated scheduling
- Scheduler DoS

**Security controls:**
- Taints and tolerations (isolate sensitive workloads)
- Pod security policies
- Resource quotas
- Node selectors and affinity

**4. Controller Manager (kube-controller-manager)**
- **Function**: Runs controller loops to maintain cluster desired state
- **Security responsibilities**:
  - Manage replication controllers
  - Handle namespaces
  - Manage endpoints
  - Maintain security contexts

**Security implications:**
- **High privilege**: Has broad cluster access
- **State management**: Creates and modifies critical objects
- **Namespace management**: Controls isolation boundaries

**Vulnerabilities:**
- Over-privileged service account
- Manipulated controllers
- Bypassed security contexts
- Controller vulnerabilities

**Security controls:**
- Least-privileged service accounts
- RBAC for controller permissions
- Audit logging
- Controller-level security policies

### Worker Node Security Architecture

**5. Kubelet**
- **Function**: Primary agent on worker nodes, manages pod lifecycle
- **Security responsibilities**:
  - Create and destroy pods
  - Mount volumes
  - Execute container runtime commands
  - Report node status

**Security implications:**
- **Critical component**: Controls pod lifecycle on nodes
- **High privilege**: Interacts with container runtime
- **Attack surface**: If compromised, attacker controls node

**Vulnerabilities:**
- Exposed Kubelet API
- Weak authentication
- Bypassed authorization
- Kubelet vulnerabilities (CVEs)

**Security controls:**
- Kubelet authentication (certificates, tokens)
- Kubelet authorization (webhook)
- Network policies (restrict API access)
- Pod security admission
- Node taints (prevent scheduling)

**6. Kube-proxy**
- **Function**: Maintains network rules on each node, implements services
- **Security responsibilities**:
  - Maintain iptables/IPVS rules
  - Implement service discovery
  - Route traffic between services

**Security implications:**
- **Network control**: Manages network rules
- **Privilege**: Modifies host network configuration
- **Attack surface**: If compromised, controls cluster networking

**Vulnerabilities:**
- Manipulated network rules
- Bypassed network policies
- Service spoofing
- Kube-proxy vulnerabilities

**Security controls:**
- Network policies (restrict pod-to-pod communication)
- RBAC (service account permissions)
- Network plugin security
- Service mesh (mutual TLS)

**7. Container Runtime**
- **Function**: Executes containers (containerd, CRI-O, Docker)
- **Security responsibilities**:
  - Run containers with security contexts
  - Provide isolation (namespaces, cgroups)
  - Enforce security profiles (seccomp, AppArmor)
  - Manage container lifecycle

**Security implications:**
- **Critical component**: Runs all pods
- **High privilege**: Interacts with kernel
- **Attack surface**: If compromised, attacker can escape to host

**Vulnerabilities:**
- Exposed container socket
- Insecure default configuration
- Container escape vulnerabilities
- Runtime vulnerabilities (CVEs)

**Security controls:**
- Security contexts (runAsNonRoot, capabilities)
- Seccomp profiles (restrict syscalls)
- AppArmor/SELinux (Mandatory access control)
- Pod security policies
- Secure container runtime configuration

### Add-on Security Architecture

**8. DNS (CoreDNS)**
- **Function**: DNS service for Kubernetes services
- **Security responsibilities**:
  - Provide DNS resolution
  - Maintain DNS records
  - Handle DNS queries

**Security implications:**
- **Attack surface**: DNS poisoning, spoofing
- **Dependency**: Many services depend on DNS
- **Network communication**: Handles DNS queries

**Security controls:**
- DNS policies
- Network policies
- RBAC for CoreDNS
- DNSSEC (if applicable)

**9. Ingress Controller**
- **Function**: Manages external access to services
- **Security responsibilities**:
  - Route HTTP/HTTPS traffic
  - Implement TLS termination
  - Apply security rules

**Security implications:**
- **External access**: Primary entry point from internet
- **Attack surface**: Web attacks, DoS, injection
- **TLS termination**: Manages certificates

**Security controls:**
- TLS/SSL for all endpoints
- Web Application Firewall (WAF)
- Rate limiting
- Network policies
- RBAC for Ingress controller

**10. Network Plugin (CNI)**
- **Function**: Implements pod networking
- **Security responsibilities**:
  - Assign IP addresses
  - Manage network isolation
  - Implement network policies

**Security implications:**
- **Network control**: Controls pod-to-pod communication
- **Attack surface**: Network attacks, bypass
- **Isolation**: Implements network segmentation

**Security controls:**
- Network policies (Kubernetes native)
- Plugin-specific security features
- Network segmentation
- Service mesh (additional layer)

### Trust Boundaries and Data Flow

**Trust Boundaries:**
- **Control plane ↔ Worker nodes**: Mutual authentication, TLS
- **API server ↔ etcd**: TLS, client certificates
- **Kubelet ↔ Container runtime**: Unix socket, filesystem
- **Pod ↔ Pod**: Network policies (if configured)
- **User ↔ Cluster**: Authentication (certificates, OIDC), Authorization (RBAC)

**Data Flow (Security View):**
1. **User request** → **API Server** (authentication, authorization, admission)
2. **API Server** → **etcd** (store/retrieve cluster state, TLS)
3. **API Server** → **Scheduler** (schedule pod)
4. **Scheduler** → **API Server** (create pod binding)
5. **API Server** → **Kubelet** (create pod, TLS)
6. **Kubelet** → **Container Runtime** (start container, socket)
7. **Pod** ↔ **Pod** (network traffic, network policies)
8. **Kubelet** → **API Server** (report status, authentication)

**Security Implications:**
- **Every hop requires authentication**: Prevent unauthorized access
- **TLS everywhere**: Prevent eavesdropping
- **Least privilege**: Each component has minimal necessary access
- **Defense in depth**: Multiple security layers

### **2. Designing Security Zones**

**Example: Multi-zone Security**

```yaml
# Control plane zone (highest security)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: control-plane-isolation
  namespace: kube-system
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    # Only allow from specific sources
    - ipBlock:
        cidr: 10.0.0.0/24
  egress:
  - to:
    # Allow to etcd
    - namespaceSelector:
        matchLabels:
          app: etcd
```

**Example: Node-level security zones**

```yaml
# Use taints to isolate sensitive workloads
apiVersion: v1
kind: Node
metadata:
  name: sensitive-workload-node
spec:
  taints:
  - key: workload
    value: sensitive
    effect: NoSchedule  # Only schedule sensitive workloads
```

### **Common Mistakes in Architecture Security**

❌ **Mistake 1**: Not securing all components
- Reality: Each component is attack surface
- Fix: Secure control plane, worker nodes, and add-ons

❌ **Mistake 2**: Not understanding trust boundaries
- Reality: Components authenticate to each other
- Fix: Configure authentication between all components

❌ **Mistake 3**: Applying wrong security controls to wrong components
- Reality: Each component needs specific security
- Fix: Understand component-specific security requirements

❌ **Mistake 4**: Not considering component dependencies
- Reality: Components depend on each other
- Fix: Design security for component interactions

### ✅ **Solution & Explanation**

**Architecture Security Analysis:**

**Control Plane Vulnerabilities:**

1. **API Server**
   - **Critical**: Gateway to cluster, all operations flow through it
   - **Vulnerabilities**: No RBAC, no admission control, no audit logging
   - **Impact**: Unauthorized cluster access, bypassed policies
   - **Remediation**: Implement RBAC, admission controllers, audit logging

2. **etcd**
   - **Critical**: Contains all cluster data (secrets, configs)
   - **Vulnerabilities**: Not encrypted at rest, network exposed
   - **Impact**: Data theft, cluster compromise
   - **Remediation**: Enable encryption, network isolation, TLS

3. **Scheduler**
   - **Important**: Controls pod placement
   - **Vulnerabilities**: Can bypass taints, evade resource limits
   - **Impact**: Compromised node placement, resource exhaustion
   - **Remediation**: Taints/tolerations, pod security, resource quotas

4. **Controller Manager**
   - **Important**: Maintains cluster state
   - **Vulnerabilities**: Over-privileged service account, weak RBAC
   - **Impact**: Manipulated cluster state, unauthorized object creation
   - **Remediation**: Least-privileged service accounts, RBAC, audit logging

**Worker Node Vulnerabilities:**

5. **Kubelet**
   - **Critical**: Manages pod lifecycle on nodes
   - **Vulnerabilities**: API exposed, weak authentication
   - **Impact**: Attacker controls node, creates arbitrary pods
   - **Remediation**: Kubelet authentication, authorization webhook, network policies

6. **Kube-proxy**
   - **Important**: Manages cluster networking
   - **Vulnerabilities**: Can manipulate network rules, bypass policies
   - **Impact**: Network attacks, service spoofing
   - **Remediation**: Network policies, service mesh, RBAC

7. **Container Runtime**
   - **Critical**: Runs all containers
   - **Vulnerabilities**: Socket exposed, insecure config
   - **Impact**: Container escape, host compromise
   - **Remediation**: Security contexts, seccomp/AppArmor, secure config

**Add-on Vulnerabilities:**

8. **DNS (CoreDNS)**
   - **Important**: Service discovery
   - **Vulnerabilities**: DNS poisoning, spoofing
   - **Impact**: Service disruption, traffic redirection
   - **Remediation**: DNS policies, network policies, DNSSEC

9. **Ingress Controller**
   - **Important**: External access point
   - **Vulnerabilities**: No TLS, no WAF
   - **Impact**: Web attacks, data theft, DoS
   - **Remediation**: TLS/SSL, WAF, rate limiting, RBAC

10. **Network Plugin (CNI)**
    - **Important**: Pod networking
    - **Vulnerabilities**: No network policies, bypass possible
    - **Impact**: Network attacks, lateral movement
    - **Remediation**: Network policies, service mesh, segmentation

**Key Learning Points:**

1. **Each component is attack surface**: Must secure all components
2. **Control plane is critical**: If compromised, cluster compromised
3. **Worker nodes are targets**: If compromised, attacker controls workloads
4. **Add-ons extend attack surface**: Must secure DNS, ingress, CNI
5. **Architecture guides security**: Understanding architecture helps design defenses
6. **Trust boundaries exist**: Components authenticate to each other
7. **Defense in depth**: Multiple security layers across architecture

## 8️⃣ Security Best Practices

### **Do's ✅**

**1. Secure All Components**
- Control plane: API server, etcd, scheduler, controller manager
- Worker nodes: Kubelet, kube-proxy, container runtime
- Add-ons: DNS, ingress, network plugin
- Don't skip any component

**2. Understand Trust Boundaries**
- Configure authentication between components
- Use TLS for all communication
- Configure authorization at each boundary
- Monitor trust boundary violations

**3. Apply Layered Security**
- Defense in depth across architecture
- Security at control plane layer
- Security at worker node layer
- Security at workload layer

**4. Monitor Component Health**
- Set up component-level monitoring
- Alert on component failures
- Monitor component interactions
- Track security events

**5. Regularly Update Components**
- Keep Kubernetes updated
- Update container runtime
- Update add-ons
- Patch vulnerabilities

**6. Document Architecture**
- Document component interactions
- Document trust boundaries
- Document security controls
- Document incident response procedures

### **Don'ts ❌**

**1. Don't Skip Components**
- Every component is attack surface
- Secure control plane, worker nodes, and add-ons
- Don't assume provider secures everything

**2. Don't Ignore Trust Boundaries**
- Components authenticate to each other
- Configure authentication at all boundaries
- Don't allow unauthorized communication

**3. Don't Apply Wrong Security Controls**
- Each component needs specific security
- Understand component-specific requirements
- Don't apply generic controls to all components

**4. Don't Assume Provider Security**

### **Common Interview Questions**

**Q1: What are the key Kubernetes components from a security perspective?**
**Good Answer**: From a security perspective, Kubernetes has:

**Control Plane Components:**
1. **API Server**: Central management endpoint, authenticates and authorizes requests, enforces admission control. Critical because all cluster operations flow through it.
2. **etcd**: Cluster state database, stores all secrets and configurations. Critical because if compromised, entire cluster is compromised.
3. **Scheduler**: Assigns pods to nodes. Important because controls pod placement and resource allocation.
4. **Controller Manager**: Maintains cluster state. Important because creates and modifies critical objects.

**Worker Node Components:**
1. **Kubelet**: Manages pod lifecycle. Critical because controls what runs on nodes.
2. **Kube-proxy**: Implements services and network rules. Important because controls cluster networking.
3. **Container Runtime**: Runs containers. Critical because if compromised, attacker can escape to host.

**Add-ons:**
1. **DNS (CoreDNS)**: Service discovery.
2. **Ingress Controller**: External access point.
3. **Network Plugin (CNI)**: Pod networking.

Each component must be secured with authentication, authorization, and monitoring.

**Q2: What are the trust boundaries in Kubernetes?**
**Good Answer**: Trust boundaries exist where components communicate and authenticate:

1. **User ↔ API Server**: Authentication (certificates, OIDC, tokens) and Authorization (RBAC)
2. **API Server ↔ etcd**: TLS + client certificates
3. **API Server ↔ Scheduler/Controller**: Service account tokens
4. **API Server ↔ Kubelet**: TLS + certificates
5. **Kubelet ↔ Container Runtime**: Unix socket (on same host)
6. **Kubelet ↔ API Server**: Certificates or tokens
7. **Pod ↔ Pod**: Network policies (if configured)
8. **Service ↔ Service**: Kube-proxy (iptables/IPVS)

Each boundary must have authentication and authorization. If any boundary is bypassed or misconfigured, attacker can move laterally through the system.

**Q3: Why is understanding Kubernetes architecture important for security?**
**Good Answer**: Understanding architecture is critical because:

1. **Identify attack surfaces**: Know which components are targets
2. **Design layered security**: Apply security controls at appropriate layers
3. **Understand attack paths**: Know how attackers can move through system
4. **Configure trust boundaries**: Set up authentication between components
5. **Troubleshoot security issues**: Know which component is compromised
6. **Plan incident response**: Understand what's affected when component fails

For example, if API server is compromised, attacker has full cluster control. If Kubelet is compromised, attacker controls specific nodes. Understanding architecture helps prioritize security efforts and design defenses effectively.

**Q4: What's the most critical Kubernetes component from a security perspective?**
**Good Answer**: While all components are important, **etcd** is most critical because:
- **Contains all cluster data**: Secrets, configs, pod definitions
- **Single source of truth**: If compromised, attacker controls cluster state
- **High impact**: Compromise = full cluster control
- **Difficult to detect**: Changes to etcd affect all components

Other critical components:
- **API Server**: Gateway to cluster, all operations flow through it
- **Kubelet**: Controls what runs on nodes
- **Container Runtime**: Runs all pods

In practice, etcd must be encrypted at rest, network-isolated, and backed up. If etcd is compromised, entire cluster must be considered compromised.

**Q5: How do trust boundaries affect Kubernetes security?**
**Good Answer**: Trust boundaries define where authentication and authorization occur between components. They're critical for security because:

1. **Prevent unauthorized access**: Components authenticate before communicating
2. **Contain compromises**: If one component is compromised, trust boundaries limit lateral movement
3. **Layer security**: Multiple authentication/authorization points create defense in depth
4. **Monitor suspicious activity**: Failed authentication attempts indicate attacks
5. **Design secure architecture**: Trust boundaries guide security design

Example trust boundary: **API Server ↔ etcd**
- Authentication: Client certificates
- Authorization: etcd-specific permissions
- Security: TLS encryption

If this boundary is bypassed (weak certificates), attacker can access etcd directly, compromising cluster. Maintaining strong trust boundaries prevents this.
