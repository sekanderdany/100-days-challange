# 03.06 - Kubelet Security (Advanced)

## 1️⃣ What This Topic Is

Kubelet Security (Advanced) examines advanced security measures for securing Kubernetes kubelet, understanding kubelet security, kubelet hardening, and advanced configurations.

**What this means:**
- Kubelet security (advanced) = securing Kubernetes node agent
- Advanced kubelet hardening (security contexts, policies)
- Kubelet isolation (namespace-level, tenant-level)
- Secure kubelet configurations

**The Key Concepts:**

1. **Kubelet Security Areas (Advanced)**
   - Kubelet authentication (mTLS, client certificates)
   - Kubelet authorization (RBAC, webhook)
   - Kubelet encryption (at rest and in transit)
   - Kubelet security contexts (non-root, drop capabilities)
   - Kubelet policies (pod security policies, resource quotas)
   - Kubelet isolation (namespace-level, tenant-level)
   - Kubelet monitoring

2. **Security Principles**
   - Defense in depth (authentication, authorization, encryption, security contexts)
   - Least privilege (kubelet permissions)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Kubelet is the node agent
- Kubelet handles all pod operations
- Kubelet is primary attack target
- Kubelet compromise = node compromise

---

## 2️⃣ What Problem It Solves

### Problem 1: Unauthenticated Kubelet Access

**Without kubelet security:**
- Unauthenticated kubelet access
- Attacker can access kubelet
- Node compromise
- Cluster-wide compromise

**With kubelet security:**
- Kubelet authentication required (mTLS, client certificates)
- Unauthorized access prevented
- Node protected

### Problem 2: Over-Privileged Kubelet Access

**Without kubelet security:**
- Over-privileged kubelet access
- Attacker can escalate privileges
- Node-wide compromise
- Cluster-wide compromise

**With kubelet security:**
- Least privilege kubelet access (RBAC, webhook)
- Privilege escalation prevented
- Node protected

### Problem 3: Insecure Kubelet Security Contexts

**Without kubelet security:**
- Insecure security contexts (root, capabilities)
- Privilege escalation possible
- Container compromise
- Node compromise

**With kubelet security:**
- Secure security contexts (non-root, drop capabilities)
- Privilege escalation prevented
- Container protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Insecure kubelet security contexts
- **Root cause**: No kubelet security contexts
- **Kubelet issue**: Privilege escalation via kubelet
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Implement kubelet security contexts

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Over-privileged kubelet access
- **Root cause**: No kubelet least privilege
- **Kubelet issue**: Attacker escalated to node-admin
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement kubelet least privilege

**Example: Capital One Breach (2019)**
- **Vulnerability**: Unauthenticated kubelet
- **Root cause**: No kubelet authentication
- **Kubelet issue**: Attacker accessed kubelet without authentication
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement kubelet authentication

## 4️⃣ How It Works (Conceptual)

### Kubelet Security Areas (Advanced)

**1. Kubelet Authentication (Advanced)**
- **Purpose**: Verify who can access kubelet
- **Security Measures**: 
  - mTLS (mutual TLS)
  - Client certificate authentication
  - Token-based authentication (service accounts)
  - Anonymous access (disabled)
  - Certificate rotation
- **Common Misconfigurations**: 
  - No kubelet authentication (all access allowed)
  - Weak authentication (weak certificates)
  - Anonymous access enabled
  - Long-lived certificates
  - Weak TLS (outdated protocols, weak ciphers)
  - No certificate rotation
- **Example**: Kubelet with mTLS and client certificates

**Kubelet Authentication Types (Advanced):**
- **mTLS (Mutual TLS)**: 
  - API server verifies kubelet certificates
  - Kubelet verifies API server certificates
  - Prevents man-in-the-middle attacks
  - Prevents unauthorized access

- **Client Certificates**: 
  - X.509 certificates
  - Certificate-based authentication
  - Certificate rotation
  - Revocation

- **Token-Based Authentication**: 
  - Service account tokens
  - Bearer tokens
  - Short-lived tokens
  - Token rotation

- **Certificate Rotation**: 
  - Regular certificate rotation
  - Automated certificate rotation
  - Certificate lifecycle management
  - Revocation

**Best Practices (Advanced):**
- Use mTLS for kubelet
- Use client certificate authentication
- Use short-lived certificates
- Implement certificate rotation
- Use strong TLS (TLS 1.3, strong ciphers)
- Disable anonymous access

**Example (Advanced)**:
```yaml
# Kubelet with mTLS and certificate rotation (secure)
apiVersion: v1
kind: Pod
metadata:
  name: kubelet
  namespace: kube-system
spec:
  containers:
  - name: kubelet
    image: k8s.gcr.io/kubelet:v1.27.0
    args:
    - --client-ca-file=/etc/kubernetes/pki/client-ca.crt
    - --tls-cert-file=/etc/kubernetes/pki/kubelet.crt
    - --tls-private-key-file=/etc/kubernetes/pki/kubelet.key
    - --tls-min-version=VersionTLS13
    - --tls-cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
    - --anonymous-auth=false
    - --rotate-certificates=true
    - --rotate-server-certificates=true
```

**2. Kubelet Authorization (Advanced)**
- **Purpose**: Control what can be done with kubelet
- **Security Measures**: 
  - RBAC (Role-Based Access Control)
  - Authorization webhook
  - Namespace-based authorization
  - Resource-based authorization
  - Default-deny with explicit allow
- **Common Misconfigurations**: 
  - No kubelet authorization (all access allowed)
  - Over-privileged RBAC
  - No resource-based authorization
  - No namespace-based authorization
- **Example**: Kubelet with RBAC and webhook

**Kubelet Authorization Types (Advanced):**
- **RBAC (Role-Based Access Control)**: 
  - Cluster roles (cluster-wide permissions)
  - Roles (namespace permissions)
  - Role bindings (associate roles with subjects)
  - Cluster role bindings
  - Least privilege

- **Authorization Webhook**: 
  - External webhook validates requests
  - Rejects or allows requests
  - Flexible authorization

- **Namespace-Based Authorization**: 
  - Namespace-level permissions
  - Tenant-level isolation
  - Least privilege

- **Resource-Based Authorization**: 
  - Resource-level permissions
  - Fine-grained permissions
  - Least privilege

**Best Practices (Advanced):**
- Use least privilege RBAC
- Use authorization webhook for flexibility
- Use namespace-based authorization for multi-tenancy
- Use resource-based authorization for fine-grained control
- Regular RBAC audits

**Example (Advanced)**:
```yaml
# Kubelet RBAC (least privilege, advanced)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: kubelet-reader
rules:
- nonResourceURLs:
  - /metrics
  - /healthz
  verbs: ["get", "list"]
- apiGroups: [""]
  resources: ["pods", "nodes"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: kubelet-reader-binding
subjects:
- kind: ServiceAccount
  name: kubelet-reader
roleRef:
  kind: ClusterRole
  name: kubelet-reader
  apiGroup: rbac.authorization.k8s.io
```

**3. Kubelet Security Contexts (Advanced)**
- **Purpose**: Enforce secure security contexts for all pods
- **Security Measures**: 
  - Non-root containers (runAsNonRoot)
  - Drop all capabilities (drop ALL)
  - Read-only root filesystem (readOnlyRootFilesystem)
  - No privilege escalation (allowPrivilegeEscalation: false)
  - Seccomp profiles
  - AppArmor profiles
- **Common Misconfigurations**: 
  - Root containers (runAsUser: 0)
  - Privileged containers (privileged: true)
  - All capabilities (drop: [])
  - Writeable root filesystem (readOnlyRootFilesystem: false)
  - Privilege escalation (allowPrivilegeEscalation: true)
- **Example**: Kubelet with security contexts

**Kubelet Security Contexts Types (Advanced):**
- **Non-Root Containers**: 
  - runAsNonRoot: true
  - runAsUser: non-zero
  - runAsGroup: non-zero
  - Prevents root compromise
  - Reduces attack surface

- **Drop All Capabilities**: 
  - drop: [ALL]
  - add: []
  - Prevents privilege escalation
  - Reduces attack surface

- **Read-Only Root Filesystem**: 
  - readOnlyRootFilesystem: true
  - Prevents filesystem modification
  - Reduces attack surface

- **No Privilege Escalation**: 
  - allowPrivilegeEscalation: false
  - Prevents privilege escalation
  - Reduces attack surface

- **Seccomp Profiles**: 
  - Seccomp profiles for system calls
  - Reduces system call surface
  - Prevents syscall abuse

- **AppArmor Profiles**: 
  - AppArmor profiles for Linux security
  - Enforces Linux security policies
  - Prevents Linux vulnerabilities

**Best Practices (Advanced):**
- Enforce non-root containers
- Enforce drop all capabilities
- Enforce read-only root filesystem
- Enforce no privilege escalation
- Enforce seccomp profiles
- Enforce AppArmor profiles

**Example (Advanced)**:
```yaml
# Kubelet with security contexts (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: security-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    allowPrivilegeEscalation: false
    capabilities:
      drop: [ALL]
    readOnlyRootFilesystem: true
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: security-container
    image: security:v1
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
      seccompProfile:
        type: RuntimeDefault
```

- Reality: Unauthenticated kubelet access
- Fix: Configure kubelet authentication (mTLS, client certificates)

❌ **Mistake 2**: No kubelet security contexts
