# 03.02 - API Server Hardening

## 1️⃣ What This Topic Is

API Server Hardening examines security measures for hardening Kubernetes API server, understanding API server security, admission controllers, and advanced configurations.

**What this means:**
- API server hardening = securing Kubernetes API gateway
- Defense in depth for API server
- Least privilege for API server
- Secure API server configurations

**The Key Concepts:**

1. **API Server Security Areas**
   - API server authentication (mTLS, client certificates)
   - API server authorization (RBAC, webhook)
   - API server encryption (at rest and in transit)
   - Admission controllers (validating, mutating)
   - API server rate limiting
   - API server auditing

2. **Security Principles**
   - Defense in depth (authentication, authorization, encryption)
   - Least privilege (API server permissions)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- API server is the cluster gateway
- API server is primary attack target
- API server compromise = cluster compromise
- API server handles all cluster operations

---

## 2️⃣ What Problem It Solves

### Problem 1: Unauthenticated API Server Access

**Without API server hardening:**
- Unauthenticated API server access
- Attacker can access cluster API
- Cluster compromise
- Data theft and service disruption

**With API server hardening:**
- API server authentication required (mTLS, client certificates)
- Unauthorized access prevented
- Cluster protected

### Problem 2: Over-Privileged API Server Access

**Without API server hardening:**
- Over-privileged API server access
- Attacker can escalate privileges
- Cluster-wide compromise
- Data theft and service disruption

**With API server hardening:**
- Least privilege API server access (RBAC, webhook)
- Privilege escalation prevented
- Cluster protected

### Problem 3: API Server Denial of Service

**Without API server hardening:**
- No API server rate limiting
- Attacker can DoS API server
- Cluster disruption
- Service unavailability

**With API server hardening:**
- API server rate limiting implemented
- DoS attacks prevented
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unauthenticated API server
- **Root cause**: No API server authentication
- **API server issue**: Attacker accessed API server without authentication
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Configure API server authentication

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Over-privileged API server access
- **Root cause**: No API server least privilege
- **API server issue**: Attacker escalated to cluster-admin
- **Impact**: 57 million customer records accessed
- **Lesson**: Configure API server least privilege

**Example: Capital One Breach (2019)**
- **Vulnerability**: API server DoS
- **Root cause**: No API server rate limiting
- **API server issue**: Attacker DoSed API server
- **Impact**: Service disruption, data access
- **Lesson**: Configure API server rate limiting

## 4️⃣ How It Works (Conceptual)

### API Server Hardening Areas

**1. API Server Authentication**
- **Purpose**: Verify who can access API server
- **Security Measures**: 
  - mTLS (mutual TLS)
  - Client certificate authentication
  - Token-based authentication (service accounts)
  - OIDC (OpenID Connect)
  - Anonymous access (disabled)
- **Common Misconfigurations**: 
  - No API server authentication (all access allowed)
  - Weak authentication (weak certificates)
  - Anonymous access enabled
  - Long-lived tokens
  - Weak TLS (outdated protocols, weak ciphers)
- **Example**: API server with mTLS and client certificates

**API Server Authentication Types:**
- **mTLS (Mutual TLS)**: 
  - API server verifies client certificates
  - Client verifies API server certificates
  - Prevents man-in-the-middle attacks
  - Prevents unauthorized access

- **Client Certificates**: 
  - X.509 certificates
  - Certificate-based authentication
  - Certificate rotation
  - Revocation

- **Token-Based Authentication**: 
  - Service account tokens
  - Bearer tokens
  - Short-lived tokens
  - Token rotation

- **OIDC**: 
  - OpenID Connect
  - Token-based authentication
  - Short-lived tokens
  - Token rotation

**Best Practices:**
- Use mTLS for API server
- Use client certificate authentication
- Use short-lived tokens
- Implement certificate rotation
- Use strong TLS (TLS 1.3, strong ciphers)
- Disable anonymous access

**Example**:
```yaml
# API server with mTLS and client certificates (secure)
apiVersion: v1
kind: Pod
metadata:
  name: kube-apiserver
  namespace: kube-system
spec:
  containers:
  - name: kube-apiserver
    image: k8s.gcr.io/kube-apiserver:v1.27.0
    args:
    - --client-ca-file=/etc/kubernetes/pki/client-ca.crt
    - --tls-cert-file=/etc/kubernetes/pki/apiserver.crt
    - --tls-private-key-file=/etc/kubernetes/pki/apiserver.key
    - --tls-min-version=VersionTLS13
    - --tls-cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
    - --anonymous-auth=false
```

**2. API Server Authorization**
- **Purpose**: Control what can be done with API server
- **Security Measures**: 
  - RBAC (Role-Based Access Control)
  - Authorization webhook
  - Namespace-based authorization
  - Resource-based authorization
  - Default-deny with explicit allow
- **Common Misconfigurations**: 
  - No API server authorization (all access allowed)
  - Over-privileged RBAC
  - No resource-based authorization
  - No namespace-based authorization
- **Example**: API server with RBAC and webhook

**API Server Authorization Types:**
- **RBAC (Role-Based Access Control)**: 
  - Cluster roles (cluster-wide permissions)
  - Roles (namespace permissions)
  - Role bindings (associate roles with subjects)
  - Cluster role bindings
  - Least privilege

- **Authorization Webhook**: 
  - External webhook validates requests
  - Rejects or allows requests
  - Flexible authorization

- **Namespace-Based Authorization**: 
  - Namespace-level permissions
  - Tenant-level isolation
  - Least privilege

- **Resource-Based Authorization**: 
  - Resource-level permissions
  - Fine-grained permissions
  - Least privilege

**Best Practices:**
- Use least privilege RBAC
- Use authorization webhook for flexibility
- Use namespace-based authorization for multi-tenancy
- Use resource-based authorization for fine-grained control
- Regular RBAC audits

**Example**:
```yaml
# API server RBAC (least privilege)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: api-server-reader
rules:
- nonResourceURLs:
  - /metrics
  - /health
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: api-server-reader-binding
subjects:
- kind: ServiceAccount
  name: api-server-reader
roleRef:
  kind: ClusterRole
  name: api-server-reader
  apiGroup: rbac.authorization.k8s.io
```

**3. Admission Controllers**
- **Purpose**: Validate and/or modify API server requests
- **Security Measures**: 
  - Validating admission controllers (security)
  - Mutating admission controllers (security)
  - Namespace validation
  - Resource quotas
  - Pod security policies
  - Image policies
- **Common Misconfigurations**: 
  - No admission controllers
  - Insecure admission controllers
  - Overly permissive admission controllers
  - No security validation
- **Example**: Admission controller for security

**Admission Controller Types:**
- **Validating Admission Controllers**: 
  - ValidatingWebhookConfiguration
  - MutatingWebhookConfiguration
  - Namespace validation
  - Resource quotas
  - Pod security policies
  - Image policies

- **Mutating Admission Controllers**: 
  - DefaultStorageClass
  - DefaultTolerationSeconds
  - NamespaceExists
  - ResourceQuota
  - LimitRanger

**Security-Focused Admission Controllers**:
- **Pod Security Policies**: 
  - Enforce security contexts (non-root, drop capabilities)
  - Enforce seccomp profiles
  - Enforce AppArmor profiles
  - Prevent privilege escalation

- **Image Policies**: 
  - Enforce image signing
  - Enforce image allowlist
  - Prevent malicious images

- **Resource Policies**: 
  - Enforce resource limits
  - Enforce resource quotas
  - Prevent resource exhaustion

**Best Practices:**
- Use validating admission controllers for security
- Use mutating admission controllers for defaults
- Use namespace validation for multi-tenancy
- Use pod security policies for security contexts
- Use image policies for image security
- Use resource policies for resource management

**Example**:
```yaml
# Validating admission webhook (security)
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: security-validating-webhook
webhooks:
- name: security-webhook.example.com
  rules:
  - operations: ["CREATE", "UPDATE"]
    apiGroups: ["*"]
    apiVersions: ["*"]
    resources: ["*/*"]
    scope: "*"
  failurePolicy: Fail
  clientConfig:
    service:
      name: security-webhook-service
      namespace: webhook-system
      path: /validate
  admissionReviewVersions: ["v1", "v1beta1"]
  timeoutSeconds: 5
```

**4. API Server Encryption**
- **Purpose**: Encrypt API server data and communication
- **Security Measures**: 
  - API server to etcd encryption (mTLS)
  - API server to worker node encryption (mTLS)
  - API server encryption at rest
  - API server encryption in transit
- **Common Misconfigurations**: 
  - No API server encryption (plaintext communication)
  - Weak TLS (outdated protocols, weak ciphers)
  - No mTLS for API server communication
  - No encryption at rest
- **Example**: API server with encryption

**API Server Encryption Types:**
- **API Server to etcd Encryption**: 
  - mTLS for API server to etcd
  - Certificate-based authentication
  - Encryption key rotation

- **API Server to Worker Node Encryption**: 
  - mTLS for API server to worker node
  - Certificate-based authentication
  - Encryption key rotation

- **API Server Encryption at Rest**: 
  - API server secrets encryption
  - KMS encryption
  - Encryption key rotation

**Best Practices:**
- Use TLS 1.3 or higher
- Use strong ciphers
- Use strong key exchange (ECDHE, etc.)
- Use certificate-based authentication
- Implement certificate rotation
- Use KMS for encryption at rest

**Example**:
```yaml
# API server encryption (secure)
apiVersion: v1
kind: Pod
metadata:
  name: kube-apiserver
  namespace: kube-system
spec:
  containers:
  - name: kube-apiserver
    image: k8s.gcr.io/kube-apiserver:v1.27.0
    args:
    - --etcd-servers=https://etcd-cluster:2379
    - --etcd-cafile=/etc/kubernetes/pki/etcd-ca.crt
    - --etcd-certfile=/etc/kubernetes/pki/etcd-client.crt
    - --etcd-keyfile=/etc/kubernetes/pki/etcd-client.key
    - --encryption-provider-config=/etc/kubernetes/encryption-config.yaml
    - --encryption-provider-type=aesgcm
    - --tls-min-version=VersionTLS13
    - --tls-cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
```

- Implement IP-based rate limiting
- Implement user-based rate limiting
- Monitor API server metrics

**Example**:
```yaml
# API server rate limiting (via API gateway)
apiVersion: v1
kind: Ingress
metadata:
  name: api-server-ingress
  namespace: kube-system
spec:
  ingressClassName: nginx
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-server
            port:
              number: 443
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls
  annotations:
    nginx.ingress.kubernetes.io/rate-limit: "100"
    nginx.ingress.kubernetes.io/rate-limit-window: "1m"
    nginx.ingress.kubernetes.io/limit-rps: "100"
```
