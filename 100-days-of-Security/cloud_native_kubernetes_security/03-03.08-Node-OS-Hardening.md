# 03.08 - Node OS Hardening

## 1️⃣ What This Topic Is

Node OS Hardening examines security measures for securing Kubernetes node operating systems, understanding node OS security, kernel hardening, and system hardening.

**What this means:**
- Node OS hardening = securing Kubernetes node OS
- Defense in depth for node OS
- Least privilege for node OS
- Secure node OS configurations

**The Key Concepts:**

1. **Node OS Security Areas**
   - Kernel hardening (GRSEC, PaX, SELinux, AppArmor)
   - User and group management (least privilege)
   - Filesystem hardening (read-only, encryption, permissions)
   - Network hardening (firewall rules, network policies)
   - Service hardening (disable unnecessary services)
   - Audit and logging (audit logs, system logs)
   - System hardening (patching, updates, hardening)

2. **Security Principles**
   - Defense in depth (kernel, user, filesystem, network, service, audit)
   - Least privilege (node OS permissions)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Node OS is foundation of cluster security
- Node OS is primary attack target
- Node OS compromise = cluster compromise
- Node OS handles all node operations

## 2️⃣ What Problem It Solves

### Problem 1: Unprotected Kernel

**Without node OS hardening:**
- Unprotected kernel
- Attacker can exploit kernel vulnerabilities
- Node compromise
- Cluster-wide compromise

**With node OS hardening:**
- Kernel protected (GRSEC, PaX, SELinux, AppArmor)
- Kernel vulnerabilities mitigated
- Node protected
- Cluster protected

### Problem 2: Over-Privileged Users

**Without node OS hardening:**
- Over-privileged users
- Attacker can escalate privileges
- Node compromise
- Cluster-wide compromise

**With node OS hardening:**
- Users with least privilege
- Privilege escalation prevented
- Node protected
- Cluster protected

### Problem 3: Unprotected Filesystem

**Without node OS hardening:**
- Unprotected filesystem
- Attacker can access node resources
- Node compromise
- Cluster-wide compromise

**With node OS hardening:**
- Filesystem protected (read-only, encryption, permissions)
- Unauthorized access prevented
- Node protected
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unprotected kernel
- **Root cause**: No kernel hardening
- **Node OS issue**: Attacker exploited kernel vulnerability
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Implement kernel hardening (GRSEC, PaX, SELinux, AppArmor)

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Over-privileged users
- **Root cause**: No user least privilege
- **Node OS issue**: Attacker escalated to root
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement user least privilege

**Example: Capital One Breach (2019)**
- **Vulnerability**: Unprotected filesystem
- **Root cause**: No filesystem hardening
- **Node OS issue**: Attacker accessed node resources
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement filesystem hardening (read-only, encryption, permissions)

## 4️⃣ How It Works (Conceptual)

### Node OS Security Areas

**1. Kernel Hardening**
- **Purpose**: Harden kernel against vulnerabilities
- **Security Measures**: 
  - GRSEC (PaX and SELinux)
  - PaX (non-executable stack, non-executable heap)
  - SELinux (Mandatory Access Control)
  - AppArmor (Mandatory Access Control)
  - Kernel patching
  - Kernel hardening (security features)
- **Common Misconfigurations**: 
  - No kernel hardening (all system calls allowed)
  - No GRSEC (no PaX or SELinux)
  - No PaX (non-executable stack, non-executable heap)
  - No SELinux (no Mandatory Access Control)
  - No AppArmor (no Mandatory Access Control)
  - Outdated kernel (vulnerable kernel)
- **Example**: Kernel hardening with GRSEC, PaX, SELinux, AppArmor

**Kernel Hardening Types:**
- **GRSEC**: 
  - PaX and SELinux
  - Kernel hardening (security features)
  - Reduce kernel attack surface
  - Prevent kernel vulnerabilities

- **PaX**: 
  - Non-executable stack
  - Non-executable heap
  - ASLR (Address Space Layout Randomization)
  - Stack protection
  - Heap protection

- **SELinux**: 
  - Mandatory Access Control
  - Enforce security policies
  - Prevent Linux vulnerabilities
  - Provide fine-grained access control

- **AppArmor**: 
  - Mandatory Access Control
  - Enforce security policies
  - Prevent Linux vulnerabilities
  - Provide fine-grained access control

- **Kernel Patching**: 
  - Security updates
  - Vulnerability patching
  - Regular updates
  - Automated updates

- **Kernel Hardening**: 
  - Kernel security features
  - Reduce kernel attack surface
  - Prevent kernel vulnerabilities

**Best Practices:**
- Implement GRSEC (PaX and SELinux)
- Implement PaX (non-executable stack, non-executable heap)
- Implement SELinux (enforcing)
- Implement AppArmor (enforcing)
- Keep kernel updated
- Enable kernel security features

**Example**:
```bash
# Kernel hardening with GRSEC, PaX, SELinux, AppArmor (secure, advanced)
# Enable GRSEC
sysctl -w kernel.grsecurity.pax.mark_mp_read_only=1
sysctl -w kernel.grsecurity.pax.mark_mprotect=1
sysctl -w kernel.grsecurity.pax.mark_randmap=1
sysctl -w kernel.grsecurity.pax.mark_heap=1
sysctl -w kernel.grsecurity.pax.aslr_enabled=1

# Enable PaX
echo "pax_softmode=0" > /etc/pax.conf

# Enable SELinux
sed -i 's/^SELINUX=.*/SELINUX=enforcing/' /etc/selinux/config
setenforce 1
sestatus

# Enable AppArmor
systemctl enable apparmor
systemctl start apparmor
aa-enforce /etc/apparmor.d/* | true

# Verify kernel hardening
sysctl kernel.grsecurity.pax.mark_mp_read_only
cat /etc/pax.conf
sestatus
aa-status
```

**3. Filesystem Hardening**

**Filesystem Hardening Types:**

  - Mount root filesystem read-only

  - Reduce attack surface
  - Limit damage from compromise

- **Filesystem Encryption**: 
  - Encrypt root filesystem
  - Encrypt data filesystem
  - Encrypt backup filesystem
  - Encrypt backup devices
  - Prevent data theft

- **Filesystem Permissions**: 
  - Set filesystem permissions
  - Set filesystem ownership
  - Set filesystem quotas
  - Prevent unauthorized access

- **Filesystem Mounting**: 
  - Mount filesystem read-only
  - Mount filesystem with noexec
  - Mount filesystem with nosuid
  - Mount filesystem with nodev
  - Prevent unauthorized access

- **Filesystem Quotas**: 
  - Set filesystem quotas
  - Set filesystem limits
  - Prevent resource exhaustion
  - Limit damage from compromise

**Best Practices:**
- Implement read-only root filesystem
- Implement filesystem encryption
- Implement filesystem permissions
- Implement filesystem mounting (read-only, noexec, nosuid, nodev)
- Implement filesystem quotas
- Monitor filesystem usage

**Example**:
```bash
# Filesystem hardening with read-only, encryption, permissions (secure, advanced)
# Mount root filesystem read-only
mount -o remount,ro /

# Encrypt filesystem (LUKS)
cryptsetup -y -v luksFormat /dev/sda1
cryptsetup open /dev/sda1 crypt_root
mkfs.ext4 /dev/mapper/crypt_root
mount /dev/mapper/crypt_root /mnt/crypt_root

# Set filesystem permissions
chmod 700 /root
chown root:root /root

# Set filesystem quotas
setquota -u container-user 10G /home/container-user
setquota -g container-group 100G /var/lib/container

# Verify filesystem hardening
mount | grep /dev/mapper/crypt_root
ls -la /root
quota -u container-user
quota -g container-group
```
