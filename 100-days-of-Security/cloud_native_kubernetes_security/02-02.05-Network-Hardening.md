# 02.05 - Network Hardening

## 1️⃣ What This Topic Is

Network Hardening examines security measures for securing Kubernetes network, understanding network policies, CNI security, and service mesh.

**What this means:**
- Network hardening = applying security controls to network traffic
- Defense in depth strategy
- Least privilege for network access
- Encrypt all network communication

**The Key Concepts:**

1. **Network Security Areas**
   - Network policies (default-deny with explicit allow)
   - Container network interface (CNI) security
   - Service mesh with mTLS
   - Ingress and egress controls
   - Network segmentation

2. **Security Principles**
   - Default-deny with explicit allow
   - Least privilege for network access
   - Encrypt all network communication
   - Network segmentation and isolation
   - Monitor and audit network traffic

**Why this matters:**
- Network attacks are common
- Lateral movement through network
- Data exfiltration through network
- Network is primary attack vector

---

## 2️⃣ What Problem It Solves

### Problem 1: Unrestricted Network Traffic

**Without network hardening:**
- All pod-to-pod traffic allowed
- Attacker can move laterally
- Data exfiltration possible
- Cluster compromise

**With network hardening:**
- Network policies restrict traffic
- Lateral movement prevented
- Data exfiltration prevented
- Cluster protected

### Problem 2: Unencrypted Network Communication

**Without network hardening:**
- Network traffic in plaintext
- Man-in-the-middle attacks
- Data theft, command injection
- Network compromise

**With network hardening:**
- All network communication encrypted
- mTLS for pod-to-pod traffic
- Man-in-the-middle attacks prevented
- Network protected

### Problem 3: No Network Segmentation

**Without network hardening:**
- All pods in same network
- Attacker can access all pods
- Tenant isolation broken
- Cluster compromise

**With network hardening:**
- Network segmentation implemented
- Tenant-level isolation enforced
- Attack surface reduced
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unrestricted network traffic
- **Root cause**: No network policies
- **Network issue**: Attacker moved laterally through network
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Implement network policies

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Unencrypted network communication
- **Root cause**: No mTLS
- **Network issue**: Attacker intercepted network traffic
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement mTLS

**Example: Capital One Breach (2019)**
- **Vulnerability**: No network segmentation
- **Root cause**: All pods in same network
- **Network issue**: Attacker accessed all pods through network
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement network segmentation

## 4️⃣ How It Works (Conceptual)

### Network Security Areas

**1. Network Policies**
- **Purpose**: Restrict pod-to-pod communication
- **Security Measures**: 
  - Default-deny with explicit allow
  - Namespace-level policies
  - Label-based policies
  - Ingress and egress controls
- **Common Misconfigurations**: 
  - No network policies (all traffic allowed)
  - Overly permissive policies
  - No egress controls (data exfiltration)
  - No network policies for namespaces
- **Example**: Default-deny network policy

**Network Policy Types:**
- **Ingress Policies**: 
  - Restrict incoming traffic to pods
  - Default-deny with explicit allow
  - Label-based policies
  - Namespace-level policies

- **Egress Policies**: 
  - Restrict outgoing traffic from pods
  - Prevent data exfiltration
  - Restrict external access
  - DNS and network policies

**Best Practices:**
- Use default-deny with explicit allow
- Use namespace-level policies
- Use label-based policies
- Implement egress policies
- Regularly review network policies

**Example**:
```yaml
# Default-deny network policy (secure)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```

**2. Container Network Interface (CNI) Security**
- **Purpose**: Secure container network interface
- **Security Measures**: 
  - Secure CNI configuration
  - CNI network policies
  - CNI encryption
  - CNI authentication
- **Common Misconfigurations**: 
  - Insecure CNI configuration
  - No CNI network policies
  - No CNI encryption
  - No CNI authentication
- **Example**: Calico CNI with network policies

**CNI Security Features:**
- **Calico**: 
  - Network policies
  - Service mesh
  - IP-in-IP encapsulation
  - Network encryption

- **Cilium**: 
  - Network policies
  - Service mesh
  - eBPF-based security
  - Network encryption

- **Flannel**: 
  - Network encryption
  - Network policies (with Canal)

- **Weave Net**: 
  - Network encryption
  - Network policies
  - Service mesh

**Best Practices:**
- Use secure CNI configuration
- Use CNI network policies
- Use CNI encryption
- Use CNI authentication
- Regularly review CNI configuration

**Example**:
```yaml
# Calico CNI with network policies (secure)
apiVersion: projectcalico.org/v3
kind: NetworkPolicy
metadata:
  name: allow-web-to-db
  namespace: production
spec:
  selector: app == database
  types:
  - Ingress
  - Egress
  ingress:
    - action: Allow
      protocol: TCP
      source:
        selector: app == web-server
      destination:
        selector: app == database
      ports:
        - 5432
```

**3. Service Mesh with mTLS**
- **Purpose**: Encrypt pod-to-pod communication
- **Security Measures**: 
  - mTLS (mutual TLS)
  - Service-to-service authentication
  - Traffic encryption
  - Traffic management
  - Observability
- **Common Misconfigurations**: 
  - No service mesh
  - No mTLS (plaintext communication)
  - Insecure service mesh configuration
  - No service-to-service authentication
- **Example**: Istio service mesh with mTLS

**Service Mesh Features:**
- **Istio**: 
  - mTLS
  - Traffic management
  - Observability
  - Service-to-service authentication
  - Network policies

- **Linkerd**: 
  - mTLS
  - Traffic management
  - Observability
  - Service-to-service authentication
  - Network policies

- **Consul Connect**: 
  - mTLS
  - Traffic management
  - Observability
  - Service-to-service authentication
  - Network policies

**Best Practices:**
- Use service mesh with mTLS
- Use service-to-service authentication
- Use traffic management
- Use observability
- Regularly review service mesh configuration

**Example**:
```yaml
# Istio service mesh with mTLS (secure)
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: web-server-mtls
  namespace: production
spec:
  mtls:
    mode: STRICT
  selector:
    matchLabels:
      app: web-server
---
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: database-mtls
  namespace: production
spec:
  mtls:
    mode: STRICT
  selector:
    matchLabels:
      app: database
```

**4. Ingress and Egress Controls**
- **Purpose**: Secure ingress and egress traffic
- **Security Measures**: 
  - Ingress controllers (TLS, WAF)
  - Egress policies (data exfiltration prevention)
  - Rate limiting
  - DDoS protection
- **Common Misconfigurations**: 
  - No ingress security
  - No egress controls (data exfiltration)
  - No rate limiting
  - No DDoS protection
- **Example**: Nginx ingress with TLS

**Ingress Security Features:**
- **Nginx Ingress Controller**: 
  - TLS termination
  - Rate limiting
  - DDoS protection
  - WAF integration
  - URL rewriting

- **Traefik Ingress Controller**: 
  - TLS termination
  - Rate limiting
  - DDoS protection
  - WAF integration

- **Envoy Ingress Controller**: 
  - TLS termination
  - Rate limiting
  - DDoS protection
  - WAF integration

**Best Practices:**
- Use ingress controllers with TLS
- Use WAF for web applications
- Use rate limiting
- Use DDoS protection
- Use egress policies for data exfiltration prevention

**Example**:
```yaml
# Nginx ingress with TLS (secure)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-server-ingress
  namespace: production
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - web.example.com
    secretName: web-tls
  rules:
  - host: web.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-server
            port:
              number: 80
```

**5. Network Segmentation**
- **Purpose**: Isolate network segments
- **Security Measures**: 
  - Namespace-level isolation
  - Network-level isolation
  - Tenant-level isolation
  - Network policies for segmentation
- **Common Misconfigurations**: 
  - No network segmentation
  - All pods in same network
  - No tenant-level isolation
  - No network-level isolation
- **Example**: Namespace-level network segmentation

**Network Segmentation Strategies:**
- **Namespace-Level Segmentation**: 
  - Network policies per namespace
  - Default-deny per namespace
  - Explicit allow per namespace

- **Tenant-Level Segmentation**: 
  - Network policies per tenant
  - Tenant-level service mesh
  - Tenant-level network policies

- **Network-Level Segmentation**: 
  - Firewall rules
  - Network policies for segmentation
  - Network isolation

**Best Practices:**
- Use namespace-level segmentation
- Use tenant-level segmentation
- Use network-level segmentation
- Use firewall rules
- Use network policies for segmentation

**Example**:
```yaml
# Namespace-level network segmentation (secure)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: tenant-a-segmentation
  namespace: tenant-a
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: tenant-a
```

## 6️⃣ Where It Should Be Applied (With Example)

Network hardening should guide **ALL Kubernetes cluster deployments**.

### **1. Applying Network Policies**

**Example: Implement Default-Deny Network Policy**

```bash
echo "=== Network Policy Implementation ==="

# 1. Implement default-deny network policy
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
EOF

# 2. Implement namespace-level allow policies
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-db
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: production
    - podSelector:
        matchLabels:
          app: web-server
    ports:
    - protocol: TCP
      port: 5432
EOF

# 3. Implement egress policy
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: web-server
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
    ports:
    - protocol: UDP
      port: 53
  - to:
    - ipBlock:
        cidr: 0.0.0.0/0
        except:
        - 10.0.0.0/8
    ports:
    - protocol: TCP
      port: 443
EOF

# 4. Verify network policies
kubectl get networkpolicies -n production
kubectl describe networkpolicy default-deny -n production
kubectl describe networkpolicy allow-web-to-db -n production
kubectl describe networkpolicy allow-dns -n production
```
