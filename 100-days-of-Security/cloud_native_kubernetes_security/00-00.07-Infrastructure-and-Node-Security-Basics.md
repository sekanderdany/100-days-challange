# 00.07 - Infrastructure & Node Security Basics

## 1️⃣ What This Topic Is

Infrastructure and Node Security Basics covers the foundational security measures needed to harden the underlying infrastructure where Kubernetes runs. This includes securing Linux operating systems, network configuration, SSH access, and container runtime.

**What this means:**
- Kubernetes runs on physical or virtual machines called nodes
- These nodes run a Linux operating system
- Nodes must be hardened before deploying Kubernetes
- Compromised nodes compromise the entire cluster

**The Components We're Securing:**

1. **Operating System (Linux)**
   - Base OS (Ubuntu, CentOS, Amazon Linux, etc.)
   - Kernel and packages
   - System services
   - File system permissions

2. **Network Configuration**
   - Network interfaces
   - Firewall rules
   - Open ports
   - Network services

3. **SSH Access**
   - SSH configuration
   - Authentication methods
   - Authorized keys
   - SSH daemons

4. **Container Runtime**
   - containerd (Kubernetes default)
   - CRI-O
   - Docker (deprecated but still used)
   - Container socket access

**Why this matters:**
- Compromised node = compromised cluster
- Attackers target vulnerable infrastructure
- Default Linux installations are not secure
- Infrastructure is foundation of security

---

## 2️⃣ What Problem It Solves

### Problem 1: Insecure Default Configurations

**Without infrastructure hardening:**
- Default Linux installations have many vulnerabilities
- Unnecessary services are running
- Default passwords or weak authentication
- Open ports expose attack surface

**With infrastructure hardening:**
- Minimal services running
- Strong authentication configured
- Attack surface reduced
- Only necessary ports open

### Problem 2: Compromised Nodes

**Without secure infrastructure:**
- Attackers can compromise nodes easily
- Privilege escalation to host is possible
- Container escape becomes easier
- Entire cluster compromised

**With secure infrastructure:**
- Hard to compromise nodes
- Privilege escalation difficult
- Container escape prevented
- Cluster remains secure

### Problem 3: Compliance Requirements

**Without infrastructure hardening:**
- Fail CIS benchmarks
- Fail regulatory audits
- Security gaps identified
- Remediation required

**With infrastructure hardening:**
- Meet CIS benchmarks
- Pass regulatory audits
- Security posture strong
- Compliance maintained

### Real-World Impact

**Example: Docker Socket Exposure (2016)**
- **Vulnerability**: Docker socket mounted in container
- **Root cause**: Insecure node allowed container escape
- **Impact**: Attacker gained host access, compromised cluster
- **Lesson**: Never expose container runtime socket

**Example: Dirty COW Vulnerability (2016)**
- **Vulnerability**: Linux kernel privilege escalation (CVE-2016-5195)
- **Root cause**: Outdated kernel on nodes
- **Impact**: Privilege escalation on unpatched systems
- **Lesson**: Keep kernel and packages updated

**Example: Kubernetes API Server Exposure (2018)**
- **Vulnerability**: Kubernetes API server accessible from internet
- **Root cause**: Insecure firewall rules on nodes
- **Impact**: Attacker gained cluster control
- **Lesson**: Restrict API server access, use secure network

## 4️⃣ How It Works (Conceptual)

### Linux Security Fundamentals

**1. Kernel Security**
- The kernel is core of Linux security
- Controls access to resources
- Manages processes and permissions
- Provides security mechanisms (capabilities, namespaces, seccomp)

**Why important:**
- Vulnerable kernel = vulnerable system
- Kernel patches fix critical vulnerabilities
- Kernel provides isolation between containers

**Key security features:**
- Namespaces: Process isolation
- cgroups: Resource limits
- Capabilities: Fine-grained permissions
- Seccomp: System call filtering
- SELinux/AppArmor: Mandatory access control

**2. Package Management**
- Packages provide software on Linux
- Outdated packages = vulnerabilities
- Updates fix security issues

**Why important:**
- Regular updates prevent known vulnerabilities
- Package signing ensures integrity
- Dependency management prevents conflicts

**Package managers:**
- **apt** (Ubuntu/Debian): `apt update && apt upgrade`
- **yum** (CentOS/RHEL): `yum update`
- **dnf** (Fedora): `dnf upgrade`
- **zypper** (SUSE): `zypper patch`

**3. Service Management**
- Services run in background
- Unnecessary services = attack surface
- Only required services should run

**Why important:**
- Fewer services = smaller attack surface
- Disabled services can't be exploited
- Systemd manages services efficiently

**Service managers:**
- **systemd**: Modern standard (most distros)
- **init**: Legacy systems
- **openrc**: Gentoo/Alpine

**4. File System Permissions**
- Permissions control file access
- Incorrect permissions = security risk
- Principle of least privilege applies

**Why important:**
- Sensitive files must be protected
- Executable files must be trusted
- Write permissions are dangerous

**Permission types:**
- **Read (r)**: Can view file
- **Write (w)**: Can modify file
- **Execute (x)**: Can run file
- **Owner/Group/Others**: Different permission levels

**5. User Management**
- Users control system access
- Default users are security risks
- Strong passwords and minimal users needed

**Why important:**
- Root access = full control
- Weak passwords = easy compromise
- Unused users = unnecessary risk

**User types:**
- **Root**: Superuser, full access (use carefully)
- **System users**: For services (shouldn't login)
- **Human users**: For administrators (use sudo)
- **Service accounts**: For applications (minimal privileges)

### Network Security

**1. Firewall Configuration**
- Firewalls control network traffic
- Only necessary traffic should be allowed
- Default-deny is safest approach

**Why important:**
- Prevents unauthorized network access
- Blocks malicious traffic
- Controls pod-to-pod communication

**Firewall tools:**
- **UFW (Uncomplicated Firewall)**: Simple, user-friendly
- **iptables**: Low-level, powerful
- **nftables**: Modern replacement for iptables
- **firewalld**: Dynamic firewall manager

**2. Port Management**
- Open ports expose services to network
- Each open port is potential attack vector
- Only necessary ports should be open

**Why important:**
- Reduces attack surface
- Prevents unauthorized access
- Controls communication paths

**Kubernetes ports:**
- **6443**: Kubernetes API server (HTTPS)
- **2379-2380**: etcd server (client/server)
- **10250**: Kubelet API
- **10251**: Scheduler
- **10252**: Controller manager
- **10255**: Read-only Kubelet (HTTP)

**3. Network Services**
- Network services provide functionality
- Unnecessary services are security risks
- Secure configuration required

**Common services:**
- **SSH**: Remote access (must be secured)
- **DNS**: Name resolution
- **NTP**: Time synchronization
- **HTTP/HTTPS**: Web services

### SSH Security

**1. SSH Configuration**
- SSH provides remote access to nodes
- Default SSH is insecure
- Must be hardened

**Why important:**
- SSH is common attack vector
- Brute-force attacks are common
- Compromised SSH = compromised node

**SSH security features:**
- **Disable root login**: Prevent direct root access
- **Disable password auth**: Use keys only
- **Limit users**: Restrict who can login
- **Use non-standard port**: Reduce automated attacks
- **Fail2ban**: Block brute-force attempts

**2. SSH Key Management**
- SSH keys are more secure than passwords
- Key management is critical
- Compromised keys = compromised access

**Key types:**
- **RSA**: Older, widely supported
- **ED25519**: Modern, secure, fast
- **ECDSA**: Elliptic curve variant

**Best practices:**
- Use strong key types (ED25519)
- Protect private keys with passphrase
- Regularly rotate keys
- Revoke unused keys

### Container Runtime Security

**1. containerd (Kubernetes Default)**
- Modern, secure container runtime
- Minimal attack surface
- Directly integrates with Kubernetes

**Security features:**
- **User namespace isolation**: Prevent privilege escalation
- **Rootless containers**: Run as non-root
- **Seccomp profiles**: Restrict syscalls
- **AppArmor/SELinux**: Mandatory access control

**2. Socket Security**
- Container runtime socket is powerful
- Exposed socket = host access
- Never expose to containers

**Socket locations:**
- **Docker**: `/var/run/docker.sock`
- **containerd**: `/run/containerd/containerd.sock`
- **CRI-O**: `/var/run/crio/crio.sock`

**Why important:**
- Socket access = container management
- Can create privileged containers
- Can escape to host

### Hardening Standards

**CIS Benchmarks**
- **Center for Internet Security (CIS) Benchmarks**
- Industry-standard security configuration
- Kubernetes has specific benchmarks
- Linux distributions have specific benchmarks

**CIS Kubernetes Benchmark**:
- 160+ security controls
- Covers control plane, nodes, workloads
- Used for compliance and security assessments
- Reference: https://www.cisecurity.org/benchmark/kubernetes

**CIS Linux Benchmarks**:
- Specific to each Linux distribution
- Ubuntu, CentOS, RHEL, etc.
- 100+ security controls
- Baseline for secure configuration

**NIST Security Controls**
- **National Institute of Standards and Technology**
- Comprehensive security framework
- Aligns with compliance requirements
- Provides best practices

## 6️⃣ Where It Should Be Applied (With Example)

Infrastructure hardening should be applied **before** deploying Kubernetes and **maintained** throughout the cluster lifecycle.

### **1. Linux OS Hardening**

**Example: Hardening Ubuntu for Kubernetes**

```bash
# 1. Update system
sudo apt update && sudo apt upgrade -y

# 2. Remove unnecessary packages
sudo apt autoremove -y
sudo apt autopurge -y

# 3. Secure SSH configuration
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

# Edit SSH config
cat <<EOF | sudo tee /etc/ssh/sshd_config
# Security settings
Port 22
Protocol 2
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys
# Restrict to specific users (optional)
# AllowUsers ubuntu
EOF

# Restart SSH
sudo systemctl restart sshd

# 4. Configure firewall (UFW)
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow SSH
sudo ufw allow 22/tcp comment 'SSH'

# Allow Kubernetes API server (if on control plane)
sudo ufw allow 6443/tcp comment 'Kubernetes API'

# Allow etcd (if on control plane)
sudo ufw allow 2379:2380/tcp comment 'etcd'

# Allow Kubelet
sudo ufw allow 10250/tcp comment 'Kubelet'

# Allow node-to-node communication
sudo ufw allow 10250:10252/tcp comment 'Kubernetes components'

# Enable firewall
sudo ufw --force enable

# 5. Install and configure fail2ban
sudo apt install -y fail2ban

cat <<EOF | sudo tee /etc/fail2ban/jail.local
[DEFAULT]
bantime = 3600
findtime = 600
maxretry = 5

[sshd]
enabled = true
port = ssh
filter = sshd
logpath = /var/log/auth.log
maxretry = 3
EOF

sudo systemctl enable fail2ban
sudo systemctl start fail2ban

# 6. Configure auditd
sudo apt install -y auditd

cat <<EOF | sudo tee /etc/audit/rules.d/kubernetes.rules
# Monitor container runtime
-w /run/containerd/containerd.sock -p wa -k container_runtime

# Monitor Kubernetes
-w /etc/kubernetes/ -p wa -k kubernetes_config

# Monitor system calls for privilege escalation
-a always,exit -F arch=b64 -S chmod -F auid>=1000 -F auid!=4294967295 -k perm_mod
-a always,exit -F arch=b32 -S chmod -F auid>=1000 -F auid!=4294967295 -k perm_mod
-a always,exit -F arch=b64 -S chown -F auid>=1000 -F auid!=4294967295 -k perm_mod
-a always,exit -F arch=b32 -S chown -F auid>=1000 -F auid!=4294967295 -k perm_mod
EOF

sudo systemctl restart auditd

# 7. Secure containerd socket
cat <<EOF | sudo tee /etc/containerd/config.toml
version = 2

[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  SystemdCgroup = true
EOF

sudo systemctl restart containerd

# 8. Configure kernel parameters
cat <<EOF | sudo tee /etc/sysctl.d/99-kubernetes.conf
# Kubernetes networking
net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward = 1

# Security hardening
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.default.rp_filter = 1
net.ipv4.conf.all.accept_source_route = 0
net.ipv6.conf.all.accept_source_route = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.default.send_redirects = 0

# Prevent SYN flood
net.ipv4.tcp_syncookies = 1
EOF

sudo sysctl --system

# 9. Remove unnecessary users
# List all users
cut -d: -f1 /etc/passwd

# Remove unused users (example)
# sudo userdel -r unused_user
```

### **2. Container Runtime Security**

**Example: Securing containerd**

```bash
# 1. Verify containerd is running
sudo systemctl status containerd

# 2. Check containerd version
containerd --version

# 3. Ensure containerd socket is not exposed
sudo chmod 600 /run/containerd/containerd.sock

# 4. Configure containerd for security
cat <<EOF | sudo tee /etc/containerd/config.toml
version = 2

[plugins]
  [plugins."io.containerd.grpc.v1.cri"]
    [plugins."io.containerd.grpc.v1.cri".containerd]
      [plugins."io.containerd.grpc.v1.cri".containerd.runtimes]
        [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
          runtime_type = "io.containerd.runc.v2"
          [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
            SystemdCgroup = true

    [plugins."io.containerd.grpc.v1.cri".registry]
      [plugins."io.containerd.grpc.v1.cri".registry.configs]
        [plugins."io.containerd.grpc.v1.cri".registry.configs."docker.io"]
          [plugins."io.containerd.grpc.v1.cri".registry.configs."docker.io".tls]
            insecure_skip_verify = false
EOF

sudo systemctl restart containerd

# 5. Test containerd
sudo ctr version
sudo ctr images pull docker.io/library/nginx:alpine
```

### **3. Network Security**

**Example: Configuring Network Security**

```bash
# 1. Check open ports
sudo ss -tulnp

# 2. Check firewall rules
sudo ufw status numbered

# 3. Add Kubernetes-specific rules
# For control plane node
sudo ufw allow 6443/tcp comment 'Kubernetes API'
sudo ufw allow 2379:2380/tcp comment 'etcd'
sudo ufw allow 10250:10252/tcp comment 'Kubernetes components'

# For worker node
sudo ufw allow 10250/tcp comment 'Kubelet'
sudo ufw allow 30000:32767/tcp comment 'NodePort services'

# 4. Check listening services
sudo netstat -tulpn | grep LISTEN

# 5. Scan own ports (security check)
sudo nmap -sS localhost

# 6. Monitor network connections
sudo watch -n 1 'sudo netstat -tulpn | grep LISTEN'
```

### **4. SSH Hardening**

**Example: SSH Security Configuration**

```bash
# 1. Current SSH configuration
sudo cat /etc/ssh/sshd_config

# 2. Test SSH configuration (before applying)
sudo sshd -t

# 3. Apply secure SSH config
cat <<EOF | sudo tee /etc/ssh/sshd_config
# Basic settings
Port 22
Protocol 2
HostKey /etc/ssh/ssh_host_rsa_key
HostKey /etc/ssh/ssh_host_ecdsa_key
HostKey /etc/ssh/ssh_host_ed25519_key

# Authentication
LoginGraceTime 60
PermitRootLogin no
PasswordAuthentication no
PermitEmptyPasswords no
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys

# Security
X11Forwarding no
MaxAuthTries 3
ClientAliveInterval 300
ClientAliveCountMax 2

# Logging
LogLevel VERBOSE
SyslogFacility AUTHPRIV
EOF

# 4. Restart SSH
sudo systemctl restart sshd

# 5. Verify SSH is running
sudo systemctl status sshd

# 6. Test SSH connection
ssh user@node-ip
```

### **Common Mistakes in Infrastructure Security**

❌ **Mistake 1**: Leaving default SSH configuration
- Reality: Default SSH allows password auth and root login
- Fix: Disable password auth, disable root login, use keys

❌ **Mistake 2**: Not configuring firewall
- Reality: All ports open, high attack surface
- Fix: Configure UFW, allow only necessary ports

❌ **Mistake 3**: Exposing container runtime socket
- Reality: Container socket = host access
- Fix: Never expose socket to containers, secure permissions

❌ **Mistake 4**: Not updating system
- Reality: Outdated packages = vulnerabilities
- Fix: Regular updates, enable automatic security updates

❌ **Mistake 5**: Running unnecessary services
- Reality: More services = larger attack surface
- Fix: Disable unnecessary services, remove unused packages

### **Common Interview Questions**

**Q1: What are the key steps to harden a Linux node for Kubernetes?**
**Good Answer**: Key steps to harden Linux nodes are:
1. **Update system**: `apt update && apt upgrade` - fixes known vulnerabilities
2. **Remove unnecessary packages**: `apt autoremove` - reduces attack surface
3. **Harden SSH**: Disable password auth, disable root login, use keys only
4. **Configure firewall**: UFW with default-deny, allow only necessary ports
5. **Secure container runtime**: Never expose socket, secure permissions
6. **Harden kernel parameters**: Network security, IP forwarding, SYN cookies
7. **Enable monitoring**: Audit logging, fail2ban, log monitoring
8. **Follow CIS benchmarks**: Apply CIS Kubernetes and Linux benchmarks

These steps create secure foundation for Kubernetes.

**Q2: Why is securing the container runtime socket critical?**
**Good Answer**: The container runtime socket (e.g., `/run/containerd/containerd.sock`) provides complete control over the container runtime. Accessing this socket allows you to:
- Create and manage containers
- Configure container settings
- Execute commands in containers
- Mount host filesystems
- Escalate privileges to host

If an attacker gains access to this socket, they effectively have full control over the host system. This is why:
- Never mount the socket in containers
- Secure socket permissions (chmod 600)
- Monitor socket access attempts
- Never expose socket to network

Container socket is essentially host root access - protect it accordingly.

**Q3: What's the purpose of CIS benchmarks for Kubernetes?**
**Good Answer**: CIS (Center for Internet Security) Benchmarks are industry-standard security guidelines. For Kubernetes:
- **CIS Kubernetes Benchmark**: 160+ specific controls covering control plane, nodes, and workloads
- **CIS Linux Benchmark**: 100+ controls for Linux hardening specific to your distribution

Purpose and benefits:
1. **Standardization**: Provides baseline for secure configuration
2. **Compliance**: Used for regulatory audits and certifications
3. **Best practices**: Based on real-world security experience
4. **Scoring**: Level 1 (essential), Level 2 (advanced)
5. **Automation**: Can be automated with kube-bench tool

In practice, use kube-bench to scan cluster against CIS benchmark and remediate findings.

**Q4: How do you configure SSH securely for Kubernetes nodes?**
**Good Answer**: Secure SSH configuration involves:
1. **Disable password authentication**: `PasswordAuthentication no` - prevents brute-force password attacks
2. **Disable root login**: `PermitRootLogin no` - prevents direct root access
3. **Enable key-based auth**: `PubkeyAuthentication yes` - stronger than passwords
4. **Limit auth attempts**: `MaxAuthTries 3` - prevents brute-force
5. **Configure timeout**: `ClientAliveInterval 300` - prevents idle sessions
6. **Use non-standard port**: Change from 22 - reduces automated attacks
7. **Enable fail2ban**: Blocks repeated failed login attempts

Configuration in `/etc/ssh/sshd_config`:
```bash
Port 22
Protocol 2
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
ClientAliveInterval 300
```

After configuration, restart SSH with `systemctl restart sshd`.

**Q5: What's the role of monitoring and auditing in infrastructure security?**
**Good Answer**: Monitoring and auditing are critical for:
1. **Detection**: Identify security breaches and attacks
2. **Investigation**: Understand what happened during incidents
3. **Compliance**: Meet regulatory requirements for logging
4. **Deterrence**: Attackers know they're being watched
5. **Response**: Quickly respond to security events

Key tools and configurations:
- **auditd**: Logs security-relevant system calls (file changes, privilege escalation)
- **fail2ban**: Blocks brute-force SSH attacks
- **log monitoring**: Review system logs for anomalies
- **intrusion detection**: Tools like AIDE, rkhunter, tripwire

Without monitoring, you won't know if you're breached until it's too late. With monitoring, you detect attacks early and respond quickly.
