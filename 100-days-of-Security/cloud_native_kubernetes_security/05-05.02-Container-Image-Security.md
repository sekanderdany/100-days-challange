# 05.02 - Container Image Security

## 1️⃣ What This Topic Is

Container Image Security examines security measures for securing Kubernetes container images, understanding image vulnerabilities, supply chain security, and secure image configurations.

**What this means:**
- Kubernetes Container Images = application packages (Docker images)
- Image Vulnerabilities = CVEs (Common Vulnerabilities and Exposures)
- Supply Chain Security = image provenance (signing, verification)
- Secure image configurations (base images, tags, scanning)

**The Key Concepts:**

1. **Kubernetes Container Image Security Areas**
   - Image scanning (vulnerability scanning, compliance scanning)
   - Image signing (image provenance, image verification)
   - Image base (official images, minimal images)
   - Image tags (specific versions, immutable tags)
   - Image policies (allow-list, deny-list)

2. **Security Principles**
   - Defense in depth (scanning, signing, base, tags, policies)
   - Least privilege (image access)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Container images are critical for cluster security
- Container images package all application code
- Container images compromise = workload compromise
- Container images handle all application code

## 2️⃣ What Problem It Solves

### Problem 1: Unmanaged Container Images

**Without container image security:**
- Unmanaged container images (vulnerable images)
- Attacker can exploit image vulnerabilities
- Cluster compromise
- Data theft and service disruption

**With container image security:**
- Managed container images (secure images)
- Attacker cannot exploit image vulnerabilities
- Cluster protected
- Data and services protected

### Problem 2: Unverified Image Provenance

**Without container image security:**
- Unverified image provenance (unsigned images)
- Attacker can inject malicious code
- Cluster compromise
- Data theft and service disruption

**With container image security:**
- Verified image provenance (signed images)
- Attacker cannot inject malicious code
- Cluster protected
- Data and services protected

### Problem 3: No Image Scanning

**Without container image security:**
- No image scanning (vulnerable images)
- Attacker can exploit image vulnerabilities
- Cluster compromise
- Data theft and service disruption

**With container image security:**
- Image scanning enabled (secure images)
- Attacker cannot exploit image vulnerabilities
- Cluster protected
- Data and services protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unmanaged container images
- **Root cause**: No image scanning
- **Container image issue**: Attacker deployed vulnerable containers
- **Impact**: Attacker accessed production secrets
- **Lesson**: Implement image scanning

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Unverified image provenance
- **Root cause**: No image signing
- **Container image issue**: Attacker deployed malicious containers
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement image signing

**Example: Capital One Breach (2019)**
- **Vulnerability**: No image scanning
- **Root cause**: No image scanning
- **Container image issue**: Attacker exploited image vulnerabilities
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement image scanning

## 4️⃣ How It Works (Conceptual)

### Kubernetes Container Image Security Areas

**1. Image Scanning**
- **Purpose**: Scan images for vulnerabilities
- **Security Measures**: 
  - Vulnerability scanning (CVE scanning)
  - Compliance scanning (CIS benchmarks, security baselines)
  - Image policies (allow-list, deny-list)
  - Image notifications (vulnerability alerts, compliance alerts)
- **Common Misconfigurations**: 
  - No image scanning (vulnerable images)
  - No vulnerability scanning (unknown vulnerabilities)
  - No compliance scanning (unknown compliance violations)
  - No image policies (all images allowed)
- **Example**: Image scanning with Trivy

**Image Scanning Types:**
- **Vulnerability Scanning**: 
  - Vulnerability scanning (CVE scanning)
  - Vulnerability databases (NVD, CVE database)
  - Vulnerability scoring (CVSS scores)
  - Vulnerability remediation (patching)
  - Least privilege

- **Compliance Scanning**: 
  - Compliance scanning (CIS benchmarks, security baselines)
  - Compliance databases (CIS benchmarks, security baselines)
  - Compliance scoring (compliance scores)
  - Compliance remediation (compliance fixes)
  - Least privilege

- **Image Policies**: 
  - Image policies (allow-list, deny-list)
  - Image policy enforcement (image admission controllers)
  - Image policy monitoring (image admission events)
  - Least privilege

**Best Practices:**
- Use image scanning (vulnerability scanning, compliance scanning)
- Implement image policies (allow-list, deny-list)
- Implement image notifications (vulnerability alerts, compliance alerts)
- Regular image audits

**Example**:
```bash
# Image scanning with Trivy (secure, advanced)
trivy image --severity HIGH,CRITICAL nginx:1.14.2
```

**2. Image Signing**
- **Purpose**: Verify image provenance
- **Security Measures**: 
  - Image signing (image signatures, image keys)
  - Image verification (image provenance, image verification)
  - Image trust (image trust policies, image trust stores)
  - Image compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
- **Common Misconfigurations**: 
  - No image signing (unsigned images)
  - No image verification (unverified images)
  - No image trust (untrusted images)
  - No image compliance (no SOC 2, PCI-DSS, HIPAA, GDPR)
- **Example**: Image signing with Cosign

**Image Signing Types:**
- **Image Signing**: 
  - Image signing (image signatures, image keys)
  - Image signing keys (RSA keys, ECDSA keys)
  - Image signing policies (signing policies, signing requirements)
  - Least privilege

- **Image Verification**: 
  - Image verification (image provenance, image verification)
  - Image verification tools (Cosign, Notary)
  - Image verification policies (verification policies, verification requirements)
  - Least privilege

- **Image Trust**: 
  - Image trust (image trust policies, image trust stores)
  - Image trust policies (trust policies, trust requirements)
  - Image trust stores (trust stores, key stores)
  - Least privilege

**Best Practices:**
- Use image signing (image signatures, image keys)
- Implement image verification (image provenance, image verification)
- Implement image trust (image trust policies, image trust stores)
- Implement image compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
- Regular image audits

**Example**:
```bash
# Image signing with Cosign (secure, advanced)
cosign sign --key cosign.key nginx:1.14.2
```

**3. Image Base**
- **Purpose**: Use secure base images
- **Security Measures**: 
  - Base images (official images, minimal images)
  - Base image security (official repositories, minimal layers)
  - Base image policies (allow-list, deny-list)
  - Base image monitoring (base image updates, base image vulnerabilities)
- **Common Misconfigurations**: 
  - No base images (unofficial images)
  - No minimal images (large images)
  - No base image security (unofficial repositories)
  - No base image policies (all images allowed)
- **Example**: Image base with Alpine

**Image Base Types:**
- **Official Images**: 
  - Official images (Docker Hub, Red Hat, SUSE)
  - Official image repositories (Docker Hub, Red Hat, SUSE)
  - Official image security (official repositories, official maintainers)
  - Least privilege

- **Minimal Images**: 
  - Minimal images (Alpine, Distroless)
  - Minimal image layers (minimal layers, minimal dependencies)
  - Minimal image security (minimal vulnerabilities, minimal attack surface)
  - Least privilege

- **Base Image Policies**: 
  - Base image policies (allow-list, deny-list)
  - Base image enforcement (image admission controllers)
  - Base image monitoring (base image updates, base image vulnerabilities)
  - Least privilege

**Best Practices:**
- Use base images (official images, minimal images)
- Implement base image policies (allow-list, deny-list)
- Implement base image monitoring (base image updates, base image vulnerabilities)
- Regular base image audits

**Example**:
```yaml
# Image base with Alpine (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: secure-namespace
spec:
  containers:
  - name: secure-container
    image: alpine:3.14.0
    securityContext:
      runAsUser: 1000
      runAsGroup: 1000
      fsGroup: 1000
```

- **Purpose**: Use secure image tags
- **Security Measures**: 
  - Image tags (specific versions, immutable tags)
  - Image tag policies (allow-list, deny-list)

**Image Tags Types:**

  - Least privilege

- **Immutable Tags**: 
  - Immutable tags (immutable tags, digest-based tags)
  - Immutable tag policies (allow-list, deny-list)
  - Immutable tag enforcement (image admission controllers)
  - Immutable tag monitoring (immutable tag updates, immutable tag vulnerabilities)
  - Least privilege

**Best Practices:**
- Use image tags (specific versions, immutable tags)
- Implement image tag policies (allow-list, deny-list)
- Implement image tag monitoring (image tag updates, image tag vulnerabilities)
- Regular image tag audits

**Example**:

**5. Image Policies**
- **Purpose**: Enforce image policies
- **Security Measures**: 
  - Image policies (allow-list, deny-list)
  - Image policy enforcement (image admission controllers, Kyverno)
  - Image policy monitoring (image admission events, image policy violations)
  - Image policy compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
- **Common Misconfigurations**: 
  - No image policies (all images allowed)
  - Weak image policies (allow all)
  - No image policy enforcement (allow all)
  - No image policy monitoring (no audit trail)
- **Example**: Image policies with Kyverno

**Image Policies Types:**
- **Allow-List Policies**: 
  - Image policies (allow-list)
  - Image policy enforcement (image admission controllers, Kyverno)
  - Image policy monitoring (image admission events, image policy violations)
  - Least privilege

- **Deny-List Policies**: 
  - Image policies (deny-list)
  - Image policy enforcement (image admission controllers, Kyverno)
  - Image policy monitoring (image admission events, image policy violations)
  - Least privilege

- **Image Admission Controllers**: 
  - Image admission controllers (image admission, image mutation)
  - Image admission monitoring (image admission events, image policy violations)
  - Least privilege

**Best Practices:**
- Use image policies (allow-list, deny-list)
- Implement image policy enforcement (image admission controllers, Kyverno)
- Implement image policy monitoring (image admission events, image policy violations)
- Implement image policy compliance (SOC 2, PCI-DSS, HIPAA, GDPR)
- Regular image policy audits

**Example**:
```yaml
# Image policies with Kyverno (secure, advanced)
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: image-policy
spec:
  validationFailureAction: enforce
  background: false
  rules:
  - name: require-image-signature
    match:
      resources:
        kinds:
        - Pod
    verifyImages:
    - name: disallow-latest-tag
    match:
      resources:
        kinds:
        - Pod
    validate:
      message: "Using the 'latest' tag is not allowed"
      pattern:
        image: "^(?!.*:latest$)"
```
