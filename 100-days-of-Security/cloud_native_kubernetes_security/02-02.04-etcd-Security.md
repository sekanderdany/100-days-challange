# 02.04 - etcd Security

## 1️⃣ What This Topic Is

etcd Security examines security measures for securing Kubernetes etcd component, understanding encryption, authentication, and access controls.

**What this means:**
- etcd = Kubernetes key-value store
- Stores cluster state and all config data
- Most critical component for cluster
- etcd compromise = cluster compromise

**The Key Concepts:**

1. **etcd Components**
   - Encryption at rest (data encryption)
   - Encryption in transit (TLS, mTLS)
   - Authentication (client certificates, tokens)
   - Authorization (RBAC, etcd user)
   - Access control (network policies, firewall rules)

2. **Security Areas**
   - Encryption at rest (KMS, secrets encryption)
   - Encryption in transit (TLS, mTLS)
   - Authentication (certificates, tokens)
   - Authorization (RBAC, etcd user)
   - Access control (network policies, firewall)
   - Backup and recovery (encryption, verification)

**Why this matters:**
- etcd stores all cluster state
- etcd stores all secrets
- etcd stores all config maps
- etcd is primary attack target
- etcd compromise = complete cluster compromise

---

## 2️⃣ What Problem It Solves

### Problem 1: Unencrypted etcd Data

**Without etcd security:**
- etcd data stored in plaintext
- Attacker can read cluster state
- Attacker can read all secrets
- Cluster compromise

**With etcd security:**
- etcd data encrypted at rest
- Only authorized users can decrypt
- Unauthorized access prevented
- Cluster protected

### Problem 2: Unauthorized etcd Access

**Without etcd security:**
- Anyone can access etcd API
- Attacker can read/modify etcd data
- Attacker can modify cluster state
- Cluster compromise

**With etcd security:**
- Authentication required for etcd access
- Authorization required for etcd operations
- Unauthorized access prevented
- Cluster protected

### Problem 3: etcd Network Exposure

**Without etcd security:**
- etcd exposed to network
- Attacker can access etcd API
- Man-in-the-middle attacks possible
- Cluster compromise

**With etcd security:**
- etcd network restricted
- TLS required for etcd communication
- Network policies restrict etcd access
- Man-in-the-middle attacks prevented

### Real-World Impact

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Unencrypted etcd data
- **Root cause**: No etcd encryption at rest
- **etcd security issue**: Attacker accessed unencrypted etcd data
- **Impact**: 57 million customer records accessed
- **Lesson**: Encrypt etcd data at rest

**Example: Capital One Breach (2019)**
- **Vulnerability**: Unauthorized etcd access
- **Root cause**: Weak etcd authentication
- **etcd security issue**: Attacker accessed etcd without proper authentication
- **Impact**: 106 million customer records accessed
- **Lesson**: Configure strong etcd authentication

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: etcd network exposure
- **Root cause**: etcd exposed to network
- **etcd security issue**: Attacker accessed etcd API
- **Impact**: Attacker read etcd data
- **Lesson**: Restrict etcd network access

## 4️⃣ How It Works (Conceptual)

### etcd Security Areas

**1. Encryption at Rest**
- **Purpose**: Encrypt etcd data stored on disk
- **Security Measures**: 
  - KMS encryption (AWS KMS, Azure Key Vault, GCP KMS)
  - Secrets encryption (API server encryption)
  - Encryption key rotation
  - Secure key management
- **Common Misconfigurations**: 
  - No encryption at rest (plaintext etcd data)
  - Weak encryption algorithms
  - Insecure key management
  - Long-lived encryption keys
- **Example**: etcd with KMS encryption

**Encryption Methods:**
- **API Server Encryption**: 
  - API server encrypts etcd data
  - Decrypts when needed
  - Transparent to etcd

- **Storage-Level Encryption**: 
  - Underlying storage encryption
  - AWS EBS encryption
  - Azure Disk encryption
  - GCP Persistent Disk encryption

- **KMS Encryption**: 
  - AWS KMS, Azure Key Vault, GCP KMS
  - Key rotation
  - Secure key management
  - Hardware Security Modules (HSM)

**Best Practices:**
- Use API server encryption (encryption at rest)
- Use KMS for key management
- Rotate encryption keys regularly
- Use strong encryption algorithms
- Implement secure key management

**Example**:
```yaml
# API server with etcd encryption (secure)
apiVersion: kubeadm.k8s.io/v1beta2
kind: ClusterConfiguration
apiServer:
  extraArgs:
  - --encryption-provider-config=/etc/kubernetes/encryption-config.yaml
  - --encryption-provider-type=aesgcm
```

**2. Encryption in Transit**
- **Purpose**: Encrypt etcd network communication
- **Security Measures**: 
  - TLS for etcd communication
  - mTLS (mutual TLS)
  - Secure ciphers and protocols
  - Certificate-based authentication
- **Common Misconfigurations**: 
  - No TLS (plaintext communication)
  - Weak TLS (outdated protocols, weak ciphers)
  - No certificate validation
  - Self-signed certificates
- **Example**: etcd with TLS

**TLS Best Practices:**
- Use TLS 1.3 or higher
- Use strong ciphers
- Use strong key exchange (ECDHE, etc.)
- Use certificate-based authentication
- Implement certificate rotation
- Use mTLS for etcd clusters

**Example**:
```yaml
# etcd with TLS (secure)
apiVersion: kubeadm.k8s.io/v1beta2
kind: ClusterConfiguration
etcd:
  extraArgs:
  - --cert-file=/etc/kubernetes/pki/etcd-server.crt
  - --key-file=/etc/kubernetes/pki/etcd-server.key
  - --client-cert-auth=true
  - --trusted-ca-file=/etc/kubernetes/pki/ca.crt
  - --cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
```

**3. Authentication**
- **Purpose**: Verify who can access etcd
- **Security Measures**: 
  - Client certificate authentication
  - Token-based authentication
  - Certificate rotation
  - Revocation
- **Common Misconfigurations**: 
  - No authentication
  - Weak authentication (weak certificates)
  - Long-lived certificates
  - No revocation
- **Example**: etcd with client certificate authentication

**Authentication Methods:**
- **Client Certificates**: 
  - X.509 certificates
  - Certificate-based authentication
  - Certificate rotation
  - Revocation

- **Tokens**: 
  - Bearer tokens
  - Short-lived tokens
  - Token rotation

**Best Practices:**
- Use client certificates
- Use short-lived certificates
- Implement certificate rotation
- Implement certificate revocation
- Use strong encryption

**Example**:
```bash
# etcd with client certificate authentication (secure)
etcdctl --cert-file=/etc/kubernetes/pki/etcd-client.crt \
  --key-file=/etc/kubernetes/pki/etcd-client.key \
  --cacert=/etc/kubernetes/pki/ca.crt \
  --endpoints=https://etcd-cluster:2379 \
  get / --keys-only
```

**4. Authorization**
- **Purpose**: Control what can be done with etcd
- **Security Measures**: 
  - RBAC for etcd access
  - etcd user permissions
  - Resource-based authorization
  - Namespace-based authorization
- **Common Misconfigurations**: 
  - No RBAC (all access allowed)
  - Over-privileged RBAC
  - No resource-based authorization
  - No namespace-based authorization
- **Example**: RBAC for etcd access

**Authorization Concepts:**
- **RBAC**: 
  - Role-Based Access Control
  - Resource-based authorization
  - Namespace-based authorization

- **etcd User**: 
  - etcd user for operations
  - User-based authorization
  - User permissions

**Best Practices:**
- Use least privilege RBAC
- Use resource-based authorization
- Use namespace-based authorization
- Regular RBAC audits
- Document etcd access

**Example**:
```yaml
# RBAC for etcd access (secure)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: etcd-reader
rules:
- nonResourceURLs:
  - /metrics
  - /health
  - /proxy
  - /config
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: etcd-reader-binding
subjects:
- kind: ServiceAccount
  name: etcd-reader
roleRef:
  kind: ClusterRole
  name: etcd-reader
  apiGroup: rbac.authorization.k8s.io
```

**5. Network Isolation**
- **Purpose**: Restrict etcd network access
- **Security Measures**: 
  - Network policies for etcd
  - Firewall rules
  - Network segmentation
  - etcd network isolation
- **Common Misconfigurations**: 
  - No network policies (all traffic allowed)
  - etcd exposed to public network
  - No firewall rules
  - No network segmentation
- **Example**: Network policy for etcd

**Network Isolation Best Practices:**
- Implement network policies for etcd
- Restrict etcd to internal network
- Implement firewall rules
- Implement network segmentation
- Monitor etcd network access

**Example**:
```yaml
# Network policy for etcd (secure)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: etcd-network-policy
  namespace: kube-system
spec:
  podSelector:
    matchLabels:
      component: etcd
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: kube-system
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
```

**6. Backup and Recovery**
- **Purpose**: Protect etcd data and enable recovery
- **Security Measures**: 
  - Encrypted backups
  - Offsite backups
  - Backup verification
  - Disaster recovery
- **Common Misconfigurations**: 
  - No backups
  - Unencrypted backups
  - No backup verification
  - No disaster recovery
- **Example**: etcd backup with encryption

**Backup Best Practices:**
- Implement regular etcd backups
- Encrypt backups
- Store backups offsite
- Verify backups regularly
- Test disaster recovery
- Implement backup retention policies

**Example**:
```bash
# etcd backup with encryption (secure)
ETCDCTL_API=3 etcdctl snapshot save /data/etcd-backup-$(date +%Y%m%d).snapshot \
  --cacert /etc/kubernetes/pki/ca.crt \
  --cert /etc/kubernetes/pki/etcd-client.crt \
  --key /etc/kubernetes/pki/etcd-client.key

# Verify backup
ETCDCTL_API=3 etcdctl snapshot verify /data/etcd-backup-$(date +%Y%m%d).snapshot \
  --cacert /etc/kubernetes/pki/ca.crt \
  --cert /etc/kubernetes/pki/etcd-client.crt \
  --key /etc/kubernetes/pki/etcd-client.key
```

### **4. Applying Backup and Recovery**

**Example: Implement etcd Backup with Encryption**

```bash
echo "=== etcd Backup and Recovery ==="

# 1. Create etcd backup script
cat <<'EOF' > /tmp/etcd-backup.sh
#!/bin/bash
echo "Creating etcd backup at $(date)..."

# Backup etcd data
ETCDCTL_API=3 etcdctl snapshot save /data/etcd-backup-$(date +%Y%m%d).snapshot \
  --cacert /etc/kubernetes/pki/ca.crt \
  --cert /etc/kubernetes/pki/etcd-client.crt \
  --key /etc/kubernetes/pki/etcd-client.key

# Verify backup
ETCDCTL_API=3 etcdctl snapshot verify /data/etcd-backup-$(date +%Y%m%d).snapshot \
  --cacert /etc/kubernetes/pki/ca.crt \
  --cert /etc/kubernetes/pki/etcd-client.crt \
  --key /etc/kubernetes/pki/etcd-client.key

# Retain backups (7 days retention)
find /data/ -name "etcd-backup-*" -mtime +7 -delete

echo "etcd backup created and verified"
EOF

/tmp/etcd-backup.sh
```
