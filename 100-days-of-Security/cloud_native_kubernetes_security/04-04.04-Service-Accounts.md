# 04.04 - Service Accounts

## 1️⃣ What This Topic Is

Service Accounts examines security measures for securing Kubernetes service accounts, understanding service account identity, tokens, and access control.

**What this means:**
- Service accounts = identity for pods to access Kubernetes API
- Service account tokens = JWT tokens for pod authentication
- Service account RBAC = role-based access for service accounts
- Secure service account configurations (least privilege, token rotation)

**The Key Concepts:**

1. **Service Account Security Areas**
   - Service account identity (cluster, namespaces)
   - Service account tokens (JWT, short-lived)
   - Service account RBAC (roles, role bindings)
   - Service account security contexts
   - Service account monitoring

2. **Security Principles**
   - Defense in depth (identity, tokens, RBAC, monitoring)
   - Least privilege (service account RBAC)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Service accounts are critical for pod identity
- Service accounts provide API access for workloads
- Service account compromise = workload compromise
- Service accounts handle all pod authentication

---

## 2️⃣ What Problem It Solves

### Problem 1: Default Service Account Usage

**Without service account security:**
- Default service account used everywhere
- All pods have same permissions
- Attacker can escalate privileges
- Workload compromise

**With service account security:**
- Dedicated service accounts per workload
- Least privilege per service account
- Privilege escalation prevented
- Workload protected

### Problem 2: Long-Lived Service Account Tokens

**Without service account security:**
- Long-lived service account tokens
- Attacker can use stolen tokens indefinitely
- Workload compromise
- Cluster compromise

**With service account security:**
- Short-lived service account tokens
- Token rotation implemented
- Token expiration enforced
- Workload protected
- Cluster protected

### Problem 3: No Service Account RBAC

**Without service account security:**
- No service account RBAC (all pods have cluster-admin)
- Attacker can access any resource
- Workload compromise
- Cluster compromise

**With service account security:**
- Service account RBAC implemented (least privilege)
- Resource access controlled
- Workload protected
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Default service account usage
- **Root cause**: No dedicated service accounts
- **Service account issue**: All pods had same permissions
- **Impact**: Attacker escalated to cluster-admin
- **Lesson**: Implement dedicated service accounts

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Long-lived service account tokens
- **Root cause**: No token rotation
- **Service account issue**: Attacker used stolen tokens indefinitely
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement service account token rotation

**Example: Capital One Breach (2019)**
- **Vulnerability**: No service account RBAC
- **Root cause**: No least privilege service accounts
- **Service account issue**: All pods had cluster-admin
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement service account RBAC

## 4️⃣ How It Works (Conceptual)

### Service Account Security Areas

**1. Service Account Identity**
- **Purpose**: Provide identity for pods to access Kubernetes API
- **Security Measures**: 
  - Dedicated service accounts per namespace
  - Dedicated service accounts per workload
  - Service account metadata (labels, annotations)
  - Service account image pull secrets
- **Common Misconfigurations**: 
  - Default service account used everywhere
  - No dedicated service accounts (all pods use default)
  - No service account metadata (no labels, annotations)
  - No service account image pull secrets (plaintext)
- **Example**: Service accounts with dedicated identities

**Service Account Identity Types:**
- **Cluster-Level Service Accounts**: 
  - Service accounts for cluster-wide resources
  - Used by system components
  - Used by add-ons

- **Namespace-Level Service Accounts**: 
  - Service accounts for namespace resources
  - Used by workloads in namespace
  - Least privilege

- **Service Account Metadata**: 
  - Labels
  - Annotations
  - Image pull secrets

**Best Practices:**
- Create dedicated service accounts per namespace
- Create dedicated service accounts per workload
- Use service account metadata (labels, annotations)
- Use service account image pull secrets
- Regular service account audits

**Example**:
```yaml
# Service accounts with dedicated identities (secure, advanced)
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
  labels:
    pod-security.kubernetes.io/enforce: restricted
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secure-service-account
  namespace: secure-namespace
  labels:
    app: secure-app
    environment: production
  annotations:
    kubernetes.io/enforce-mountable-secrets: "false"
imagePullSecrets:
- name: docker-registry-secret
```

**2. Service Account Tokens**
- **Purpose**: Provide authentication tokens for pods to access Kubernetes API
- **Security Measures**: 
  - JWT tokens (short-lived)
  - Token rotation
  - Token expiration
  - Token binding
  - Token projection
- **Common Misconfigurations**: 
  - Long-lived tokens (no expiration)
  - No token rotation (static tokens)
  - No token binding (tokens not bound to pods)
  - No token projection (legacy tokens)
- **Example**: Service account tokens with JWT

**Service Account Token Types:**
- **JWT Tokens**: 
  - JSON Web Tokens
  - Short-lived tokens
  - Token rotation
  - Token expiration
  - Token binding

- **Token Rotation**: 
  - Automatic token rotation
  - Manual token rotation
  - Token lifecycle management
  - Token revocation

- **Token Expiration**: 
  - Token expiration policies
  - Short-lived tokens
  - Automatic token expiration
  - Token expiration enforcement

- **Token Binding**: 
  - Token audience binding
  - Token issuer binding
  - Token subject binding

- **Token Projection**: 
  - Token projection API
  - Projected tokens
  - Token expiration
  - Token binding

**Best Practices:**
- Use short-lived tokens
- Implement token rotation
- Implement token expiration
- Implement token binding
- Use token projection

**Example**:
```yaml
# Service account tokens with JWT (secure, advanced)
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secure-service-account
  namespace: secure-namespace
  annotations:
    service-account.kubernetes.io/autogen-managed-secret: "true"
    service-account.kubernetes.io/token-expiration: "3600"
---
apiVersion: v1
kind: Pod
metadata:
  name: secure-token-pod
  namespace: secure-namespace
spec:
  serviceAccountName: secure-service-account
  containers:
  - name: secure-token-container
    image: secure-token:v1
    env:
    - name: KUBERNETES_SERVICE_ACCOUNT_TOKEN
      valueFrom:
        fieldRef:
          fieldPath: /var/run/secrets/kubernetes.io/serviceaccount/token
    - name: KUBERNETES_SERVICE_ACCOUNT_CA_CERT
      valueFrom:
        fieldRef:
          fieldPath: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
```

**3. Service Account RBAC**
- **Purpose**: Provide role-based access for service accounts
- **Security Measures**: 
  - Roles (namespace-level, cluster-level)
  - Role bindings (associate roles with service accounts)
  - Cluster roles (cluster-level)
  - Cluster role bindings (associate cluster roles with service accounts)
  - Least privilege
- **Common Misconfigurations**: 
  - No service account RBAC (all pods have cluster-admin)
  - Over-privileged service accounts (root access for all)
  - No service account separation (all resources in one role)
  - No least privilege (allow all verbs)
- **Example**: Service account RBAC with roles and role bindings

**Service Account RBAC Types:**
- **Roles**: 
  - Namespace-level roles
  - Resource-level roles
  - Verb-level roles
  - Least privilege

- **Role Bindings**: 
  - Namespace-level role bindings
  - Associate roles with service accounts
  - Namespace-level RBAC

- **Cluster Roles**: 
  - Cluster-wide roles
  - Resource-level cluster roles
  - Verb-level cluster roles
  - Least privilege

- **Cluster Role Bindings**: 
  - Cluster-wide role bindings
  - Associate cluster roles with service accounts
  - Cluster-level RBAC

**Best Practices:**
- Use namespace-level roles
- Use least privilege service accounts
- Use resource-level service accounts
- Use verb-level service accounts
- Regular service account RBAC audits

**Example**:
```yaml
# Service account RBAC with roles and role bindings (secure, advanced)
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secure-service-account
  namespace: secure-namespace
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-role
  namespace: secure-namespace
rules:
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-role-binding
  namespace: secure-namespace
subjects:
- kind: ServiceAccount
  name: secure-service-account
  namespace: secure-namespace
roleRef:
  kind: Role
  name: developer-role
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader-role
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: node-reader-role-binding
subjects:
- kind: ServiceAccount
  name: secure-service-account
  namespace: secure-namespace
roleRef:
  kind: ClusterRole
  name: node-reader-role
  apiGroup: rbac.authorization.k8s.io
```

**4. Service Account Security Contexts**
- **Purpose**: Provide security isolation for pods
- **Security Measures**: 
  - Pod-level security contexts
  - Container-level security contexts
  - Non-root containers
  - Drop all capabilities
  - Read-only root filesystem
  - Seccomp profiles
  - AppArmor profiles
- **Common Misconfigurations**: 
  - No security contexts (root, privileged containers)
  - No seccomp profiles (all system calls allowed)
  - No AppArmor profiles (no Linux security policies)
  - Writable root filesystem
  - Privilege escalation allowed
- **Example**: Service accounts with security contexts

**Service Account Security Context Types:**
- **Pod-Level Security Contexts**: 
  - Run as non-root user
  - Run as non-root group
  - No privilege escalation
  - Drop all capabilities
  - Read-only root filesystem
  - Seccomp profiles
  - AppArmor profiles

- **Container-Level Security Contexts**: 
  - Run as non-root user
  - Run as non-root group
  - No privilege escalation
  - Drop all capabilities
  - Read-only root filesystem
  - Seccomp profiles
  - AppArmor profiles

**Best Practices:**
- Enforce pod-level security contexts
- Enforce container-level security contexts
- Use non-root containers
- Drop all capabilities
- Use read-only root filesystem
- Use seccomp profiles
- Use AppArmor profiles

**Example**:
```yaml
# Service accounts with security contexts (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: security-context-pod
  namespace: secure-namespace
spec:
  serviceAccountName: secure-service-account
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    allowPrivilegeEscalation: false
    capabilities:
      drop: [ALL]
    readOnlyRootFilesystem: true
    seccompProfile:
      type: RuntimeDefault
    appArmorProfile:
      type: unconfined
    fsGroup: 2000
    supplementalGroups:
    - 3000
    sysctls:
    - net.ipv4.ip_unprivileged_port_start: 80
  containers:
  - name: security-context-container
    image: security-context:v1
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
      seccompProfile:
        type: RuntimeDefault
      appArmorProfile:
        type: unconfined
```
