# 02.01 - Cluster Hardening Basics

## 1️⃣ What This Topic Is

Cluster Hardening Basics examines fundamental security measures for hardening Kubernetes clusters, understanding baseline security controls, configuration best practices, and common misconfigurations.

**What this means:**
- Cluster hardening = applying security controls to reduce attack surface
- Baseline security controls before deploying workloads
- Defense in depth strategy
- Security by design and default

**The Key Concepts:**

1. **Hardening Areas**
   - Cluster infrastructure (nodes, network)
   - Control plane components (API server, etcd, scheduler, controller manager)
   - Worker node security (kubelet, container runtime, kernel)
   - Network security (CNI, policies, encryption)
   - Identity and access management (RBAC, service accounts)
   - Secrets management (encryption, rotation)

2. **Hardening Principles**
   - Defense in depth (multiple security layers)
   - Least privilege (minimum necessary access)
   - Secure by default (secure configurations)
   - Minimize attack surface (reduce exposed services)
   - Encrypt everything (data in transit and at rest)
   - Audit and monitor (detect and respond)

**Why this matters:**
- Hardening reduces attack surface
- Prevents common vulnerabilities and misconfigurations
- Provides security foundation for all workloads
- Reduces impact of security incidents

## 2️⃣ What Problem It Solves

### Problem 1: Default Cluster is Insecure

**Without cluster hardening:**
- Default cluster configurations are not secure
- All components run with maximum privileges
- No authentication or encryption enabled
- Wide attack surface for attackers

**With cluster hardening:**
- Secure default configurations
- Reduced privileges and attack surface
- Authentication and encryption enabled
- Strong security foundation

### Problem 2: Misconfigured Components

**Without cluster hardening:**
- Components misconfigured accidentally
- Vulnerable configurations go unnoticed
- Common misconfigurations exploited by attackers
- Cluster compromise

**With cluster hardening:**
- Secure configurations documented and enforced
- Automated validation of configurations
- Infrastructure as code (IaC) with security checks
- Misconfigurations prevented before deployment

### Problem 3: No Security Baseline

**Without cluster hardening:**
- No security baseline established
- Security controls not standardized
- Hard to measure security posture
- Difficult to ensure security across environments

**With cluster hardening:**
- Security baseline documented
- Security controls standardized
- Security posture measurable
- Security consistent across environments

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Insecure cluster configuration
- **Root cause**: No baseline security controls
- **Hardening issue**: Exposed Kubelet API
- **Impact**: Attacker accessed cluster resources
- **Lesson**: Establish baseline security controls

**Example: Capital One Breach (2019)**
- **Vulnerability**: Insecure worker node configuration
- **Root cause**: No node hardening
- **Hardening issue**: Vulnerable container runtime
- **Impact**: Attacker escaped container to host
- **Lesson**: Harden worker nodes and container runtime

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Insecure etcd configuration
- **Root cause**: No etcd hardening
- **Hardening issue**: Unencrypted etcd data
- **Impact**: Attacker accessed cluster state
- **Lesson**: Harden etcd with encryption

## 4️⃣ How It Works (Conceptual)

### Cluster Hardening Areas

**1. Control Plane Security**
- **Purpose**: Secure cluster management components
- **Hardening Measures**: 
  - API server authentication and authorization
  - etcd encryption and access control
  - Scheduler and controller manager security
  - Audit logging and monitoring
- **Common Misconfigurations**: 
  - Unauthenticated API access
  - Unencrypted etcd data
  - Exposed control plane ports
- **Example**: API server with no authentication

**Hardening Checklist:**
- [ ] API server authentication configured
- [ ] etcd encryption enabled
- [ ] Control plane ports restricted
- [ ] Audit logging enabled
- [ ] RBAC configured
- [ ] Network policies for control plane
- [ ] Secrets encrypted at rest

**Example**:
```yaml
# API server with authentication (secure)
apiVersion: kubeadm.k8s.io/v1beta2
kind: ClusterConfiguration
authentication:
  mode: Webhook
webhook:
  config:
    clusterInfo: /etc/kubernetes/webhook/authentication.conf
authorization:
  mode: Webhook
webhook:
  config:
    clusterInfo: /etc/kubernetes/webhook/authorization.conf
```

**2. Worker Node Security**
- **Purpose**: Secure worker nodes and containers
- **Hardening Measures**: 
  - Kubelet authentication and authorization
  - Container runtime security
  - Kernel hardening
  - File system security (read-only)
  - Security contexts (non-root, drop capabilities)
- **Common Misconfigurations**: 
  - Unauthenticated Kubelet API
  - Privileged containers
  - Vulnerable container runtime
  - Root user in containers
- **Example**: Worker node with unauthenticated Kubelet

**Hardening Checklist:**
- [ ] Kubelet authentication configured
- [ ] Kubelet authorization configured
- [ ] Container runtime updated
- [ ] Kernel updated and hardened
- [ ] File system read-only (where possible)
- [ ] Security contexts (non-root, drop capabilities)
- [ ] Pod security policies enforced
- [ ] Seccomp/AppArmor profiles configured

**Example**:
```yaml
# Kubelet with authentication (secure)
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
authentication:
  anonymous:
    enabled: false
  webhook:
    cacheTTL: 2m
    enabled: true
    timeout: 10s
authorization:
  mode: Webhook
  webhook:
    cacheAuthorizedTTL: 5m
    timeout: 10s
```

**3. Network Security**
- **Purpose**: Secure cluster network traffic
- **Hardening Measures**: 
  - Network policies (default-deny with explicit allow)
  - Container network interface (CNI) security
  - Service mesh with mTLS
  - DNS security (DNSSEC)
  - Ingress and egress controls
- **Common Misconfigurations**: 
  - No network policies (all traffic allowed)
  - Unencrypted pod-to-pod traffic
  - Exposed services (NodePort, LoadBalancer)
  - DNS without DNSSEC
- **Example**: Cluster with no network policies

**Hardening Checklist:**
- [ ] Network policies (default-deny with explicit allow)
- [ ] CNI security configured
- [ ] Service mesh with mTLS
- [ ] DNSSEC configured
- [ ] Ingress security (TLS, WAF)
- [ ] Egress controls (data exfiltration prevention)
- [ ] Encrypted pod-to-pod communication
- [ ] Encrypted control plane communication

**Example**:
```yaml
# Default-deny network policy
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```

**4. Identity and Access Management**
- **Purpose**: Secure authentication and authorization
- **Hardening Measures**: 
  - RBAC with least privilege
  - Service account token limits
  - Short-lived credentials
  - External identity providers (OIDC, SAML)
  - Audit logging
- **Common Misconfigurations**: 
  - No RBAC (cluster-admin by default)
  - Long-lived service account tokens
  - Excessive permissions
  - No audit logging
- **Example**: Cluster with no RBAC restrictions

**Hardening Checklist:**
- [ ] RBAC configured with least privilege
- [ ] Service account token limits (TTL)
- [ ] Short-lived credentials
- [ ] External identity providers configured
- [ ] MFA for administrative access
- [ ] Regular RBAC audits
- [ ] Service account token rotation

**Example**:
```yaml
# RBAC with least privilege (secure)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: production
subjects:
- kind: ServiceAccount
  name: application-sa
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**5. Secrets Management**
- **Purpose**: Secure secrets storage and access
- **Hardening Measures**: 
  - External secret management (Vault, AWS Secrets Manager)
  - Encryption at rest
  - Secret rotation
  - No secrets in code or configmaps
  - Short-lived credentials
- **Common Misconfigurations**: 
  - Secrets in configmaps (plaintext)
  - Secrets in environment variables
  - No secret rotation
  - No secret encryption
  - Secrets in source code
- **Example**: Secrets stored in configmaps (plaintext)

**Hardening Checklist:**
- [ ] External secret management (Vault, etc.)
- [ ] Secrets encrypted at rest
- [ ] Secret rotation automated
- [ ] No secrets in code
- [ ] No secrets in configmaps
- [ ] No secrets in environment variables
- [ ] Short-lived credentials
- [ ] Secret access audit logging

**Example**:
```yaml
# External secret (secure)
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: database-credentials
  namespace: production
spec:
  refreshInterval: 1h
  secretStoreRef:
    kind: SecretStore
    name: aws-secrets-manager
  target:
    name: /prod/database/url
    template:
      type: Opaque
      data:
        DATABASE_URL: "{{ .database_url }}"
        DATABASE_PASSWORD: "{{ .database_password }}"
```

### Hardening Principles

**1. Defense in Depth**
- Multiple security layers
- No single point of failure
- Reduces attack surface
- Provides multiple opportunities to detect attack

**2. Least Privilege**
- Minimum necessary access
- Reduces blast radius
- Limits damage from compromise
- Prevents privilege escalation

**3. Secure by Default**
- Secure configurations by default
- No insecure defaults
- Requires explicit insecure choices
- Reduces misconfigurations

**4. Minimize Attack Surface**
- Reduce exposed services
- Restrict network access
- Reduce privileges
- Limit data access

**5. Encrypt Everything**
- Encrypt data in transit (TLS, mTLS)
- Encrypt data at rest
- Encrypt secrets
- Encrypt storage

**6. Audit and Monitor**
- Log all security events
- Monitor for anomalies
- Detect and respond to incidents
- Continuous improvement

### **Common Mistakes in Cluster Hardening**

❌ **Mistake 1**: Not applying security baseline
- Reality: Default cluster is insecure
- Fix: Apply security baseline before deploying workloads

❌ **Mistake 2**: No network policies
- Reality: All pod-to-pod traffic is allowed
- Fix: Implement default-deny with explicit allow

❌ **Mistake 3**: No RBAC
- Reality: Anyone can access all cluster resources
- Fix: Implement RBAC with least privilege

❌ **Mistake 4**: No secret encryption
- Reality: Secrets stored in plaintext
- Fix: Use external secret management, encrypt at rest

- Use service account token limits

- Regular RBAC audits

- Encrypt data in transit (TLS, mTLS)
- Encrypt data at rest (Vault, etc.)
- Encrypt secrets
- Encrypt storage

**4. Implement Network Policies**
- Default-deny with explicit allow
- Restrict pod-to-pod communication
- Restrict egress traffic
- Implement service mesh with mTLS

**5. Use External Secret Management**
- Use Vault, AWS Secrets Manager, etc.
- Encrypt secrets at rest
- Rotate secrets regularly
- No secrets in code

**6. Conduct Regular Security Reviews**
- Review cluster configurations
- Review RBAC regularly
- Review network policies regularly
- Conduct penetration testing

**7. Monitor and Alert**
- Monitor for security events
- Set up alerts for suspicious activity
- Implement automated response
- Continuous monitoring

### **Don'ts ❌**

**1. Don't Skip Security Baseline**
- Default cluster is insecure
- Always apply security baseline

**2. Don't Skip Network Policies**
- All pod-to-pod traffic is allowed
- Always implement default-deny with explicit allow

**3. Don't Skip RBAC**
- Anyone can access all cluster resources
- Always implement RBAC with least privilege
