# 01.06 - Denial of Service Attacks

## 1️⃣ What This Topic Is

Denial of Service (DoS) Attacks examines how attackers disrupt Kubernetes services and availability, understanding DoS vectors, detection techniques, and mitigation strategies.

**What this means:**
- DoS = disrupting service availability
- Attacker wants to make services unavailable
- Multiple DoS vectors in Kubernetes
- Understanding DoS helps design resilient architectures

**The Key Concepts:**

1. **DoS Types**
   - Volumetric attacks (flood resources)
   - Resource exhaustion attacks
   - Protocol attacks (exploit protocols)
   - Application-layer attacks (exploit applications)
   - Distributed attacks (multiple sources)

2. **DoS Vectors**
   - CPU exhaustion (cryptojacking)
   - Memory exhaustion (OOM kills)
   - Network flooding (SYN floods, UDP floods)
   - Storage exhaustion (disk fills up)
   - API server overload (request floods)

**Why this matters:**
- DoS causes service disruption
- DoS causes customer impact
- DoS causes revenue loss
- DoS causes reputation damage

## 4️⃣ How It Works (Conceptual)

### DoS Attack Vectors

**1. Volumetric DoS**
- **Purpose**: Overwhelm services with traffic
- **Attacker Use**: Botnets to flood network
- **Detection Challenge**: Legitimate traffic looks like attack
- **Example**: HTTP request flood to API server

**Attack Flow:**
```
Attacker uses botnet → Floods API server with HTTP requests → API server overwhelmed → Services unavailable → DoS successful
```

**Detection:**
- Monitor for unusual request rates
- Monitor for suspicious source IPs
- Monitor for unusual request patterns
- Implement rate limiting

**Mitigation:**
- Rate limiting at API server
- DDoS protection services (Cloudflare, AWS Shield, etc.)
- CDN to absorb traffic
- Autoscaling to handle load
- Network policies to block attack traffic

**Example**:
```bash
# Attacker floods API server
for i in {1..100000}; do
  curl -X GET https://api.cluster.com/api/v1/pods
done
```

**2. Resource Exhaustion DoS (CPU/Memory)**
- **Purpose**: Consume all cluster resources
- **Attacker Use**: Deploy miners or resource-intensive workloads
- **Detection Challenge**: Legitimate workloads also use resources
- **Example**: Cryptojacking across entire cluster

**Attack Flow:**
```
Attacker deploys DaemonSet with miners → Scheduler schedules to all nodes → Kubelet creates pods on each node → Miners consume all CPU/Memory → Legitimate workloads starved → Cluster unavailable → DoS successful
```

**Detection:**
- Monitor for unusual resource usage (100% CPU)
- Monitor for new DaemonSets
- Monitor for new pods with high resource requests
- Monitor for connections to mining pools

**Mitigation:**
- Resource quotas (prevent resource consumption)
- Resource limits (cap pod resources)
- Monitoring and alerting
- Network policies (block connections to mining pools)
- Admission controllers (validate resource requests)

**Example**:
```yaml
# DaemonSet with miner
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: crypto-miner
spec:
  selector:
    matchLabels:
      name: miner
  template:
    metadata:
      labels:
        name: miner-pod
    spec:
      containers:
      - name: miner
        image: xmrminer/xmrig:latest
        resources:
          limits:
            cpu: "4"  # High CPU usage
            memory: "8Gi"  # High memory usage
```

**3. Network DoS**
- **Purpose**: Overwhelm network infrastructure
- **Attacker Use**: Botnets to flood network with packets
- **Detection Challenge**: Distinguish attack from legitimate traffic
- **Example**: SYN flood to nodes, DNS amplification attacks

**Attack Flow:**
```
Attacker uses botnet → Floods network with SYN packets → Node network overwhelmed → Services unavailable → DoS successful
```

**Detection:**
- Monitor for unusual network traffic
- Monitor for unusual packet rates
- Monitor for suspicious source IPs
- Implement network policies

**Mitigation:**
- DDoS protection services (AWS Shield, Azure DDoS, etc.)
- Network policies to block attack traffic
- Rate limiting at network level
- CDN to absorb traffic

**Example**:
```bash
# Attacker floods node with SYN packets
for i in {1..1000000}; do
  hping3 -S -p 80 -i u1000 --rand-source --flood node.cluster.com
done
```

**4. Storage DoS**
- **Purpose**: Fill up cluster storage
- **Attacker Use**: Deploy workloads that consume storage
- **Detection Challenge**: Legitimate workloads also use storage
- **Example**: Deploying workloads that fill up etcd or PV

**Attack Flow:**
```
Attacker deploys storage-consuming workloads → Kubelet creates pods → Pods consume all storage → etcd or PV fills up → New pods can't be scheduled → Services unavailable → DoS successful
```

**Detection:**
- Monitor for unusual storage usage
- Monitor for new PVs consuming space
- Monitor for etcd growth
- Alert on storage exhaustion

**Mitigation:**
- Storage quotas (limit PV size)
- Monitor storage usage
- Set up alerts on storage usage
- Implement cleanup policies

**Example**:
```yaml
# Pod that consumes storage
apiVersion: v1
kind: Pod
metadata:
  name: storage-doer
spec:
  containers:
  - name: filler
    image: busybox:1.36
    command:
    - /bin/sh
    - -c
    - "dd if=/dev/zero of=/data/largefile bs=1M count=10240"
    volumeMounts:
    - name: storage-volume
        mountPath: /data
  volumes:
  - name: storage-volume
    persistentVolumeClaim:
      claimName: large-pvc
```

**5. Application Layer DoS**
- **Purpose**: Exploit application vulnerabilities
- **Attacker Use**: Slowloris attacks, HTTP floods
- **Detection Challenge**: Attacks look like legitimate requests
- **Example**: Slow HTTP requests to web server

**Attack Flow:**
```
Attacker sends slow HTTP requests → Application server overwhelmed → Services unavailable → DoS successful
```

**Detection:**
- Monitor for unusual request patterns
- Monitor for slow HTTP connections
- Monitor for request queue length
- Monitor for connection timeout patterns

**Mitigation:**
- Rate limiting at application level
- Connection timeouts
- Request queue limits
- WAF (Web Application Firewall)
- CDN to absorb traffic

**Example**:
```bash
# Attacker sends slow HTTP requests
for i in {1..1000}; do
  curl -X GET -H "Connection: keep-alive" http://webserver.cluster.com/api/slow &
  sleep 10  # Slow request
done
```

**6. API Server DoS**
- **Purpose**: Overwhelm API server
- **Attacker Use**: Flood API server with requests
- **Detection Challenge**: Distinguish attack from legitimate requests
- **Example**: Creating thousands of pods rapidly

**Attack Flow:**
```
Attacker floods API server with create pod requests → API server overwhelmed → API server unavailable → Services unavailable → DoS successful
```

**Detection:**
- Monitor for unusual request rates to API server
- Monitor for suspicious source IPs
- Monitor for unusual object creation rates
- Implement rate limiting

**Mitigation:**
- Rate limiting at API server
- Admission controllers to validate requests
- Resource quotas to limit object creation
- Autoscaling of API server
- Audit logging

**Example**:
```bash
# Attacker floods API server with pod creation requests
for i in {1..10000}; do
  kubectl run malicious-$i --image=nginx --rm --restart=Never
done
```

### DoS Detection Techniques

**1. Behavioral Monitoring**
- Monitor for unusual request rates
- Detect anomalies in resource usage
- Identify unusual network traffic
- Track suspicious source IPs

**2. Resource Monitoring**
- Monitor CPU/memory usage
- Detect resource exhaustion (crypto mining)
- Monitor storage usage
- Alert on unusual patterns

**3. Network Monitoring**
- Monitor for network attacks
- Detect SYN floods, DNS amplification
- Monitor for unusual traffic patterns
- Implement DDoS detection

**4. Application Monitoring**
- Monitor for slow HTTP requests
- Detect request queue length
- Monitor for unusual connection patterns
- Implement application-level DoS detection

**5. API Monitoring**
- Monitor for unusual API request rates
- Detect object creation attacks
- Monitor for suspicious API calls
- Implement API-level DoS detection

### **Common Mistakes in DoS Detection/Mitigation**

❌ **Mistake 1**: Not implementing resource quotas
- Reality: Without quotas, workloads can consume all resources
- Fix: Implement resource quotas per namespace

❌ **Mistake 2**: Not implementing resource limits
- Reality: Without limits, pods can consume unlimited resources
- Fix: Implement resource limits on all pods

❌ **Mistake 3**: Not monitoring resource usage
- Reality: Can't detect resource exhaustion attacks
- Fix: Monitor CPU/memory/storage usage

❌ **Mistake 4**: Not using DDoS protection services
- Reality: Volumetric attacks require DDoS protection
- Fix: Use DDoS protection services for public-facing services

#!/bin/bash
echo "Starting DoS detection..."

while true; do
  # Monitor for resource exhaustion
  for node in $(kubectl get nodes -o name); do
    cpu=$(kubectl top node $node 2>/dev/null | grep -m1 "CPU%" | awk '{print $2}')
    if [ "${cpu%}" -gt 90 ]; then
      echo "[$(date)] ALERT: Resource exhaustion detected on node $node: CPU ${cpu}%"
    fi
  done
  
  # Monitor for storage exhaustion
  for ns in $(kubectl get ns -o name); do
    storage_used=$(kubectl get pvc -n $ns -o jsonpath='{.items[*].status.capacity.storage}')
    if [ -n "$storage_used" ]; then
      storage_used_mb=$((storage_used / 1024 / 1024))
      if [ "$storage_used_mb" -gt 102400 ]; then  # 100GB threshold
        echo "[$(date)] ALERT: Storage exhaustion detected in namespace $ns: ${storage_used_mb}MB"
      fi
    fi
  done
  
  sleep 60
done
EOF

## 8️⃣ Security Best Practices

### **Do's ✅**

**1. Implement Resource Quotas**
- Limit CPU, memory, storage per namespace
- Prevent resource exhaustion
- Ensure fair resource allocation

**2. Implement Resource Limits**
- Cap CPU, memory, storage for pods
- Prevent runaway workloads
- Ensure Quality of Service

**3. Monitor Resource Usage**
- Monitor CPU/memory/storage usage
- Detect unusual consumption patterns
- Set up alerts for thresholds

**4. Implement Autoscaling**
- Horizontal Pod Autoscaler (HPA) for pods
- Cluster Autoscaler for nodes
- Absorb load during DoS
- Scale down when DoS ends

**5. Use DDoS Protection Services**
- For public-facing services
- Use CDN to absorb traffic
- Implement rate limiting
- Use DDoS protection (Cloudflare, AWS Shield, etc.)

**6. Implement Network Policies**
- Default-deny with explicit allow
- Limit pod-to-pod communication
- Reduce attack surface
- Implement segmentation

**7. Use Admission Controllers**
- Validate resource requests
- Implement image scanning
- Implement security policies

### **Don'ts ❌**

**1. Don't Allow Unlimited Resources**
- Without quotas, workloads can consume all resources
- Implement resource quotas per namespace

**2. Don't Run Without Resource Limits**
- Without limits, pods can consume unlimited resources
- Implement resource limits on all pods

**3. Don't Skip Monitoring**
- Can't detect DoS without monitoring
- Implement comprehensive monitoring

**4. Don't Ignore DDoS Protection**
- Public-facing services need DDoS protection
- Implement DDoS protection services

### **Common Interview Questions**

**Q1: What are common DoS vectors in Kubernetes?**
**Good Answer**: Common DoS vectors in Kubernetes include:

1. **Resource Exhaustion**: 
   - CPU exhaustion (crypto mining)
   - Memory exhaustion (OOM kills)
   - Storage exhaustion (disk fills up)
   - Attackers consume all cluster resources, starve legitimate workloads

2. **Network DoS**: 
   - SYN floods, UDP floods
   - DNS amplification
   - Attackers flood network infrastructure

3. **Volumetric DoS**: 
   - HTTP request floods
   - UDP floods
   - Attackers overwhelm services with traffic

4. **API Server DoS**: 
   - Request floods
   - Object creation attacks
   - Attackers overwhelm API server

5. **Storage DoS**: 
   - Fill up cluster storage
   - Attackers prevent new pods from being scheduled

Each vector causes service disruption and customer impact.

**Q2: How do you detect DoS in Kubernetes?**
**Good Answer**: DoS detection in Kubernetes includes:

1. **Resource Monitoring**: Detect resource exhaustion
   - Monitor CPU usage (detect crypto mining)
   - Monitor memory usage (detect OOM)
   - Monitor storage usage (detect disk fills)

2. **Network Monitoring**: Detect network attacks
   - Monitor for unusual traffic patterns
   - Detect SYN floods, DNS amplification
   - Implement DDoS detection

3. **API Monitoring**: Detect API server attacks
   - Monitor for unusual request rates
   - Detect unusual API call patterns
   - Monitor for object creation attacks

4. **Behavioral Monitoring**: Detect anomalies
   - Unusual resource usage patterns
   - Unusual network patterns
   - Unusual API call patterns

Detection tools: Prometheus, Grafana, Falco, network monitoring tools, DDoS protection services.

**Q3: How do you mitigate DoS in Kubernetes?**
**Good Answer**: DoS mitigation in Kubernetes includes:

1. **Resource Quotas**: Limit resource consumption
   - Limit CPU, memory, storage per namespace
   - Prevent resource exhaustion
   - Ensure fair allocation

2. **Resource Limits**: Cap pod resources
   - Prevent runaway workloads
   - Ensure Quality of Service
   - Prevent resource overconsumption

3. **Autoscaling**: Absorb load during DoS
   - Horizontal Pod Autoscaler (HPA) for pods
   - Cluster Autoscaler for nodes
   - Scale during DoS, save costs after

4. **DDoS Protection**: Protect against volumetric attacks
   - Use DDoS protection services
   - Implement CDN
   - Implement rate limiting

5. **Network Policies**: Reduce attack surface
   - Default-deny with explicit allow
   - Segment network traffic
   - Implement DDoS protection

6. **Admission Controllers**: Validate requests
   - Validate resource requests
   - Implement image scanning
   - Implement security policies

7. **Monitoring and Alerting**: Detect and respond
   - Monitor for DoS attacks
   - Set up alerts
   - Implement automated response

Combined approach provides defense in depth against DoS attacks.

**Q4: What's the most dangerous DoS vector in Kubernetes?**
**Good Answer**: The most dangerous DoS vectors are:

1. **Resource Exhaustion (Crypto Mining)**: Because it's invisible
   - Attackers consume resources without external traffic
   - Internal attack, hard to detect
   - Causes service disruption and cost impact

2. **Network DoS (DDoS)**: Because it's hard to mitigate
   - Volumetric attacks are common
   - Require specialized DDoS protection
   - Can be massive (botnets)

3. **API Server DoS**: Because it's central
   - API server is central to cluster
   - Can affect all workloads
   - Can cause cluster-wide disruption

Resource exhaustion (crypto mining) is most dangerous because it's internal and invisible. Network DoS is most dangerous because it's massive and hard to mitigate. API server DoS is most dangerous because it's central and affects all workloads.

**Q5: How does autoscaling help with DoS?**
**Good Answer**: Autoscaling helps with DoS by:

1. **Absorbs Load**: Scales services to handle attack traffic
   - Horizontal Pod Autoscaler (HPA) scales pods
   - Cluster Autoscaler scales nodes
   - Services remain available during DoS

2. **Scales During Attack**: Responds to increased load
   - Automatically adds resources during DoS
   - Maintains service availability

3. **Scales Down After Attack**: Saves costs when load decreases
   - Automatically removes resources after DoS ends
   - Optimizes resource usage

4. **Resilience**: Improves overall resilience
   - Services can handle variable load
   - Reduces customer impact
   - Improves uptime

Autoscaling is critical for DoS protection because it ensures services remain available during attack and saves costs when attack ends.
