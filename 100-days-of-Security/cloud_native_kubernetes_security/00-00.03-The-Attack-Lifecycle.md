# 00.03 - The Attack Lifecycle

## 1️⃣ What This Topic Is

The attack lifecycle (also known as the **cyber kill chain**) is a framework that describes the stages attackers go through when executing an attack. Understanding this lifecycle helps you detect, disrupt, and respond to attacks at every stage.

**What this means:**
- Attacks are not random—they follow a predictable sequence
- Each stage has specific objectives and techniques
- By understanding the stages, you can detect attacks earlier
- You can disrupt attacks at any stage, not just at the end
- Different security controls target different stages

**Why it matters:**
- You can't defend against what you don't understand
- Knowing the attack lifecycle helps with early detection
- You can implement targeted defenses for each stage
- Incident response becomes more effective
- You can anticipate attacker movements

**The 7 Stages of the Attack Lifecycle:**

1. **Reconnaissance** - Gathering information about the target
2. **Delivery & Exploitation** - Gaining initial access
3. **Establish Persistence** - Maintaining access over time
4. **Privilege Escalation** - Gaining higher permissions
5. **Lateral Movement** - Moving to other systems
6. **Collection & Exfiltration** - Stealing valuable data
7. **Command & Control** - Remote control and maintenance

**Real-world analogy:**
Think of it like a burglar breaking into a house:
1. **Reconnaissance**: Casing the neighborhood, finding an empty house
2. **Delivery**: Breaking a window or picking a lock
3. **Persistence**: Leaving a door unlocked for future access
4. **Privilege Escalation**: Finding the safe with valuables
5. **Lateral Movement**: Moving to other rooms in the house
6. **Collection**: Stealing jewelry, cash, and documents
7. **C2**: Using a hidden camera to monitor the house remotely

## 2️⃣ What Problem It Solves

### Problem 1: Reactive Security

**Without understanding the attack lifecycle:**
- You only respond after damage is done
- You can't detect attacks in early stages
- Incident response is slow and ineffective
- Attackers have time to complete their objectives

**With attack lifecycle understanding:**
- You can detect attacks early (during reconnaissance)
- You can disrupt attacks before they cause damage
- You can predict attacker movements
- You can respond quickly and effectively

### Problem 2: Misplaced Security Controls

**Without understanding the attack lifecycle:**
- You might focus all controls on one stage
- Other stages remain vulnerable
- Attackers can bypass your defenses
- You waste resources on ineffective controls

**With attack lifecycle understanding:**
- You implement controls for every stage
- Multiple layers of defense (defense in depth)
- Attackers must bypass many controls
- Resources are allocated effectively

### Problem 3: Blind Spots

**Without understanding the attack lifecycle:**
- You don't know what to monitor for
- You miss indicators of compromise (IOCs)
- You can't detect attack patterns
- You're reactive instead of proactive

**With attack lifecycle understanding:**
- You know what to look for at each stage
- You set up detection for specific IOCs
- You recognize attack patterns
- You're proactive in detecting threats

### Real-World Impact

**Example: Detecting a Kubernetes Attack Early**

**Without attack lifecycle knowledge:**
- Attacker scans for exposed API server (reconnaissance) → Undetected
- Attacker exploits weak authentication (exploitation) → Undetected
- Attacker creates backdoor pod (persistence) → Undetected
- Attacker escalates privileges via RBAC (privilege escalation) → Undetected
- Attacker exfiltrates secrets (exfiltration) → Data breach detected (too late!)

**With attack lifecycle knowledge:**
- Attacker scans for exposed API server (reconnaissance) → **DETECTED** by monitoring
- Alert: "Unusual port scanning activity from external IP"
- Response: Block IP, review logs, strengthen authentication

**Result**: Attack disrupted at stage 1, no damage occurred

### Attack Lifecycle in Kubernetes: Example Scenario

Let's walk through a realistic Kubernetes attack:

**Stage 1: Reconnaissance**
```
Attacker: Scans for exposed Kubernetes API servers
Tool: Shodan search: "kubernetes" port 6443
Found: api.example.com:6443 (exposed to internet)
Next: Try to authenticate
```

**Stage 2: Delivery & Exploitation**
```
Attacker: Tries default credentials
Attempt: admin/admin (failed)
Attempt: kubernetes-admin (failed)
Found: Leaked API token in GitHub repository
Success: Authenticated to API server
Access: Can list pods, deployments, secrets
```

**Stage 3: Establish Persistence**
```
Attacker: Creates backdoor pod
Deployment: Creates "system-updater" pod
Scheduled: CronJob runs every hour
Looks legitimate: Named like system component
Objective: Maintain access even if token is rotated
```

**Stage 4: Privilege Escalation**
```
Attacker: Examines RBAC permissions
Found: Service account has "secrets" resource access
Action: Lists all secrets
Found: Database credentials, API keys
Action: Attempts to create privileged pods
Result: Can now access host filesystem
```

**Stage 5: Lateral Movement**
```
Attacker: Moves to other namespaces
Access: Uses service account to list all namespaces
Found: "production" namespace with sensitive data
Action: Moves to production namespace
Access: Production database, customer data
```

**Stage 6: Collection & Exfiltration**
```
Attacker: Accesses production database
Connection: Uses stolen database credentials
Action: Exports customer records
Transfer: Sends data to attacker's server
Size: 100,000 customer records (PII)
Impact: Data breach
```

**Stage 7: Command & Control**
```
Attacker: Maintains access
Method: CronJob executes commands from C2 server
Objective: Can issue new commands anytime
Capability: Update malware, access new data
Persistence: Hard to detect in normal traffic
```

### Disrupting the Attack Lifecycle

**You can disrupt attacks at ANY stage:**

**At Stage 1 (Reconnaissance):**
- Don't expose API server to internet
- Monitor and block scanning activity
- Detect and alert on reconnaissance attempts
- **Result**: Attackers can't find entry point

**At Stage 2 (Exploitation):**
- Use strong authentication (OIDC, certificates)
- Implement MFA
- Scan for leaked credentials
- **Result**: Attackers can't gain initial access

**At Stage 3 (Persistence):**
- Monitor for new resources
- Implement admission controllers
- Use immutable infrastructure
- **Result**: Attackers can't maintain access

**At Stage 4 (Privilege Escalation):**
- Implement least privilege RBAC
- Use security contexts
- Avoid privileged containers
- **Result**: Attackers can't gain more permissions

**At Stage 5 (Lateral Movement):**
- Implement network policies
- Segment namespaces
- Use service mesh
- **Result**: Attackers can't move around

**At Stage 6 (Exfiltration):**
- Encrypt secrets at rest
- Monitor data access
- Implement DLP
- **Result**: Attackers can't steal data

**At Stage 7 (C2):**
- Monitor network traffic
- Detect C2 beacons
- Use egress filtering
- **Result**: Attackers can't maintain control

## 6️⃣ Where It Should Be Applied (With Example)

The attack lifecycle should be applied **everywhere** in security operations.

### **1. Setting Up Security Monitoring**

**Objective**: Detect attacks at each stage

```yaml
# Example: Monitoring for Stage 1 (Reconnaissance)
# Using a simple pod to monitor API access

apiVersion: v1
kind: Pod
metadata:
  name: audit-monitor
  namespace: monitoring
spec:
  containers:
  - name: monitor
    image: alpine:3.18
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: audit-log
      mountPath: /var/log/kubernetes
      readOnly: true
  volumes:
  - name: audit-log
    hostPath:
      path: /var/log/kubernetes
```

### **2. Implementing Controls per Stage**

**Stage 1 Controls (Reconnaissance)**
```yaml
# Don't expose API server
apiVersion: v1
kind: Service
metadata:
  name: kubernetes
  namespace: default
spec:
  type: ClusterIP  # Not LoadBalancer or NodePort
  ports:
  - port: 443
```

**Stage 2 Controls (Exploitation)**
```yaml
# Use OIDC authentication
apiVersion: v1
kind: ConfigMap
metadata:
  name: oidc-config
  namespace: kube-system
data:
  oidc-issuer-url: "https://auth.example.com"
  oidc-client-id: "kubernetes"
  oidc-username-claim: "email"
  oidc-groups-claim: "groups"
```

**Stage 3 Controls (Persistence)**
```yaml
# Use admission controller to prevent malicious pods
apiVersion: v1
kind: Pod
metadata:
  name: admission-controller
  namespace: kube-system
spec:
  containers:
  - name: admission-webhook
    image: admission-controller:latest
    args:
    - --webhook-server-port=8443
    - --deny-privileged-pods
    - --validate-service-accounts
```

**Stage 4 Controls (Privilege Escalation)**
```yaml
# Implement least privilege RBAC
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-role
  namespace: production
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update"]
# NO access to secrets, pods, or cluster-level resources
```

**Stage 5 Controls (Lateral Movement)**
```yaml
# Implement network policies
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-cross-namespace
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: production
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: production
```

### **3. Detecting Attack Stages**

**Detecting Stage 1: Reconnaissance**
```bash
# Monitor for unusual API access patterns
kubectl auth can-i list pods --all-namespaces

# Check audit logs for scanning
kubectl get events --sort-by='.lastTimestamp' | grep -i "unauthorized"

# Monitor for failed authentication attempts
kubectl logs -n kube-system kube-apiserver | grep "Unauthorized"
```

**Detecting Stage 2: Exploitation**
```bash
# Check for new pods created by unknown users
kubectl get pods --all-namespaces -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.annotations.kubernetes\.io/created-by}{"\n"}{end}'

# Monitor for unusual authentication successes
kubectl logs -n kube-system kube-apiserver | grep "authentication succeeded"

# Check for compromised pods (running as root)
kubectl get pods --all-namespaces -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.securityContext.runAsUser}{"\n"}{end}' | grep "0"
```

**Detecting Stage 3: Persistence**
```bash
# Check for new CronJobs
kubectl get cronjobs --all-namespaces --sort-by='.metadata.creationTimestamp'

# Check for new service accounts
kubectl get serviceaccounts --all-namespaces --sort-by='.metadata.creationTimestamp'

# Monitor for modifications to existing resources
kubectl get pods --all-namespaces -o json | jq '.items[] | select(.metadata.uid != .metadata.annotations["kubernetes.io/creator-uid"])'
```

**Detecting Stage 4: Privilege Escalation**
```bash
# Check for privileged containers
kubectl get pods --all-namespaces -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].securityContext.privileged}{"\n"}{end}' | grep "true"

# Check for service accounts with excessive permissions
kubectl get clusterrolebindings --all-namespaces -o json | jq '.items[] | select(.subjects[].kind == "ServiceAccount")'

# Monitor for unusual API access patterns
kubectl logs -n kube-system kube-apiserver | grep "get.*secrets"
```

**Detecting Stage 5: Lateral Movement**
```bash
# Check for cross-namespace access
kubectl get networkpolicies --all-namespaces

# Monitor for unusual network traffic
kubectl logs -n kube-system kube-proxy | grep ".*"

# Check for pods accessing unexpected namespaces
kubectl logs -n kube-system kube-apiserver | grep "list.*namespaces"
```

**Detecting Stage 6: Exfiltration**
```bash
# Monitor for secret access
kubectl logs -n kube-system kube-apiserver | grep "get.*secrets"

# Check for large data transfers
kubectl top pods --all-namespaces

# Monitor for database access
kubectl logs -n production application-pod | grep "SELECT.*FROM.*customers"
```

**Detecting Stage 7: C2**
```bash
# Monitor for scheduled network communication
kubectl logs -n kube-system kube-proxy | grep "periodic.*connection"

# Check for DNS queries to unusual domains
kubectl logs -n kube-system coredns | grep "NXDOMAIN"

# Monitor for regular beaconing patterns
kubectl logs -n suspicious-pod | grep "curl.*http://"
```

### **Common Mistakes in Applying Attack Lifecycle Knowledge**

❌ **Mistake 1**: Only monitoring for exploitation
- Reality: Early detection (reconnaissance) prevents attacks
- Fix: Monitor all stages, not just exploitation

❌ **Mistake 2**: Assuming attacks are random
- Reality: Attacks follow predictable patterns
- Fix: Learn and recognize attack patterns

❌ **Mistake 3**: Only defending at the perimeter
- Reality: Attackers can bypass perimeter
- Fix: Defend at every stage

❌ **Mistake 4**: Ignoring persistence mechanisms
- Reality: Attackers will try to maintain access
- Fix: Monitor for new resources and modifications

- **What happened**: Attacker gained initial access via service account
- **Detection indicators**: Successful authentication, new pod creation
- **Defenses**: Strong authentication, least privilege RBAC

**Stage 3: Persistence**
- **What happened**: Attacker created backdoor pod and CronJob
- **Detection indicators**: New unexpected resources, CronJobs
- **Defenses**: Monitor for new resources, admission controllers

**Stage 4: Privilege Escalation**
- **What happened**: Attacker attempted to gain more permissions
- **Detection indicators**: Privilege escalation attempts, unusual RBAC usage
- **Defenses**: Least privilege, security contexts, pod security admission

**Stage 5: Lateral Movement**
- **What happened**: Attacker tried to access other namespaces
- **Detection indicators**: Cross-namespace access attempts
- **Defenses**: Network policies, namespace isolation

**Stage 6: Collection & Exfiltration**
- **What happened**: Attacker accessed and decoded database credentials
- **Detection indicators**: Secret access, unusual data transfers
- **Defenses**: Encrypt secrets, monitor data access, DLP

- **What happened**: Not observed in this simulation

3. **Early detection prevents damage**: Disrupting at Stage 1 is better than Stage 6
4. **Multiple defense layers**: Controls at each stage provide redundancy
5. **Persistence is dangerous**: Attackers maintain access through backdoors
6. **Privilege escalation is common**: Attackers always seek more permissions

### **Common Interview Questions**

**Q1: What is the attack lifecycle, and why is it important?**
**Good Answer**: The attack lifecycle (cyber kill chain) describes the predictable sequence of stages attackers go through: Reconnaissance (gathering information), Delivery & Exploitation (gaining access), Persistence (maintaining access), Privilege Escalation (gaining more permissions), Lateral Movement (moving to other systems), Collection & Exfiltration (stealing data), and Command & Control (remote control). It's important because understanding these stages helps you detect attacks early, implement targeted defenses for each stage, disrupt attacks before they cause damage, and predict attacker movements. Instead of reacting to breaches, you can proactively prevent them.

**Q2: How does the attack lifecycle apply to Kubernetes?**
**Good Answer**: In Kubernetes, the attack lifecycle looks like:
1. **Reconnaissance**: Scanning for exposed API servers, enumerating namespaces, searching for leaked credentials
2. **Exploitation**: Exploiting weak authentication, using stolen tokens, misconfiguration exploits
3. **Persistence**: Creating backdoor pods, scheduling CronJobs, adding service accounts
4. **Privilege Escalation**: Exploiting RBAC misconfigurations, using privileged containers, accessing secrets
5. **Lateral Movement**: Moving between namespaces, accessing other pods, pivoting through services
6. **Exfiltration**: Stealing secrets, accessing databases, exfiltrating data
7. **C2**: Establishing remote control through CronJobs or network connections

Each stage has specific Kubernetes-specific indicators and defenses.

**Q3: At which stage should you detect an attack?**
**Good Answer**: You should detect attacks as early as possible—ideally during reconnaissance (Stage 1). However, you should implement detection capabilities for every stage because:
- **Stage 1 detection**: Prevents the attack entirely
- **Stage 2 detection**: Prevents initial access
- **Stage 3 detection**: Prevents persistence
- **Stage 4 detection**: Limits damage from privilege escalation
- **Stage 5 detection**: Prevents lateral movement
- **Stage 6 detection**: Prevents data loss
- **Stage 7 detection**: Disrupts attacker control

The earlier you detect, the less damage occurs. But you need defense in depth—controls at every stage—because attackers may bypass early detection.

**Q4: What are the detection indicators for each attack stage?**
**Good Answer**: Detection indicators include:
- **Stage 1 (Reconnaissance)**: Unusual port scanning, high rate of API requests, access from unusual geolocations, failed authentication attempts
- **Stage 2 (Exploitation)**: Successful exploitation attempts, unusual authentication successes, new unknown processes, suspicious file access
- **Stage 3 (Persistence)**: New unexpected pods/services, modified resource configurations, unusual CronJobs, new service accounts
- **Stage 4 (Privilege Escalation)**: Unusual API access patterns, access to sensitive resources, privileged container usage, RBAC violations
- **Stage 5 (Lateral Movement)**: Unusual network traffic, access from unexpected namespaces, cross-namespace API calls, suspicious service communication
- **Stage 6 (Exfiltration)**: Unusual data access, large data transfers, access to sensitive resources, secret access attempts
- **Stage 7 (C2)**: Regular C2 beaconing, unusual DNS queries, encrypted traffic patterns, connections to unknown external IPs

**Q5: How can you disrupt attacks at each stage of the lifecycle?**
**Good Answer**: You can disrupt attacks at every stage:
- **Stage 1**: Don't expose services, monitor and block scanning, detect reconnaissance attempts
- **Stage 2**: Use strong authentication (OIDC, certificates), implement MFA, scan for leaked credentials
- **Stage 3**: Monitor for new resources, implement admission controllers, use immutable infrastructure
- **Stage 4**: Implement least privilege RBAC, use security contexts, avoid privileged containers
- **Stage 5**: Implement network policies, segment namespaces, use service mesh, limit pod-to-pod communication
- **Stage 6**: Encrypt secrets at rest, encrypt data in transit, monitor data access, implement DLP
- **Stage 7**: Monitor network traffic, detect C2 beacons, use egress filtering, implement anomaly detection
