# 02.02 - API Server Security

## 1️⃣ What This Topic Is

API Server Security examines security measures for securing Kubernetes API server, understanding authentication, authorization, and security configurations.

**What this means:**
- API server = cluster control plane component
- Handles all cluster API requests
- Authentication and authorization critical
- Security configurations essential

**The Key Concepts:**

1. **API Server Components**
   - Authentication (who you are)
   - Authorization (what you can do)
   - Admission control (validating requests)
   - API server configuration
   - Encryption (TLS, API server encryption)

2. **Security Areas**
   - Authentication mechanisms (OIDC, certificates, tokens)
   - Authorization (RBAC)
   - Admission controllers (validating, mutating)
   - Encryption (TLS, encryption at rest)
   - Rate limiting and auditing

**Why this matters:**
- API server controls entire cluster
- API server compromise = cluster compromise
- All cluster operations go through API server
- API server is primary attack target

---

## 2️⃣ What Problem It Solves

### Problem 1: Unauthenticated API Access

**Without API server security:**
- Anyone can access API server
- Unauthorized cluster access
- Attacker can control cluster
- Data theft and service disruption

**With API server security:**
- Authentication required
- Only authenticated users can access
- Unauthorized access prevented
- Cluster protected

### Problem 2: Over-Privileged Authorization

**Without API server security:**
- Default permissions are too broad
- Users have excessive access
- Attacker can escalate privileges
- Cluster-wide compromise

**With API server security:**
- RBAC with least privilege
- Only necessary permissions granted
- Privilege escalation prevented
- Damage limited

### Problem 3: No Request Validation

**Without API server security:**
- Malicious requests accepted
- Attacker can exploit vulnerabilities
- Invalid objects created
- Cluster compromise

**With API server security:**
- Admission controllers validate requests
- Malicious requests rejected
- Objects validated before creation
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Unauthenticated API access
- **Root cause**: No API server authentication
- **API server issue**: Attacker accessed API server without authentication
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Configure API server authentication

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Over-privileged RBAC
- **Root cause**: No RBAC limits
- **API server issue**: Attacker used cluster-admin to access all resources
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement least privilege RBAC

**Example: Capital One Breach (2019)**
- **Vulnerability**: Unvalidated requests
- **Root cause**: No admission controllers
- **API server issue**: Attacker created malicious pods
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement admission controllers

## 4️⃣ How It Works (Conceptual)

### API Server Security Areas

**1. Authentication**
- **Purpose**: Verify who you are
- **Security Measures**: 
  - OIDC (OpenID Connect)
  - Certificate authentication
  - Service account tokens
  - Token authentication
- **Common Misconfigurations**: 
  - No authentication
  - Weak authentication (weak passwords)
  - Long-lived tokens
  - No token rotation
- **Example**: API server with OIDC authentication

**Authentication Methods:**
- **OIDC (OpenID Connect)**: 
  - Modern authentication standard
  - External identity providers (Okta, Auth0, etc.)
  - MFA support
  - Token management

- **Certificates**: 
  - X.509 certificates
  - Mutual TLS
  - Certificate rotation
  - Revocation

- **Service Account Tokens**: 
  - Kubernetes service accounts
  - Token-based authentication
  - Token rotation
  - TTL (time-to-live)

**Example**:
```yaml
# API server with OIDC authentication (secure)
apiVersion: kubeadm.k8s.io/v1beta2
kind: ClusterConfiguration
apiServer:
  extraArgs:
  - --oidc-issuer-url=https://oidc.example.com
  - --oidc-client-id=kubernetes
  - --oidc-username-claim=email
  - --oidc-groups-claim=groups
```

**2. Authorization (RBAC)**
- **Purpose**: Control what you can do
- **Security Measures**: 
  - RBAC (Role-Based Access Control)
  - Namespace-level RBAC
  - Cluster-level RBAC
  - Least privilege
- **Common Misconfigurations**: 
  - No RBAC (all access allowed)
  - Over-privileged RBAC (cluster-admin by default)
  - Excessive permissions
  - No RBAC audits
- **Example**: RBAC with least privilege

**RBAC Concepts:**
- **Role**: Defines permissions within namespace
- **ClusterRole**: Defines permissions cluster-wide
- **RoleBinding**: Binds Role to subject within namespace
- **ClusterRoleBinding**: Binds ClusterRole to subject cluster-wide
- **Subject**: User, group, or service account

**RBAC Best Practices:**
- Use least privilege (minimum necessary access)
- Use RoleBindings instead of ClusterRoleBindings
- Regular RBAC audits
- Document RBAC configuration
- Review RBAC for compliance

**Example**:
```yaml
# RBAC with least privilege (secure)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: production
subjects:
- kind: ServiceAccount
  name: application-sa
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**3. Admission Controllers**
- **Purpose**: Validate and/or modify API requests
- **Security Measures**: 
  - Validating admission controllers
  - Mutating admission controllers
  - Pod security policies
  - Image validation
  - Resource quotas
- **Common Misconfigurations**: 
  - No admission controllers
  - Admission controllers not enforced
  - Malicious admission controllers
  - Admission controller bypass
- **Example**: Validating admission controller

**Admission Controller Types:**
- **Validating**: Validate requests (reject if invalid)
  - Pod security policies (PSPs)
  - Image validation
  - Resource quotas

- **Mutating**: Modify requests (add defaults, etc.)
  - Inject sidecars
  - Add labels/annotations
  - Set resource limits

**Best Practices:**
- Use validating admission controllers
- Use PSPs to enforce security
- Use image validation
- Use resource quotas
- Review admission controller logs

**Example**:
```yaml
# Validating admission controller (secure)
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: pod-security-policy
webhooks:
- name: pod-security-policy
  rules:
  - operations: ["CREATE"]
    apiGroups: [""]
    apiVersions: ["v1"]
    resources: ["pods"]
    scope: "Namespaced"
  failurePolicy: Fail
  clientConfig:
    service:
      name: pod-security-policy-service
      namespace: kube-system
      path: /validate
```

**4. Encryption**
- **Purpose**: Protect API server communication and data
- **Security Measures**: 
  - TLS for API server communication
  - TLS for etcd communication
  - API server encryption at rest (KMS)
  - Secret encryption
- **Common Misconfigurations**: 
  - No TLS (plaintext communication)
  - Weak TLS (outdated protocols, weak ciphers)
  - No encryption at rest
  - Plaintext secrets
- **Example**: API server with TLS

**Encryption Best Practices:**
- Use TLS 1.3 or higher
- Use strong ciphers (no weak ciphers)
- Use strong key exchange (ECDHE, etc.)
- Use certificate-based authentication
- Encrypt secrets at rest
- Use KMS (Key Management Service)

**Example**:
```yaml
# API server with TLS (secure)
apiVersion: kubeadm.k8s.io/v1beta2
kind: ClusterConfiguration
apiServer:
  extraArgs:
  - --tls-cert-file=/etc/kubernetes/pki/apiserver.crt
  - --tls-private-key-file=/etc/kubernetes/pki/apiserver.key
  - --tls-cipher-suites=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
```

**5. Rate Limiting and Auditing**
- **Purpose**: Prevent abuse and detect attacks
- **Security Measures**: 
  - Rate limiting (API request limits)
  - Audit logging
  - Monitoring and alerting
  - SIEM integration
- **Common Misconfigurations**: 
  - No rate limiting (DoS attacks)
  - No audit logging (attacks undetected)
  - No monitoring (no incident response)
  - No SIEM integration
- **Example**: API server with rate limiting

**Rate Limiting Best Practices:**
- Implement API request rate limits
- Use API gateway for rate limiting
- Monitor for abusive requests
- Set up alerts for suspicious activity
- Use DDoS protection

**Auditing Best Practices:**
- Enable audit logging
- Log all API requests
- Use structured logging
- Use SIEM integration
- Set up alerts for suspicious activity

**Example**:
```yaml
# API server with audit logging (secure)
apiVersion: kubeadm.k8s.io/v1beta2
kind: ClusterConfiguration
apiServer:
  extraArgs:
  - --audit-log-path=/var/log/kubernetes/audit.log
  - --audit-log-maxage=7
  - --audit-log-maxbackup=10
```
