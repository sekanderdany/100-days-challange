# 03.07 - Container Runtime Security

## 1️⃣ What This Topic Is

Container Runtime Security examines security measures for securing Kubernetes container runtime, understanding container runtime security, runtime isolation, and secure runtime configurations.

**What this means:**
- Container runtime security = securing container execution environment
- Defense in depth for container runtime
- Least privilege for container runtime
- Secure container runtime configurations

**The Key Concepts:**

1. **Container Runtime Security Areas**
   - Container runtime isolation (process, network, filesystem)
   - Container runtime hardening (seccomp, AppArmor, SELinux)
   - Container runtime resource limits (CPU, memory, storage)
   - Container runtime policies (image policies, admission controllers)
   - Container runtime monitoring

2. **Security Principles**
   - Defense in depth (isolation, hardening, resource limits, monitoring)
   - Least privilege (container runtime permissions)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- Container runtime is execution environment
- Container runtime is primary attack target
- Container runtime compromise = node compromise
- Container runtime handles all container operations

## 4️⃣ How It Works (Conceptual)

### Container Runtime Security Areas

**1. Container Runtime Isolation**
- **Purpose**: Isolate container runtime from host and other containers
- **Security Measures**: 
  - Process isolation (namespaces, cgroups)
  - Network isolation (network policies, bridge modes)
  - Filesystem isolation (read-only, volumes, mounts)
  - User isolation (non-root containers)
- **Common Misconfigurations**: 
  - No process isolation (containers run as root)
  - No network isolation (containers can access host network)
  - No filesystem isolation (containers can write to host filesystem)
  - No user isolation (containers run as root)
- **Example**: Container runtime with process, network, filesystem isolation

**Container Runtime Isolation Types:**
- **Process Isolation**: 
  - Namespaces
  - Cgroups
  - Seccomp profiles
  - AppArmor profiles
  - SELinux profiles

- **Network Isolation**: 
  - Network policies
  - Bridge modes
  - Host network (disabled)
  - Host ports (disabled)

- **Filesystem Isolation**: 
  - Read-only root filesystem
  - Volumes
  - Mounts
  - Host filesystem (disabled)

- **User Isolation**: 
  - Non-root containers
  - Non-zero UID
  - Non-zero GID

**Best Practices:**
- Enforce process isolation (namespaces, cgroups)
- Enforce network isolation (network policies)
- Enforce filesystem isolation (read-only, volumes)
- Enforce user isolation (non-root containers)

**Example**:
```yaml
# Container runtime isolation (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: isolation-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    allowPrivilegeEscalation: false
    capabilities:
      drop: [ALL]
    readOnlyRootFilesystem: true
    seccompProfile:
      type: RuntimeDefault
    appArmorProfile:
      type: unconfined
    selinuxOptions:
      level: s0:c123,c456
    fsGroup: 2000
    supplementalGroups:
    - 3000
    sysctls:
    - net.ipv4.ip_unprivileged_port_start: 80
  hostNetwork: false
  hostPID: false
  hostIPC: false
  dnsPolicy: ClusterFirst
  containers:
  - name: isolation-container
    image: isolation:v1
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
      seccompProfile:
        type: RuntimeDefault
```

**2. Container Runtime Hardening**
- **Purpose**: Harden container runtime against vulnerabilities
- **Security Measures**: 
  - Seccomp profiles (system call filtering)
  - AppArmor profiles (Linux security policies)
  - SELinux profiles (Linux security policies)
  - Kernel hardening (GRSEC, PaX)
  - Container runtime patching (security updates)
- **Common Misconfigurations**: 
  - No seccomp profiles (all system calls allowed)
  - No AppArmor profiles (no Linux security policies)
  - No SELinux profiles (no Linux security policies)
  - Outdated kernel (vulnerable kernel)
  - Outdated container runtime (vulnerable runtime)
- **Example**: Container runtime with seccomp, AppArmor, SELinux

**Container Runtime Hardening Types:**
- **Seccomp Profiles**: 
  - System call filtering
  - Reduce system call surface
  - Prevent syscall abuse
  - Seccomp profiles (runtime default, restricted, custom)

- **AppArmor Profiles**: 
  - Linux security policies
  - Enforce security policies
  - Prevent Linux vulnerabilities
  - AppArmor profiles (unconfined, custom)

- **SELinux Profiles**: 
  - Linux security policies
  - Enforce security policies
  - Prevent Linux vulnerabilities
  - SELinux profiles (permissive, enforcing, custom)

- **Kernel Hardening**: 
  - GRSEC (PaX and SELinux)
  - Kernel security features
  - Prevent kernel vulnerabilities
  - Kernel patching

- **Container Runtime Patching**: 
  - Security updates
  - Vulnerability patching
  - Regular updates
  - Automated updates

**Best Practices:**
- Enforce seccomp profiles (restricted)
- Enforce AppArmor profiles (custom)
- Enforce SELinux profiles (enforcing)
- Keep kernel updated
- Keep container runtime updated

**Example**:
```yaml
# Container runtime hardening (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: hardening-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    allowPrivilegeEscalation: false
    capabilities:
      drop: [ALL]
    readOnlyRootFilesystem: true
    seccompProfile:
      type: RuntimeDefault
    appArmorProfile:
      type: unconfined
    selinuxOptions:
      level: s0:c123,c456
  containers:
  - name: hardening-container
    image: hardening:v1
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      add: []
      readOnlyRootFilesystem: true
      seccompProfile:
        type: RuntimeDefault
      appArmorProfile:
        type: unconfined
      selinuxOptions:
        level: s0:c123,c456
```

**3. Container Runtime Resource Limits**
- **Purpose**: Limit container runtime resources
- **Security Measures**: 
  - CPU limits
  - Memory limits
  - Storage limits
  - Resource quotas
  - Limit ranges
- **Common Misconfigurations**: 
  - No CPU limits (unlimited CPU)
  - No memory limits (unlimited memory)
  - No storage limits (unlimited storage)
  - No resource quotas (unlimited resources)
  - No limit ranges (unlimited ranges)
- **Example**: Container runtime with resource limits

**Container Runtime Resource Limits Types:**
- **CPU Limits**: 
  - CPU requests
  - CPU limits
  - CPU quotas
  - CPU limits (CPU throttling)

- **Memory Limits**: 
  - Memory requests
  - Memory limits
  - Memory quotas
  - Memory limits (memory limits, OOM kill)

- **Storage Limits**: 
  - Storage requests
  - Storage limits
  - Storage quotas
  - Storage limits (storage limits, disk I/O limits)

- **Resource Quotas**: 
  - Namespace quotas
  - Cluster quotas
  - Tenant quotas
  - Resource quotas (CPU, memory, storage)

- **Limit Ranges**: 
  - Namespace limit ranges
  - Cluster limit ranges
  - Tenant limit ranges
  - Limit ranges (CPU, memory, storage)

**Best Practices:**
- Enforce CPU limits
- Enforce memory limits
- Enforce storage limits
- Enforce resource quotas
- Enforce limit ranges
- Monitor resource usage

**Example**:
```yaml
# Container runtime resource limits (secure, advanced)
apiVersion: v1
kind: Pod
metadata:
  name: resource-limits-pod
spec:
  containers:
  - name: resource-limits-container
    image: resource-limits:v1
    resources:
      requests:
        cpu: "500m"
        memory: "512Mi"
      limits:
        cpu: "1000m"
        memory: "1024Mi"
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
      seccompProfile:
        type: RuntimeDefault
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-resources
  namespace: default
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    persistentvolumeclaims: 4
```

**4. Container Runtime Policies**
- **Purpose**: Enforce security policies for container runtime
- **Security Measures**: 
  - Image policies (image signing, image scanning)
  - Admission controllers (validating, mutating)
  - Pod security admission (baseline, restricted, custom)
  - Resource policies (resource quotas, limit ranges)
  - Security policies (seccomp, AppArmor, SELinux)
- **Common Misconfigurations**: 
  - No image policies (all images allowed)
  - No admission controllers (all pods allowed)
  - No pod security admission (insecure pods allowed)
  - No resource policies (unlimited resources)
  - No security policies (all system calls allowed)
- **Example**: Container runtime with image policies and admission controllers

**Container Runtime Policies Types:**
- **Image Policies**: 
  - Image signing
  - Image scanning
  - Image allowlist
  - Image denylist
  - Image registries

- **Admission Controllers**: 
  - Validating admission controllers
  - Mutating admission controllers
  - Security validation
  - Security defaults

- **Pod Security Admission**: 
  - Privileged (baseline, restricted, custom)
  - Host namespaces (baseline, restricted, custom)
  - Host path volumes (baseline, restricted, custom)
  - Host ports (baseline, restricted, custom)
  - Host network (baseline, restricted, custom)
  - Volume types (baseline, restricted, custom)
  - Non-root groups (baseline, restricted, custom)
  - SELinux (baseline, restricted, custom)
  - Seccomp (baseline, restricted, custom)
  - AppArmor (baseline, restricted, custom)
  - Sysctl (baseline, restricted, custom)
  - Proc mount (baseline, restricted, custom)

- **Resource Policies**: 
  - Resource quotas
  - Limit ranges
  - Namespace quotas
  - Resource limits (CPU, memory, storage)

- **Security Policies**: 
  - Seccomp policies
  - AppArmor policies
  - SELinux policies
  - Security contexts (non-root, drop capabilities)

**Best Practices:**
- Enforce image policies (image signing, image scanning)
- Enforce admission controllers (validating, mutating)
- Enforce pod security admission (restricted)
- Enforce resource policies (resource quotas, limit ranges)
- Enforce security policies (seccomp, AppArmor, SELinux)

**Example**:
```yaml
# Container runtime policies (secure, advanced)
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: image-policy-webhook
webhooks:
- name: image-policy-webhook.example.com
  rules:
  - operations: ["CREATE", "UPDATE"]
    apiGroups: ["*"]
    apiVersions: ["*"]
    resources: ["pods"]
    scope: "*"
  failurePolicy: Fail
  clientConfig:
    service:
      name: image-policy-webhook-service
      namespace: webhook-system
      path: /validate
  admissionReviewVersions: ["v1", "v1beta1"]
  timeoutSeconds: 5
```
