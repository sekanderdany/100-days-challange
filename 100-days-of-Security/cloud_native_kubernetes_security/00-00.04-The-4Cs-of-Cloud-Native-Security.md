# 00.04 - The 4Cs of Cloud Native Security

## 1️⃣ What This Topic Is

The **4Cs of Cloud Native Security** is a framework that describes the four layers where security must be applied in cloud-native environments. It provides a structured way to think about security across the entire technology stack.

**The 4Cs are:**

1. **Cloud** - The cloud provider infrastructure
2. **Cluster** - The Kubernetes orchestration platform
3. **Container** - The container runtime and workloads
4. **Code** - The application code and supply chain

**Why this framework matters:**
- Security must be applied at EVERY layer
- A vulnerability at any layer can compromise the entire system
- Each layer has unique security considerations
- Defense in depth requires securing all 4Cs
- Helps identify where security controls should be implemented

**Visual Representation:**

```
┌─────────────────────────────────────────────────────────────┐
│ 1. CLOUD                                                   │
│    Physical infrastructure, data centers, network              │
│    Provider: AWS, GCP, Azure                               │
└────────────────────┬──────────────────────────────────────────┘
                     │
┌────────────────────▼──────────────────────────────────────────┐
│ 2. CLUSTER                                                 │
│    Kubernetes control plane, nodes, orchestration              │
│    Platform: EKS, GKE, AKS, self-hosted                   │
└────────────────────┬──────────────────────────────────────────┘
                     │
┌────────────────────▼──────────────────────────────────────────┐
│ 3. CONTAINER                                               │
│    Container runtime, images, pods, workloads                 │
│    Runtime: containerd, CRI-O                               │
└────────────────────┬──────────────────────────────────────────┘
                     │
┌────────────────────▼──────────────────────────────────────────┐
│ 4. CODE                                                    │
│    Application code, dependencies, supply chain                 │
│    Artifacts: Source code, binaries, libraries                │
└─────────────────────────────────────────────────────────────┘
```

**Key Principle:**
**You cannot secure the entire system by only securing one layer.** Security must be comprehensive across all 4Cs. A weakness at any layer can be exploited to compromise the entire stack.

## 2️⃣ What Problem It Solves

### Problem 1: Fragmented Security Approach

**Without the 4Cs framework:**
- Teams focus on security in silos (network team, app team, ops team)
- Some layers get attention while others are ignored
- Security gaps exist between layers
- Attackers find and exploit unprotected layers

**With the 4Cs framework:**
- Holistic view of security across all layers
- Every layer gets appropriate attention
- No security gaps between layers
- Attackers must bypass multiple layers

### Problem 2: Unclear Responsibility

**Without the 4Cs framework:**
- Unclear who secures what
- "Security team's job" mentality
- Developers don't think about security
- Operations team focuses only on infrastructure

**With the 4Cs framework:**
- Clear understanding of responsibilities at each layer
- Everyone has security responsibilities
- Developers secure their code
- Operations team secures infrastructure
- Shared ownership of security

### Problem 3: Misplaced Priorities

**Without the 4Cs framework:**
- Focus on one layer (usually perimeter)
- Other layers remain vulnerable
- Resources wasted on over-securing some layers
- Attackers bypass strong controls by exploiting weak layers

**With the 4Cs framework:**
- Balanced security investment across layers
- Resources allocated based on risk at each layer
- No layer is ignored or over-emphasized
- Attackers must bypass comprehensive defenses

### Real-World Impact

**Example: The Equifax Breach (2017)**
- **Cloud**: AWS infrastructure was properly configured ✓
- **Cluster**: Not applicable (didn't use Kubernetes)
- **Container**: Not applicable (monolithic application)
- **Code**: Vulnerability in Apache Struts library (CVE-2017-5638) ✗

**Lesson**: Even with secure infrastructure, a vulnerability in code can cause a massive breach. All layers matter.

**Example: Tesla Kubernetes Breach (2018)**
- **Cloud**: AWS infrastructure was properly configured ✓
- **Cluster**: Kubernetes console exposed to internet with no authentication ✗
- **Container**: Container images were not scanned for vulnerabilities ✗
- **Code**: Application code was secure ✓

**Lesson**: Infrastructure security alone is insufficient. Cluster and container security are equally important.

### **ALWAYS** - The 4Cs framework should guide all security decisions

**During Security Architecture Design:**
- Ask: What security controls are needed at each C?
- Design security for all 4Cs from the start
- Identify dependencies between layers
- Plan defense in depth strategy

**During Security Reviews:**
- Check security controls at all 4Cs
- Identify gaps in any layer
- Review configurations for each C
- Ensure comprehensive coverage

**During Incident Response:**
- Determine which C was compromised
- Understand how attackers moved between Cs
- Assess impact across all layers
- Remediate vulnerabilities at all affected Cs

**During Security Audits:**
- Audit each of the 4Cs systematically
- Ensure no layer is overlooked
- Verify controls are in place at each layer

## 4️⃣ How It Works (Conceptual)

### Deep Dive into Each C

#### **C1: Cloud Security**

**What it includes:**
- Physical security of data centers
- Network infrastructure (VPC, subnets, load balancers)
- Compute infrastructure (EC2, GCE, Azure VMs)
- Storage infrastructure (S3, GCS, Azure Blob)
- Database infrastructure (RDS, Cloud SQL, Azure SQL)
- Identity and access management (IAM)
- Encryption at rest and in transit
- DDoS protection
- Web Application Firewall (WAF)

**Who's responsible:**
- **Cloud Provider**: Physical security, network infrastructure
- **You**: Everything you deploy (VMs, databases, storage buckets, IAM policies)

**Key security controls:**
- VPC and subnet design
- Security groups and firewall rules
- IAM policies and roles
- Encryption configuration
- DDoS protection settings
- WAF rules
- CloudTrail / Cloud Audit Logs

**Common vulnerabilities:**
- Publicly accessible resources (S3 buckets, databases)
- Overly permissive IAM policies
- Unencrypted storage
- Misconfigured security groups
- Disabled audit logging
- Weak authentication

**Example:**
```bash
# Insecure: Publicly accessible S3 bucket
aws s3api put-bucket-acl --bucket sensitive-data --acl public-read

# Secure: Private S3 bucket with encryption
aws s3api put-bucket-acl --bucket sensitive-data --acl private
aws s3api put-bucket-encryption --bucket sensitive-data \
  --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
```

#### **C2: Cluster Security**

**What it includes:**
- Kubernetes control plane (API server, etcd, scheduler, controller manager)
- Worker nodes (kubelet, kube-proxy, container runtime)
- Cluster networking (CNI plugins, network policies)
- Cluster authentication and authorization (RBAC, OIDC)
- Cluster secrets management
- Cluster admission controllers
- Cluster auditing and logging
- Cluster upgrades and patching

**Who's responsible:**
- **Cloud Provider** (managed clusters): Control plane security
- **You**: Node security, RBAC configuration, network policies, secrets management

**Key security controls:**
- Control plane hardening (CIS benchmarks)
- RBAC configuration
- Network policies
- Pod security policies (now Pod Security Admission)
- Secrets encryption at rest
- Admission controllers
- Audit logging
- Node hardening

**Common vulnerabilities:**
- Exposed API server to internet
- Weak authentication
- Overly permissive RBAC (cluster-admin for developers)
- No network policies
- Unencrypted secrets
- Misconfigured admission controllers
- Outdated Kubernetes version

**Example:**
```yaml
# Insecure: Overly permissive ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: developer-cluster-role
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["*"]  # Full cluster access!

# Secure: Least privilege ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: developer-cluster-role
rules:
- apiGroups: ["coordination.k8s.io"]
  resources: ["leases"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
```

#### **C3: Container Security**

**What it includes:**
- Container images (base images, application images)
- Container runtime security (containerd, CRI-O)
- Container security contexts
- Linux capabilities
- Seccomp profiles
- AppArmor profiles
- Container filesystem security
- Container resource limits
- Container image scanning
- Container supply chain

**Who's responsible:**
- **You**: Everything related to containers

**Key security controls:**
- Image scanning (Trivy, Clair)
- Security contexts (runAsNonRoot, drop capabilities)
- Seccomp profiles
- AppArmor profiles
- Resource limits
- Read-only root filesystem
- Minimal base images
- Signed images

**Common vulnerabilities:**
- Vulnerable base images
- Running as root
- Privileged containers
- Unnecessary Linux capabilities
- Large attack surface (bloated images)
- Unverified image sources
- No image scanning

**Example:**
```yaml
# Insecure: Privileged container running as root
apiVersion: v1
kind: Pod
metadata:
  name: insecure-pod
spec:
  containers:
  - name: app
    image: nginx:latest
    securityContext:
      privileged: true
      runAsUser: 0

# Secure: Non-privileged, non-root container
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:1.25-alpine
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
      readOnlyRootFilesystem: true
```

#### **C4: Code Security**

**What it includes:**
- Application source code
- Third-party libraries and dependencies
- Build scripts and CI/CD pipelines
- Application configuration
- API security
- Input validation
- Output encoding
- Authentication and authorization
- Secrets management (in code)
- Static and dynamic analysis

**Who's responsible:**
- **Developers**: Application code, dependencies, CI/CD security
- **Security Team**: Code review, security testing, tooling

**Key security controls:**
- Static Application Security Testing (SAST)
- Dynamic Application Security Testing (DAST)
- Software Composition Analysis (SCA)
- Dependency management
- Secure coding practices
- Code review processes
- Secret scanning (GitGuardian, TruffleHog)
- API security testing
- Input validation
- Output encoding

**Common vulnerabilities:**
- Known vulnerable dependencies (CVEs)
- Hardcoded secrets in code
- SQL injection
- XSS (Cross-Site Scripting)
- Authentication bypasses
- Authorization flaws
- Insecure deserialization
- XXE (XML External Entity)

**Example:**
```python
# Insecure: Hardcoded secret, SQL injection vulnerability
import pymysql

def get_user(user_id):
    connection = pymysql.connect(
        host='database.example.com',
        user='admin',
        password='MySecretPassword123',  # Hardcoded secret!
        database='users'
    )
    cursor = connection.cursor()
    query = f"SELECT * FROM users WHERE id = {user_id}"  # SQL injection!
    cursor.execute(query)
    return cursor.fetchall()

# Secure: No hardcoded secrets, parameterized queries
import os
import pymysql

def get_user(user_id):
    connection = pymysql.connect(
        host=os.getenv('DB_HOST'),
        user=os.getenv('DB_USER'),
        password=os.getenv('DB_PASSWORD'),  # From environment variable
        database=os.getenv('DB_NAME')
    )
    cursor = connection.cursor()
    query = "SELECT * FROM users WHERE id = %s"  # Parameterized
    cursor.execute(query, (user_id,))
    return cursor.fetchall()
```

### How the 4Cs Interact

**Attacker can exploit any layer to compromise the entire system:**

```
Attack Path 1: Cloud → Cluster → Container → Code
Attack Path 2: Code → Container → Cluster → Cloud
Attack Path 3: Container → Cluster → Cloud
Attack Path 4: Cluster → Container → Code
Attack Path 5: Any single layer compromise
```

**Example: Attack through C1 (Cloud)**
```
1. Attacker exploits misconfigured S3 bucket (C1)
2. Gains access to Kubernetes configuration files
3. Uses credentials to access Kubernetes API server (C2)
4. Deploys malicious container image (C3)
5. Executes code in cluster (C4)
Result: Entire system compromised through C1
```

**Example: Attack through C4 (Code)**
```
1. Attacker finds vulnerability in application code (C4)
2. Exploits code to execute arbitrary commands
3. Escapes container isolation (C3)
4. Gains access to Kubernetes API server (C2)
5. Accesses cloud resources via service account (C1)
Result: Entire system compromised through C4
```

### Defense in Depth Across the 4Cs

**Layered security ensures attackers must bypass multiple controls:**

```
If attacker exploits C1 (Cloud):
- C2 (Cluster) RBAC limits what they can do
- C3 (Container) security contexts limit container escape
- C4 (Code) input validation prevents code injection

If attacker exploits C4 (Code):
- C3 (Container) security contexts limit lateral movement
- C2 (Cluster) network policies prevent pod-to-pod access
- C1 (Cloud) IAM policies limit cloud resource access
```

### **1. Designing Security Architecture**

**Example: Multi-layered security for a web application**


### **2. Implementing Security Controls per C**

**C1 (Cloud) Security Controls**

```bash
# Secure S3 bucket with encryption and IAM
aws s3api create-bucket --bucket my-secure-bucket

# Enable encryption
aws s3api put-bucket-encryption --bucket my-secure-bucket \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "AES256"
      }
    }]
  }'

# Restrict access with IAM policy
aws s3api put-bucket-policy --bucket my-secure-bucket \
  --policy '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::my-secure-bucket/*",
      "Condition": {
        "NotIpAddress": {
          "aws:SourceIp": ["1.2.3.4/32"]
        }
      }
    }]
  }'
```

**C2 (Cluster) Security Controls**

```yaml
# Implement RBAC with least privilege
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-developer
  namespace: secure-app
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update"]
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list", "watch"]
# No access to secrets, pods creation, or cluster-level resources
```

**C3 (Container) Security Controls**

```yaml
# Secure pod with security contexts
apiVersion: v1
kind: Pod
metadata:
  name: secure-container
  namespace: secure-app
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: nginx:1.25-alpine  # Minimal, patched image
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
      readOnlyRootFilesystem: true
    resources:
      requests:
        memory: "64Mi"
        cpu: "50m"
      limits:
        memory: "128Mi"
        cpu: "100m"
```

**C4 (Code) Security Controls**

```python
# Secure code example
import os
import pymysql
from typing import Optional

# Dependencies from requirements.txt with versions locked
# Security: Regular dependency scanning

def get_user(user_id: int) -> Optional[dict]:
    """
    Secure database access with:
    - Input validation
    - Parameterized queries
    - Secrets from environment
    - Error handling
    """
    # Input validation
    if not isinstance(user_id, int) or user_id <= 0:
        raise ValueError("Invalid user ID")
    
    try:
        # Secrets from environment (not hardcoded)
        connection = pymysql.connect(
            host=os.getenv('DB_HOST'),
            user=os.getenv('DB_USER'),
            password=os.getenv('DB_PASSWORD'),
            database=os.getenv('DB_NAME'),
            ssl_disabled=False  # Use TLS
        )
        
        cursor = connection.cursor()
        # Parameterized query (SQL injection prevention)
        query = "SELECT id, username, email FROM users WHERE id = %s"
        cursor.execute(query, (user_id,))
        result = cursor.fetchone()
        return dict(result) if result else None
        
    except Exception as e:
        # Don't expose internal errors
        raise RuntimeError("Database error") from e
    finally:
        if 'connection' in locals():
            connection.close()
```

### **3. Auditing Security Across the 4Cs**

**C1 (Cloud) Audit Checklist**
```bash
# Check for publicly accessible S3 buckets
aws s3 ls | xargs -I {} aws s3api get-bucket-acl --bucket {}

# Check for overly permissive IAM policies
aws iam list-roles | jq '.Roles[] | select(.AssumeRolePolicyDocument.Statement[].Effect == "Allow")'

# Check encryption status
aws s3api get-bucket-encryption --bucket my-bucket

# Check audit logging
aws cloudtrail describe-trails
```

**C2 (Cluster) Audit Checklist**
```bash
# Check for exposed API server
kubectl cluster-info dump | grep server

# Check RBAC permissions
kubectl auth can-i "*" "*" --all-namespaces

# Check for cluster-admin bindings
kubectl get clusterrolebindings -o json | jq '.items[] | select(.roleRef.name == "cluster-admin")'

# Check network policies
kubectl get networkpolicies --all-namespaces
```

**C3 (Container) Audit Checklist**
```bash
# Check for privileged containers
kubectl get pods --all-namespaces -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].securityContext.privileged}{"\n"}{end}' | grep "true"

# Check for root containers
kubectl get pods --all-namespaces -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.securityContext.runAsUser}{"\n"}{end}' | grep "^0"

# Scan images for vulnerabilities (requires Trivy)
trivy image myregistry.com/webapp:v1.2.3
```

**C4 (Code) Audit Checklist**
```bash
# Scan for hardcoded secrets (requires GitGuardian)
ggshield scan

# Check for vulnerable dependencies
pip-audit  # Python
npm audit  # Node.js
yarn audit  # Node.js

# Static analysis (requires tools like semgrep)
semgrep --config=auto .

# Check code quality
pylint myapp/  # Python
eslint myapp/  # JavaScript
```

### **Common Mistakes in Applying the 4Cs**

❌ **Mistake 1**: Only securing one layer
- Reality: Attackers can exploit any layer
- Fix: Implement security across all 4Cs

❌ **Mistake 2**: Assuming cloud provider handles everything
- Reality: Provider secures infrastructure, you secure what you deploy
- Fix: Understand shared responsibility model

❌ **Mistake 3**: Focusing only on container security
- Reality: Code vulnerabilities can compromise entire system
- Fix: Secure code, containers, clusters, and cloud infrastructure

❌ **Mistake 4**: Treating the 4Cs as independent
- Reality: Layers interact and depend on each other
- Fix: Design security holistically across all layers

```bash
cat > secure_app.py <<'EOF'
import os
import pymysql
from typing import Optional

# Dependencies: Use locked versions in requirements.txt
# Security: pip-audit checks for vulnerabilities

def get_user(user_id: int) -> Optional[dict]:
    """
    Secure database access with:
    - Input validation
    - Parameterized queries
    - Secrets from environment
    - Error handling
    """
    # Input validation
    if not isinstance(user_id, int) or user_id <= 0:
        raise ValueError("Invalid user ID")
    
    try:
        # Secrets from environment (not hardcoded)
        connection = pymysql.connect(
            host=os.getenv('DB_HOST', 'localhost'),
            user=os.getenv('DB_USER', 'app_user'),
            password=os.getenv('DB_PASSWORD'),
            database=os.getenv('DB_NAME', 'app_db'),
            ssl_disabled=False
        )
        
        cursor = connection.cursor()
        # Parameterized query (SQL injection prevention)
        query = "SELECT id, username, email FROM users WHERE id = %s"
        cursor.execute(query, (user_id,))
        result = cursor.fetchone()
        return dict(result) if result else None
        
    except Exception as e:
        raise RuntimeError("Database error") from e
    finally:
        if 'connection' in locals():
            connection.close()

if __name__ == "__main__":
    # Usage
    user = get_user(1)
    print(f"User: {user}")
EOF
```

### **Common Interview Questions**

**Q1: What are the 4Cs of cloud native security?**
**Good Answer**: The 4Cs are Cloud, Cluster, Container, and Code. Cloud (C1) is the cloud provider infrastructure like AWS, GCP, or Azure. Cluster (C2) is the Kubernetes orchestration platform. Container (C3) includes container runtime, images, and workloads. Code (C4) is the application code, dependencies, and supply chain. Security must be implemented at all 4Cs because a vulnerability at any layer can compromise the entire system. Attackers can exploit any layer, so defense in depth requires securing all 4Cs comprehensively.

**Q2: How does the shared responsibility model apply to the 4Cs?**
**Good Answer**: In the shared responsibility model, the cloud provider is responsible for securing the physical infrastructure and network (C1), but you're responsible for everything you deploy. For Cluster (C2), managed cluster providers secure the control plane, but you secure worker nodes, RBAC, network policies, and configurations. For Container (C3) and Code (C4), you're fully responsible. Understanding this helps you implement appropriate security controls and know what's your responsibility vs. the provider's.

**Q3: Why is it important to secure all 4Cs?**
**Good Answer**: It's important because:
1. **Attackers can enter through any layer**: Exploiting a vulnerability in code, container, cluster, or cloud infrastructure
2. **Lateral movement between layers**: Compromise at one layer can spread to others
3. **No single layer provides complete security**: Each layer has unique attack vectors
4. **Defense in depth**: Multiple layers of security reduce risk
5. **Real-world breaches**: Most breaches happen because one layer was overlooked

For example, the Equifax breach was due to a code vulnerability (C4), not infrastructure or cluster security. The Tesla breach was due to cluster security (C2), not code or container security.

**Q4: What security controls should be implemented at each C?**
**Good Answer**: 
**C1 (Cloud)**: S3 bucket policies, encryption, IAM policies, security groups, CloudTrail logging, DDoS protection
**C2 (Cluster)**: Pod security admission, RBAC, network policies, secrets encryption, audit logging, CIS benchmarks
**C3 (Container)**: Image scanning, security contexts (non-root, drop capabilities), seccomp profiles, resource limits, minimal images
**C4 (Code)**: Input validation, output encoding, parameterized queries, dependency scanning, secret scanning, code reviews

Each layer requires different controls, but all are necessary for comprehensive security.

**Q5: How does defense in depth work across the 4Cs?**
**Good Answer**: Defense in depth means implementing multiple security controls at each of the 4Cs. If an attacker exploits a vulnerability at one layer, controls at other layers limit the damage. For example, if attackers exploit code (C4) to execute arbitrary commands, container security contexts (C3) prevent container escape, cluster network policies (C2) prevent lateral movement, and cloud IAM policies (C1) prevent access to cloud resources. Attackers must bypass controls at all 4Cs to fully compromise the system, making attacks exponentially harder.
