# 00.05 - Shared Responsibility Model

## 1️⃣ What This Topic Is

The **Shared Responsibility Model** is a framework that defines who is responsible for what security in cloud environments. It's a critical concept because misunderstanding it leads to security vulnerabilities.

**What this means:**
- Security is a partnership between cloud provider and customer
- Provider secures some things, you secure others
- The division depends on the service type (IaaS, PaaS, SaaS)
- Misunderstanding leads to security gaps

**The Core Principle:**
"Cloud providers secure **of** the cloud (infrastructure), you secure what's **in** the cloud (your data, applications, configurations)."

**Why this matters:**
- You can't secure what you don't own
- Provider doesn't secure your applications
- Confusion leads to breaches
- Understanding prevents security gaps

**Service Types & Responsibility Split:**

```
┌─────────────────────────────────────────────────────────────┐
│ SAAS (Software as a Service) - e.g., Gmail, Slack      │
│ Provider: Everything except user data & access             │
│ You: User data, access management                         │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ PAAS (Platform as a Service) - e.g., EKS, GKE, AKS    │
│ Provider: Infrastructure, control plane                       │
│ You: Applications, data, configurations, cluster config      │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ IAAS (Infrastructure as a Service) - e.g., EC2, GCE      │
│ Provider: Physical infrastructure, network, virtualization    │
│ You: OS, applications, data, network config, security groups  │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ KUBERNETES ON CLOUD                                            │
│ Provider: Nodes, storage, network, DNS, load balancers           │
│ You: Kubernetes configuration, workloads, RBAC, policies        │
└─────────────────────────────────────────────────────────────┘
```

## 2️⃣ What Problem It Solves

### Problem 1: Confusion About Security Ownership

**Without understanding shared responsibility:**
- Teams assume provider handles everything
- No one takes ownership of security
- Critical components left unsecured
- "It's the cloud provider's job" mentality

**With clear understanding:**
- Everyone knows what they're responsible for
- Clear ownership of security tasks
- No security gaps due to confusion
- Teams collaborate effectively

### Problem 2: Misplaced Security Efforts

**Without understanding shared responsibility:**
- Teams secure things provider already secures
- Teams ignore things they're responsible for
- Wasted effort on already-secured components
- Gaps in security where responsibility is unclear

**With clear understanding:**
- Teams focus on their responsibilities
- No duplication of effort
- Comprehensive security coverage
- Efficient use of resources

### Problem 3: Compliance and Auditing Issues

**Without understanding shared responsibility:**
- Compliance auditors point out gaps
- Unclear who's accountable for breaches
- Difficulty proving security posture
- Failed compliance audits

**With clear understanding:**
- Clear accountability for each component
- Easier compliance reporting
- Proven security posture
- Successful compliance audits

### Real-World Impact

**Example: Capital One Breach (2019)**
- **Provider responsibility**: AWS infrastructure was secure ✓
- **Your responsibility**: IAM policies and WAF configuration ✗
- **Root cause**: Over-privileged IAM role + misconfigured WAF
- **Lesson**: AWS secured infrastructure, but Capital One was responsible for IAM and WAF configuration

**Example: Tesla Kubernetes Breach (2018)**
- **Provider responsibility**: AWS infrastructure was secure ✓
- **Your responsibility**: Kubernetes configuration ✗
- **Root cause**: Kubernetes console exposed without authentication
- **Lesson**: AWS secured infrastructure, but Tesla was responsible for securing Kubernetes

**Example: Code Spaces Breach (2014)**
- **Provider responsibility**: AWS infrastructure was secure ✓
- **Your responsibility**: AWS account security (MFA) ✗
- **Root cause**: Attacker compromised AWS credentials, deleted all data
- **Lesson**: AWS secured infrastructure, but Code Spaces was responsible for securing their AWS account

## 3️⃣ When You Should Use This

### **ALWAYS** - The shared responsibility model applies to ALL cloud usage

**When Using Cloud Services:**
- Understand what provider secures
- Understand what you secure
- Verify responsibilities in documentation
- Ensure security controls are in place

**When Designing Architecture:**
- Choose services based on security responsibilities
- Understand security implications of each service
- Plan security controls for your responsibilities
- Document ownership of security tasks

**When Conducting Security Reviews:**
- Verify all your responsibilities are secured
- Don't waste time on provider responsibilities
- Focus on components you own
- Ensure comprehensive coverage

**When Responding to Incidents:**
- Determine if breach was in your area or provider's
- Coordinate with provider if needed
- Understand your liability
- Plan remediation accordingly

### Scenarios where this is critical:

**When deploying Kubernetes on cloud:**
- What does provider secure? (Nodes, storage, network)
- What do you secure? (Kubernetes config, RBAC, policies)
- How do they interact? (IAM roles, service accounts)

**When using managed databases (RDS, Cloud SQL):**
- What does provider secure? (Database software, infrastructure)
- What do you secure? (Data access, encryption keys, IAM policies)

**When using object storage (S3, GCS):**
- What does provider secure? (Storage infrastructure)
- What do you secure? (Bucket policies, encryption, access)

**When using serverless (Lambda, Cloud Functions):**
- What does provider secure? (Runtime, infrastructure)
- What do you secure? (Function code, IAM policies, configuration)

## 4️⃣ How It Works (Conceptual)

### Detailed Breakdown by Service Type

#### **SaaS (Software as a Service)**

**Examples**: Gmail, Slack, Salesforce, Dropbox, Microsoft 365

**Provider Responsibilities:**
- Application software
- Infrastructure (servers, network)
- Data centers (physical security)
- Operating systems
- Runtime environment
- Application security
- Compliance certifications

**Your Responsibilities:**
- User access management (who can use)
- Data classification (what data goes in)
- Configuration (user settings, permissions)
- API access (if using APIs)
- End-user security (passwords, MFA)
- Data governance (privacy, retention)

**Key Point**: Provider does almost everything, you manage access and data.

#### **PaaS (Platform as a Service)**

**Examples**: EKS (AWS), GKE (GCP), AKS (Azure), Cloud Functions

**Provider Responsibilities:**
- Physical infrastructure (data centers)
- Network infrastructure (VPC, subnets)
- Compute infrastructure (hypervisors)
- Storage infrastructure (disks, object storage)
- Platform software (Kubernetes control plane, runtime)
- Platform security (patches, updates)
- Platform availability
- Platform compliance

**Your Responsibilities:**
- Applications and workloads
- Application configuration
- Data security (encryption, access)
- IAM policies and roles
- Network configuration (security groups, firewalls)
- Kubernetes configuration (RBAC, network policies)
- Container security (images, security contexts)
- Application security (code, dependencies)
- Backup and disaster recovery
- Monitoring and logging

**Key Point**: Provider secures the platform, you secure what you deploy on it.

#### **IaaS (Infrastructure as a Service)**

**Examples**: EC2 (AWS), Compute Engine (GCP), Azure VMs

**Provider Responsibilities:**
- Physical infrastructure (data centers)
- Network infrastructure (VPC, subnets)
- Compute infrastructure (hypervisors, physical servers)
- Storage infrastructure (EBS, S3, etc.)
- Platform virtualization
- Network connectivity (internet gateways, VPNs)
- Physical security

**Your Responsibilities:**
- Operating system (patches, updates, hardening)
- Application software
- Application configuration
- Data security
- IAM policies and roles
- Network configuration (security groups, NACLs)
- Security groups and firewall rules
- Data encryption (at rest and in transit)
- Backup and disaster recovery
- Monitoring and logging

**Key Point**: Provider provides raw infrastructure, you secure everything on top.

### Shared Responsibility for Kubernetes on Cloud

**For Managed Kubernetes (EKS, GKE, AKS):**

**Provider (AWS/GCP/Azure) Secures:**
- **Control Plane**: API server, etcd, scheduler, controller manager
- **Nodes**: EC2/GCE/Azure VM instances (provisioning)
- **Storage**: EBS/GPD/Azure Disk volumes
- **Network**: VPC, subnets, load balancers
- **DNS**: Cloud DNS or Route 53
- **Container Runtime**: containerd or CRI-O
- **Platform Updates**: Kubernetes version upgrades
- **Platform Security**: Control plane certificates, etcd encryption
- **Platform Availability**: SLA guarantees

**You Secure:**
- **Kubernetes Configuration**: RBAC, network policies, pod security
- **Workloads**: Deployments, pods, services, configmaps, secrets
- **Container Images**: Scanning, security, signatures
- **Application Security**: Code, dependencies, configurations
- **Data Security**: Secrets encryption, application data
- **Network Security**: Security groups, firewall rules
- **IAM Integration**: IAM roles for service accounts
- **Monitoring**: Application and cluster monitoring
- **Backup**: etcd backups, application backups
- **Compliance**: Meeting regulatory requirements

**Visual Representation:**

```
┌─────────────────────────────────────────────────────────────┐
│ CLOUD PROVIDER (AWS/GCP/Azure)                         │
│ Physical infrastructure, data centers, network              │
│ VPC, subnets, load balancers                             │
│ Control plane (API server, etcd, scheduler)               │
│ Node provisioning, storage                                  │
│ Kubernetes version upgrades                                  │
└────────────────────┬──────────────────────────────────────────┘
                     │
┌────────────────────▼──────────────────────────────────────────┐
│ YOUR RESPONSIBILITY                                        │
│ Kubernetes configuration (RBAC, policies)                   │
│ Workloads (pods, deployments, services)                   │
│ Container images (scanning, security)                      │
│ Application security (code, dependencies)                   │
│ Data security (secrets, encryption)                        │
│ Network configuration (security groups)                        │
│ IAM roles and policies                                     │
│ Monitoring and logging                                      │
│ Backup and disaster recovery                                │
└─────────────────────────────────────────────────────────────┘
```

### Responsibility Split for Common Services

**1. Object Storage (S3, GCS, Azure Blob)**

| Component | Provider Secures | You Secure |
|-----------|------------------|-------------|
| Storage infrastructure | ✓ | - |
| Data encryption (default) | ✓ | - |
| Data encryption (customer-managed keys) | - | ✓ |
| Bucket policies | - | ✓ |
| Access control (IAM) | - | ✓ |
| Versioning | ✓ (feature) | ✓ (enable/configure) |
| Data | - | ✓ |

**2. Managed Databases (RDS, Cloud SQL, Azure SQL)**

| Component | Provider Secures | You Secure |
|-----------|------------------|-------------|
| Database software | ✓ | - |
| Infrastructure | ✓ | - |
| Backups | ✓ (automated) | ✓ (retention, encryption) |
| Encryption at rest | ✓ | - (or CMK) |
| Encryption in transit | ✓ | - |
| Data access | - | ✓ |
| IAM policies | - | ✓ |
| Database configuration | - | ✓ |
| Data | - | ✓ |

**3. Load Balancers (ELB, Cloud Load Balancing)**

| Component | Provider Secures | You Secure |
|-----------|------------------|-------------|
| Load balancer infrastructure | ✓ | - |
| SSL/TLS certificates | - | ✓ (or ACM) |
| Security groups | - | ✓ |
| Target group configuration | - | ✓ |
| Health checks | - | ✓ |

**4. Function as a Service (Lambda, Cloud Functions)**

| Component | Provider Secures | You Secure |
|-----------|------------------|-------------|
| Runtime environment | ✓ | - |
| Infrastructure | ✓ | - |
| Scaling | ✓ | - |
| Function code | - | ✓ |
| IAM policies | - | ✓ |
| Configuration | - | ✓ |
| Secrets/Environment variables | - | ✓ |

This is a **conceptual framework**—no installation required. However, to understand and practice with shared responsibility, you'll need:

### **Prerequisites**

**1. Cloud Account**
```bash
# AWS CLI setup
aws configure

# Verify access and understand your account
aws sts get-caller-identity
```

```bash
# Create cluster to understand responsibilities

eksctl create cluster --name shared-resp-lab --region us-west-2

# GCP
gcloud container clusters create shared-resp-lab --region us-central1

# Azure
az aks create --resource-group myResourceGroup --name sharedResplab
```

**3. Documentation Review**
- AWS Shared Responsibility Model: https://aws.amazon.com/compliance/shared-responsibility-model/
- GCP Shared Responsibility: https://cloud.google.com/security
- Azure Shared Responsibility: https://azure.microsoft.com/en-us/support/legal/

### **What You Need to Understand NOW**

1. **Provider secures infrastructure**: Physical, network, virtualization
2. **You secure what you deploy**: Applications, data, configurations
3. **Responsibility depends on service type**: SaaS vs PaaS vs IaaS
4. **Never assume provider secures everything**: Always verify
5. **Document your responsibilities**: Clear ownership prevents gaps

## 6️⃣ Where It Should Be Applied (With Example)

The shared responsibility model should be applied **everywhere** in cloud security planning.

### **1. Designing Cloud Architecture**

**Example: Web Application on AWS with EKS**

```yaml
# Provider (AWS) responsibilities:
# - VPC, subnets, internet gateway
# - EC2 instances for worker nodes
# - EBS volumes for storage
# - Load balancers
# - EKS control plane
# - Route 53 DNS

# Your responsibilities:
# - VPC configuration (CIDR, subnets)
# - Security groups and NACLs
# - EKS cluster configuration
# - Node groups and instance types
# - RBAC and Kubernetes security
# - Container images and scanning
# - Application deployments
# - IAM roles and policies
# - S3 buckets for storage
# - RDS for database
# - CloudWatch for monitoring
```

**Implementation Example:**

```bash
# 1. Create VPC (your responsibility)
aws ec2 create-vpc --cidr-block 10.0.0.0/16

# 2. Create subnets (your responsibility)
aws ec2 create-subnet --vpc-id vpc-xxx --cidr-block 10.0.1.0/24
aws ec2 create-subnet --vpc-id vpc-xxx --cidr-block 10.0.2.0/24

# 3. Configure security groups (your responsibility)
aws ec2 create-security-group --group-name webapp-sg --description "Web application security group"

# 4. Create EKS cluster (your responsibility)
eksctl create cluster --name shared-resp-lab \
  --vpc-private-subnets subnet-xxx,subnet-xxx \
  --managed-node-groups

# 5. Configure IAM roles (your responsibility)
aws iam create-role --role-name EKSClusterRole \
  --assume-role-policy-document trust-policy.json

# 6. Configure RBAC (your responsibility)
kubectl create rolebinding eks-admin-binding \
  --clusterrole=cluster-admin \
  --user=<your-iam-arn>

# 7. Secure S3 bucket (your responsibility)
aws s3api create-bucket --bucket webapp-bucket
aws s3api put-bucket-encryption --bucket webapp-bucket \
  --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
```

### **2. Configuring Security for Each Responsibility**

**Provider-Managed Security (You Configure, Provider Enforces):**

```yaml
# 1. IAM policies (your responsibility)
apiVersion: v1
kind: ConfigMap
metadata:
  name: aws-auth
  namespace: kube-system
data:
  mapRoles: |
    - rolearn: arn:aws:iam::123456789012:role/EKSNodeRole
      username: system:node:{{EC2PrivateDNSName}}
      groups:
      - system:bootstrappers
      - system:nodes

# 2. Security groups (your responsibility via AWS)
resource "aws_security_group" "webapp_sg" {
  name        = "webapp-security-group"
  description = "Security group for web application"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

# 3. S3 bucket policies (your responsibility)
data "aws_iam_policy_document" "s3_access" {
  statement {
    actions   = ["s3:GetObject", "s3:PutObject"]
    resources = ["arn:aws:s3:::webapp-bucket/*"]
    effect    = "Allow"
    principals {
      type        = "AWS"
      identifiers = [aws_iam_role.webapp_role.arn]
    }
  }
}
```

**Your-Managed Security (You Implement and Maintain):**

```yaml
# 1. Kubernetes RBAC (your responsibility)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: webapp-developer
  namespace: webapp
rules:
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch", "create", "update"]
# Provider doesn't configure this

# 2. Network policies (your responsibility)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: webapp-network-policy
  namespace: webapp
spec:
  podSelector:
    matchLabels:
      app: webapp
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: ingress-nginx
  egress:
  - to:
    - namespaceSelector: {}
# Provider doesn't configure this

# 3. Pod security (your responsibility)
apiVersion: v1
kind: Pod
metadata:
  name: secure-webapp
  namespace: webapp
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: webapp:1.2.3
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
      readOnlyRootFilesystem: true
# Provider doesn't configure this
```

### **3. Auditing Security Coverage**

**Check Provider-Secured Components:**

```bash
# 1. Verify VPC and network (provider secures infrastructure)
aws ec2 describe-vpcs
aws ec2 describe-subnets

# 2. Verify control plane (provider secures)
kubectl get componentstatuses -n kube-system

# 3. Verify node health (provider manages, you monitor)
kubectl get nodes

# 4. Verify load balancers (provider manages)
kubectl get svc -o jsonpath='{.items[*].status.loadBalancer}'
```

**Check Your-Secured Components:**

```bash
# 1. Verify RBAC (you configured)
kubectl auth can-i "*" "*" --all-namespaces
kubectl get roles,rolebindings --all-namespaces

# 2. Verify network policies (you configured)
kubectl get networkpolicies --all-namespaces

# 3. Verify pod security (you configured)
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.securityContext.runAsUser}{"\n"}{end}'

# 4. Verify IAM policies (you configured)
aws iam list-roles | jq '.Roles[] | select(.Path == "/eks/" or .Path == "/app/")'

# 5. Verify S3 bucket security (you configured)
aws s3api get-bucket-acl --bucket webapp-bucket
aws s3api get-bucket-encryption --bucket webapp-bucket
```

### **Common Mistakes in Applying Shared Responsibility**

❌ **Mistake 1**: Assuming provider secures Kubernetes configuration
- Reality: Provider secures control plane, you secure configuration
- Fix: Understand EKS/GKE/AKS responsibilities

❌ **Mistake 2**: Not securing S3 buckets
- Reality: Provider secures storage infrastructure, you secure bucket access
- Fix: Configure bucket policies and encryption

❌ **Mistake 3**: Not implementing RBAC
- Reality: Provider doesn't configure RBAC, you must
- Fix: Implement least privilege RBAC

❌ **Mistake 4**: Not monitoring your responsibilities
- Reality: Provider monitors infrastructure, you monitor applications
- Fix: Set up monitoring for your components

**Task 4: Secure S3 Bucket (Your Responsibility)**

```bash

      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::sensitive-data/*",
      "Condition": {

      "Effect": "Deny",
```

### **Common Interview Questions**

**Q1: What is the shared responsibility model?**
**Good Answer**: The shared responsibility model is a framework that defines who is responsible for what security in cloud environments. Cloud providers secure the **of** the cloud (infrastructure, data centers, network), while customers secure what's **in** the cloud (data, applications, configurations). The split depends on service type: SaaS (provider does most), PaaS (provider secures platform, you secure applications), IaaS (provider secures infrastructure, you secure OS and everything above). Understanding this is critical because assuming the provider handles everything leads to security gaps and breaches.

**Q2: What are your responsibilities when using Kubernetes on cloud (EKS/GKE/AKS)?**
**Good Answer**: When using managed Kubernetes, the cloud provider (AWS/GCP/Azure) secures:
- Control plane components (API server, etcd, scheduler, controller manager)
- Infrastructure (EC2/GCE/Azure VMs, VPC, load balancers)
- Container runtime (containerd)
- Kubernetes version upgrades
- Control plane availability

You are responsible for:
- Kubernetes configuration (RBAC, network policies, pod security)
- Workloads (pods, deployments, services, secrets)
- Container images (scanning, security)
- Application security (code, dependencies)
- IAM integration (IAM roles for service accounts, IAM policies)
- Network configuration (security groups, firewall rules)
- Data security (encryption, access controls)
- Monitoring and logging
- Backup and disaster recovery

**Q3: What's the difference between SaaS, PaaS, and IaaS from a security perspective?**
**Good Answer**: From a security perspective:
- **SaaS** (Software as a Service): Provider secures almost everything (application, infrastructure, OS, data centers). You only secure user access, data classification, and configuration. Example: Gmail, Slack.
- **PaaS** (Platform as a Service): Provider secures platform and infrastructure. You secure applications, data, and configurations. Example: EKS, GKE, Lambda, Cloud Functions.
- **IaaS** (Infrastructure as a Service): Provider secures physical infrastructure. You secure OS, applications, data, network configuration, and everything above. Example: EC2, Compute Engine, Azure VMs.

The more control you have (IaaS), the more security responsibility you have. The less control (SaaS), the less security responsibility you have.

**Q4: Why is understanding the shared responsibility model important?**
**Good Answer**: It's important because:
1. **Prevents security gaps**: If you assume provider handles something they don't, that component is unsecured
2. **Clarifies ownership**: Teams know what they're responsible for, avoiding confusion
3. **Compliance**: You're accountable for your responsibilities in audits
4. **Incident response**: Understanding responsibilities helps coordinate response with provider
5. **Resource allocation**: Focus security efforts on your responsibilities, not provider-managed ones
6. **Real-world breaches**: Many breaches (Capital One, Tesla, Code Spaces) happened because teams misunderstood their responsibilities

**Q5: What are common mistakes teams make regarding the shared responsibility model?**
**Good Answer**: Common mistakes include:
1. **Assuming provider secures everything**: Leading to unsecured configurations
2. **Not implementing RBAC in Kubernetes**: Assuming provider handles it
3. **Leaving S3 buckets public**: Assuming provider secures bucket access
4. **Using default IAM policies**: Which are overly permissive
5. **Not monitoring applications**: Assuming provider monitors everything
6. **Skipping encryption**: Assuming provider encrypts by default (they provide feature, you must enable)
7. **Not backing up data**: Assuming provider backs up (they backup infrastructure, not your data)

Understanding the shared responsibility model prevents these common mistakes and ensures comprehensive security coverage.
