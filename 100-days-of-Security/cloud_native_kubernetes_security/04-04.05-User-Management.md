# 04.05 - User Management

## 1️⃣ What This Topic Is

User Management examines security measures for securing Kubernetes users, understanding user identity, authentication, and authorization.

**What this means:**
- Kubernetes users = human identity to access Kubernetes API
- User management = creating, deleting, and managing users
- User authentication = verifying who you are (OIDC, LDAP)
- User authorization = verifying what you can do (RBAC, ABAC)
- Secure user configurations (least privilege, separation of duties)

**The Key Concepts:**

1. **Kubernetes User Management Areas**
   - User identity (external users, managed users)
   - User authentication (OIDC, LDAP)
   - User authorization (RBAC, ABAC)
   - User audit logging (authentication events, authorization events)
   - User lifecycle management (creation, deletion, rotation)

2. **Security Principles**
   - Defense in depth (authentication, authorization, auditing)
   - Least privilege (user permissions)
   - Zero-trust (never trust, always verify)
   - Default-deny (deny all, allow explicitly)
   - Audit everything (audit logging)

**Why this matters:**
- User management is critical for cluster security
- User management controls all human access to cluster resources
- User management compromise = cluster-wide compromise
- User management handles all user authentication and authorization

## 2️⃣ What Problem It Solves

### Problem 1: Unmanaged Kubernetes Users

**Without user management:**
- Unmanaged Kubernetes users
- Attacker can impersonate users
- Cluster compromise
- Data theft and service disruption

**With user management:**
- Managed Kubernetes users
- Attacker cannot impersonate users
- Cluster protected
- Data and services protected

### Problem 2: Over-Privileged Kubernetes Users

**Without user management:**
- Over-privileged Kubernetes users
- Attacker can escalate privileges
- Cluster compromise
- Data theft and service disruption

**With user management:**
- Least privilege Kubernetes users
- Privilege escalation prevented
- Cluster protected
- Data and services protected

### Problem 3: No User Audit Logging

**Without user management:**
- No user audit logging
- User authentication events undetected
- User authorization events undetected
- Incident response delayed
- Cluster compromise

**With user management:**
- User audit logging enabled
- User authentication events detected
- User authorization events detected
- Real-time detection
- Rapid incident response
- Cluster protected

### Real-World Impact

**Example: Tesla Kubernetes Breach (2018)**
- **Vulnerability**: Over-privileged Kubernetes users
- **Root cause**: No user least privilege
- **User management issue**: Attacker escalated to cluster-admin
- **Impact**: Attacker deployed miners across cluster
- **Lesson**: Implement user least privilege

**Example: Uber Data Breach (2016)**
- **Vulnerability**: Unmanaged Kubernetes users
- **Root cause**: No user management
- **User management issue**: Attacker impersonated cluster-admin
- **Impact**: 57 million customer records accessed
- **Lesson**: Implement user management

**Example: Capital One Breach (2019)**
- **Vulnerability**: No user audit logging
- **Root cause**: No user audit logging
- **User management issue**: User authentication events undetected
- **Impact**: 106 million customer records accessed
- **Lesson**: Implement user audit logging

## 4️⃣ How It Works (Conceptual)

### Kubernetes User Management Areas

**1. User Identity**
- **Purpose**: Provide identity for humans to access Kubernetes API
- **Security Measures**: 
  - External users (LDAP)
  - External users (OIDC)
  - Managed users (cloud provider IAM)
  - User RBAC (roles, role bindings)
  - User audit logging
- **Common Misconfigurations**: 
  - No user RBAC (all users have cluster-admin)
  - No user audit logging (no audit trail)
  - No user management (unmanaged users)
  - Long-lived user tokens
  - No user authentication (plaintext authentication)
- **Example**: User identity with external users

**User Identity Types:**
- **External Users**: 
  - LDAP users
  - OIDC users
  - SSO integration
  - User management

- **Managed Users**: 
  - Cloud provider IAM users
  - Managed users (Azure AD, Google Workspace)
  - SSO integration
  - User management

- **User RBAC**: 
  - User RBAC (roles, role bindings)
  - Cluster-level user RBAC
  - Namespace-level user RBAC
  - Least privilege

- **User Audit Logging**: 
  - User authentication logging
  - User authorization logging
  - User audit trail
  - Compliance reporting

**Best Practices:**
- Use external users (LDAP, OIDC)
- Use managed users (cloud provider IAM)
- Implement user RBAC (least privilege)
- Implement user audit logging
- Implement SSO integration
- Regular user audits

**Example**:
```yaml
# User identity with external users (secure, advanced)
# This would be configured via OIDC, LDAP, or cloud provider IAM
# For example, using Azure AD (AAD Pod Identity):
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: secure-service-account
  namespace: secure-namespace
  annotations:
    azure.workload.identity/use: "true"
    azure.workload.identity/client-id: "${AAD_CLIENT_ID}"
    azure.workload.identity/tenant-id: "${AAD_TENANT_ID}"
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: user-role-binding
  namespace: secure-namespace
subjects:
- kind: Group
  name: "developers@example.com"
roleRef:
  kind: Role
  name: developer-role
  apiGroup: rbac.authorization.k8s.io
```

**3. User Authorization**
- **Purpose**: Provide user authorization to access Kubernetes API
- **Security Measures**: 
  - User RBAC (roles, role bindings)
  - Cluster RBAC (cluster roles, cluster role bindings)
  - Namespace RBAC (roles, role bindings)
  - User least privilege
- **Common Misconfigurations**: 
  - No user RBAC (all users have cluster-admin)
  - Over-privileged users (root access for all)
  - No user separation (all resources in one role)
  - No least privilege (allow all verbs)
  - No user RBAC audits
- **Example**: User authorization with RBAC

**User Authorization Types:**
- **User RBAC**: 
  - Roles (namespace-level, cluster-level)
  - Role bindings (associate roles with subjects)
  - Cluster roles (cluster-level)
  - Cluster role bindings (associate cluster roles with subjects)
  - Least privilege

- **User Least Privilege**: 
  - User RBAC with least privilege
  - Namespace-level user RBAC
  - Resource-level user RBAC
  - Verb-level user RBAC
  - Regular user RBAC audits

- **User Separation**: 
  - Resource-level user RBAC
  - Verb-level user RBAC
  - Namespace-level user RBAC
  - User RBAC separation
  - Regular user RBAC audits

**Best Practices:**
- Implement user RBAC (least privilege)
- Implement namespace-level user RBAC
- Implement resource-level user RBAC
- Implement verb-level user RBAC
- Regular user RBAC audits

**Example**:
```yaml
# User authorization with RBAC (secure, advanced)
apiVersion: v1
kind: Namespace
metadata:
  name: secure-namespace
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-role
  namespace: secure-namespace
rules:
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-role-binding
  namespace: secure-namespace
subjects:
- kind: User
  name: "developer@example.com"
roleRef:
  kind: Role
  name: developer-role
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader-role
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: node-reader-role-binding
subjects:
- kind: User
  name: "node-reader@example.com"
roleRef:
  kind: ClusterRole
  name: node-reader-role
  apiGroup: rbac.authorization.k8s.io
```
